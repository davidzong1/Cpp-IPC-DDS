## 3. 测量契约与数据有效性

### 3.1 不变的工作负载

两个版本使用同一份 `benchmark.cc` 和同一份 Python 启动工装，分别针对各自头文件/库编译。固定单发布者、预构造 StdImage DZFlat、100Hz、预热 2 秒；诊断通常采 10 秒，内核探针冒烟采 3 秒，正式验收采 30 秒。载荷参数与实际 `wire_bytes` 都要记录并核对一致。

保留订阅端收到样本后的逐字节校验和现有 CSV 写入行为。它们虽不在当前消息端到端计时内，仍会改变下一次消息的缓存、频率和调度条件。若做缓冲日志诊断，两侧同时改变并单列实验，不能偷偷用于正式成绩。

A 使用 IPC_SHM，不启动网关；B/C 使用 `shared_v1` 并启动网关，这是正式对比的架构差异。不得为 A 添加虚假网关以制造“对称”。记录 B/C 的网关 CPU、线程和活动，必要时再做独立的空闲网关干扰对照。`shared_v1` 是现有工装模式名，不意味着整合版本仍采用旧网络协议。

当前 `benchmark.py` 默认 `data-shards=4`，`data-workers` 默认等于 shards；在计划中冻结实际参数。工装隔离 user/mount/ipc 命名空间，**没有独立 network namespace**；记录端口与路由状态，排除端口冲突、意外远端 peer 或数据走网卡的情况。保留业务进程 UDP FD 为零的检查，并核对本机投递指标。

### 3.2 观测层级

| 层级 | 内容 | 可以用于什么 |
|---|---|---|
| L0 | 关闭所有可选分段、CPU、消息追踪和 perf；保留原工装完整性工作 | 端到端筛查及正式验收 |
| L1 | 应用分段、线程角色、同线程 CPU 时间；有界内存记录 | 消息路径与实现差异定位 |
| L2 | L1 加 sched waking/wakeup/switch/migrate、cpu_idle；不采栈 | 唤醒、迁移和 CPU 等待关联 |
| L3 | 在必要短窗增加内核探针、栈、目标 CPU 完整调度及 IRQ/softIRQ | 拆分特定内核区间及竞争者 |
| L4 | 独立 PMU/复制计数器窗口 | 复制执行成本验证 |

L2 中关闭 perf 仅回到 L1。各层的开销必须通过同版本交错对照报告；不从结果中减去固定“perf 开销”。L3/L4 默认不叠加，避免观测本身淹没目标。

### 3.3 环境、顺序和失败处置

1. 编译、链接、测试、解码、压缩和绘图全部在采样窗口之外完成；不与其他 Agent 的编译/压测重叠。每窗启动前连续至少 20 秒未观察到已知竞争任务；静置方式在整批保持相同，不在窗口之间临时添加保温负载。
2. 记录活动进程、CPU 使用、loadavg、上下文切换、频率与温度（接口可用时），每窗前后记录拓扑、允许 CPU、cpuidle 驱动/state、governor 和内核。已有按秒/进程名检测会漏掉短任务，应明确这一观测边界，不能声称系统绝对空闲。
3. 开始前冻结完整窗口计划与哈希。两版本对照默认 8 窗：`A B B A | B A A B`。每个 4 窗块包含一对 AB、一对 BA，报告全部相邻配对，不挑最有利基线。后文另行指定的正式顺序保持原工装约定。
4. 四条件的观测开销对照固定为 `A0 B0 B1 A1 | A1 B1 B0 A0`，0/1 表示相邻观测层，每个条件出现 2 次且位置镜像。样本少时结论仅为筛查；若方向不一致，只允许按预先登记的规则再完整重复一次，再不稳定则报告不确定并转入环境/分段分析。
5. 外部干扰、加载库错误、数据丢失、权限/事件缺失均记录状态与原因。已完成且完整但延迟超限的窗口是有效失败，不能改标为干扰。受干扰/中断窗口不删除；对照诊断补跑整个受影响平衡块，记录替代关系，禁止拼接有利单窗。
6. 每批二进制、库或诊断开关发生变化即结束该批，重新冻结批次；不得在同一个 manifest 中悄悄换库。只清理本任务创建的进程、命名空间及探针，不终止别人的工作。

此前观测为 `intel_idle`，P 核 CPU0～15、E 核 CPU16～31；本轮需重新核验物理核、SMT sibling、簇和 NUMA。`C1_ACPI/C2_ACPI/C3_ACPI` 名称不代表驱动是 `acpi_idle`；公布的退出延迟也不是该样本实测时间。正式环境仍要求全部 CPU0～31 允许，不把进程允许集合与瞬时实际运行 CPU 混为一谈。

### 4.1 双版本驱动接口要求

新增或扩展驱动时至少接受以下配置，并先实现配置校验和只列计划的能力：

- A/B/C 各自源码 SHA、工作区、binary、动态库、gateway、编译记录及诊断能力清单。
- 显式窗口列表：唯一 ID、版本、场景、重复/配对块、预热/时长/速率、观测层、CPU 布置、网关配置、输出目录。
- 输出目录必须为空；每窗结束落盘退出码、失败原因和产物哈希，再启动下一窗。
- 采样用户/组从当前运行身份获取并核验，不硬编码 UID；普通业务、提权采集器的真实身份分别记录。
- perf 事件存在性/字段/权限预检，准确记录实际命令。当前正确解码使用 `perf script --ns --show-lost-events --hide-call-graph`，禁止再次使用本机不支持的 `--no-call-graph`。
- 进程活动检测、开始/结束快照和后处理必须有明确时段；离线解析失败不能丢掉已录制数据。

正式调度仍沿用原 `performance_matrix.py` 的实验定义。可修复参数化与审计，不可顺便更改负载、门槛、合并方式或顺序。新增局部汇总器与正式汇总器分清入口，不为凑齐表格填造缺失 case。

### 4.2 角色、消息与等待周期关联

每条记录至少有：`run_id`、版本、消息 `(publisher_id, sequence)`、订阅者 ID、线程角色、TID、时间戳、CPU、有效性/缺失原因。基线没有公开 publisher_id 时，可使用该窗口单发布者的工装身份，字段注明来源，不冒充协议身份。

角色至少区分发布线程、实际 SHM 接收线程、getter、后台 worker、网关线程。同一 TID 可以承担多个角色，但不能反向假设这些角色必定是同一 TID。PID/TID 带进程启动标识，避免跨窗口复用误关联。

按代码实际语义记录以下事件：

```text
发布起点 → loan/复制 → commit/notify 开始与结束
接收线程 wait_begin / wait_end → recv → 分流/入队
getter 等待 / 出队 → API 返回
后台 owner/assist 交接及恢复
```

等待开始时消息序号可能尚未知：分配等待周期 ID，接收成功后关联消息；没有阻塞、空读、虚假唤醒、一个唤醒读取多个消息、多个唤醒对应一个读取都必须可表达。禁止把距消息最近的一条 `sched_waking` 无条件当作它的来源。

基线若缺必要 seam，优先从已有钩子补齐角色记录；确需插桩则建立 A 的诊断补丁，保持等待机制、线程数量、生命周期和算法不变。B 使用相同语义边界，不要求两种架构拥有相同数量的事件。不能补齐的字段用 `null` 与能力标记，不补零，不把缺失时间算成零开销。

时间使用本机单调时钟；perf/BPF 时钟要声明并验证与应用时钟同域或有可验证换算。记录跨 CPU 时序误差及探针开销。线程 CPU 时间只能在同一线程内相减；不同线程的 CPU 时间之和是资源消耗，不是端到端墙钟。

诊断记录预分配、有界、不逐消息申请内存、不在生产钩子中写盘或等待。容量计入预热、正式消息、空等和一条消息的多个事件；按事件数量预算，不能仅用消息数量判断够用。溢出必须显式失败并保留证据。

### 4.3 可比统计与解析器守门

- 每窗先合并该场景所有订阅者原始接收样本，计算算术平均、nearest-rank p50/p95/p99；同时提供各订阅者数据。不要平均各订阅者分位数来冒充总体分位数。
- p45～p55 组沿用整数秩：零基切片 `[N*45//100 : (N*55+99)//100]`；最慢 1% 取 `ceil(N/100)` 条。排序有稳定并列规则并写入报告。
- 端到端分组后，再对同一组消息计算各阶段均值。只有同一消息完整、有序、不重叠的分段才能做守恒求和；独立 p50/p99 不相加。
- 基线接收与发布可能重叠，发布返回可能晚于接收。先构建消息的跨线程因果图，分别报告线程区间与关键路径；不能把重叠分段强行串接、夹成零或伪装成优化。
- 所有接收消息都保留；关联结果分为完整阻塞链、合法无等待、跨消息/多唤醒、缺点、歧义、丢事件。报告各类数量及延迟分布，尤其是慢样本覆盖率。
- 核心阶段归因要求目标组全部样本可解释：有唯一链或明确合法的无等待路径。存在未知缺失、LOST、探针丢弃或歧义时，不得用匹配子集解释整个组；可报告限定子集结论并补工装。
- 32 SUB 的 32 个接收不是 32 次独立发布。广播排序在同一 sequence 内完成；统计不确定性按窗口/时间块或发布 sequence 聚类，不把接收条目直接当独立随机样本。

解析器变化要有针对性测试：后台 receiver 与 getter 不同、无等待、虚假/多次唤醒、跨线程重叠、迁移、相同时间戳、缺失/未知/LOST、序号重复/缺口、TID 复用、中间组秩边界及完整窗口唯一性。先跑原有 10 项分析器测试，再补新失效模式的测试；不要靠删断言适配数据。

### D02：三项失败的同期 L0 对照

**假设：** 当前波动可能是 A/B 共有的调度状态，也可能是 B 的特定路径放大；先检验差异是否在组合版本仍然存在。

按 1SUB/4KiB → 32SUB/64B → 1SUB/1MiB 顺序，每场景 8 窗 `ABBA|BAAB`，每窗 2 秒预热+10 秒正式、100Hz、全部 CPU0～31。共 24 窗，24000 次正式发布/272000 次正式接收。

输出每窗端到端、发布耗时、各订阅者分布、实际 CPU 分布和逐秒趋势。相邻 AB/BA 对报告 B−A 原始差值及原阈值下的筛查结果，不把 10 秒结果写成正式验收。两侧序号只用于各窗内部关联，不把不同时间窗的同号消息当作同一次系统事件。

判定：

- 两种顺序均出现 B 的同方向额外延迟：优先寻找实现增加的阶段。
- A/B 都出现相似快慢状态：进入 D03/D04，验证共同慢段以及 B 是否改变落入慢状态的比例；相邻时间窗也不能证明环境完全相同。
- 未复现：保留全部结果，仍完成低开销路径比较；按预登记规则最多增加一组完整 8 窗。不得宣布历史失败失效，也不得为了复现而临时制造系统负载。

### D03：应用链与观测开销

4KiB 和 32SUB 各跑 8 窗四条件对照，0=L0、1=L1，共 16 窗。先验证基线 receiver→队列→getter 与 B 的实际接收路径，再比较同组消息的通知前、等待、recv、分流、排队、交接和 API 返回。

主要输出：

- 完整线程角色图、每个消息的实际执行 TID、等待次数及真实交接次数。
- 各窗中间 10% 与最慢 1% 的同组分段均值及其样本覆盖；完整端到端 p50/p99 另列。
- A/B 各自 L1−L0 的变化。若 L1 改变了快慢状态或掩盖差异，减少打点/拆分采集；不能带着明显观测偏差直接决定生产优化。

这里要回答“B 比 A 多了哪一段”，而不仅是“B 自己最慢在哪一段”。没有额外交接证据，不添加或删除 worker 试运气。

### D04：调度链对照

对 4KiB、32SUB 各跑 8 窗，0=L1、1=L2，共 16 窗。两侧按实际 receiver/getter 角色采集，不只过滤工装 getter 的 TID/comm。

逐接收者构造并核对：

```text
notify_begin → sched_waking → sched_wakeup
             → 首次使目标线程运行的 sched_switch → wait_end
             → recv/入队 → getter 出队/API 返回
```

这只是可能的阻塞路径；无等待、已经可运行、连续多次阻塞、收发交叠均按实际图处理。记录 wake 发起 CPU、目标 CPU、激活 CPU、实际执行 CPU和迁移事件，不能仅用两个 CPU 字段是否相同判断全部迁移。

按以下证据选择分支：

| A/B 额外慢段 | 下一步 |
|---|---|
| 通知前、尤其复制 CPU 成本 | D07 |
| notify→各 receiver 的 waking 累计 | D08，并保留 D05 对激活长尾的区分 |
| waking→wakeup | D05；核型/迁移相关时接 D06 |
| wakeup→scheduled | D05 的目标 CPU 竞争者记录 |
| wait_end 后 recv/排队/getter | 以 D03 角色/队列证据拟定 D09，不用更多内核栈代替用户态定位 |

输出每秒趋势、发布核/目标核型、唤醒顺位、等待状态等条件分布；保持各子组样本数和未匹配原因。迁移与长尾相关不等于迁移造成长尾。

### D05：细分目标核激活与激活后等待

**假设：** 慢段可能发生在唤醒端处理、跨核投递、目标核响应、待激活队列处理或获得 CPU 之前。此前栈只确认路径，不能区分这些成本。

先只读枚举本机 tracefs 事件/字段、可用函数、BTF、perf/BPF 支持情况，并保存版本。优先用现成 tracepoint，必要时使用限范围 fentry/kprobe/kretprobe。`try_to_wake_up`、`ttwu_queue_wakelist`、`sched_ttwu_pending`、`ttwu_do_activate`、IPI/call-function 处理仅为候选观察位置；静态、内联或被优化掉的函数未必可挂，必须以本机实测为准。

目标时间线：

1. 发起唤醒，目标 task/TID 已确定。
2. 入目标核待处理队列/请求投递。
3. 目标核进入相关 IPI/call-function 处理。
4. 对这个 task 执行待激活处理并成为可运行。
5. 目标线程真正上 CPU，随后返回等待。

保存 task、源/目标 CPU、时间及事件来源。IPI可能合并处理多个任务，不能将通用 IPI 到达时间一对一强配到每条消息；有 task 关联才计算精确区间，否则输出可证明的上下界/集合归属和歧义。缺少投递点时明确“中间区间尚不可分”，不得用两个相邻栈帧之间的距离臆造时间。

对 wakeup→scheduled 长尾，单独短窗采目标 CPU 的全部 `sched_switch` 和 IRQ/softIRQ 进入/退出，保留非 benchmark 竞争者，重建可运行期间 CPU 被谁占用。原仅匹配 benchmark 的过滤器看不到这些竞争者。取证范围限制在本次目标 CPU/时间段，不无差别收集进程参数或业务内容。

每个被触发场景先 1 个 3 秒探针冒烟检查丢事件和时钟；通过后 8 个 3 秒四条件窗口，0=L2、1=L3。计数单列，冒烟不拼进配对。若短窗慢样本不足，可在计划中一次性登记改为 10 秒整组；禁止只延长不利一侧或只保留出现长尾的窗口。

没有受控电源状态干预，本轮最多证明“与观测到的 idle 状态及目标核处理区间有关”，不能关闭“深 C-state 导致全部延迟”的因果命题；也不能凭 hook 栈帧归因第三方 syscall hook。

### D06：固定核的诊断对照

使用重新读取的拓扑，先对 4KiB 进行 P→P、P→E、E→P 三组；箭头为发布线程核型→实际接收/订阅进程核型。每组 8 窗 ABBA|BAAB、L1、10 秒，共 24 窗。示例 CPU0/4/16 只有确认不是不合适的 SMT/簇共享关系后才可采用。

每一组 A/B 的发布进程和订阅进程允许 CPU 完全一致，网关使用固定且独立记录的位置。当前 `--affinity` 是进程级映射，子线程通常继承，不能将它写成已经控制了单独 receiver 线程。若需要角色级绑核，执行者先实现并记录全部线程映射，保持两侧同等 CPU 预算，另列实验。

比较 PP 与 PE 时只改变接收位置，PP 与 EP 时只改变发布位置。核型改变通常也伴随缓存拓扑和频率变化，应报告为“放置效应”；进一步机制解释需 D05/D07 支持。

32SUB 仅在 D04 显示放置相关时追加两种布局，各 8 窗：均衡分散布局与固定核型布局。两侧总 CPU 集合、每 CPU 订阅者数、发布/网关占用及额外后台线程争用均要列出；若固定核型导致过度订阅，与均衡布局相比是复合变化，不能只归因核型。禁止给 B 多分配 CPU 来制造改善。

绑核只用于定位。任何候选都必须回到全部 CPU0～31、无 affinity 的 L0 窗口验证。

### D07：1MiB 复制执行成本

**假设：** 大消息差异可能来自复制次数、源/目的地址与复用、频率/缓存/TLB、抢占或复制外围分配，而不是某种 memcpy 指令天然较慢。

第一步，A/B 在相同接收位置下分别固定 P 发布核与 E 发布核，每个配置 8 窗 ABBA|BAAB、10 秒、L1 复制墙钟/线程 CPU 诊断，共 16 窗。两侧分别记录：

- 每条消息实际复制次数、字节数、源/目的地址、对齐、真实容量、池档、页跨度、复用周期、首次触页位置。
- loan、复制、commit、notify 的墙钟；同线程复制 CPU 时间、进入/退出 CPU、调度抢占；API 发布耗时与端到端分开。
- 源缓冲构造、payload 校验、写 CSV 的时段与工作量，不能把这些计时外行为忽略。

第二步，仅对稳定出现差异的放置配置做 L4。先枚举 PMU 能力，再选择 cycles、instructions、cache/TLB、page faults、迁移/上下文切换等可用事件；记录事件编码、核型 PMU、`time_enabled/time_running`、权限及不支持项。P/E 混合 PMU 的同名事件可能含义不同，不可直接比较未经说明的计数。

PMU 优先定位发布线程和复制区间，或使用相同复制次数/缓冲访问模式的独立工装。单独完整进程 `perf stat` 只给全进程相关证据，不能宣称精确解释一次 memcpy。默认有效运行比例要求至少 95%；不满足时拆小事件组，完整重跑平衡块并保留失败组，不以线性缩放包装为精确计数。

第三步，按证据一次只改一个变量：源地址复用、目的池槽复用、对齐/页跨度、首次触页位置、日志缓冲策略等。先固定核/速率/容量/复制次数做 8 窗平衡对照，再在另一版本复现同一因素，避免把 B 的缓冲实验误当 A/B 架构收益。缓存冷热属于诊断条件，不替换正式访问模式；不能靠减少字节校验或复制次数却改变所有权语义获得正式成绩。

通过条件：同组复制 CPU 与端到端变化方向一致，重排顺序后仍成立，PMU或缓冲证据能区分假设。若只有墙钟增加而 CPU 时间相近，转查调度；若复制 CPU 已增加，不能把全部原因归到空闲唤醒。没有新证据时继续使用标准 memcpy。

### D08：32SUB 广播最小复现

**假设：** 约 31～32µs 的唤醒顺位累计可能来自广播遍历/通知系统调用，也可能包含 SDK 的额外处理；激活长尾是另一段。

先在 D04 数据上按同一次发布排序 32 个 receiver 的 waking，报告首/中/末位、相邻增量、同一消息最慢接收者和全部 32 条链。用 futex 系统调用进入/退出、真实地址/操作/唤醒数量与返回值对应通知边界；若实际是 waitv 或多个调用，按实际实现记录，不预设“一次发布必有一次 futex_wake”。

只对 D04 确认存在额外成本的版本逐级缩减：

1. 完整 SDK：现有预构造 DZFlat、MPMC 和等待路径。
2. 最小 SHM 工装：复用同一版本的 SHM 通道、广播语义、等待 backend、通知协议和缓冲策略，去掉无关业务层。
3. 有必要时再实现 futex/waitv 原语工装，准确还原等待值更新、检查后入睡竞态及广播，不用不同原语冒充等价复现。

每次缩减先只测 32 个等待者，完整/缩减两条件 8 窗 ABBA|BAAB、100Hz、10 秒、相同观测层。若证据指向随人数增长的成本，再补 1 和 8 个等待者，每档 8 窗；不要默认运行全部层级×人数×版本×CPU 的组合。

工装必须让每个订阅者收到每条消息，保留序号校验、相同 CPU 布置、等待者就绪证明和真实阻塞；不能改成工作队列分摊，也不能增加轮询或窗口内轮次屏障改变唤醒模式。发布源、接收校验/日志不等价时，只能比较原语阶段，不把端到端差值全部归给删除的 SDK 层。

判定：若通知累计在最小 SHM 中保留，继续查通知/等待原语；若仅完整 SDK 出现，用 D03 追踪多出的处理。若通知累计减少但 p99 主因仍在目标核激活，不能宣布广播优化已解决尾延迟。

### D09～D10：根因与生产候选

每个问题填写一行根因证据表，至少包括：现象、A/B 差异、同组主导阶段、覆盖率、两种顺序结果、单因素干预、替代解释、候选改动、预期改善量、撤回条件。

证据强度明确分级：

- 定位：慢消息耗时落在某一区间。
- 相关：慢区间与核型、迁移、队列或频率共同出现。
- 因果支持：一次只改变一个因素，目标阶段和端到端按预先预测改变，交换顺序及独立完整块仍复现，其他关键因素有记录。
- 正式修复：冻结候选通过 D11 和 D12。

生产候选 C 每次只包含一个可解释改动。先对 B/C 做对应场景 8 窗无绑核 L0 对照；另做 L1 同组分段确认目标阶段确实改善。观察开销敏感时采用四条件对照；有收益的诊断绑核实验必须再通过无绑核筛查。多项修复逐项提交，保留单项及组合结果。

继续条件：至少两个完整平衡块方向一致，没有用内容损失、忙等、CPU预算变化、提前释放 lease 或降低校验工作量换延迟；其余两失败场景各 8 个 L0 对照未出现一致退化。统计区间跨零或效果受顺序支配时，不声称稳定收益，补最能区分假设的实验。

无效候选恢复生产行为并提交负面证据；若候选曾提交，以可追溯的 revert 记录撤回。禁止修改发布者序号/所有权、消费锁、取消/停止、代次 barrier、顺序、公平性与 I5 语义以绕过瓶颈。

### D11：功能、生命周期与构建回归

测试与性能采样分时执行，先列 CTest 清单和依赖，再构建后执行。普通共享网络标签可用现有命令：

```bash
ctest --test-dir build-latency-formal -N -L shared_net
ctest --test-dir build-latency-formal -L shared_net --output-on-failure -j1
```

需要交付的验证范围：

| 类别 | 最低覆盖与证据 |
|---|---|
| 身份/网络整合 | local/offline publisher_id 与独立 sequence、partial_submit、共享网络完整标签；保留 v2 endpoint/worker/回退及 CLI 用例 |
| DZFlat/MPMC | 预构造消息、混合类型、队列顺序、广播完整性、慢订阅者及背压；按改动影响选择已有测试 |
| 接收生命周期 | recv worker、消费锁/owner、get 超时/取消、析构、重建/Ready 转换、I5 已取出样本有效性；改动边界增加确定性回归 |
| 接收回退 | 同一候选 `DZIPC_SHARED_RECV_ASSIST=0/1` 的相关完整性和生命周期测试；不能只验证协作路径 |

| 资源与空闲 | FD、线程数、SHM、CPU及退出清理；A/B/C 同工装 1/8/32 SUB 空闲窗各 10 秒，保持既有 get 超时，报告计数粒度及观测边界 |

旧 I5/析构/Ready 等失败只能在对应对照版本实际复现后标为既有，不继承历史标签自动豁免。sanitizer 报错和新回归必须处理；已知失败单列原日志、对照与风险，不写“全部通过”。通过项无需为了美化汇总反复重跑；修复或产物改变后复测受影响项。

若 C 同时改变多发布者共享路径，增加真实并发多发布身份/顺序完整性回归；这属于正确性保护，不把单发布正式矩阵扩写为多发布延迟结论。

### D12：原 54 窗口正式验收

冻结 C 的完整 SHA、源码/工装/库哈希和全部诊断关闭状态，A 使用原始未插桩库。原要求全部保留：

- `1/8/32 SUB × 64B/4KiB/1MiB`，单发布者，100Hz，预热 2 秒、正式 30 秒。
- 3 轮×9 场景×A/C，共 54 窗；轮 1 A→C、轮 2 C→A、轮 3 A→C，场景顺序沿用原工装。
- 全部 CPU0～31 允许、无 affinity、无分段/PMU/perf/新增消息追踪、无新增忙轮询；网关参数及完整性工作按冻结计划执行。
- 每轮每场景先合并全部订阅者原始样本，再分别计算 nearest-rank p50/p99。两指标都满足才算该场景该轮通过：

```text
候选指标 − 基线指标 ≤ max(基线指标 × 10%, 5µs)
```

每窗 3000 次正式发布，正式序号 `200..3199`；54 窗合计 **162000 次发布、2214000 次接收**。预热单列，不加入这些计数。完整性必须零损坏、零重复、零观察丢失、零拒收，每个订阅者的实际序号集合与发布集合完全相等。

目前 `performance_matrix.py` 对库布局有要求：候选为 `current.parent.parent/lib/libipc.so`，基线为 `baseline.parent/lib/libipc.so`。D01 必须参数化或建立明确、已审计的运行布局，不能在不相关目录放旧库凑路径。下列命令只使用现有选项，**前提是执行者已在这些示例路径构建并审计冻结产物**：

```bash
python3 test/shared_net/performance_matrix.py --baseline /tmp/dzipc-local-latency-root-cause/baseline-run/shared_net_benchmark --current /tmp/dzipc-local-latency-root-cause/build-latency-formal/bin/shared_net_benchmark --gateway /tmp/dzipc-local-latency-root-cause/build-latency-formal/bin/dzipc_gateway --output docs/shared_network_endpoint_evidence/20261007-local-root-cause/formal-001

```

第二条仅在 54 个唯一窗口和完整性预审通过后执行。现有汇总进程退出 0 不等于性能通过，必须检查 `all_paired_round_gates`、全部内容错误和新审计结果；`len(cases)==54` 也不足以排除重复覆盖或缺格。

正式采集中止或遭已证实干扰时保留整批及原因，修复执行条件后另开完整批次；不能拼接两批凑 54 窗。完整有效批次若仍有超限，报告实际通过数并回到证据分析，禁止无改动反复跑矩阵挑成绩。三轮中位数仅作补充，不能替代 27 个逐轮判定。
