# C1：无条件变量等待者的通知快速路径

父版本为 B 的 `3918e999`，D04 原始对照为 `d04-ab-role-001`。
本候选独立于该冻结诊断产物，失败时只保留实验分支和负面数据。

## 可检验机制

D04 的 B 四个 perf 窗口中，所有消息由 getter 的 futex 双槽等待接收，
后台 worker 的 `recv(0)` 不登记传统 condition 等待者。
`waiter::wake()` 仍无条件获取传统 waiter 的共享 robust mutex 后检查 count。
这道锁是传统 condition 登记的屏障，不能只删除锁而保留旧登记位置。

候选保留每次发布的 sequence 递增和共享 futex wake，只在传统 waiter count 为 0
时省去传统 mutex 屏障。`wait_if()` 在谓词检查之前登记 count，并在同一锁域读取
sequence；通知 sequence、等待者登记和观察均使用顺序一致原子操作，保证通知方
不可能漏掉已登记的等待者，同时登记后谓词必须看见已完成的发布。
有等待者时沿用原 mutex 屏障、condition notify/broadcast 和取消协议。

## 预测与退出条件

预测：发布 notify 区间/CPU 开销减小，消息唤醒数量不变；不预测消除 CPU idle
退出长尾。先通过通知早于登记、通知与谓词检查交叠、混合 futex/condition、
停止/重建/并发发布的正确性测试，再以 B/C 两个完整平衡块验证。

L1 检查 notify 段，L0 检查 1 SUB/4KiB、32 SUB/64B、1 SUB/1MiB。
端到端无稳定收益、任一完整性/生命周期失败、兼容等待超时或两块方向不一致，
不进入正式 D12，并保留负面证据。保持复制、校验、频率、池容量、门槛及系统设置。

## 执行结果：拒绝

`c1-abba-l2` 完成 24/24 窗，24000 次发布、272000 次接收及调度链全部完整。
两个平衡块的 C−B：4KiB p50 为 −13.521/+3.991 µs，1MiB p50 为
−24.449/+14.449 µs；32 SUB p99 为 +33.946/+5.885 µs。
1 SUB 通知 p50 下降，但没有稳定端到端收益，32 SUB 的尾延迟也未改善。

补充的旧协议接收者用例更发现确定性兼容问题：旧进程仍在谓词检查后登记
`waiters`，其共享段名和布局与本候选相同。候选在该窗口读到零计数会提前返回，
旧接收者随后进入 condition 等待并超时。同一源码的测试对父版本为 5/5 通过，
对候选为 4/5 通过。顺序一致握手只能保护采用新登记顺序的接收者。
