## 0. 一句话

`chunk->conns()` 是**位图不是计数**, 清它的地方有三处、由不同线程驱动, 而"谁有权还池"用的是
**位置判据**(位图现在空不空)而不是**动作判据**(这一位是不是我清掉的) ⇒ 同一块 chunk 会被
归还两次 ⇒ `id_pool::release` 头插时 `cursor_` 已等于 `id` ⇒ `next_[id] == id` 自环 ⇒
`acquire()` 永远返回同一块、池里其余 id 永久不可达。

修法 = 把归还判据换成动作判据(**每人只清自己那一位; 谁把位图清空, 谁还池**)。

## 3. 修复内容(一处函数, `src/libipc/ipc.cpp: sub_rc(broadcast)`)

```cpp
// 旧: 清掉 curr_conns & ~conn_id(接收时在连的**所有**人), 再看"清完空不空"
auto last_conns = curr_conns & ~conn_id;

auto nxt = chunk_conns & ~conn_id;
```

`discard_storage`(写方覆写归还)同步加同一判据: 若 `(cur_conns & rem_cc) == 0` ——

**射程**: 只对 broadcast 生效。unicast 的 `sub_rc` 仍无条件返回 true —— 它的收方上限是 1、
写方永不替它清位, 位图只有一个驱动者 ⇒ 不存在二次归还。⛔ 若将来 unicast 也接入覆写/借样

## 5. 本轮**被实测证伪**的假设(八条, 逐条留档)

这一节比结论更重要 —— 每一条都曾看起来"显然成立", 而实测把它推翻了:

1. **"单收方就能复现"** —— 20 轮 0 次。必须两条归还路径同时开火。
2. **"纯落后(全不读)就能复现"** —— 20 轮 0 次(1 个和 3 个收方都试过)。
3. **"洪泛期间边发边采样更灵敏"** —— 反了: 采样要 fopen/fread 段文件, 拖慢发布方、改变
   竞态窗口 ⇒ 48 轮 0 次。**量具改变了被测对象**。改为只在轮末采样后立刻 8/8 红。
4. **"守卫把自环换成了泄漏(两个都要治)"** —— 部分成立: 先测到的 `free = 36~39/40` 里混着
   **收尾不干净**(见 6)与真泄漏; 分开量之后, 自环那一条已被完整闭合。
5. **"断开收方后再灌小消息就能把在飞的收回来"** —— 错。`push`/`force_push` 开头就是
   `if (cc == 0) return false;` ⇒ 一个收方都没有时**根本不落笔**, 覆写不发生。必须挂一个
   **新**收方再覆写, 否则量到的是"环里还剩多少在飞"而非"池漏了多少"(两者同形)。
6. **"量具门放每轮循环里更稳"** —— 错: 泄漏逐轮累积, 那时量具门读到 `cap−2` 是"又漏了一轮"
   不是"量具坏了"。守卫臂两次红全是量具门, 自环判据一次都没机会说话。量具门只能跑一次、
   且必须在池干净时跑。
7. **"每轮建两个收方就能复现"** —— 两个收方**都**持有时环满, 但只有一个在丢 ⇒ 退化形态。
   有效构造必须是一读一落后。
8. **"修完应该池永远回满"** —— 不是。见 §6。

## 6. ⛔ 未闭合的残余(为什么只能记 🔶部分修)

**(a) 归还得太早 ⇒ ABA(不在本次射程)**
`pop()` 先拷数据、后才清自己的 `rc` 位, 所以"已读到 storage id 但尚未清位"的收方会被写方
算进 `rem_cc`, 被当成"永远看不到这格"而**提前收回** —— 那个收方随后拿一个已回池(可能已复用)
的 id 去建 `buff_t`。本次改的是"同一块被还两次", **没有**碰这一条。
那一侧的防护在 `prod_cons.h` 的 `pop()` 里(拷贝前后与进 clear 前各比一次 epoch, 已落码)。
⇒ 判据与修法各管一头, ⛔ 不得把本项读成"撕裂窗已修"。

**(b) 偶发、位置不固定的 `free = cap−1`(未定位)**
同一构造连跑两次: 一次只在末 3 轮出现, 另一次 39/40 轮都出现 ⇒ **不可复现**, 已按"未定位"
登记。用例默认只**登记**这个读数, 不作门(`UF011_EXPECT_LEAK_FREE=1` 可把它变成硬判据用于
继续追查)。

**(c) `id_pool::release` 本身仍不幂等**
本次是在**调用方**保证幂等, `id_pool` 没有加任何守卫(加了就是布局变更, 要过互通性拍板)。
⇒ 任何**新增**的归还路径都必须自己带上这个判据, 否则同样的自环会从新路径回来。

## 8. 仪化: "读方拷贝"与"写方落笔"重叠(方案 A 那扇窗)

> 2026-09-21。此前这条只是**推演**(见 §6a 与上文"A 关的是哪扇窗"), 本轮把它变成了读数。

**构造**: 先只发不读把收方甩到落后 >256 槽 ⇒ 下一次 `pop()` 触发重同步
(`prod_cons.h` 把游标夹到 `cursor() - kRingSlots`, 而 `index_of(cursor()-256) ==
index_of(cursor())` ⇒ **落地那一格就是写头**)。随后一边持续发、一边排空, 3 秒 / 约 590 万条。

**仪化点**(插桩构建, 仅在沙箱; 判据见下):
- 写方: 在 `f(&el->data_, rem_cc)` 两侧写入 `g_writing = 本槽 index` / `kNone`;
- 读方: 拷贝前后各读一次 `g_writing`, 命中本槽 ⇒ `g_overlap++`;
  若同时 `(rc1 & ~ep_mask) == (rc0 & ~ep_mask)`(即 **② 的 epoch 比对没响**)⇒ `g_overlap_blind++`。

| 读数 | 不跳过写头 | 跳过写头(A′) |
|---|---|---|
| `g_head_read`(读到写头那一格) | 3148 | 5 / 12 / 103 |
| `g_overlap`(拷贝与落笔重叠) | 1360 | 0 / 6 / 20 |
| **`g_overlap_blind`(②③ 看不见的重叠)** | **1096** | **0 / 0 / 0** |

**非退化门**: `g_head_read > 0` —— 遭遇路径**真实存在**, 不是理论。(两次独立运行同号。)

**结论**: 重叠里 **81%(1096/1360)** 是 epoch 检查**看不见**的。机制是 `push` **先声明后落笔**:
`rc_` 的 CAS 在 `f(&el->data_, rem_cc)` **之前**(`prod_cons.h:267` vs `:273`), 所以若收方读到的是
CAS **之后**的值, epoch 在它拷贝**之前**就已经变了 ⇒ ②③ 全程沉默, 而载荷可能正被逐字节改写
⇒ 收下一个撕裂的 `storage_id`(指向池里另一条消息的 chunk)。⭐ 对照: **mmb 是反的** ——
`f()` 之后才 `f_ct_.store(...)`(`prod_cons.h:505-507`)。

**仪化可撤销性**: 插桩只加在沙箱。撤销后 `prod_cons.h` 回到 `7e90f14c847ff62b69c655863ff3b831`、
`ipc.cpp` 回到 `fb37a18834d0eb23c27918a0344b8f1c`, 与插桩前**逐位一致**;
`grep -c uf011_probe` 两者均为 **0**。

## 9.5 泄漏机制已定位 ⇒ **方案 B 撤销**(2026-09-21)

> 这是本轮最重要的订正: §6b 那个"偶发泄漏"曾被我归到"归还权不唯一", 并据此要立
> 方案 B。**实测把那个归因推翻了。**

**工具**: `docs/probe_leak_mech.cpp`(沙箱仪化 + 直读池段)。400 轮里约 20~40 轮复现
一次, 且每次给出卡住块的**完整位图变化史**(每次清位: 旧值→新值 + 站点)。

**读数**(典型一次, `free=39/40`, 卡住 `id=31 conns=0x1`):

```
#57291  acquire  → conns = 0x3        两个收方都在
#57377  discard  → 0x3 → 0x1          写方只清了落后那位(rx_lag), 留下 bit0 ⇒ 没还池,
                                      等 bit0 的持有者来还
（此后 id=31 再没有任何事件）
```

同一探针里正常周期长这样, 对比鲜明:
```
acquire(0x3) → recycle(0x3→0x2) → discard(0x2→0x0, 写方还池)
```

**这条链只能推到一个结论**:
1. 写方留下 bit0 的前提是 **bit0 的槽位位已被清** ⇒ 那个收方 **pop 过了**;
2. pop 过 ⇒ `recv` 拿到了消息并建了 `buff_t` —— `recv` 里三条"不建 buff_t 就返回"的
   出口(`r_size<=0` / `find_storage` 失败 / `recycle_t` 分配失败)**都有日志, 且实测
   一条都没出现**;
3. 而 buff_t 的归还**记在了别的 id 上** —— 否则这里必有一条 recycle 事件(它缺席)。

⇒ **那个收方从槽位里读出的 `storage_id` 不是它该读的那个。它读错了 id, 于是把 buff_t
建在别的 chunk 上、把归还还给了别人。** 旁证: 同一探针里的
`chunk returned twice: site = recycle_storage, conn_mask = 1` —— 归还时发现"我这一位
已经不是我的了"。

**⇒ 方案 B 的前提是错的。** B 要给位图加"谁已取走"; 但这里卡住的位, 其持有者
**从来没有取走那块 chunk** —— 不是"归还权没有唯一持有者", 是**读到了不属于它的 id**。
再加精细的权威判据也救不了 ⇒ **B 撤销, 转去做撕裂窗(§8/§9 那扇, 读数 `blind=1096`)**。

⚠️ 遗留说明: §6a 那条"归还得太早 ⇒ ABA"与本条**不是同一件事**, 仍按原样挂着。

## 10. 方案 B 的状态(⛔ 已撤销, 见 §9.5)

B 要解决的是**另一扇窗**: 位图只记得"谁还没放手", **不记得"谁已经取走"**, 于是写方按 `rem_cc`
清位时无法区分"没取过"与"已取走但没放手" ⇒ 归还权同时落在两个人手上(实测指纹
`site = recycle_storage, conn_mask = 1`)。

正解 = 给槽位加**每收方已消费位图**(32 位足够)。这是 **wire 级**: `elem_size` 变 ⇒
`block_size` 变([elem_array.h:31-32](../src/libipc/circ/elem_array.h#L31-L32)), 而段按
`sizeof(Elems)` 打开([queue.h:37](../src/libipc/queue.h#L37))⇒ **同一话题**的新旧进程环段大小
不一致。**可借用的先例**: 本轮另一 Agent 正在给 chunk 段名加容量分量 `__C<cap>` 来隔离布局
不同的段 —— 同一手法可套到环段名上。⛔ 未拍板前不动。
