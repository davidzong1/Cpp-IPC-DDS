# 同机多订阅者共享一个接收 socket —— 设计方案

> **状态**: 设计文档, **未实施**。本文档回答一个具体问题: 用 **socket 作对外接收后端 +
> SHM 作本机分发后端** 是否合理, 以及若做, 该怎么分期落地。
> **编写日期**: 2026-09-14
> **基线**: HEAD = 8663dab
> **相关**: [shm_defect_fixes.md](shm_defect_fixes.md)(第 3/5 条是本文动机的一部分)、
> [dds_interface_roadmap.md](dds_interface_roadmap.md)(拦路石 3: 发现与传输绑定)、
> [dzflat_shm.md](dzflat_shm.md)(本机分发的底座)

---

## 0. 结论先说

**合理, 而且这是标准模型** —— DDS-RTPS 就是这个形状: 一个 DomainParticipant 持有标准端口的
接收线程, 收到后**分发给本机所有 DataReader**; reader 不会各自去开一个 socket。iceoryx 同理
(网关收网, 本机走共享内存)。当前实现"每个订阅者一个 socket"反而是**非标准**的那一侧。

而且这个改动会带来一个超出预期的好处: **它让两个方向对称**。现在只有"本机发→本机收"没有
本机旁路, 而"远端发→本机收"更是每个订阅者各自收一遍; 补上共享入口之后, 收发两侧就统一成
"本机走 SHM、跨机走网络", 这正是所有成熟实现的样子。

**但"合理"不等于"现在就该做"。** 它有四个前提条件(§4)与三个必须处理的陷阱(§5), 其中
"bridge 会把手上的 CPU 从 N 个线程收到 1 个"是**真实的反向风险**, 高带宽话题上可能得不偿失。
所以 §7 给的是分期方案, 第一步是**量测**, 不是改代码。

## 1. 问题: 同机 N 个订阅者 = N 份完整网络栈工作

### 1.1 现状(有出处的数字)

| 项 | 值 | 出处 |
|---|---|---|
| 每 topic 占用的 UDP 端口 | **5** 个(数据/响应/握手/ACK-数据/ACK-响应) | `common/hash.h` 的 `kUdpPortOffset*` |
| 每个 socket 订阅者开的 socket | **2** 个(数据 socket 入组 + ACK 发送) | `socket_pub_sub_ipc.cc:532`、`:536` |
| 每个 socket 订阅者的线程 | **2** 个 | `socket_pub_sub_ipc.cc` 两处 `new std::thread` |
| 入组 socket 的接收缓冲 | 请求 1MB, **内核截到 208KB** | 代码自报的 `warn_if_buffer_truncated` |
| 组播 TTL | **1**(不出 L2 段) | `platform/posix/udp.h:226-227` |

于是同一台机器上 N 个订阅者订阅同一话题时, **同一份数据报会被内核复制 N 份**分别投进 N 个
socket, 每个订阅者再各自跑一遍**完整的分片重组 + NACK 抑制 + RTO 估计状态机**。

### 1.2 三条路径的覆盖, 以及那个洞

这是问题的核心, 值得画清楚:

| 场景 | 现状走哪条路 | 是否重复劳动 |
|---|---|---|
| 同进程 pub → sub | **nodelet 快速路径**(`LocalPubSubRegistry`, 共享 ptr 扇出) | 否 —— 已经是零拷贝 |
| **跨进程 · 同机** pub → sub | **内核 UDP 组播栈走两遍**(发出去 + 回绕收回来) | **是 —— N 个订阅者各收一份** |
| 跨机 pub → sub | 内核 UDP 组播 | 是(但跨机无法避免,**每个接收主机一份是合理的**) |

注: socket 路径**确有**一个 nodelet 快速路径(`socket_pub_sub_ipc.cc:210-301`), 但它
**只在进程内**有效(靠 `LocalPubSubRegistry`, 键含 topic/domain/msg_id)。所以第二行那个洞
是真实存在的: 本机两个进程之间传数据, 现在要绕内核两遍, 且订阅者越多越糟。

**这不是"话题数量多"的问题, 而是"订阅者数量 × 流量"的问题** —— 一个话题 10 个订阅者比
10 个话题各 1 个订阅者更糟。而机器人/车载场景里"多消费者订阅同一路大流量传感器"恰恰是常态
(感知、记录、可视化、诊断同时订阅同一路图像/点云)。

## 2. 提议的架构

### 2.1 形状

```
                    ┌─────────────── 本机(host) ───────────────┐
   网络组播  ──────▶ │  共享入口 (per topic×domain, 引用计数)      │
   (远端发布者)      │    · 唯一的 socket / 入组 / 重组状态机      │
                    │    · 收到完整消息 → 写进本机 SHM 通道        │
                    └──────────────────┬───────────────────────┘
                                       │  DZFlat chunk + Sample 借用
                          ┌────────────┼────────────┐
                          ▼            ▼            ▼
                      订阅者 A      订阅者 B      订阅者 C     (各自进程, 零拷贝读)
```

即: **共享入口就是"代表网络的本机发布者"**。它不是新概念 —— 它是把 §1.2 表格第二行那个洞
补上, 让"跨机来的数据"和"本机产生的数据"在订阅者眼里**没有区别**。

### 2.2 收发两侧因此对称

```
发布侧:  有本机订阅者? → 走本机 SHM 通道(DZFlat 借样, 0 拷贝)
         有远端订阅者? → 走 UDP 组播
订阅侧:  数据来自本机?  → 读本机 SHM 通道(0 拷贝)
         数据来自远端?  → 共享入口收下来 → 写进本机 SHM 通道 → 读(见 §5.4 去重)
```

**两半的底座都已经存在**: SHM 通道 + DZFlat 借样 + Sample 视图是 `dzflat_shm.md` 那一整套
(已落地、41/41 绿); 进程内扇出是 `LocalPubSubRegistry`。缺的只是把它们**串到跨进程同机这
条路上**。

## 3. 拷贝与延迟账

### 3.1 拷贝次数(远端发布者 → 本机 N 个订阅者)

| | 现状 | 提议 |
|---|---|---|
| 内核复制进 socket | **N** | **1** |
| 分片重组 memcpy | **N** | **1** |
| 写进 SHM chunk | — | **1**(新增) |
| 反序列化 / copy_to | N | **0**(借样视图) |
| **合计(以 1 次全载荷 memcpy 为单位)** | **≈ 2N** | **≈ 2** |

**关键结论**: 新方案的固定成本是"重组 1 次 + 写 chunk 1 次", 与订阅者数**无关**; 而现状是
每个订阅者两份。**N=1 时两者打平**(所以单订阅者必须走快速路径跳过 bridge, 见 §5.5);
**N≥2 就是净赚**, N 越大赚越多。

### 3.2 延迟

多了一跳: 入口进程重组完 → 写 SHM → 订阅者被唤醒读。SHM 那一跳本身是亚微秒级(环 + chunk
元数据), 但**跨进程唤醒**(入口线程 → 订阅者线程)会引入调度延迟, 实测通常在数微秒到数十微秒,
取决于是否绑核/实时优先级。

**这一条必须实测**(§7 第一步), 不能靠估。若本机订阅者对延迟敏感(控制回路), 那 bridge 引入
的这一次跨进程唤醒可能就是不可接受的 —— 这也是为什么 §7 把它排在量测之后。

## 4. 四个前提条件(缺一不可)

### 4.1 本机分发必须复用 DZFlat 借样, 不能走 TLV 序列化

如果 bridge 收到报文后**序列化成 TLV 再发进 SHM**, 那本机订阅者要付的是"重组 1 + 序列化 1 +
反序列化 1", 而现状每个订阅者是"重组 1 + 反序列化 1" —— **N=1 时新方案更差, N=2 时也只是
打平**。整个方案的收益来自"DZFlat 借样让本机那一跳零拷贝", 没有这一点就不成立。

**结论: 本方案与 DZFlat 是强耦合的**, 不是可选项。

### 4.2 单订阅者必须绕过 bridge

§3.1 的 N=1 打平意味着 bridge 在单订阅者时是**纯开销**(多一个进程、多一跳唤醒)。必须先查
本机同话题的订阅者计数, **只有 ≥2 才启用 bridge**。计数从哪来 —— `IpcInfoPool` 已经能做
(它按 topic/domain 记录所有 ShmSub/SocketSub 条目, `ipc_info_pool.h`), 且已有心跳与
`kill(pid,0)` 判活。

### 4.3 bridge 的粒度是 (topic × domain), 不是 (domain)

若做成"每个 domain 一个 bridge", 它要加入该 domain 下**所有**话题的组播组 —— 组表爆炸, 且
单进程要处理全机所有组播流量, 反而放大了 §1.1 的问题。**按话题分**, 于是 bridge 数量 ≤ 当前
订阅者 socket 数量, 严格更优。这也与现有"每 topic 一个 SHM 通道"的结构天然对齐。

### 4.4 入口必须是唯一的, 且不能各自为政

同一 (topic, domain) 在同一主机上只能有**一个**入组接收者, 否则又回到 N 份。这需要一个
**选定机制**: 引用计数的认领(第一个本机订阅者创建, 最后一个销毁)或独立守护进程。选型见 §5.3。

## 5. 三个必须处理的陷阱

### 5.1 双重投递: 本机发布者的组播会回绕进自己的入口 ⚠️

这是最容易漏掉、且会造成**静默重复数据**的一条。

`IP_MULTICAST_LOOP` 必须保持 1(否则同机其他进程收不到, `hash.h` 的注释明确写了这一点)。
于是本机发布者发出的组播,**会被本机的共享入口收到**。而如果 §2.2 里发布侧也走了本机 SHM
通道, 那么本机订阅者会**同时**从 SHM 直接拿到一份、又从 bridge 转发拿到一份 → 同一条消息
投递两次。

**处置**: 入口必须能识别并丢弃"源自本机"的报文。可用手段:
- 发布者在本机 SHM 通道与网络报文中带上同一个**源标识 + 序号**(现在报文已带 `sender_id` 与
  `sequence`, 见 `data_rev.cc` 的 `local_node_id`/`sequence`), 入口按源标识过滤本机源;
- 或者发布侧在检测到"本机已有订阅者走 SHM"时, 对该话题**关闭组播回绕**(`IP_MULTICAST_LOOP=0`
  是 per-socket 的, 只影响本 socket 的回绕, 不影响其他主机 —— 但同机**其他** dzIPC 进程若是
  纯网络订阅者(不认识 SHM 通道), 就会收不到, 所以这条要慎重)。

**推荐第一条**: 按源标识过滤, 语义清晰且不依赖 socket 选项的微妙语义。

### 5.2 可靠性语义变了: 谁在 ACK?

现状**每个订阅者各自维护重传状态**(NACK 抑制、RTO 估计、位图 NACK, 见 `data_rev.cc`)。N 个
本机订阅者 = N 份独立的 NACK 流。

改成共享入口之后, 只有入口能 ACK/NACK。语义上, `reliable` 退化成"**入口收到了**", 而不是
"**应用收到了**"。于是:
- **好处**: N 份重复 NACK 收敛成 1 份, 反向带宽与发布端重传压力都降 N 倍(这是实打实的收益);
- **代价**: 本机某个订阅者消费慢、队列溢出时, 消息**已经被 ACK 了**, 不会重传 —— 该订阅者
  静默丢数据, 而发布端认为送达成功。

这与 iceoryx 的取舍一致, 但**必须显式决定并写进文档**, 不能默认。两条路:
1. **接受**并在文档里写明"本机 reliable = 入口级可靠, 不保证每个本机订阅者";
2. **本机订阅者也回 NACK**: 入口汇总本机订阅者的缺片再统一 NACK —— 复杂度显著上升, 且需要
   入口维护每订阅者的接收水位。

建议先走第 1 条, 并把"本机订阅者队列溢出计数"暴露成可观测指标(否则第 1 条的代价是隐形的)。

### 5.3 归属、崩溃与接管

入口需要进程承载。三种归属:

| 方案 | 优点 | 缺点 |
|---|---|---|
| **引用计数认领**(首个订阅者创建, 末个销毁) | 无新守护进程; 生命周期随使用者 | 认领/释放有竞态; **owner 崩溃 → 其余订阅者必须能接管**, 接管期丢数据 |
| **独立守护进程**(类 iceoryx RouDi) | 生命周期清晰、便于统一配置 | 新增运维面; 需要开机拉起与看护 |
| **首个订阅者的进程内线程 + 崩溃后他人重认领** | 折中 | 最复杂 |

**建议**: 先做引用计数认领 + 崩溃重认领, **不引入守护进程** —— 后者会把这个优化变成一次
运维模型变更, 收益/代价比立刻变差。判活用现有的 `IpcInfoPool` 心跳(`kill(pid,0)` 已实现)。

### 5.4 §5.1 与 §5.2 的关系

两条都指向同一件事: **入口是一个"代表网络的本机发布者", 而不是一个透明的管道**。透明管道
的直觉会让人漏掉去重与 ACK 语义 —— 把它当发布者看, 两个问题都会自然浮现(发布者不该把自己
发的东西再收一遍; 发布者的可靠性只到"交给中间层")。

## 6. 反向风险: bridge 把手上的 CPU 从 N 个线程收到 1 个 ⚠️

**这是本方案最容易被忽略的代价, 必须单独说。**

现状: N 个订阅者各自重组 → 重组工作是**并行**在 N 个线程/核上的。
提议: 入口**一个线程**做全话题的重组 → 对高带宽话题, 这可能成为**单核瓶颈**。

也就是说: 本方案用"省掉 N-1 份重复工作"换来了"把剩余那份工作集中到单线程"。当话题带宽
接近单核处理能力时, **集中化是劣化而非优化** —— 现状虽然浪费, 但浪费是并行的。

**缓解**:
- 入口线程必须绑核 + 实时优先级(仓库已有 `ThreadDispatch`/`QoS` 机制, 见 `type.h` 的
  `DispatchPriority` 与 `CPU_CORE`);
- 粒度是 per-topic(§4.3), 所以不同话题的入口天然分布在不同的核上;
- 若单话题带宽仍压不住, 退化为"该话题不启用 bridge"。

**这条决定了 §7 第一步必须先量测**: 先回答"本机重复投递到底烧掉多少 CPU/带宽", 再决定值不值。

## 7. 分期方案

### 第一步(必做, 不改产品代码): 量测

在动手之前先回答三个问题, 每个都要有数字:

1. **同机 N 个 socket 订阅者, 内核侧的实际开销是多少?**
   量: 每订阅者的 CPU 占用、`/proc/net/udp` 的 drops、`netstat -s` 的组播计数、N=1/2/4/8 的
   曲线。**判据: 若 N 增大时总 CPU 近似线性增长, 说明重复劳动真实存在且在量级上值得治。**
2. **本机 pub → sub 走内核 UDP 两遍, 相对 SHM 直连的代价是多少?**
   对比: 同机两进程, 分别用 `IPC_SOCKET` 与 `IPC_SHM` 传同一话题, 比吞吐与延迟。
   **这一条独立成立、独立有价值** —— 即使最终不做 bridge, "同机该走 SHM"本身就该是个明确结论。
3. **bridge 那一跳的唤醒延迟是多少?**
   原型: 一个进程收 UDP 写 SHM, 另一进程读, 测端到端 p50/p99 相对"订阅者直接收 UDP"的差值。
   **判据: 若增加的中位延迟 > 该话题的时限预算, 本方案对它不适用。**

### 第二步: 本机发布侧走 SHM(独立可交付, 建议先做)

只做 §2.2 的发布侧: 发布者检测到本机有订阅者时, **额外**往本机 SHM 通道发一份(同时照常
发组播给远端)。这一步:
- 不引入 bridge、不引入新进程、不改变接收侧任何代码;
- 立刻消掉"本机 pub → 本机 sub 绕内核两遍"的全部浪费;
- 是 §5.1 去重问题的**前身** —— 做了这一步, 去重就必须一起做(否则本机订阅者会收两份:
  SHM 一份 + 组播回绕一份)。所以这一步与 §5.1 是同一件事的两半, 必须同时交付。

### 第三步: 共享入口(真正有风险的一步)

仅在第一步量测支持、且第二步已稳定之后做。交付物:
- 入口的引用计数认领 + 崩溃重认领;
- 源标识去重(§5.1);
- ACK 语义决策落地 + 本机溢出计数可观测(§5.2);
- **单订阅者自动跳过 bridge**(§4.2)。

---

## 8. 不做什么

- **不引入守护进程**(§5.3) —— 会把优化变成运维模型变更。
- **不做 per-domain 的入口**(§4.3) —— 组表爆炸, 放大问题。
- **不在本机分发这一跳用 TLV**(§4.1) —— 收益会全部消失。
- **不改组播寻址本身** —— 组碰撞是另一个问题, 见 [shm_defect_fixes.md](shm_defect_fixes.md) §5,
  两者的修法可以独立决策。
- **不动跨机路径** —— 跨机每主机一份是合理的, 没有可省。

## 9. 与其他文档的关系

- **与 `dzflat_shm.md`**: 本方案**依赖**它。DZFlat 借样是本机那一跳零拷贝的前提(§4.1)。
- **与 `shm_defect_fixes.md` 第 3/5 条**: 那是"同机不同话题互相串扰", 是**寻址**问题; 本文是
  "同机同话题重复接收", 是**拓扑**问题。两者独立, 但都指向"当前 UDP 层的寻址/分发模型需要
  一次整体审视"。
- **与 `dds_interface_roadmap.md` 拦路石 3**: 那条说"发现是本机共享内存表, 传输绑定是算出来的
  而非协商出来的"。本方案的"共享入口 + IpcInfoPool 认领"其实**顺手补上**了其中一小块(本机
  范围内的端点发现与角色协商), 是那条拦路石上成本最低的一格。
