## 1. 一分钟口径

| 项 | 值 |
|---|---|
| 进程模型 | **恒为跨进程**：发布/订阅是两个 `fork+exec` 出来的新映像（`--role=pub` / `--role=sub`），父进程只做编排与合并，不参与数据面 |
| 时基 | `CLOCK_MONOTONIC`（W03 `monotonic_clock.h`），每次运行实测计时成本并写进 manifest |
| 路径 | `tlv` / `dzflat-a` / `dzflat-b` / `cyclonedds-udp` / `cyclonedds-iox` |
| 尺寸档 | 至少 64 B / 1 KiB / 64 KiB / 1 MiB。`--payloads=` 给的是**应用逻辑载荷**目标，时间戳头 32 B 另计（`header_bytes`）；实际值见 `payload_bytes`（三段取整后会与目标差个位数） |
| 速率 | 定速档小消息（≤64 KiB）用 `--rate`（默认 1000 Hz），**>64 KiB 自动降到 500 Hz** 并把实际目标写进 `rate_target` —— 1 MiB × 1000 Hz = 1 GB/s 超出本机 UDP 回环能力，硬用会让"负载未达标"掩盖真实结论（方案 §6.2 的"1000 Hz 小消息 / 500 Hz 大消息"口径） |
| 工作负载 | `timestamp`（只读头部）/ `crc`（CRC 顺序全读）/ `full`（逐元素比对） |
| 等待策略 | `blocking`（主对照）/ `busy`（单列组，CPU 单独报） |
| 发送计划 | 定速档按 `t0 + k/rate` 预排，**与接收完成无关**；迟发与积压分别计数 |
| 结果目录 | `artifacts/perf/<run_id>/`，只追加：重跑生成新目录，不覆盖 |

## 2. 用法

```bash
# 0) 重建（§10.6：file(GLOB) 是配置期展开的，必须重跑 cmake）
cmake -S . -B build && cmake --build build --target xproc_benchmark -j$(nproc)

# 1) 四档正确性用例（TLV / DZFlat A / DZFlat B × 64B/1KiB/64KiB/1MiB × 三工作负载 + 1KiB 忙等组）
test/w02_benchmark.sh smoke

# 2) 追加 CycloneDDS 两档（需要 RouDi；脚本会尝试自动拉起，失败则显式跳过）
test/w02_benchmark.sh smoke-dds

# 3) 只跑 DDS 两档
test/w02_benchmark.sh dds

# 4) 单档细查
build/bin/xproc_benchmark --path=dzflat-b --payload=65536 --workload=full --rate=1000
build/bin/xproc_benchmark --path=cyc-iox --payload=1024 --workload=timestamp --rate=500

# 5) 多档交替比较（ABBA，禁止顺序跑）
build/bin/xproc_benchmark --compare=tlv,dzflat-a,dzflat-b --payloads=64,1024 --rounds=3

# 6) 小规模正确性用例（gtest，自己会拉起一次 0.3s 的跨进程运行再反证三条验收）
ctest --test-dir build -R test_w02_xproc_benchmark --output-on-failure
```

常用参数：

| 参数 | 含义 |
|---|---|
| `--path=P` | 单档路径（`tlv`/`dzflat-a`/`dzflat-b`/`cyc-udp`/`cyc-iox`）；给了就只跑这一档 |
| `--compare=A,B,...` | 多档交替（每轮反序，ABBA） |
| `--payloads=N,...` | 载荷目标值（字节） |
| `--payload=N` | 单档载荷 |
| `--workload=W` | 给了就只跑这一组（`timestamp`/`crc`/`full`） |
| `--wait=MODE` | `blocking`（默认）/ `busy` |
| `--rate=N` | 定速 N msg/s；`0` = 满速开环 |
| `--duration=S` `--warmup=S` | 测量窗口 / 预热 |
| `--queue=N` `--queue-wait-ms=N` | 订阅队列长度 / SHM `publish_blocking` 有界等待 |
| `--rounds=N` | 交替重复轮数 |
| `--run-id=ID` `--out-dir=DIR` | 运行编号与结果目录 |
| `--sample-limit=N` | 每个用例每个角色的逐样本上限（超出计 `rows_truncated`，不静默丢） |
| `--best-effort` | 用 `publish_best_effort` 取代 `publish_blocking`（对照用） |
| `--dds-only` / `--smoke-dds` | DDS 档选择 |
| `--dds-uri-udp=URI` `--dds-uri-iox=URI` | 两份 CycloneDDS 配置（默认指向仓库 `test/w02_dds_*.xml`） |

环境变量：`W02_DEBUG=1` 打开角色进程的诊断输出（默认关闭，避免污染测量窗口）。

## 3. 三条计时边界（**禁止混用结束点**）

对应方案 §10.7 的三个实验组。`samples.csv` 的列与派生量：

| 时间戳写入点 | 写在哪 | 含义 |
|---|---|---|
| `produced_ns` | 生产端 | 为本条消息生成新数据之前（序号已分配） |
| `publish_enter_ns` | 生产端 | 发布 API 入口 |
| `transport_done_ns` | 生产端 | 发布 API 返回（数据已对订阅端可见） |
| `app_obtained_ns` | 订阅端 | 应用拿到可用视图/对象 |
| `fully_consumed_ns` | 订阅端 | 完整载荷遍历与校验结束 |

| 派生量 | 定义 | 回答 |
|---|---|---|
| `transport_ns` | `transport_done_ns - publish_enter_ns` | 发布侧 API 成本（组1的一部分，本进程可测） |
| `delivery_ns` | `app_obtained_ns - transport_done_ns` | **通知与交付路径开销**（组1） |
| `app_read_ns` | `fully_consumed_ns - app_obtained_ns` | **应用完整读取/校验成本**（组2） |
| `e2e_ns` | `fully_consumed_ns - produced_ns` | **生产到消费**（组3） |

⚠️ `transport_done_ns` **不在消息头里**：发布 API 返回时消息已离开发布进程，它不可能随
同一条消息送达。父进程按 `seq` 把发布侧与订阅侧两张原始表合并后才算 `delivery_ns` ——
这样"把上一帧的完成时刻当成这一帧"这类错误在结构上不可能发生。

⚠️ 组2 的两种形态成本不同，报告里分列：`crc`（一次 CRC32C 覆盖全部载荷字节）与
`full`（逐元素与序号相关模式比对，元素数进 `elements_checked`）。

## 4. 结果目录结构（§12）

```text
artifacts/perf/<run_id>/
├── command.txt            启动脚本把完整命令行写在这里
├── console.log            采集器 stdout 全量（脚本模式）
├── manifest.json          §12 最低字段集 + dds_qos/dds_precheck_skipped/child_killed_total
├── config.json            有效配置全量 + canonical 串 + config_hash
├── environment.json       W03 platform_info 同构（governor/SMT/NUMA/rlimit/THP…）
├── topology.json          角色与进程模型、topic、domain、RouDi pid（若存在）
├── field_schema.json      W03 单一事实来源生成的样本/汇总字段 schema
├── results.json           逐用例结构化结果（含三条边界分布与计数）
├── summary.csv            逐用例汇总（86 列，见下节）
├── counters.json          采集器计数 + 各用例的路径/失败计数并列（不做跨进程加法）
├── path_evidence.json     每条路径的调用点/运行证据/指纹/计数，缺项标"未确认"
├── verdict.md             逐项引用原始文件与字段的判定
├── samples/               <case>.pub_raw.csv / .sub_raw.csv（两个角色的原始表）
│                          <case>.samples.csv / .samples.jsonl（父进程按 seq 合并）
│                          <case>.*.counters.json（角色各自的计数导出）
├── stdout/ stderr/        每个用例每个角色的 stdout/stderr
└── ddscheck_<path>.txt    DDS 预检结果
```

`manifest.json` 里字段为空时写 `null` 并在 `verdict.md` 说明原因（不省略后假定已满足）。

## 5. 逐样本字段（`samples/*.samples.csv`）

表头直接由 W03 `include/dzIPC/measure/field_schema.h` 的 `sample_csv_header()` 生成，
字段名与语义以那里为**唯一事实来源**：`run_id, seq, route, generation, path, produced_ns,
publish_enter_ns, transport_done_ns, app_obtained_ns, fully_consumed_ns, transport_ns,
delivery_ns, app_read_ns, e2e_ns, payload_bytes, wire_bytes, payload_checksum_ok,
retry_count, evicted, dropped`。

两个角色的**原始表**（`pub_raw.csv` / `sub_raw.csv`）额外保留各自的细节：

| 文件 | 列 |
|---|---|
| `<case>.pub_raw.csv` | `seq,idx,flags,produced_ns,enter_ns,done_ns,app_bytes,wire_bytes,ok,publish_rc,backlog_ns,retry` |
| `<case>.sub_raw.csv` | `seq,idx,flags,app_obtained_ns,fully_consumed_ns,checksum_ok,elements_checked,rx_wire_bytes,abnormal,view_kind` |

`flags` 高 16 位相位：`1`=探测帧、`2`=预热、`4`=测量、`8`=停止哨兵。
`view_kind`：`0`=物化对象、`1`=DZFlat 借样视图、`2`=DDS 样本。

分开落盘的理由：发布侧的 `done` 与订阅侧的 `app` 属于两个进程，只有父进程能按 `seq`
合并；也让"发出去了但没收到"在原始文件里一眼可见（`missing` 行会带 `dropped=1`）。

## 6. `summary.csv` 关键列

分组：`case_id, path, experiment_group, workload, wait_mode`
载荷：`payload_target, payload_bytes, header_bytes, wire_bytes_per_msg, wire_bytes_source`
速率：`rate_target, duration_plan/actual, rate_actual_attempt, rate_actual_ok`
**发送计划**：`plan, attempts, sent_ok, send_failed, send_blocked, late, late_threshold_ns, backlog_max_ns, backlog_sum_ns`
接收与完整性：`recv_measure, recv_probe, recv_warmup, missing, duplicate, out_of_order, checksum_bad, abnormal, bad_header, samples_merged, rows_truncated, elements_checked`
**失败量判定（t47 新增）**：`late_ok, backlog_ok, send_blocked_ok, abnormal_ok, bad_header_ok`（0 = 该 gate 判失败，1 = 通过；
阈值见 `manifest.failure_thresholds`；`bad_header` 是**新补的原始量列**，修前它只写进子进程日志）
路径计数：`pub_dzflat, pub_fallback, sub_flat_accepted, sub_tlv_accepted, sub_rx_defects, loan_fail`
三条边界分布：`transport_*` / `delivery_*` / `app_read_*` / `e2e_*`（各含 `min/p50/p99/p999/max/mean`，单位 ns）
资源：`pub_cpu_s, sub_cpu_s, roudi_cpu_s, pub_cpu_cores, sub_cpu_cores, total_cpu_cores, *_ctx_*, *_maxrss_kb`
判定：`load_ok, timing_ok, case_ok, child_killed, failure_reasons`

**字段别名**（同一事实、不同产物里的列名；⛔ 不是两个独立来源）：`summary.csv:late` ↔ `results.json:late_sends`；
五个 gate 在 summary 是 `*_ok` 的 0/1、在 results.json 是 `gates.{...}` 的 true/false。
映射机器可读地写在 `manifest.field_aliases`（t50 中性观察①）。

### 迟发与积压的口径
`late` = 超过阈值（`late_threshold_ns = max(50 µs, 周期/10)`）的发送次数；
`backlog_max_ns`/`backlog_sum_ns` 是**原始**迟发量与累计。设阈值的原因：`sleep_until`
本身有几十 µs 抖动，不设阈值会让每轮都是 100% 迟发、指标失去分辨力（实测）。

### "负载未达标"的判定
定速档要求 `attempts ≥ 99% × plan` 且 `rate_actual_ok ≥ 90% × rate_target`；不满足即在
`failure_reasons` 里点名。这样"接收变慢 → 发送量下降 → 统计变好看"不会被当成成绩。

### 失败量进判定的阈值（t47/W02-F3；**逐量给理由**）

任务书第 3 条要求「失败与异常**不被静默排除**」。修前 `late`/`backlog`/`send_blocked`/`abnormal`
只落列、`bad_header` 连列都没有 ⇒ r23 里 **17/75 case 的 `late` 合计 71 全不进判定、`case_ok` 全 True**，
那是「用仅落列实现静默排除」。修后：

| 量 | 判定式（阈值见 `manifest.failure_thresholds`） | 为什么是阈值而不是无条件失败 | 本量是否进判定 |
|---|---|---|---|
| `late` | `late > 20` **且** `late/attempts > 5%` | `sleep_until` 本身有几十 µs 抖动，要求 0 等于把调度噪声判成失败；两个条件同时成立才说明「结构性跟不上声明速率」 | ✅ 进判定（`late_ok`） |
| `backlog_max_ns` | `backlog_max / 周期 > 10` | 峰值积压包含一次调度量子 + 唤醒链开销；以「周期数」为单位 ⇒ 跨速率档可比 | ✅ 进判定（`backlog_ok`） |
| `send_blocked` | `> 0` | 有界等待耗尽 = 发布路径真的被卡住；它**本来就该**为 0 | ✅ 进判定（`send_blocked_ok`） |
| `abnormal` | `> 0` | 结构异常样本（段头/长度自相矛盾）不该出现在正常运行里 | ✅ 进判定（`abnormal_ok`） |
| `bad_header` | `> 0` | 同上；本量修前**完全不落列**（只在子进程日志 `bad_hdr=`） | ✅ 进判定（`bad_header_ok`） |
| `rows_truncated` | `> 0` | 逐样本表被 `sample_limit` 截断 ⇒ 该轮计数不完整 | ✅ 进判定（既有） |
| `checksum_bad` | `> 0` | 载荷校验失败 | ✅ 进判定（既有，逐样本 `payload_checksum_ok` 可查） |
| `via_view` / `via_object` / `via_dds` | **仅信息性**，不进判定 | 它们是**通道构成**（这一轮的各通道各走了多少），不是失败；且实测 A/B 同形（§7.1）⇒ 判它没有意义 | ⛔ **显式声明：仅信息性** |

阈值可被命令行覆盖（`--late-abs-max` / `--late-rate-max` / `--backlog-max-periods` /
`--send-blocked-max` / `--abnormal-max` / `--bad-header-max`），覆盖后 `manifest.failure_thresholds.cli_overridden=true`
⇒ **用于反例验证**（把阈值压到 0 证判据会亮）。默认值的敏感度与前后对照见现行 run 的 `f3_before_after.md`。

## 7. 路径生效证据（§10.6 的假通过防线）

| 档 | 必须满足 |
|---|---|
| `tlv` | `pub_dzflat == 0`（路径隔离） |
| `dzflat-a` / `dzflat-b` | `pub_dzflat > 0` **且** `sub_flat_accepted > 0`；否则标"实际走 TLV 回退，不能算该档成绩" |
| `dzflat-b` | 生产端调用点必须是真实的 `loan → 就地构造 → publish_loaned`（`warmup` 与 `measure` 两段**同形**，见下） |
| `cyc-udp` / `cyc-iox` | 预检（`--role=ddscheck`，12 s 超时）通过；RouDi 是否存在、`CYCLONEDDS_URI` 指向哪份配置写进 `config.json` 与 `counters.json` |

### 7.1 ⚠️ A/B 的可分性**只在发布侧**成立（C)② 更正，含实测对照）

**更正**：本文档早前把 `via_view > 0` 列为 **B 档专属判据**。队长独立复算 + 本轮实测均表明
**该判据无区分力**——消费者侧两档同形：

| 档 | `via_view`（10 轮 full 档合计） | `via_object` | `via_dds` | 发布侧 `wire_bytes_source` |
|---|---|---|---|---|
| `dzflat-a` | **13500** | 0 | 0 | `对象 dzflat_size()` |
| `dzflat-b` | **13500** | 0 | 0 | `B 借样 chunk 容量` |
| （对照）`tlv` | 0 | 1000/轮 | 0 | `对象 serialize() 长度` |

⇒ **A/B 可分性证据只在发布侧**：① `summary.csv:wire_bytes_source`（A 与 B 不同）；② 实际路径条数计数
（W03 的 `dzflat_a_messages` / `dzflat_b_messages`，见 §7.3 的两套基准说明）。
⛔ **不得**用 `via_view` 作 B 档的唯一判据，也不得用消费者侧计数区分 A/B。
`via_view > 0` 仍然保留在判定里，但它证明的是「**走的是视图/借样通道**（A 与 B 都属于），而非对象拷贝」，
不是「B 与 A 有别」。

### 7.2 B 档 `warmup` 与 `measure` 必须**同形**（t47 新发现并已修）

`warmup` 段的帧与测量帧走同一个订阅侧视图处理器；处理器**先按 workload 校验载荷**（`full`/`crc` 档）
再判 flag。修前 B 档的 warmup 帧只 `set_data4(true)` 就发布（没有三段分配、没有时间戳头）⇒
每条 warmup 帧都被记成 `bad_header` + `abnormal`。

| 时点 | B 档 `bad_header`（每 case） | 可见性 |
|---|---|---|
| 修前（t47 之前的全部 run） | **686 – 1210**（视尺寸档；跨 r19/r20/r23 45 条记录；见 `r4_bad_header_inventory.txt`） | ⛔ **只写进子进程日志** `bad_hdr=`，`summary.csv` 里根本没有该列 ⇒ 对判定不可见 |
| 修后（现行 r34） | **0** | `summary.csv:bad_header` + `bad_header_ok` 列，逐 case 可判 |

⇒ 这条正好演示「量存在但不进判定」的危害：**一个真实存在的 1200/case 异常在补列之前完全不可见**。

### 7.3 本仓存在**两套**基准（B)⑥ 更正，含队长错误记录的撤回）

**撤回**：此前「本仓只存在一套 W02 基准（`xproc_benchmark`）」的表述**不成立**，队长已记录该错误。
实际：

| 基准 | 入口 | A/B 计数口径 | 用途 |
|---|---|---|---|
| **W02** | `test/xproc_benchmark.cpp`（`build/bin/xproc_benchmark`） | **合并**：只有 `summary.csv:pub_dzflat`（A+B 合在一起），无 A/B 分列 | 跨进程、多路径、多尺寸档的**统一对照**（本工作包） |
| **W08** | `test/test_w08_dzflat_ab.cpp`（`grep xproc_benchmark` 零命中） | **分开**：`dzflat_a_messages` / `dzflat_b_messages` 逐入口断言 | W08 的 A 推广 / B 专项验证 |

**跨包引用规则**：
1. ⛔ **不得**用 W02 的合并读数 `pub_dzflat` 冒充「A/B 可分」——它把两档加在一起；
2. 要引用 A/B 分列的量，引用 **W08** 的 `test_w08_dzflat_ab` 结果（或 W03 的路径计数逐 ID）；
3. 两个基准**互不替代**：W02 出「同一逻辑载荷在不同路径/尺寸档下的对照」，W08 出「A/B 各自的正确性」；
4. 两套基准的 run/证据目录**各自署名**（W02 的 `work_package="W02"` 不参数化，见 §11.1）。

DDS 档**不采集 wire 字节**：`wire_bytes_per_msg` 写 `null`，`wire_bytes_source` 说明原因。
"组合包加载成功 / 进程接上 iceoryx 段"都不能证明"这条消息走了共享内存"，所以
`path_evidence.json` 里 CycloneDDS 路径的证据等级只到 S3 时仍会在 `verdict.md` 标注
未确认项。

## 8. 跨进程身份可核验（§10.6）

每个用例在 `verdict.md` 的 `identity:` 行登记：

```
parent_pid=<父进程> pub_pid=<发布进程> sub_pid=<订阅进程>
| pub_ready_ns=<N> in [<spawn 前读数>,<观察到 ready 后读数>]
| sub_ready_ns=<N> in [...]
| pub_starttime_ticks=<...> sub_starttime_ticks=<...>
| pub_lib=<实际加载的 libipc.so 路径> | sub_lib=<...>
```

判据（机器可判，非自述）：

1. 两个角色都是 `fork+exec` 的新映像，`pid` 与父进程不同；
2. 角色写入的 `CLOCK_MONOTONIC` 值必须落在父进程的括号区间内（时基不同源必然失败）；
3. `pid` + `/proc/<pid>/stat` 的 `starttime` 一起登记（防 pid 复用）；
4. 角色进程实际加载的 `libipc.so` 路径写进控制块，与 manifest 的 `loaded_library_paths` 对照。

正常退出：停止哨兵重发到订阅侧确认（`stop_frames_recv ≥ 3`）→ 订阅侧正常析构并置
`sub_done` → 发布侧等待后再析构。任何一步靠超时 SIGKILL 收尾的用例，会在
`failure_reasons` 里显式列为失败（`child_killed`），**不得**当作通过。

1. **DDS 档的零拷贝落地未确认**：`cyc-iox` 只证明"配置指向开启 SharedMemory 的 URI 且

6. **`busy` 组只在与正对照相同的单档（默认 1 KiB）上运行**：它是 CPU 对照点，不是全量矩阵。
7. **CycloneDDS 档的路径证据标"未确认"**：`path_evidence.json` 里

### 11.4 样本表的跳过与空值语义（W02-F1 / D-19 裁决）

**跳过以「行」为单位**：一行里只要有任一派生列（`transport_ns`/`delivery_ns`/`app_read_ns`/
`e2e_ns`）为空字段，整行计 `skipped_rows`，该行 4 个单元格**都不计入 `cells`**。
于是恒有 **`cells == 4 × (rows − skipped_rows)`**。

同一份 `r20` 曾被两个复核者算出不同数字，根因是**判据宽窄**而非数据差异：

| 口径 | rows | cells | skipped | 说明 |
|---|---|---|---|---|
| 按单元格跳过（**错**） | 67500 | 269962 | 38 | 整行跳过却只扣 1 个单元格，恒等式不成立（针对 r20） |
| 只跳「时间戳字段为空」（偏窄） | 67500 | 269896 | 26 | 漏掉 `ao<td` 这一类（**这是 t25 合同里引用的数字，对应 r19**） |
| **行口径（规范）** | 67500 | **269848** | **38** | 覆盖两类跳过，恒等式成立（r20） |
| **行口径（现行 run r34）** | 67500 | **269868** | **33** | 判据同上；**逐 run 波动**（r19=26、r20=38、r23=37、r34=33），⛔ 不得把某一轮的 skipped 写成常量 |

> **口径差异的唯一来源**：`skipped` 的行判据是 `ao<td ∪ 任一派生列为空`。
> 只统计「时间戳字段为空」会得到 26（r19）；两种跳过都算得到 38（r20）。⇒
> **cells 不是常量**（逐 run 变化），能被机械复核的是**恒等式** `cells == 4×(rows−skipped_rows)`
> 与 `mismatches == 0`，⛔ 不是某个固定的 cells 数字。

**为什么会有 `delivery_ns` 为空**（物理成因）：`delivery_ns = app_obtained_ns − transport_done_ns`，
而 `transport_done_ns` 是**发布侧** `send()` 返回的时刻、`app_obtained_ns` 是**订阅侧**
取到对象的时刻（两个进程，靠单机 `CLOCK_MONOTONIC` 同源合并）。订阅侧**可能先于**发布侧
`send()` 返回就取到对象，此时差值为负。基准的处理是 **不入账、也不写 0 冒充未测**
（`xproc_benchmark.cpp` 的 `if (app >= done) r.delivery_ns.push_back(...)`），原始两列
（`app_obtained_ns` / `transport_done_ns`）照常保留，使该情形**可被独立发现**。
最小反例：r20 的 `r40_dzflat-b_crc_blocking_65536B_1000Hz.samples.csv` 第 863 行 `seq=1000861`，
`ao − td = −61806` ns。实测条数随运行波动（属正常）：r20 = 38 行 / 最负 −61806；r21 = 14 行 / −27107；
r23 = 37 行 / −5762；**r34（现行）= 53 行**。判据（行口径）不随次数变化。

**另一类空字段是「正常」，不是缺失**：`payload_checksum_ok` 在 **`timestamp`（只读头部）**
工作负载下恒为空（现行 r34 实测 `timestamp` 22500/22500 空；`crc` 0/22500；`full` 0/22500）。
⚠️ `crc` 档**做**校验（它按定义覆盖全部载荷字节算 CRC32C），**不能**把"不校验"写成
"`timestamp`/`crc` 都不校验"。

**未测项写空字段、不写 0**（W03 §2.1）：DDS 档不采集 wire 字节 ⇒
`samples.csv:wire_bytes` 与 `summary.csv:wire_bytes_per_msg` 都写**空字段**、
`results.json:wire_bytes_per_msg` 写 `null`、`summary.csv:wire_bytes_source` 写
`not_collected(DDS 侧无 dzIPC wire 计数)`。⛔ 不得写 `0` —— 0 是"实测 0 字节"的合法取值，
把它当"未知"会诱导出"wire=0 = 零拷贝"的方向性错误结论（方案 §10.7/§13.3）。
