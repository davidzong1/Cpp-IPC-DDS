## 1. 口径歧义的本质（为什么两者都不假）

| 计数 | 定义（实现处） | tlv 档（DZFlat 关闭）的语义 |
|---|---|---|
| `DzFlatFallbackCount`（既有，W08 前就在） | `NoteDzFlatPublish(false)` 的次数 = **"尝试过 DZFlat 但没走成"** | 开关关闭 ⇒ `try_publish_dzflat` 第 1 行即返回 false ⇒ **每条消息都 +1** ⇒ = 该档消息数（实测 120） |
| W03 `fallback_total`（新接线） | **"DZFlat 已启用且尝试过、但降级"** 的次数 | 开关关闭 ⇒ **根本没有"尝试"** ⇒ **0（正确值）** |

⇒ **两者分母不同**：前者是"**没走成 DZFlat**"（含"本来就不该走"），后者是"**该走却没走成**"（真降级）。
⇒ 报告里出现的 `fallback_total=0` 与 `dzflat_fallback=120` **不再构成矛盾**：一个说"没有真回退"，一个说"这 120 条都不是 DZFlat"。§3 给出可写死的期望值，§6 给出机器判据。

**W08 的 `w08_scope_note` 覆盖关系**：其 manifest 声明「回退原因计数未接线，其值恒 0，不代表已测」——本任务完成后该声明**对原因维度已过期**（原因维度**已接线**、其值可非 0）；但**调用点尚未落地**（§7），因此**当前仍为恒 0**。⇒ 建议 W12 把该声明改写为：
> `回退原因计数已实现并接线就绪（W09/t19）；在 EX-1 窗口重开、调用点补丁应用之前，`fallback_*` 仍恒 0，**不得**据此判"无回退"。`

## 2. 三种语义（**不得混算**）

```
(a) 路径选择  path_selection_dzflat_disabled / path_selection_type_unsupported
      DZFlat 关闭 ⇒ 正常 TLV。⛔ 一个 fallback_* 都不 +1。
      信息量：两组**二选一**，合计 = 关闭态下的 TLV 条数（可与 tlv_messages 对账）
              · type_unsupported 的运维含义：**即使开启 DZFlat，这些消息仍走 TLV**
              · dzflat_disabled   的运维含义：**开启即有收益（属"待启用"集合）**

(b) 真回退    fallback_total  +  对应原因（同时 +1，"首个失败资源"语义）
      DZFlat **已启用且尝试过**但降级。可精确判定的原因：
        · fallback_type_incompatible —— 启用 + 类型无平坦布局（**队长 D-16 精确化**：
          此时"预期走 DZFlat"成立，是一次真实降级）
        · fallback_capacity_full     —— 启用 + 无接收方
        · fallback_oversized         —— 启用 + `need_bytes > capacity_bytes`（有容量证据）
      ⛔ 无法精确判定的 ⇒ fallback_reason_unknown（**不猜分**），见 §5.3

(c) B 借样失败  borrow_failed_no_receiver / _pool_exhausted / _oversized / _publish / _reason_unknown
      `LoanedMessage` 三条出口的失败。⛔ **绝不**进 fallback_total：
      借样契约（`loaned_message.h` 顶部三条）明写"失败是常态、由应用回退到普通 publish"，
      那一次回退已在 A/TLV 的调用点被记一次；这里再记会把 `fallback/(dzflat+fallback)` 比值算歪。
```

**互斥性**：分类器 `classify_dzflat_attempt()` 的返回**恰好落到三类之一**（`dzflat_delivered` / `path_selection` / `fallback` / `borrow_failed`），判据 `BorrowFailureIsSeparateFromTransportFallback` 直接断言 `borrow_failed_*` 与 `fallback_total` 不互相污染。

**为什么选 (i)「不改签名 + 旁用局部状态」而不是 (ii)「追加 `try_publish_dzflat_ex`」**（任务书第 2 条要求说明理由）：
1. **证据本来就在调用点手里**：是否启用、类型是否支持、有无接收方、`dzflat_size()`、B 路径的三个返回值 —— 全部零成本可得，**不需要**新签名；
2. **改签名会污染 W08 的已验收面**：`try_publish_dzflat` 是 `shm_pub_sub_ipc.h` 的私有方法，但仍然被 W08 的三路径计数环绕；新增 `_ex` 版本意味着两条并存路径，存在"接线一半"的风险；
3. **方案 §10.4 的措辞**是「沿用冻结 API **或**追加兼容接口」——(i) 属前者（沿用），优先；
4. **代价边界清楚**：只有两类原因不可精确判定（§5.3），且都**如实登记为 unknown**，没有"看起来更全"的假精度。

## 6. 口径对照与判读规则（任务书第 4 条）

```
读 counters.json 时的三条规则（建议写进 W10/W11 的判读脚本）：
 1. fallback_total == 0 且 fallback_reason_unknown == 0
      ⇒ 该档**没有真回退**（不是"未接线"）。tlv 档（DZFlat 关闭）**就应该**是 0。
 2. fallback_total > 0
      ⇒ 逐项读原因；若 fallback_reason_unknown > 0，报告**必须**写出"其中 N 次原因不可判定"，
         ⛔ 不得把它摊到其它原因上，也不得省略。
 3. borrow_failed_* > 0
      ⇒ 这是**应用侧借样失败**，与 (b) 回退无关；它与 fallback_total **不得相加**。
         fallback/(dzflat+fallback) 的比值里**只用** fallback_total，⛔ 不含 borrow_failed_*。
```

**与 `DzFlatFallbackCount` 的关系（一段话）**：
> `DzFlatFallbackCount` = 「没走成 DZFlat 的条数」（含**路径选择**：开关关闭时每条都计）；`fallback_total` = 「**该走** DZFlat 却没走成」的条数。两者在三种档位下的关系：**tlv 档** `DzFlatFallbackCount=N` 而 `fallback_total=0`（正确）；**A/B 档且没有回退** 两者都是 0；**A/B 档且有回退** `DzFlatFallbackCount` 只在"该条最终走了 TLV"时 +1，而 `fallback_total` 包含"`try_publish_dzflat` 失败"的次数 —— 在应用随后成功走 A 路径的情形下（B 失败 → 应用回退 A 成功），`fallback_total` 会 +1 而 `DzFlatFallbackCount` **不**变，这正是两者必须分开读的原因。

## 8. 更正：W09-F2 的机制归因（队长 D-16 第 3 条）

### 8.1 撤回

**撤回表述**：「`loan` 路径上『每进程每档位至多 1 块』的上界不成立」——该结论**证据不支持**，归因错误。

**错误原因（逐条核对源码后确认）**：原探针（`w09_probe_loan_dead_hold_*`）两端用**完全相同的 route 名**（`w09leak / w09leak_topic`），观测到的 `PARENT_CAN_LOAN=0` 伴随 stderr `fail: loan, que->ready_sending() == false` —— 而
- `src/libipc/ipc.cpp:1818-1822`：`loan()` 里 `if (!que->ready_sending()) return {}` 发生在**任何 chunk 借用之前**；
- `src/libipc/queue.h:143-146` 的 `ready_sending()` 在单生产端策略下走 `sender_checker<P,false>::connect()`（`src/libipc/circ/elem_array.h:62-68`）= **`atomic_flag.test_and_set()` 互斥占用**；
- 子进程 `_exit(0)` **不跑析构** ⇒ `disconnect_sender()` 从不执行 ⇒ 该 route 的 sender flag **永久置位**。

⇒ 原实验测到的是**「单生产端 sender flag 因暴死未释放而永久占用」**，与 chunk 池里有多少块**无关**（这也解释了为什么是 0 而不是 40−N）。

### 8.2 重做后的两条独立条目（各配复现件与原始输出）

**条目 1：未发布借样的 chunk 占用（重测，符合预期上界）**

构造：子进程在 `prefix=空`、**全新 route 名**上借 N 块 `loan` 后不发布 `_exit`；父进程用**另一个 route 名**（避开 sender flag）借同一尺寸档。

| CHILD_HELD (N) | 1 | 4 | 20 | 39 | 40 |
|---|---|---|---|---|---|
| `PARENT_CAN_LOAN` | **39** | **36** | **20** | **1** | **0** |
| 40 − N | 39 | 36 | 20 | 1 | 0 |

⇒ **逐点精确符合 `40 − N`**：未发布借样**确实**占住 chunk，但**上界就是"该进程在飞的借样数"**这一朴素关系，**没有**超出 UF-003 登记的语义（`published()==0` 的块由清扫方让路；本轮 N=40 时整档不可用）。⇒ **撤回"上界不成立"**；`uf003_crash_reclaim_decision.md:163` 的"死路由孤儿块直到同名路由再现才可回收"仍是准确的既有登记。

**条目 2：单生产端 sender flag 暴死泄漏（新条目，属"route 生产端声明"而非 chunk 容量）**

| 实验 | 子进程行为 | 父进程（**同 route 名**）能否借到 |
|---|---|---|
| A | 借 1 块后 `_exit`（不跑析构） | **0 / 40**（stderr：`fail: loan, que->ready_sending() == false`） |
| B | 借 1 块后**正常返回**（跑析构 ⇒ `disconnect_sender()`） | **40 / 40** |

⇒ 同一个 route 上，**暴死进程把生产端 flag 永久占住**，后续任何生产端（同进程的新对象、或另一进程）都**无法再借样**（`send()` 不受此限，因为它不走 `ready_sending()`）。这条**不是** chunk 池容量问题，属**route 生产端声明（sender flag）的崩溃回收**缺口。
