## 1. 两类泄漏（分开成条目，各配受控实验）

### 条目 1｜未发布借样的 chunk 占用（**本包修复对象**）

**现象（判决性实验，队长 t23 已逐文件复核）**：`build/test-scratch/t23_evidence/leak_exp/`

| 步骤 | 结果 |
|---|---|
| `0_baseline` 无泄漏 | 单跑 builder **100% passed**（本包复现：`1_baseline.log` rc=0 / 9 OK） |
| `1_leaker` loan 40 块 **unpublished** → 外部 SIGKILL | 残留 `__IPC_SHM__CHUNK_INFO__132096__C40`（本包复现：`2_leaker.log`） |
| `2v_solo_after_leak` 单跑（**无任何并发邻居**） | rc=8 / 0% passed（本包在**基线库**上复现：`cf_builder_after_inject.log` rc=1 / `chunk pool exhausted: kind = loan, chunk_size = 132096`） |
| `3_clear` 仅删该未被映射段 | — |
| `4v_after_clean` 单跑 | rc=0 / 100% passed（本包复现：清理后全绿） |

**准确表述**（按队长更正）：失败**与并发邻居无直接关系、但与「并发窗口内产生的异常退出段」强相关**；
段一旦遗留则**跨运行/跨进程持续**（只要未 unlink），**单跑照挂**；**清理段即恢复**。

**机制（本包读源码确认）**：
- `src/libipc/platform/posix/shm_posix.cpp:232` 的 `::shm_unlink` 只在「本进程引用计数归零的 `release()`」内发生；
- `created_registry`（`shm_posix.cpp:44-52`，UF-004 保留面）退出扫除**只覆盖本进程创建的段**；
- ⇒ **`SIGKILL` 跳过析构即不 unlink，段永久遗留**；
- 叠加 `reclaim_dead_chunks`（`ipc.cpp`，调用点**唯一**、仅在池穷尽时触发一次）：`published()==0` 的未发布借样被跳过 ⇒ 段内位图永远显示「已被用掉」。

**⛔ 为什么"逐块回收未发布借样"在本包被判为不可行**（这是不选那条路的**实证理由**，不是托辞）：
1. chunk 的 `conns` 位图是**接收方**集合（`acquire_storage` 借出时就写好了当时的收方位图），
   `owner_table` 记的也是**接收方**身份；**未发布借样的持有者是发送方，它的身份没有记在任何地方**
   ⇒ "证明发送方已死"没有依据。
2. 即便有依据，`proven_dead_bits` 也救不了：那些收方是**活的**（在等一条永远不会来的消息），
   所以 `(cur & ~dead) != 0` 这条判定本来就会让清扫放弃。
   ⇒ 这也**从谓词本身**证明了「调换 `:577/:578` 顺序」不但有 UAF 风险（UF-003 §5），**而且不足以判定**。

### 条目 2｜同 route 名单生产端 sender flag 暴死泄漏（**不属 chunk 容量，单列**）

- 受控对照（W09 重做实验，`证据/t19_leak_experiments.out.txt`）：**暴死** 0/40 vs **正常退出** 40/40。
- 机制：`ipc.cpp` 的 `ready_sending()` 在**借块之前**；`queue.h:143-146` → `elem_array.h:62-68` 的
  `atomic_flag.test_and_set()` 互斥（`sender_checker<P,false>`）；`ipc::route` 默认 `flag_t = relat::single`
  ⇒ 单生产端；`_exit`/SIGKILL 不跑析构 ⇒ `disconnect_sender()` 从不执行。
- **定性：这是"route 生产端声明（sender flag）的崩溃回收"缺口，与 chunk 池容量无关**
  （这也解释了为什么实测是 0 而不是 40−N）。
- **本包处置**：⚠️ **未修**（属 `ready_sending`/`elem_array` 的生产端声明语义，改动面会触及
  `elem_array` 布局与 `sender_checker` 契约，超出 D-14 的"不改正常路径语义/不改 ABI"边界）。
  已登记为**独立条目**（建议编号沿 UF 系列另立），并给出三个候选方向供后续裁决：
  ① `sender_flag_` 改为带 (pid, starttime) 的 owner 记录（同 UF-003 口径）并在 `ready_sending()` 失败时做一次探活；
  ② 把"生产端声明"与"route 生命周期"绑定，由控制面在检测到 owner 死亡时清除；
  ③ 明确接受为有界残余（每个 route 至多失效一次，重启进程即可恢复）。
  ⛔ 不以"既有文档已记录"结案——见 §7 的残余登记。

### 条目 1 与条目 2 的关系（⛔ 不得混算）

| | 条目 1 | 条目 2 |

## 2. 修复方案（v2：复位点 = 首次 attach）

### 2.1 判据与两个前提

```
复位前提 = ①本进程此刻尚未持有本档任何 chunk
         ∧ ②除本进程外没有活进程映射该段
         ∧ ③（探活前后）池的字节镜像未变
```

| 前提 | 为什么成立 | 不成立时的行为 |
|---|---|---|
| ① | 复位只在 `handles_[prefix]` 由"无效→有效"的那一次调用（首次 attach）。要持有本段 chunk（或接收侧 `buff_t`）都必须**先映射本段** ⇒ 此刻本进程不可能持有 | — |
| ② | 持有载荷指针者必须先 `mmap`；死者不再执行任何代码 ⇒ **不可能再 `mark_published`**。判据 = 扫 `/proc/<pid>/maps` 找除本进程外映射了该段文件的活进程 | `/proc` 打不开、某个 `maps` 因权限读不到 ⇒ **`unknown` ⇒ 放弃**（退化为现状行为） |
| ③ | 探活前（持池锁）取 `id_pool` 字节快照，探活后持锁复核；借出/归还必然改动空闲链 ⇒ 有并发借出即不一致 ⇒ 放弃；真正复位与复核在**同一把池锁内** | 不一致 ⇒ 放弃 |

**为什么不用"引用计数归零"**：崩溃进程不会 `release` ⇒ `acc_` **永不归零**（`shm_posix.cpp:214` +1 / `:229` −1）
⇒ "计数为 0" 不是可用判据。这是本包否掉的第一个候选判据。

**为什么 ⛔ 不看 `published()`**：`published` 是**块级**标记，而本问题的失真在**段级**
（空闲链只反映死进程留下的状态）；且按 UF-003 §5，`published()==0` 的块**必须**让路
（防 `acquire_storage` 置位图 → `mark_published` 之间回收导致 UAF）。
本修复**不触碰**该标记的读写，也不改变 reclaim 的射程 —— 它改的是**复位的作用域**（段级）。

### 2.2 与 UF-003 §5"窗口论证"的关系（为什么没有破坏它）

- UF-003 §5 的窗口论证：`acquire_storage` 置 `conns` 位图与 `try_push` 成功之间存在窗口，
  若此间回收，发布者手里的指针立即 UAF ⇒ 故 `published()==0` 一律不碰。
- 本修复的射程是**段内已无任何活持有者**的情形 —— 那时**不存在**"手里有指针的发布者"
  （有指针者必定映射了该段）。
- ⇒ 两者互补：`published` 门保护"段内有人"的窗口；段级复位处理"段内无人"的遗留。
  ⛔ 未改 `published` 的置位/清位点（`acquire_storage`/`mark_published`/`return_unpublished` 逐字不变）。

## 4. 自证伪：我的第一版设计不成立（⛔ 记录在案）

**v1 做法**：在 `acquire_storage` 的**池穷尽分支**里判"除本进程外无人映射该段" ⇒ 复位空闲链。

**为什么错**：`scan_segment_mappers` 只排除本进程 ⇒ 它只能证明"**别的**进程没映射"，
**证明不了"本进程此刻没有在飞借样"**。当池是被**本进程自己**借空时（完全正当的构造），
判据照样成立 ⇒ 复位把**自己正持有的 id 重新发出去**。

**被自己的对照实验当场证伪**（`UNSOUND_v1_selfhold.md` + 日志）：
- `solo_chunk_capacity.log`：`test_chunk_capacity_backpressure` **5 FAILED**，日志里直接可见
  `chunk pool orphan segment reset: ... prefix = 'w09_c1_0'` —— 复位发生在"本进程借空 40 块"的正当场景；
- `solo_dzflat_transport.log`：`DzFlatTransport.ChunkPoolExhaustionFallsBackToTlv` FAILED
  （该用例正是"本进程借空 40 块构造耗尽场景"）。

⇒ 修正为 v2（§2.1 前提 ①：取"首次 attach"时刻，此刻本进程必然尚未持有）。

## 7. 池耗尽策略（逐条可判定，与 W09 `容量与背压_交付.md` §4 冻结条款一致）

| 策略 | 何时适用 | 判定依据 | 本包是否改变 |
|---|---|---|---|
| **沿用回退**（A/TLV 整包路径） | `send()` / `no_member_send` 池空 ⇒ 退化为 64 B 分片 | `acquire_storage` 返回空 ⇒ `send` 走分片分支 | ⛔ 不变 |
| **拒绝**（借样路径） | `loan()` / `publish_loaned()` 池空 ⇒ 返回无效 `loan_t` / `false`，**不阻塞** | `chunk pool exhausted: kind = loan` | ⛔ 不变（契约明确：⛔ 不得改成静默等待） |
| **有限等待** | 环满时的 `wait_for`（`wait_for(inf->wt_waiter_, …, tm)`）—— 属**环**背压，非池 | `publish_blocked` 计数 | ⛔ 不变 |
| **丢弃** | `force_push` 覆写槽位（环套圈）⇒ `discard_storage` 条件归还 | `queue_evicted` / `discard_storage` 计数 | ⛔ 不变 |
| **段级复位（本包新增）** | 池空 **且** 段已无活映射者（崩溃遗留） | `orphan segment reset: kind = attach` | ✅ 新增；**只作用于"已被用过且无活映射者"的段**，全新段与有活持有者一律不触发 |

**两类泄漏是缺陷而非策略** —— 它们必须**有界**：本条修复后，残留段的影响被限制在
"从崩溃到下一个进程 attach 之间"，而不是"直到永远"。

## 8. 归因与诊断（靶心第 3 项：`prefix=''`）

- 判据：池段名 = `make_prefix(prefix, {"CHUNK_INFO__", size, "__C", cap})` ⇒ **`prefix` 就是这一档池的归属判别键**；
  默认 `prefix` 为空串 ⇒ **同一尺寸档全机只有一档池**（`docs/shm_chunk_pool_occupancy_plan.md` §18/§297/§471 已记）。
- 本包**保留**既有那句显式归因（`<= 空前缀: 本档池无话题/进程区分, 全机共享, 归因须查其他进程`），
  并把新增的复位诊断同样带上 `prefix`（`note_orphan_reset` 首报/每 1024 次节流，与 `note_pool_exhausted`/`note_reclaimed` 同口径）。
- ⛔ 本包**不改** `prefix` 的构成（那会改段名 = 改共享布局身份），也不引入唯一前缀 —— 后者属
  `UF-003 §1`（段名版本分量）与部署决策，已在 §9 登记为后续项。
