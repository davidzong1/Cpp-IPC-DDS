# 事件驱动接收线程池 vs Eclipse iceoryx —— 性能对比分析

> 任务：分析 `docs/消息接收架构改造/事件驱动线程池需求.md` 所定义的 SHM 事件驱动接收线程池架构，与 Eclipse iceoryx 的性能对比。
> 性质：**只读分析 + 本机复测**。⛔ 未修改任何产品代码、测试与既有报告；新增本文件与 `tmp/iox_probe/`、`tmp/perf_current_shm/`、`tmp/perf_match_{64,1m}/` 四组复测原始数据。
> 架构图：`docs/消息接收架构改造/事件驱动线程池架构图.svg`（本文引用其分层编号 ①–⑥）。
> 复测环境：Intel i9-14900KF / 32 逻辑核 / 24 物理核 / 内核 6.8.0-138 / Ubuntu 22.04.5 / GCC 11.4 / `-O2`；`cpu_governor=powersave`、无 CPU 隔离、测试窗口内 load average ≈ 10。
> 关键前提：**本机 iceoryx 是"CycloneDDS + iceoryx"的组合**（见 §1.2 的五条本机证据），不是裸 iceoryx API。全文区分「官方裸 iceoryx 数据」与「本机 CycloneDDS+iceoryx 组合数据」，不混用。

## 0. 结论摘要（先读这段）

1. **两者优化的是不同的轴，不能用一个数字判高下。** 事件驱动线程池解决的是**规模轴**（线程数/空闲唤醒/fd 不随话题数线性增长），iceoryx 的强项是**单条延迟轴**（零拷贝、恒定延迟与载荷无关）。本仓在这两条轴上的位置完全不同：规模轴已达到工程可用（1000 订阅 33 线程恒定），延迟轴落后约 1–2 个数量级。

2. **本机同机对照（同 CPU、同内核、同一份 `cyclonedds_shm.xml`、同一天顺序执行）：**

   | payload | dzIPC SHM pub/sub p50 | CycloneDDS+iceoryx p50 | dzIPC p99 | iceoryx p99 | 谁赢 |
   |---|---|---|---|---|---|
   | 64 B @1000 Hz | **8.2 µs**（本波 9.3） | 12.0 µs | 92.5–102.1 µs | 105.0 µs | **dzIPC（≈1.3×）** |
   | 1 MiB @500–1000 Hz | 253–298 µs | **157.7 µs** | 381–477 µs | 313.5 µs | **iceoryx（≈1.6–1.9×）** |

3. **与 iceoryx 官方极限的差距是"拷贝与编解码"造成的，不是线程模型造成的。** 官方 iceperf 报 0.58–0.73 µs 且 1 kB–4 MB 平坦（[iceperf README](https://github.com/eclipse-iceoryx/iceoryx/blob/main/iceoryx_examples/iceperf/README.md)），iceoryx2 单向 92–99 ns（[官方原始数据](https://github.com/eclipse-iceoryx/iceoryx2/blob/main/internal/plots/benchmark_mechanism_comparison_i7_13700h.dat)）。本仓 64 B 单向 8–12 µs，差 **≈12–100×**。而 §5 的逐条归因显示：线程/唤醒层不是主因，**每消息 ≥1 次整包字节流搬运 + 一次向共享段的拷贝**才是。

4. **本仓自己的"延迟杠杆"已经存在，且与线程模型无关。** 本机限速 1 MiB 复测：TLV p50 481.5 µs → **DZFlat（loan-and-build）33.6 µs，14.3×**；p99 704.3 µs → 131.1 µs，**5.4×**（`build/bin/ipc_benchmark --compare`，本机本波实测）。把这条路径变成大消息的默认路径，比任何线程池调优都更接近 iceoryx 的量级。

5. **线程池买到的是规模与空闲成本，读数明确：** 1000 订阅 `threads_max ≡ 33`（兼容路径 101、改造前基线 481，且 1000 处基线 abort）；静默 2 s 空闲 CPU **1.124 核 → 0.0050 核（≈225×）**，空闲上下文切换 19325 → 10（2 s 窗口）。

6. **可比性缺口必须承认（§6 全清单）：** iceoryx 侧未测满速吞吐与 1000 订阅规模；1000 订阅数据来自 **socket** 模块（SHM 订阅侧尚未接入线程池，见 §5.5）；两套 Harness（gtest 计时 vs 专用基准）不可直接相减；本机 iceoryx 是否走零拷贝路径**无计数口可验证**。

> **一句话**：这张架构图里的线程池，是"把 O(话题数) 的开销压成 O(1)"的正确工程；它对标 iceoryx 的是**可扩展性与空闲开销**，而不是单条消息延迟。要在延迟上追平 iceoryx，要动的是**数据面拷贝次数与 wire**（本仓已有 DZFlat B），不是 worker 数量。

## 1. 对比对象与前提

### 1.1 两个系统各是什么

| | 本仓（dzIPC + 事件驱动接收池） | iceoryx |
|---|---|---|
| 定位 | 机器人中间件传输层：pub/sub + ser/cli，SHM 与 socket 双传输，DZFlat/TLV 双 wire | 同机零拷贝 IPC 中间件（ROS 2 的 SHM 后端之一） |
| 发现/控制面 | 共享段控制面（`control_plane`）+ 阶段 1 的进程级 `ShmControlScheduler`（10 ms/50 ms/2 s） | iceoryx 1.x：RouDi 守护进程；iceoryx2：无守护进程，服务发现靠文件系统 + 文件锁监控 |
| 等待原语 | 共享内存 sequence 字 + `futex_waitv`（Linux，最多 127 路/worker） | 1.x：共享内存里的 POSIX `sem_t`（每 Listener/WaitSet 一个）；2.x：**epoll** + 进程间 unix domain datagram socket 门铃 |
| 收包线程 | 进程级固定 N 个 worker（N=CPU，上限 128），route→worker 固定归属，空闲退出归还 OS | 1.x：订阅者 0 线程（等待由用户线程/WaitSet 承担）；2.x：`Subscriber` 无事件接口，事件需另配 Notifier/Listener |
| 载荷约束 | 任意可序列化对象；DZFlat 平坦布局可选；TLV 兼容 | 1.x/2.x 均要求共享内存可放置（无堆/指针/虚函数；2.x 为 `ZeroCopySend`） |

架构层的详细对照见 §2。

## 2. 架构分层对照

对照本仓架构图 ①–⑥ 与 iceoryx 的对应构件。

| 维度 | 本仓（架构图编号） | iceoryx 1.x | iceoryx 2.x |
|---|---|---|---|
| **等待机制**（④） | 共享段 sequence 原子字 + `futex_waitv`；`kMaxRoutes=127`/worker（`src/libipc/recv_wait_set.cpp:23`） | 共享内存 `ConditionVariableData`，底层 POSIX `sem_t`；**每 Listener/WaitSet 一个信号量** | Linux：**epoll**；单次 `epoll_wait` 上限 **512** 事件（[epoll.rs](https://github.com/eclipse-iceoryx/iceoryx2/blob/main/iceoryx2-bb/linux/src/epoll.rs)）；进程间门铃 = **unix domain datagram socket**，进程内 = socketpair |
| **唤醒粒度** | **按 route 定位**：`consume_ready()` 返回就绪 token，worker 精确 `recv_once()` 该 route | 条件变量"有事件"，订阅者自行 `take()` 查所有端口 | reactor 返回就绪 fd；Subscriber 本身无事件接口，需另行 Notifier/Listener |
| **线程模型**（③） | 进程级池：N=CPU（上限 128）固定 worker，route→worker 固定归属，**空闲退出归还 OS** | 1.x 订阅者 **0 线程**（等待发生在用户线程或 WaitSet/Listener）；Listener 自带 1 后台线程 | **无 per-subscriber 线程**；事件驱动需 Notifier/Listener（Listener 也是独立线程） |
| **fd / 句柄成本** | SHM 路径 **0 fd/route**（等的是共享段字，不是 fd）；socket 路径 1 fd/route | 订阅者 0 fd、0 线程；`sem_t` 不占 fd | **每 Listener 1 个接收 fd + 每 Notifier 1 个发送 fd + 每 shm 对象 1 句柄**；官方 FAQ 有 `Running Out of File Descriptors` 章节，建议 `ulimit -n 8192` |
| **队列/背压** | `view_queue_`/`msg_queue_` 有界队列 + evict 回调；chunk 池**每尺寸档 40 块**（`include/libipc/def.h:49`，全进程共享），环 256 槽 | 订阅者队列=可持有 chunk 上限（默认 **256**），溢出"安全丢最旧" | buffer/history 可配（默认 buffer 2、history 0） |
| **内存配置** | chunk 池按 1 KiB 台阶分档、容量**编译期固定**（40/档），段名编码容量 | **发行时必须预配置** mempool（本机 `1MB×50` 等）；池耗尽即丢包 | publisher 预分配 data segment |
| **零拷贝** | A 级 1 拷贝（用户容器→chunk）；**B 级 `loan`+就地构造 = 0 拷贝**（`include/dzIPC/common/loaned_message.h`） | loan/publish 全程 0 拷贝 | `loan`/`loan_slice` 0 拷贝 |
| **类型约束** | 无（任意可序列化对象；DZFlat 为可选优化，TLV 兜底） | 须共享内存可放置：无堆/指针/虚函数、可重定位；不要求 IDL | 须 `ZeroCopySend`（`repr(C)`、无堆/指针、`'static`） |
| **单条上限** | 无硬上限；>chunk 档位或池耗尽时退化 64 B 分片（`src/libipc/ipc.cpp:770-798`）——**是悬崖不是优雅降级** | 单条=所配 chunk；本机最大 1 MiB×50，官方示例到 4 MiB×10 | publisher 预分配段 |
| **编译期规模上限** | `kMaxRoutes=127`/worker → 超限返回 `wait_set_full`，模块**显式回退兼容线程**（`recv_worker.cc:614-625`） | `IOX_MAX_SUBSCRIBERS=1024`、`MAX_NUMBER_OF_NOTIFIERS=256`、`MAX_NUMBER_OF_CONDITION_VARIABLES=1024` | 事件端口默认 16 listener/16 notifier，可配 |

**读法**：架构图 ③（固定分片收包池）+ ④（共享等待层）对标的是 iceoryx 的"等待与线程归属"这一层；两者在"唤醒精确到 route"这个能力上**同级**（iceoryx2 靠 reactor 返回 fd，本仓靠 `consume_ready()` 返回 token）。真正的分水岭在**「一条消息要搬几次字节」**——见 §5.1。

### 3.2 三条读数解读

1. **64 B：本仓略优（p50 1.3×、p99 1.1×）。** 小消息下两边都被"唤醒 + 调度"支配，而本仓的订阅者始终阻塞在 `recv(50)`/等待层上，iceoryx 侧经 CycloneDDS 多了一层 DDS 实体调度。此档位**不能用来说明架构优劣**（差值在噪声与 governor 抖动带内）。
2. **1 MiB：iceoryx 优 1.6–1.9×。** 157.7 µs 搬运 1 MiB ≈ **6.6 GB/s**，本仓 298.5 µs ≈ **3.5 GB/s** —— 两者都落在"内存带宽/memcpy"量级，说明**这一档比的不是唤醒，是每条消息搬了几遍**：iceoryx 由发布端直接写进共享 chunk（应用→chunk 1 次），本仓 TLV 路径是"serialize（含整包 `new` 与页尾分段拷贝）→ 入 chunk"，多出一次整包搬运。
3. **p99 都不好。** 两侧 p99/p50 ≈ 2–10×，共同环境因素：`powersave` 调频（当前 2.6 GHz / 最大 5.7 GHz）、未绑核、无 CPU 隔离、测试窗口 load average ≈ 10。**不要把本表的 p99 当作任何一方的架构能力**。

## 4. 线程池买到的东西：规模与空闲成本

这一节是本次架构改造的**主场**，也是 iceoryx 与本仓差距最小、最值得比的部分。

### 4.1 线程数与规模（本仓实测）

口径：`test/perf/out/20260927_t6_probes/t6scale.cpp`（按当前头文件重编），`socket_pub_sub` 路径，静默窗口 2 s，每 200 ms 采样 `/proc/self/task`。**注意：该探针只覆盖 socket 模块**（日志首行 `mode=socket_pub_sub`，`test/perf/out/20260927_t6_scale/worker_1000.log:1`）。

| scale | worker 路径 threads_max | worker threads_min | compat threads_max | 改造前基线 threads_max |
|---|---|---|---|---|
| 1 | **33** | 2 | 2 | 5 |
| 100 | **33** | 2 | 101 | 104 |
| 477 | **33** | 2 | 478 | 481 |
| 1000 | **33** | 2 | abort | abort（基线 1000 实测 abort） |

- worker 路径线程数**恒定 33**（32 worker + 主线程），规模 1→1000 完全不增长；静默后回落到 **2**（空闲退出真实发生）。
- 对照口径（iceoryx 1.x）：订阅者 **0 线程**；iceoryx 2.x：`Subscriber` **0 线程**（事件驱动需另配 Listener，每个 Listener 1 线程）。**在"线程数"这一项上，iceoryx 的模型本身就更省**——它把等待交给用户线程，本仓则要保证"用户不写等待循环也能收包"。这是设计取舍，不是缺陷：本仓保留了 `get/try_get` 的异步语义（需求 §1.2 明确不可变），代价就是必须有收包侧线程。

### 4.2 空闲成本（本仓实测，这是收益最大的一项）

静默 2 s 窗口（`集成测试与性能基准报告.md` §3.2）：

| scale | 路径 | voluntary ctx switches /2s | 空闲 CPU（核） |
|---|---|---|---|
| 1 | 基线 | 4080 | 0.025 |
| 100 | 基线 | 7077 | 0.173 |
| 477 | 基线 | 19325 | **1.124** |
| 477 | **worker** | **10** | **0.0050** |
| 477 | compat | 10 | 0.0749 |

- **1.124 核 → 0.0050 核，≈225×**；空闲上下文切换 19325/2s（≈9662/s）→ 10/2s（=5/s）。
- 归因清楚：改造前每个订阅者一条线程、每 50 ms 一次 `select()` 空轮询；改造后 worker 阻塞在等待层，**超时不是错误、也不轮询**（架构图 ③ 的 strip）。
- 对照 iceoryx：其等待同样是**阻塞 + 事件唤醒**（`sem_wait`/`epoll_wait`），空闲成本与订阅数无关。**在本项上双方同级**；本仓原先的劣势来自"每话题一条轮询线程"，而这正是本次改造消掉的东西。

### 4.3 fd 成本与规模上限（两者都有硬边界，位置不同）

| | 本仓 | iceoryx 1.x | iceoryx 2.x |
|---|---|---|---|
| SHM 路径 fd/route | **0**（等共享段字） | 0（`sem_t` 不占 fd） | 每 shm 对象 1 句柄 + event 端口 fd |
| socket 路径 fd/route | 1 | — | — |
| 单进程规模硬边界 | SHM：`kMaxRoutes=127`/worker → `wait_set_full` → **回退兼容线程**；socket：**fd 号 ≥ FD_SETSIZE(1024) 时 `select()` 触发 `__fdelt_chk` abort**（既有缺陷，归 ipc-transport） | `IOX_MAX_SUBSCRIBERS=1024`（编译期） | epoll 单次 wait 512 事件；`max_user_watches`；官方 FAQ 明列 fd 耗尽章节 |

- 两条边界的**性质不同**：本仓 SHM 侧超限是**显式回退**（`backend_unavailable`/`wait_set_full` → 保留兼容线程，架构图右侧面板），socket 侧 fd 越界是**进度崩溃**（已知缺陷 D9/L1）。
- iceoryx 侧超限是**预配置/编译期**上限（`IOX_MAX_SUBSCRIBERS`、mempool 容量），撞上就是注册失败或丢包——**没有"退化为每路一条线程"的路径**。在"超限时的行为可推理"这一点上，本仓的显式回退设计（需求 §9、§11.7）是**优于** iceoryx 的工程属性。

## 5. 差距归因：延迟差在哪一层

### 5.1 R1｜每消息字节流搬运次数（主因，已量化）

本机限速 1 MiB、`build/bin/ipc_benchmark --compare=3 --payload=1048576 --duration=2 --rate=500`（本波实测）：

| 轮次 | TLV p50 | DZFlat p50 | TLV p99 | DZFlat p99 | dzflat 生效/回退 |
|---|---|---|---|---|---|
| 1 | 487.6 µs | 33.4 µs | — | — | 0 / 1000 → 1000 / 0 |
| 2 | 479.0 µs | 33.6 µs | — | — | — |
| 3 | 481.5 µs | 35.5 µs | 704.3 µs | 131.1 µs | — |
| **汇总** | **481.5 µs** | **33.6 µs（14.32×）** | **704.3 µs** | **131.1 µs（5.37×）** | 回退率 0.0% |

- DZFlat B（loan-and-build）把发布侧"用户容器 → serialize 堆缓冲 → chunk"压成"用户直接写 chunk"，**两端 0 拷贝**（`include/dzIPC/common/loaned_message.h` 头部契约）。
- 33.6 µs 已**优于**本机 CycloneDDS+iceoryx 实测的 157.7 µs（1 MiB）。也就是说：**本仓不需要换线程模型、也不需要抄 iceoryx，只要把已经实现的 DZFlat 变成大消息默认路径，就能在 1 MiB 档反超本机 iceoryx 组合。**
- 嵌套数组场景差距更大：10 万点云编码 **40×**、堆分配 100,004 → **0**、消费者端到端 **75×**（`docs/dzflat_shm.md` §9.2）。注意该文档同时诚实说明：5.93 MB 图像端到端只有 **1.24×**，因为大 blob 遍历本身就是内存带宽瓶颈。

### 5.2 R2｜chunk 池天花板：40/档 vs 可配置 mempool

- 本仓每尺寸档 **40 块**全进程共享（`include/libipc/def.h:49`；`ipc.cpp:461` 的注释仍写 32，**以代码 40 为准**，该不一致已登记为 L8）。
- 后果：池满时大消息退化为 **64 B 分片**打进 256 槽环（`src/libipc/ipc.cpp:770-798`）。文档明确定性为"**性能悬崖，不是优雅降级**"（`docs/dzflat_shm.md` §5.3）。
- iceoryx：mempool **发行前按业务配置**（本机 1 MB×50、128 B×10000…；官方示例到 4 MiB×10）。这是"配置换确定性"，代价是内存常驻与 IDL 式上界声明。
- 对本仓的直接含义：**DZFlat B 的 14.3× 只有在池容量与消费速率匹配时才拿得到**（上面那次复测的告警正是"回退占比偏高"的历史成因）。这是 P0 建议里必须一并处理的一半。

### 5.3 R3｜控制面与 DDS 层

本机 iceoryx 数据经 CycloneDDS（`DomainParticipant` → reader/writer → iceoryx）。这解释了为什么本机 iceoryx 组合是 12 µs/158 µs，而官方裸 iceoryx 是 0.6 µs/0.1 µs：**DDS 实体与串行化栈的固定成本被计入了**。因此 §3.1 的 1–2× 是本仓与"实际部署形态"的差距，§3.3 的 12–250× 是本仓与"理论极限"的差距。混用这两个数字会得出错误结论。

### 5.4 R4｜p99 抖动：环境而非架构

两侧 p99 都劣化 2–10×，共同环境：`powersave`、未绑核、`load ≈ 10`。本仓提供了显式逃逸通道（`--pin=A,B` 绑核、`ThreadDispatch` 的 `SCHED_FIFO` opt-in，架构图 ③ 的"逃逸通道"），但**默认不启用**（需求 §6 明确）。要做 apples-to-apples 的尾延迟对比，必须两侧都绑核并固定 governor，本轮**未做**。

### 5.5 R5｜覆盖缺口：SHM 订阅侧尚未接入线程池

本波核对当前工作区：

| 模块 | 是否接入池 | 证据 |
|---|---|---|
| `socket_pub_sub_ipc` | ✅ `SocketRecvWorkerPool` | 5 处引用；`worker_mode_` |
| `socket_ser_cli_ipc` | ✅ `SocketRecvWorkerPool` | 6 处引用 |
| `shm_ser_cli_ipc` | ✅ `RecvWorkerPool` | 7 处引用；`SerRequestRoute` |
| **`shm_pub_sub_ipc`（SHM pub/sub 订阅侧）** | ❌ **0 处** | 仍为 `sub_handshake_thread_` + `subscribe_thread_`（`src/dzIPC/shm_pub_sub_ipc.cc:940-941`），`recv(50)` 在 lease 内执行 |

- 因此：架构图 ① 里 `shm_pub_sub_ipc` 同时持 `RouteSession`（已接入，阶段 2）与**兼容收包线程**（未接入阶段 5）。
- 影响面：**§4.1 的"1000 订阅 33 线程"只证明了 socket 两模块**；SHM 订阅侧目前仍是每订阅 1 条收包线程 + 1 条握手线程（且控制面调度器 `ShmControlScheduler` **全仓零接入点**，只被自己的 `.cc` 与单测引用）。这是需求 §11.1/§11.2 尚未完全闭环的部分，也是与 iceoryx 比"规模轴"时**必须承认的未完成项**。

## 6. 可比性边界与未测项（诚实清单）

**未测：**
1. iceoryx 侧**满速吞吐**（本轮只跑定速时延；`latency_publisher` 是限速发送模型，没有全速档）。
2. iceoryx 侧 **1000 订阅/多话题**规模对照（本机 perf_tests 只提供单 topic 与双 topic 场景）。
3. iceoryx2（0.10.0）**实测**——本机只装了 iceoryx **2.0.5**（这是"2.0.5 版本号"≠"iceoryx2 产品"的常见误读，本文全篇区分：`iceoryx 2.0.5` 是 1.x 产品线的最后一个稳定版）。
4. p99.9/max 尾延迟的受控对比（需绑核 + governor 固定）。
5. 跨机路径（两者都只测了本机）。
6. CycloneDDS 是否走零拷贝路径的**直接证据**（无计数器）。

**不可比：**
7. Harness 不同：本仓基准是专用多进程基准（写 CSV/JSON/样本），iceoryx 侧是 gtest 之外的示例程序，只输出统计摘要；**不能把两侧的 mean/σ 直接相减**。
8. 订阅语义不同：本仓默认进入有界队列、由用户 `try_get` 消费（本轮测量含入队）；iceoryx 侧是回调/`take` 语义。队列深度与消费时机不同会让"延迟"含义发生偏移。
9. 载荷类型不同：本仓 1 MiB 档是 `TestMsg`（`float64[] + int32[] + string[] + bool`）的 TLV/DZFlat；iceoryx 档是 `Float64Array` 经 CDR 编码。字节数相同，编码成本不同。
10. 官方 iceperf 的 0.58–0.73 µs 为往返口径折半与否**未在 README 明示**。

**已知不对称（有利于本仓的）：**
11. 本机 iceoryx 组合多一层 CycloneDDS；纯 iceoryx API 会更快。
12. 本机 RouDi mempool 最大档 1 MiB×50，而本仓 chunk 池"1 KiB 台阶 × 40/档"没有大档位预配置压力 —— 严格说本仓的池更容易在大消息上退化为分片（见 §5.2），这一点反而**不利于**本仓，故不构成"本仓占便宜"。

## 7. 优化建议（按收益排序）

> 判断依据：**先动数据面拷贝次数（R1），再动规模覆盖（R5），最后才动调度细节（R4）。** 线程池已经处于"没有明显可再压的空闲成本"的状态（0.0050 核）。

| 优先级 | 动作 | 预期收益 | 验证方法 | 归属 |
|---|---|---|---|---|
| **P0** | 把 **DZFlat B（loan-and-build）** 变成 SHM pub/sub 大消息（≥64 KiB）的默认路径，并同步核算 chunk 池容量与背压联动 | 1 MiB p50 **481.5 → 33.6 µs（14.3×）**，p99 **704 → 131 µs（5.4×）**；1 MiB 档**优于**本机 iceoryx 组合 | `build/bin/ipc_benchmark --compare=3 --payload=1048576 --rate=500`（回退率必须 0%）+ `docs/hotpath_gate.sh build` | ipc-transport |
| **P0** | **SHM 订阅侧接入 `RecvWorkerPool`**（消除 per-route `recv(50)` 线程），补齐需求 §11.1/§11.2 的 SHM 半边 | 1000 订阅 SHM 路径 threads 从 O(N) → 33 恒定；消除 `channel_mtx_` 与 50 ms 空轮询 | 复用 `test/perf/out/20260927_t6_probes/t6scale.cpp` 的 **SHM 版**（当前只有 socket 版） | ipc-transport |
| **P1** | 让 `ShmControlScheduler` 真正被 `shm_pub_sub_ipc`/`shm_ser_cli_ipc` 接入（当前**全仓零接入点**） | 握手线程 O(N) → 1；与架构图 ⑤ 一致 | `test/test_shm_control_scheduler.cpp` + 模块级线程计数 | ipc-transport |
| **P1** | 固定 `governor=performance` + `--pin` 绑核，重跑双方 p99/p99.9 | 把 §3.1 的 p99 从"环境噪声"变成"架构读数"；预计两侧 p99 各降 2–5× | 两侧同条件重跑；本仓 `--pin=A,B` | 测试 |
| **P2** | socket 数据面 `select()` → `poll()`（L1/D9，既有缺陷） | 解除 `fd ≥ 1024` abort；1000 订阅 socket 数据面可达 | `test/perf/out/20260927_t6_probes/fdprobe --scale=1000` | ipc-transport |
| **P2** | chunk 池容量与 `ViewQueueCap()` 的联动配置化（当前 40 硬编码），并把 `large_msg_cache` 的 **40 vs 注释 32** 口径不一致（L8）收敛 | 让 P0 的 14.3× 在压测/满负载下不退化为分片 | `docs/dzflat_shm.md` §5.3 的持有预算推算 + 池耗尽计数 | ipc-transport |

**明确不建议做：**
- **不要把"iceoryx 式定容 POD"当默认载荷模型。** `docs/dzflat_shm.md` §6 已给代价：IDL 须声明上界、4 MB × 32 槽 = 128 MB/topic、Python 侧要另写。本仓的价值之一恰是"任意可序列化对象都能走"，TLV 兜底不能拆。
- **不要用"减少 worker 数/统一单线程收包"去追 iceoryx 的延迟。** §4.2 已证明空闲成本已经接近零；再收敛线程数只会损失并行度（阶段 6 的"统一 spin"在需求里就是被明确限制的可选项）。
- **不要拿注册规模换 fd**：iceoryx2 的 epoll 路线把成本转成了 fd（每 Listener 1 fd + 每 shm 对象 1 句柄，官方 FAQ 明列 fd 耗尽），本仓 SHM 路径 0 fd 反而是优势，不应放弃。
