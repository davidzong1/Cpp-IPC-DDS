## C-01 A/B 标注错误

**初版原文（§5.1）**
> - DZFlat B（loan-and-build）把发布侧"用户容器 → serialize 堆缓冲 → chunk"压成"用户直接写 chunk"，**两端 0 拷贝**（`include/dzIPC/common/loaned_message.h` 头部契约）。

**复核结论（❌ 错）**
`build/bin/ipc_benchmark --compare` 传给发布 API 的是**已构造好的 `TestMsg`**：
- `test/ipc_benchmark.cpp:322` → `pub->publish_blocking(pmsg->topic(), 100)`；`pmsg` 来自 `make_payload()`（同文件 175-186），**数据早已在用户容器里**。
- 进入 `src/dzIPC/shm_pub_sub_ipc.cc:460-486` 的 `try_publish_dzflat()`：`:475` `publisher_->loan(need)` → `:480` `msg->dzflat_write(lo.data, …)` → `:485` `publish_loan(lo, tm)`。
- `dzflat_write` 是**逐字段把消息容器的内容写进借来的 chunk** ⇒ **存在容器 → chunk 的 1 次拷贝**。
- B 级的定义是 `loaned_message.h` 里那条路径：应用拿到 `loan<T>()` 后**直接在共享内存上构造**，从不经过"已有对象"。

⇒ 该档是 **A 路径**（省掉 `serialize()` 的整包 `new` 与 TLV 页尾分段拷贝，但仍有 1 次拷贝）。判据三重（见证据索引 E-01/E-02/E-03），**其中第 3 条是决定性的：B 路径要求应用侧调 `loan<T>()`/`publish_loaned()`，`--compare` 从不这么做。**

**本版处理**
- §5.1 改为"A 路径已实现，B 路径**尚无性能证据**"，给出以上三重判据；
- §0.4 明确"**不得称 B 级 loan-and-build**"；
- 新增 UF-04（B 无性能证据）与 §7 的 P0「B 路径专项基准」。

## C-04 上下文切换口径

**初版原文（§0.5 / §4.2）**
> 静默 2 s 空闲 CPU **1.124 核 → 0.0050 核（≈225×）**，空闲上下文切换 **19325 → 10**（2 s 窗口）
> - **1.124 核 → 0.0050 核，≈225×**；空闲上下文切换 19325/2s（≈9662/s）→ 10/2s（=5/s）。

**复核结论（⚠️ 初版只说了一半 —— 真正的缺陷是"两侧口径不同"，不是"数字都不对"）**

| 侧 | 探针 | 读数来源 | 口径 | 二进制指纹 |
|---|---|---|---|---|
| 基线（19325） | `baseline_probe` | **全线程组聚合** | 探针**自报** `ctx_scope=sum(/proc/self/task/<tid>/status) 全线程聚合`（`base_477.log:3`） | sha256 `ac098bd6…`，含该字符串 |
| worker/compat（10） | `t6scale` | `/proc/self/status`（`t6scale.cpp:41`） | **仅主线程自身** | sha256 `2b3fafda…`，**不含** `ctx_scope` |

本轮新增可复现实证（`本机复现/csw_cpu_scope_probe.{c,output.txt}`）：
```
window=2.0s  8× usleep(1ms) 保活线程 + 1× 忙转线程
A  /proc/self/status voluntary delta = 1
B  task-group       voluntary delta = 15171
C  /proc/self/stat   utime+stime delta = 205 ticks (1.0250 core over 2s)
D  task-group        utime+stime delta = 206 ticks (1.0300 core over 2s)
```
⇒ `/proc/self/status` 的 ctxt switch **不是**全线程组累计（A≪B）；而 `/proc/self/stat` 的 utime+stime **是**全线程组累计（C/D=0.995）。

**这就把"225×"劈成两半：**
- **CPU（1.124 → 0.0050）：口径一致，结论保留。** 两侧都取 `/proc/self/stat`（线程组累计）。
- **ctx（19325 → 10）：口径不一致，结论删除。** 拿全线程组累计值去减主线程自身值，不成立。

**本版处理**
- §0.5 与 §4.2 按上述拆分重写，表格新增"探针声明的 ctx 口径"列；
- 归因（每路 50 ms `select()` 空轮询）保留但降级为【推测】（未做定量对账）；
- 新增 UF-03（解除条件：同口径 + 窗口 ≥60 s）与 UF-06（内核实现层缺源码存证）。

## C-09（追加）过度归因

## C-10（追加）iceperf 方向疑问 —— 已解决

**初版原文（§3.3 表下注）**
> ⚠️ iceperf 的 README **未明示**表格中的"Average Latency"是单向还是往返折半，故该 0.58–0.73 µs 只作量级参照

**复核结论（✅ 由源码确认）**：`iceoryx_examples/iceperf/base.cpp:49-52`
```cpp
constexpr uint64_t TRANSMISSIONS_PER_ROUNDTRIP{2U};
auto duration = std::chrono::duration_cast<std::chrono::nanoseconds>(finish - start);
auto latencyInNanoSeconds =
    (static_cast<uint64_t>(duration.count()) / (numRoundTrips * TRANSMISSIONS_PER_ROUNDTRIP));
```
⇒ README 的"Average Latency" **已折半为单向**。
⚠️ 新的保留限制：该 ping-pong 把**对端 echo 的处理时间**计入了往返再除以 2，对"纯单向交付延迟"是**近似**。

**本版处理**：§3.3 表加"已折半为单向（`base.cpp:49-52`）"，注文改为"已由源码确认为单向"并补上述限制；§6 原"不可比第 10 条"标记为**已解决**。

## C-13（追加）1 MiB 档消费者工作量不对称

**初版**：未提及（只比 p50）。

**复核结论（❌ 重大缺口，直接影响 §3 的结论强度）**
- 本仓侧：`test/dzipc_perf_benchmark.cpp:898` `try_get_clone(rcv)` = 对 `TestMsg` **整包克隆**；1 MiB 档的 `TestMsg` ≈ 0.6 MiB `float64[]` + 0.2 MiB `int32[]` + **约 1638 条 64 B `std::string`** + bool（构造见 `test/ipc_benchmark.cpp:175-186`，两侧同一构造）⇒ 约 **1 MiB memcpy + ~1600 次堆分配**；计时终点 `:917` `rx = now_ns()` 在**克隆之后**。
- iceoryx 侧：`latency_subscriber.cpp:29-31` 回调**第一句**取时间戳，只读 header 并压样本，**不遍历载荷**。

**本版处理**：§3.2 与 §6 新增为**不可比项第 10 条**；§0.2 明确 `298.47 vs 157.7` 只能称"两条不同工作负载的端到端读数"；登记 UF-12。

## C-14（追加）iceoryx 探针日志字段陷阱

**复核结论**：`latency_subscriber` 打印的 `Publish Rate:` / `Size:` 是**它自己的 CLI 默认值回显**，不是该轮真值。`sub_l1m.log` 头部写 `Rate: 1000 Hz`、`Size: 64 bytes`，而发布端该轮是 `--rate 500 --size 1048576`（`pub_l1m.log`），结果块 `Message Size: 1048576 bytes` 才是真值。

**本版处理**：§1.3 末尾新增"⚠️ 日志字段陷阱"块，规定引用必须以发布端日志或结果块为准；登记 UF-14 与证据索引 N-26。
