## UF-03 空闲上下文切换无可比数字（口径不一致）

- **事实**：主报告原稿写"空闲上下文切换 19325 → 10（2 s 窗口）≈225×"。
- **现状**：
  - 基线侧 19325 是**全线程聚合**（探针自报 `ctx_scope=sum(/proc/self/task/<tid>/status) 全线程聚合`，`base_477.log:3`；二进制含该字符串，sha256 `ac098bd6…`）。
  - worker 侧 10 来自 `/proc/self/status`（`t6scale.cpp:41`），**只是主线程自身的值**；二进制**不含** `ctx_scope`（sha256 `2b3fafda…`）。
  - 本轮实证：8 保活线程 + 1 忙转线程、2 s 窗口 → `self/status` 增量 **1** vs 全线程组 **15171**。
- **影响**：**"225×"对 CPU 列成立（同口径，见 UF-06 的实测）**，对 ctx 是**无效比较**。不能再用 19325 vs 10 说明任何结论。
- **解除条件（已按 W03 口径细化，2026-09-28）**：
  1. **完整口径 = `wait4`/`getrusage` 的 `ru_nvcsw`/`ru_nivcsw`** —— 覆盖线程组**整个生命周期**（含已退出线程），是唯一可称"全量"的口径；
  2. 若只能**逐 TID 采样**，**必须处理新生/退出线程**（否则结果须标 `complete=false` / "不完整"），不得静默低估；
  3. `/proc/self/status` 只作 `main_thread_only_*_reference` **参考值**，**绝不**作为全进程/线程组合计；
  4. 窗口 ≥ 60 s（方案 §10.1/§6.2）；基线/worker/compat 三档**同口径**重测。
  依据：W03 任务 t4（`artifacts/perf/20260928-r03-W03-ctxscope/cpu.json` 的三口径对照）；本条与 **UF-06** 的内核源码结论互为支撑（`/proc/<pid>/status` 只读单个 `task` 的 `nvcsw/nivcsw`）。
- **第三份证据（W03 侧复现，2026-09-28）**：`rusage` 全生命周期 **22800** vs 逐 TID 采样 **22107**（`complete=false`）vs `/proc/<pid>/status` 主线程参考 **7** —— 同一进程同一窗口内三者相差约 3158×，进一步证明口径选择决定结论。
- **⏳ 当前状态：未闭环（口径侧已闭合、预算侧未闭合）—— 不得标为"已解除"**（队长 2026-09-28 裁决）：
  - W03 证明的是"**口径应当怎么取**"（已冻结，S3），**不是**门槛达成。W00《基线与门槛.md》**门槛 3**（§6.2 表第 3 行）的预算是「**1000 有效订阅 + 无发布**」场景：**CPU ≤ 0.20 core**、`voluntary+nonvoluntary ≤ 50 s⁻¹·进程⁻¹`、稳定活动线程 ≤ 8。
  - ⚠️ W03 的复现负载是「**校准负载 18 线程 / 100 sim routes**」，**不是**门槛 3 定义的「1000 有效订阅 + 无发布」⇒ **不得据此宣布门槛 3 达成**（W00 §11.3 **P-2** 原文；方案 §6.5）。
  - 收口路径（W00 §11.3 **P-2** + §11.4 **D-8**）：**W05/W06 接入后由 W10** 按方案 §10.1 三态空闲（无 route / 已注册无发布 / 已连接静默）实测，用 D-8 口径校准 `0.20 core` / `50 s⁻¹·进程⁻¹` 两项，再由**架构负责人追加冻结**（责任链：W03 口径已完成 → W10 校准 → 架构负责人冻结）。

## UF-06 `/proc` 两字段的聚合语义缺内核源码存证 —— ✅ **已解除（2026-09-28）**

- **原事实**：本轮已用自建探针**实测**（N-44/N-45）：`/proc/self/status` 的 `voluntary_ctxt_switches` **不是**线程组累计；`/proc/self/stat` 的 `utime+stime` **是**线程组累计（C/D = 0.995）。
- **原现状**：解释该差异的内核实现（`do_task_stat` 的 whole/task 分支）**未取到源码存证**——`raw.githubusercontent.com/torvalds/linux` 两次抓取超时（各 55 s）。本机 `man 5 proc`（man-pages 5.10-1ubuntu1）只给字段定义，未给聚合语义。
- **✅ 解除证据（W03 / 任务 t4，attempt `4a9d66ec-6b54-4ec5-a55c-6f609e821e90`；文档负责人独立复核）**
  - **版本化内核来源**：`fs/proc/array.c` @ torvalds/linux **v6.8**，经 `git.kernel.org` plain 端点取回（HTTP 200）。
    存证：`团队改造交付/W03/外部来源存证/proc_array_v6.8_do_task_stat.md`（逐字摘录 + 判读）。
    URL：<https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/fs/proc/array.c?h=v6.8>
  - **本文档负责人独立复核（2026-09-28 复取同一 URL 并逐段读取源码，非仅采信转述）**：
    ① `task_context_switch_counts(m, p)` 只输出 `p->nvcsw` / `p->nivcsw`（**单任务**），且 `proc_pid_status()` 传入的是**单个** `task` —— 该路径**无** `__for_each_thread` 求和 ⇒ 对应实测 **A=1**；
    ② `do_task_stat(..., whole)`：`if (whole) thread_group_cputime_adjusted(...) else task_cputime_adjusted(...)`，且 `proc_tgid_stat()` 传 `whole=1`、`proc_tid_stat()` 传 `whole=0` ⇒ `/proc/<pid>/stat` 的 utime+stime **是**线程组累计、`/proc/<pid>/task/<tid>/stat` 是**单线程** ⇒ 对应实测 **C≈D**；
    ③ `starttime = nsec_to_clock_t(timens_add_boottime_ns(task->start_boottime))` ⇒ **boottime 时基**，与 `/proc/uptime` 同基。
    ⚠️ 勘误：`do_task_stat` 内确有 `__for_each_thread` 循环，但它只累加 `min_flt`/`maj_flt`/`gtime`（**不含** utime/stime），故与本条结论不冲突。
  - **第三份独立证据（W03 侧复现）**：把本探针作为**被观测进程**由 W03 采集器采样 —— `rusage` 全生命周期 ctx 自愿切换 **22800**（`complete=true`）vs 逐 TID 采样 **22107**（`complete=false`：窗口内 10 条线程新生、9 条退出）vs `/proc/<pid>/status` 主线程参考 **7**；同轮 `cpu_scope_check`：`/proc/<pid>/stat` 线程组 CPU 2.98 s vs 逐 TID 求和 2.91 s（比值 0.977）⇒ 与上面 ② 一致。
    产物：`artifacts/perf/20260928-r03-W03-ctxscope/`（`cpu.json`、`stdout/w01_csw_cpu_scope_probe.log`、`binary-fingerprint.txt`）。
- **影响（解除后）**：`/proc` 两字段的聚合语义现为"**版本化内核源码 + 三份实测**（W01 探针 / W01 归档输出 / W03 采集器）"，不再是"仅本机实测"。
- **残余（不得过度外推，保持登记）**：
  - (a) 存证是**上游 v6.8**，不是本机 `6.8.0-138-generic` 的 Ubuntu 补丁树；"本机二进制 == 上游源码"**未逐字节核对**（W03 亦登记同一条）。
  - (b) 本机 `CLK_TCK=100`（tick 粒度 10 ms）：tick 记账**不会把短于 10 ms 的线程片段计入其 utime/stime**，因此**逐 TID 求和不能用作 CPU 口径**；CPU 应取 `/proc/<pid>/stat`（线程组累计）或 `rusage`。
  - (c) 本来源只回答**聚合语义（what）**，不给出任何具体进程的切换数（how many）。
- 证据索引：N-44、N-45、**E-42（已由 E-X 升级为 E-C）**；另见 `团队改造交付/W03/外部来源存证/` 与 `artifacts/perf/20260928-r03-W03-ctxscope/`。

## UF-10 p99 / p99.9 未受控

- **事实**：两侧 p99 都劣化 2–10×；同一份 dzIPC 64 B 用例两轮 p99 = 92.47 / 446.90 µs。
- **现状**：`powersave`、未绑核、无 CPU 隔离、load ≈ 4–10。

- **解除条件**：两侧同条件固定 `governor=performance`、绑核、隔离；p99.9 累计 ≥ 100 万有效样本（方案 §6.2）。

- **事实**：两者都只测本机同一台机器。**影响**：结论不外推到网络路径。**解除条件**：属方案明确不在本轮范围，保留空白即可。

## UF-12 1 MiB 档两侧消费者工作量不对称

- **事实**：dzIPC 侧 `try_get_clone` 整包克隆（≈1 MiB memcpy + ~1600 次 `std::string` 堆分配），计时终点在克隆**之后**（`dzipc_perf_benchmark.cpp:898,917`）；iceoryx 侧回调第一句取时间戳，只读头部（`latency_subscriber.cpp:29-31`）。
- **现状**：无同工作量的对照。
- **影响**：`298.47 µs vs 157.7 µs` **不能**解读为 wire 差距（既不能判本仓 wire 差 1.9×，也不能判 iceoryx 因零拷贝而快）。
- **解除条件**：方案 §10.7 的三组实验（传输机制 / 完整读取 / 生产到消费）分别计时。
- 证据索引：E-14、E-39、N-06、N-23。

## UF-13 延迟归因未分层

- **事实**：初版判定"差距由拷贝决定、线程/唤醒层不是主因"。
- **现状**：现有实验未隔离编解码、堆分配、等待、调度、排队的各自成本；也没有"同一实现换 wire"或"同一 wire 换等待方式"的单变量实验。
- **影响**：§5 的因果结论整体降级为【推测】。
- **解除条件**：方案 §10.2（扫描/等待开销计数）+ §10.7（三实验组）+ W02 的单变量控制。
- 证据索引：§6 不可比第 9–13 条。

## UF-14 iceoryx 侧日志字段是命令行回显（引用风险）

- **事实**：`latency_subscriber` 打印的 `Publish Rate:` / `Size:` 来自它自己的 CLI 默认值。`sub_l1m.log` 头部写 `Rate: 1000 Hz` / `Size: 64 bytes`，而该轮实际是 `--rate 500 --size 1048576`（`pub_l1m.log`），结果块 `Message Size: 1048576 bytes` 才是真值。
- **现状**：任何直接 grep 头部字段的引用都会写错速率/尺寸。
- **解除条件**：修探针（属外部仓 `lejulab_platform`，**不在本轮范围**）或在引用约定中强制使用"发布端日志或结果块"。本版已在主报告 §1.3 加警示。
- 证据索引：N-26。

## UF-15 规模轴只有 socket 证据

- **事实**：`t6scale.cpp` 固定 `mode=socket_pub_sub`；**SHM 版探针不存在**。
- **影响**：`threads_max ≡ 33` 不能外推到 SHM；而 SHM 是需求 §11.1/§11.2 的主战场。
- **解除条件**：W06 交付 SHM 版规模探针（独立话题）+ 模块级线程计数。
- 证据索引：E-17、N-30。

## UF-16 `--compare` 附属读数不可回溯

- **事实**：除 UF-01 的 p50/p99 外，"回退率 0.0%"、"dzflat 生效/回退计数"亦出自同一未落盘的 stdout。
- **解除条件**：同 UF-01（统一基准必须落盘 `counters.json`，方案 §12）。
- 证据索引：N-50…N-52。

## UF-18 兼容路径（SHM 侧）空闲行为未单独核验
