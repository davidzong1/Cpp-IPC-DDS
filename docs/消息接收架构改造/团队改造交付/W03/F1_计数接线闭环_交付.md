## 2. 要求 2：接入四类（与 t19 三语义分离口径一致）

### 2.1 `chunk_exhausted` / `chunk_alloc_failed` → `src/libipc/ipc.cpp`

写入点选在 `note_pool_exhausted()` 内部 —— 它是**全仓唯一的池穷尽出口**（`acquire_storage()` 的
唯一 `id < 0` 分支；三条取块路径 `send` / `no_member_send` / `loan` 全都汇合于此），
因此"记账"与"诊断"共用同一次 `(kind, chunk_size)` 归并，**不可能出现"报了日志但没计数"或反之**。

`kind` → ID 映射**逐字沿用 W09-F5 冻结口径**（`W09/容量与背压_交付.md:184`）：

| `kind` | ID | 语义（W09 §5.1） | 返回值 |
|---|---|---|---|
| `loan` | `chunk_alloc_failed` | B 借样被拒，**未交付**（调用方**必须**回退整包） | `loan.valid()==false` |
| `send` / `no_member_send` | `chunk_exhausted` | A/TLV 降级为 64 B 分片，**仍交付** | `publish` 仍 `true` |

⛔ **不碰** `fallback_total` 与 `borrow_failed_*`：池穷尽是**传输层容量事实**，不是
"DZFlat 尝试过但降级"、也不是"应用 `loan()` 失败"。这与该函数既有日志口径一致（日志从不说"回退"）。

### 2.2 `queue_evicted` → `include/dzIPC/common/circularqueue.h`

写入点位于 `push_owned()` 的淘汰分支：**"抢不到槽位而挤掉最老"这个既成事实之后、`evict_cb_` 调用之前**。

⛔ 为什么不能只钩 `evict_cb_`：回调是**可选**的（`set_evict_cb` 只有 shm 订阅端注册）。只钩回调会让
"没注册回调的队列"淘汰**全不计数** —— 这正是本任务要修的漏计形态。实测 ARM-C 用**不注册回调**的
`CircularQueue<int>` 证明：`pushed=100, capacity=2` ⇒ `queue_evicted=98`（= 100−2，**条数**口径）。

**关于引入头依赖的说明**：`counters.h` 是 header-only（`<array>/<atomic>/<cstddef>/<cstdint>/<cstdio>/<string>/<vector>`
+ `monotonic_clock.h`，无环）。本头被 4 个模块头 + 测试包含；本次**未改**任何既有类型/布局/模板签名，
只新增一条 include 与一次 `fetch_add`。⛔ 该文件在《接口责任表》里**未列 owner** ⇒ 我按任务书
"可改 `CircularQueue` 淘汰点"的授权实施，并在此声明。

### 2.3 `wait_set_full` / `wait_token_invalid` → 复核为**已接线、无需改动**

两者写入点在 `shm_pub_sub_ipc.cc` 的 `fallback_to_compat()` 原因码分派里（W06 落地），
分工按 W09/t19 冻结口径：`wait_set_full` 是**独立类别**，与 `fallback_total`/`fallback_capacity_full`
**同时** +1 是设计（不是双计数）；`wait_token_invalid` 只记自己 + `registration_invalid_token`
（`kInvalidToken` 分支**不**记 `fallback_total` —— 它表达的是"这条 route 进不了等待集合"的能力缺口，
不是"后端不可用"）。⛔ 本次**未改**这两处。

### 3.1 反例闭环（t31 的原件，逐字复跑）

| 库 | `verify_w10_chunk_counter` 输出 |
|---|---|
| 接线前 `d69c5863…` | `loaned=40 rejected=160` + stderr `chunk pool exhausted` ⇒ **`chunk_exhausted=0`**（判决性反例） |

### 3.2 `first_failed_resource`（§13.3 十类顺序）

复刻 `w10_matrix.cpp:1086-1117` 的**同一张表与同一顺序**（`registration_rejected` → `wait_token_invalid`
→ `wait_set_full` → `fd_limit` → `chunk_exhausted` → `queue_backpressure` → `generation_mismatch`
→ `fallback_activated` → `publish_blocked` → `rx_timeout`，取第一个非零）：

| 时刻 | 读数 |
|---|---|
| ARM-A 之前 | `first_failed_resource = none` |
| ARM-A 之后（池穷尽已发生） | **`first_failed_resource = chunk_exhausted`** ✅ 定位到首个失败资源 |

⇒ "0 个失败类 + `none`"这个组合的**排除力**现在成立：以前 `chunk_exhausted` 恒 0，
`none` 是**假阴性**；现在它要么真为 0（没发生），要么非 0（发生了且能定位）。

### 3.3 我踩过并记入交付的两个"构造陷阱"（避免下游重踩）

1. **只有订阅者时 SHM route 永不出现**：route 由控制面 Ready 之后的 generation 重建产生，
   而 Ready 需要发布端存在。ARM-D 第一版只建订阅者 ⇒ `registration_attempts` 恒 0、五类全 0，
   我据此**判定探针构造错误**（而非宣布"接线失败"），补上发布端后才复现 `wait_set_full=13`。
2. **tmpfs 的"尺寸不匹配"不会让 `shm_open` 失败**：ARM-E2 第一版用 `ftruncate(fd,1)` 预占
   `…_WAITER_STATE_`，三次均 `NOT_REPRODUCED` —— 因为 `mmap` 长度大于对象尺寸不报错（越界页首次访问才
   SIGBUS）。改用**把该名预建为目录**后 `shm_open` 直接失败 ⇒ 一次复现 `wait_token_invalid=1`。
