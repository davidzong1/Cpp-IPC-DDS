## 2. 复核项 1：固定 worker 接入 + lease 全出口配对（**运行期读数**）

### 2.1 千路：route 确实由固定 worker 池持有（不是"线程数少了"）

| 读数 | worker 臂（默认） | compat 臂（`DZIPC_SHM_RECV_COMPAT=1`） |
|---|---|---|

| `valid_rx_count` | **1000/1000** | 1000/1000 |
| `worker_path_count` / `compat_total` | **1000 / 0** | **0 / 1000**（`path_choice=1000`，reason=1） |
| `threads_after_create` | **34** | **1002** |
| `registered_after_rx` | 1000/1000 | 1000/1000 |
| `counters` 全 0（`fallback_total/backend_unavailable/capacity_full/wait_set_full/wait_token_invalid`） | ✅ | ✅（另 `registration_*` 全 0，因未走池） |

⇒ **接入形态成立**：`worker_path=1000` 来自 **seam 事件**（`kRecvPathWorker` 在"首次拿到 route 那一刻"发一次），不是从线程数反推 —— 与 W06 §6 的口径一致，且**两臂的 route 归属互不重叠**（1000/0 vs 0/1000）。

### 2.2 lease 全出口配对（seam 计数，非 grep）

自建探针 `r59_lease_pairing.cpp`：装 seam 钩子统计 `kAfterRecv`（**lease 持有中**）与 `kAfterRecvRelease`（**已释放**），稳态发 50 条：

```
case=lease sent=50 arm=worker after_recv=101 after_recv_nonempty_delta=50 after_release=101 delta=0
verdict=PASS lease_all_exits_paired(after_recv==after_release, 且非空交付>0)
```

**3 轮逐字一致**（`r59_lease.log`）。判据：`after_recv == after_release`（**配对数恒等**，差值 0）且**非空交付 50 > 0**（证明这 101 次 lease 不是空转：50 次真取到数据 + 51 次空轮）。
⇒ **每个成功 lease 恰好一次 release** —— 泄漏一次会让计数单调分离，本判据会立刻显形。

### 2.3 ⚠️ 异常出口：**有代码路径，无独立注入证据**（如实登记）

- 代码在 `src/dzIPC/shm_pub_sub_ipc.cc:501-508`：`catch (...)` 内先 `session.release_receive()` 再返回（`sub_recv_attempt` 的 `recv` 调用被 try 包住）。
- **但 `recv()` 本身不抛**：`ipc::route::recv()` 走 `buff_t` 返回、失败即返回空（`src/libipc/ipc.cpp:1898` 起）。唯一的抛出源是 `std::bad_alloc` 等**分配失败**。
- 我尝试用仓库既有工装 `tools/alloc_fault_inject`（`DZIPC_FI_ALLOC_SIZE_LO/HI` + `SKIP_N`）**在 recv 路径上注入**：扫 `skip=2100..2145`（`r59_inject_sweep.log`）—— 命中档时全部是 `terminate called after throwing an instance of 'std::bad_alloc'`（在**别处**抛出、无人捕获），**没有一次落在 `sub_recv_attempt` 的 try 内**。

⇒ **本包不能支撑的结论**：「异常出口在运行期被真实走过且配对」（详见 §8 清单）。本节只支撑：**稳态全出口配对**（2.2）+ **代码存在该出口**（静态）。这是 W06 §2 条件 1 的证据强度边界，我按原样登记而不替它加码。

### 6.3 🔴 Finding R1-W06-F2

- **事实**：对「删除 `teardown_recv_path()`」这一**特定变异**，三个按臂改判的用例中只有 2 个有牙（1 个变红、1 个崩），`test_wakeup_artifact` 的 worker 臂判据**不响应**。
- **为什么不是阻断**：W06 §4 的措辞是「反例（用例有牙的直接证据）」并**只引 dtor_gate**，**没有**声称三者都有负控 ⇒ **不构成过度声明**。
- **为什么仍要登记**：本任务验收条明确要求「复核三个测试文件的按臂改判**是否有负控**（去掉 teardown 步骤 ⇒ 变红）」。逐个核对的结果必须如实写出，包括"第 3 个没有"。
- **技术解读（不夸大）**：`test_wakeup_artifact` 的 worker 臂判据是 `compat_path==0` + `recv_release_ticks >= kRounds` + `WakeupArtifactCount()==0`。删掉 `teardown_recv_path()` **不会**让 `compat_path` 变非 0、也不会让心跳消失，因此这三条**对这一变异天然不敏感** —— 它守的是"**回退线程不得顶替固定 worker**"（方案 §13.2 条件 4），而不是"析构是否摘除注册"。**⇒ 它需要的是另一个变异**（例如让 `kRecvPathCompat` 在该场景也发一次），而不是说它没有牙。
- **requiredFix**：为 `test_wakeup_artifact` 的 worker 臂补一个**对口变异**的负控（如临时在 worker 路径上多发一次 `kRecvPathCompat` ⇒ 期望 `compat_path==0` 判据变红），或者在其注释里**显式写明**"本用例的牙针对回退顶替，不针对析构摘除"。
