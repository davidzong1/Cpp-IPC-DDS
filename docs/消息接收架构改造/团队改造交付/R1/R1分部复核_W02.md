**交叉核验（awk 独立实现，防脚本自身 bug）**：

四条恒等式 `transport==td−pe`、`delivery==ao−td`、`app_read==fc−ao`、`e2e==fc−produced` **全部成立**。

### ⚠️ 与队长读数的差异（W02-F1）
| 来源 | files | cells | mismatches | skipped |
|---|---|---|---|---|
| 队长（t25 合同） | 75 | **269,896** | 0 | **26** |
| 本复核（python + awk 双实现） | 75 | **269,848** | 0 | **38** |

差额 = **48 cells = 12 行 × 4 恒等式**。根因已定位：**skipped 的口径不同**，而 cells 随之不同。

**我这边 skipped 的精确含义**：该行**任一**时间戳列或派生列为空 ⇒ 整行跳过。实测「空值组合」在 67500 行中**唯一**为 `('delivery_ns',)`，共 **38 行**（分布：`r45`(7)、`r63`(7)、`r46`(6)、`r50`(5)、`r6`(5)、`r49`(2)、`r40/r41/r47/r51/r54/r67` 各 1）。

**这 38 行不是数据损坏，而是语义边界**（我读了源码确认）：
```cpp
// test/xproc_benchmark.cpp:2226
if (app >= done) r.delivery_ns.push_back(app - done);   // ← 只在 ao >= td 时才计入统计
```
这 38 行的 `app_obtained_ns < transport_done_ns`（最小反例：`r40_dzflat-b_crc_blocking_65536B_1000Hz.samples.csv` 第 863 行，`seq=1000861`，`ao−td = −61806`）。跨进程下这**物理上成立**：订阅侧在发布侧 `send()` 返回前就已取到对象（发布侧计时点在自己进程里）。

- **⇒ 判定**：W02 的**统计正确**（负值不入统计、不写成 0 冒充），`samples.csv` 保留原始两列使该情形**可被独立发现**；**但该语义未在结果格式文档中声明**，读方看到空 `delivery_ns` 无法自行判断是「未测」还是「本值应为负」。
- **⇒ 最小修复**：`W02_统一跨进程基准_结果格式与使用.md` 的派生量表加一行：「`delivery_ns` 在 `app_obtained_ns < transport_done_ns` 时为空（跨进程并发可见，不入统计）；`summary.csv` 的 `delivery_*` 统计对应 `results.json:cases[].delivery_ns.n = samples_merged − 空行数`」。**无需重跑**。
- **skip 口径差异（26 vs 38）**：我无法从合同描述复现 26；请队长或基准负责人给出其脚本。**若双方口径不同，任何「cells=269,896」引用都应替换为等价表述**，否则同一 run 会出现两个「验算过的 cells 数」。

### 关于「消息头不放 `transport_done`」与父进程按 seq 合并
- **机制正确性**：`transport_done_ns` 由**发布侧本地**记录（`send()` 返回时刻），**物理上不可能随消息送达**；把它放进消息头只会把同一条消息的完成时刻错误地绑到上一条的接收上。文档 `结果格式…:98` 明确此点，属**设计正确**而非遗漏。
- **错序/丢行风险**：父进程按 `seq` 合并（`pub_by_seq` / `sub_by_seq`），我实测该合并的产物**自洽性**：`samples_merged` 在 75 case 中为 1000（60 个）或 500（15 个），**无一行缺失合并**；`out_of_order` 全量合计 **0**；`missing`/`duplicate` 全量合计 **0**。⇒ 合并逻辑在本次 run 未出现错序或丢行。
