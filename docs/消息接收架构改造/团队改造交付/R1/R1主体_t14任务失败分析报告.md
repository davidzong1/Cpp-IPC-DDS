## 3. W02-F3（high）：**失败量未进判定** —— 用「仅落列」实现「静默排除」

### 3.1 实测反例（队长独立复算，与复核者一致）

```
late 非零 case 数 = 17，late 合计 = 71
late 非零 但 failure_reasons 为空 = 17 / 17        ← 全部
```

**另有**：`send_blocked` / `late` / `backlog` / `abnormal` **不进** `failure_reasons`；**`bad_header` 根本不落列**。

### 3.2 为何这是 high

t14 合同（沿用方案 §4 W02）第 3 条明确要求「**失败与异常不被静默排除**」：

> `send_failed/send_blocked/late/backlog/missing/duplicate/out_of_order/checksum_bad/abnormal/rows_truncated/child_killed` 全落列并进 `failure_reasons`

反例显示：**17 个 case 共 71 次迟发，而 `case_ok` 全 True、`failure_reasons` 全空**。这使「未被静默排除」这一验收条件**在实现上不成立**，而「仅落列」并不等于「进判定」。

### 3.3 队长裁决：**改实现**，不接受只改措辞

**拒绝「改任务书措辞声明这 4 个仅落列、不进判定」**，理由：
- 任务书原文要求「不被静默排除」；若 71 次迟发可全部不进判定而判通过，则是**用「仅落列」实现「静默排除」**
- 把措辞改宽 = **移动球门**

**要求**（t47）：
1. `late`/`backlog`/`send_blocked`/`abnormal` 必须进入**机器可读判定通路**，并配**显式声明的阈值**（阈值写入 `manifest`，逐 case 可判）—— ⛔ 不是无条件失败
2. **`bad_header` 补为列**
3. 给出「修复前 17/75 不进判定 → 修复后逐 case 可判」的对照
4. 若某量确应仅信息性保留，必须**逐量说明理由 + 写显式声明入 manifest**，⛔ 不得静默
