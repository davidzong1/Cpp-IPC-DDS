命名约定：`W`=`RecvWorker`（或 `SocketRecvWorker`）；`R`=宿主 route 适配器（`RecvRouteSource` / `SocketRecvRouteSource`）；`S`=`RouteSession`；`C`=控制面调度器 `ShmControlScheduler`。

### 4.1 注册（`W.add_route(R)` / `RecvWorkerPool::add_route`）

判定顺序（**勘误 E2 优先**：一次 CAS + 一次查表；对外语义与契约正文一致）：

```text
R == nullptr                          -> invalid_route
!running()（未 start / 已 stop）        -> stopped
read_wait_token()/wait_token() 无效     -> invalid_token
try_claim_recv(worker) 成功             -> 继续注册
try_claim_recv(worker) 失败：
     本 worker 表内已有同一 R            -> duplicate   // 自己重复注册
     否则（别的 owner，如 compat_thread） -> busy        // 兼容线程正在 recv
wait_set.add 失败 && 从未成功            -> backend_unavailable  // 显式回退信号（永久）
wait_set.add 失败 && 曾成功              -> wait_set_full      // 容量满
```

成功路径的原子性由**两个不变量拼出**（不是靠一个临界区，`recv_worker.cc:640-660`）：

- 线程「清 `alive`」与「判定 route 表为空」在**同一个 `mtx` 临界区**内（`loop()` 的 idle-exit 分支，`:382-391`）；
- 「插入 route 表」与「读 `alive`」也在**同一个 `mtx` 临界区**内（`add_route` `:635-639`）。

⇒ 任一侧先拿锁都安全，**「返回 ok 却无人消费」（静默丢包）被禁止**。`ensure_thread_alive()` 必须在 `mtx` **之外**调用（`:656-660`；理由见 §5.2）。

**注册成功时无条件让新 route 至少被处理一次**（进 deferred FIFO + `remove`/`add` 敲一次唤醒通道，`recv_worker.cc:681-689`）：注册前已在通道里的数据不会产生新的 seq/事件，只靠「变化」判据会永久看不到它。守门：`RecvWorker.MessagesArrivingWhileThreadIsIdleExitingAreNotLost`；socket 侧对应 `SocketRecvWorker` 同款（`socket_recv_worker.cc` 的 `requeue` + `remove/add`）。

### 4.2 注销（`W.remove_route(R)`，**同步**完成，返回即安全释放）

逐步顺序（契约 §4.4 原文；勘误对第 2 条补充「`epoll_ctl(DEL)` 不唤醒 `epoll_wait`，唤醒靠内部 eventfd/中断字」）：

```text
1. 从 route 表摘除 + 标记 removed       // 同一锁区间内完成（禁止新的 recv_once）
2. wait_set.remove(token)              // 摘除 + 唤醒阻塞中的 worker wait
3. R->stop_and_wake()                  // 禁止新 lease + 打断在途 recv（SHM: disconnect；socket: cancel_wait）
4. 等 worker 侧 in_flight 归零          // 在表锁之外；上界 = 一个预算轮；超时 2000ms 只打诊断
5. R->wait_quiescent()                 // 等宿主自己的 lease/in-flight 记账归零（同样有界 2000ms）
6. R->release_recv()                   // 归还收包独占（owner 回到 none）
```

**死锁排除**（契约原文 + 实现一致）：第 4 步在 `mtx` 之外等待，worker 减少 `in_flight` 不需要 `mtx`（`Entry` 由本地 `shared_ptr` 保活）⇒ 不存在「注销等 worker、worker 等表锁」。

**已验证的关键语义**（本包 §9 L2/L7/L6）：

- `wait_set_full` / `invalid_token` / `busy` / `duplicate` 等**任何非 ok 出口都必须归还 owner**，否则兼容线程此后永久 `busy`（`recv_worker.cc:601/610/616/677` 四处 `release_recv()`）— L2 用可判据钉死；
- `W.stop()` **不**摘 route、**不**归还 owner（L7）：模块必须**先** `remove_route` 再 `stop`（契约 §4.4「析构顺序 1-6」）；
- 重复 `remove_route` 幂等；未知 route / `nullptr` 是无操作。

**W04-F1（high）**：头文件声称「同线程调用只做摘除与唤醒、不等待」。实现里**没有**这条分支，同线程 `remove_route` 会等满 2000 ms 打诊断（实测见 §9 R-02 与 `W04/证据/`）。**收敛动作**（二选一，属实现或注释变更，须由 owner 落地）：
(a) 在 `remove_route` 入口比对「当前线程 == worker 线程」→ 只摘除+标记+唤醒、跳过第 4/5 步并打诊断；
(b) 删除该承诺，并把头文件注释改成**可机械核对**的形式：`grep -c "this_thread::get_id" src/dzIPC/threepools/recv_worker.cc` 期望值 = **2**（只在 `stop()` `:547` 与析构 `:502` 里；无 2000 ms 等待的旁路），且注释里写明「同线程调用会等满 `kQuiesceTimeout`」。当前实测 = **2**（socket 侧同为 2）⇒ 即「该项承诺在实现里不存在」。

### 4.3 关闭（模块析构 / `stop_data_plane` / `teardown_receive_path`）

模块侧**唯一合法**顺序（方案 §4 + 契约 §4.4 析构顺序）：

```text
1. 注销 LocalPubSubRegistry(或模块自己的 registry)      // 先断快路径投递
2. pool.remove_route(route)                            // 即 §4.2 的 1-6 步（同步）
3. 注销控制面调度器（W05：RegistrationToken::reset()）   // 同步；等该项在途 tick 结算
4. 关闭 socket / release route（socket: close_data_plane；SHM: 段与句柄）
5. 释放队列与 shared state
```

已接入模块的实测位置：`shm_ser_cli_ipc.cc:653-660`（注释逐条对应 1-8 步）、`socket_pub_sub_ipc.cc:1183-1224`、`socket_ser_cli_ipc.cc:1099-1130`、`socket_ser_cli_ipc.cc:708-740`（`restart_data_plane` 的「注销→关→开→注册」）。
**未接入模块（W06 的施工面）**：`shm_pub_sub_ipc.cc:676-706` 现在是「registry 注销 → `running=false` → `route_session_.stop_and_wake()` → join 收包线程 → `wait_quiescent` → `release`」。W06 必须在 `route_session_.stop_and_wake()` **之前**插入 `pool.remove_route(route_adapter)`，并且**不能**保留「先 release 再摘 wait 项」的任何路径（§7.2 的崩溃根因）。

### 4.4 generation 切换（**本包最重要的硬约束**）

`RouteSession::begin_rebuild(new_gen, create)` 内部顺序（`shm_route_session.cc:45-120`）：

```text
锁内: rebuilding_=true（拒绝新 lease）；拷出旧 route 的 shared_ptr
锁外: old->disconnect()                     // 唤醒卡在 recv(50) 的线程
锁内: cv.wait(receive_inflight_ == 0)       // 归零后不会被新 acquire 占用
锁内: old->release(); route_.reset()        // ← 共享内存被释放/解映射
锁外: create()（可能阻塞：打开共享段）
锁内: route_=新对象；generation_=new；rebuilding_=false；stopping_=false；notify_all
      （create 失败 ⇒ route_ 保持空、generation_ 不变、rebuilding_ 复位，可重试）
```

**规则（W04-F2）**：`W.remove_route(R)` 必须在 `begin_rebuild`/`release()` **之前**完成。理由是机制性的：`R.read_wait_token()` 返回的 token 指向 route 内部共享段里的 sequence 字地址（`src/libipc/waiter.h:173-183` 的 `read_wait_token()` 返回 `&st->seq`）。一旦旧 route 的句柄被释放/段被解映射，wait-set 里那条 entry 仍持有旧地址：

- worker 下一轮 `wait()` 会**读该地址** ⇒ **SIGSEGV**（已复现，§7.2）；
- 即使没崩，也会「静默停收」（等待一个永不变化的字）。

**已验证的对照（60 秒内可复跑）**：

| 顺序 | 动作序列 | 结果（6 轮） |
|---|---|---|
| 不安全 A（mode 1） | 换对端 → `rebuild()`（内部 release 旧 route） | **6/6 SIGSEGV（rc=139）** |
| 不安全 B（mode 2） | `rebuild()` → 换对端 | **4/6 SIGSEGV**，另 2 轮「存活但停收」 |
| 安全（mode 9） | `remove_route` → `rebuild()` → `add_route` | **6/6 rc=0，且重建后继续收到消息（received=2）** |

gdb 栈（不安全 A）：`#0 ipc::recv_wait_set::wait` ← `#1 RecvWorker::Impl::wait_once` ← `#2 Impl::loop` ← `#3 Impl::thread_main`（**worker 线程**）。

**同时成立的补充结论（正向，已实测）**：`clear_storage` 之后**同段名**重建，sequence 字地址**逐次相同**（`0x…a004`，3 种场景全 STABLE）⇒ 不能靠「地址没变」侥幸；地址稳定**不代表**对象还活着，危险窗口只由「有没有先摘 wait 项」决定。

**socket 侧同构要求**：`socket_ser_ipc::restart_data_plane()` 已按「`teardown_receive_path()`（含 `remove_route`）→ `close_data_plane()` → `open_data_plane()` → `start_receive_path()`」实现（`:708-740`），注释写明「旧 route 的 wait 项/在途 recv_once 还指着旧 fd ⇒ fd 复用事件误关联」。W06 的 SHM 侧照此办理。

### 4.5 控制 tick（W05 的施工面 + 冻结语义）

`ShmControlScheduler` 冻结语义（`shm_control_scheduler.h:180-221`，20 条用例守门）：

| 项 | 约定 |
|---|---|
| 线程数 | worker 构造期启动，注册任意多项**不再新增线程**（`RegisterDoesNotAddThreads`） |
| 时间语义 | `sub_heartbeat=10ms`、`pub_heartbeat=50ms`、`peer_dead_timeout=2s`；**不得为提高空闲性能而降低频率** |
| 同轮顺序 | 按 `EntryId`（注册先后）确定性排序（`SameRoundDispatchOrderFollowsRegistrationOrder`） |
| `unregister` | 标记 inactive → 唤醒 → 等**该项**在途 tick 结算 → 摘除 → 返回；幂等；**等的是项不是整轮** |
| ⛔ 回调内不得 `unregister` 自身 | 会等一个只有本回调返回后才被清除的标志 ⇒ 永久阻塞（实现检测到同线程时跳过等待并打诊断，属兜底） |
| ⛔ 回调内不得 `stop()` | 在 worker 线程 join 自己 ⇒ `std::system_error` → `noexcept` 下 `std::terminate`（**实测复现过 SIGABRT**） |
| ⛔ 回调不得抛出 | 实现自己 try/catch；例外会带走该进程**全部**话题的控制面 |
| 注册不回调 | 第一次回调在下一个到期点 |
| 慢 tick | `tick_overrun_count`/`tick_duration_max_ns` 可观测；W05 必须记录千路下的扫描耗时 |

**与接收 lease 的关系（W05 关键）**：回调不得持有裸宿主指针（`RegistrationToken` 持 `shared_ptr<Impl>`；调度器只持 `shared_ptr<SubControlState>`）。但**回调里做 generation 重建时**，若该 route 已注册进 worker，会踩到 §4.4 的崩溃根因 ⇒ **回调必须按 §7.2 的顺序：先 `pool.remove_route`，再 `begin_rebuild`，再 `add_route`**。

### 4.6 接收 lease（`RouteSession::acquire_receive` / `release_receive`）

| 不变式 | 内容 | 失效形态（全部静默） |
|---|---|---|
| I1 | `acquire_receive` 返回的 `shared_ptr` 在 recv 全程保活 route | 悬垂 route |
| I2 | 不并发 release：只有 `receive_inflight_==0` 且已禁新 lease 才允许 `release()` | 并发 `release`/`recv` ⇒ 偶发 SIGSEGV |
| I3 | `stopping_`/`rebuilding_` 置位后 `acquire_receive` 一律返回空 | 重建期新 recv 进旧对象 |
| I4 | 每次成功 acquire 恰好一次 release（含所有异常出口） | 漏一次 ⇒ `wait_quiescent` 永不返回；多一次 ⇒ `size_t` 下溢 ⇒ 同样永不返回 |
| I5 | **generation 只用于阻止新 recv 与决定何时 release，不得丢弃已弹出的字节** | 丢消息 |

宿主（route 适配器）义务：`recv_once()` 内部完成 lease 配对；`release_receive()` 在**所有**出口调用。已接入模块实证：`shm_ser_cli_ipc.cc` 用 `state->receive_inflight` 自记账（`recv_once()` 的 `try/catch` 全覆盖），socket 模块同型。`release_receive` 的越界保护在 `shm_route_session.cc:34-38`（`assert` + 提前返回，防下溢）。

> ⚠️ `assert` 在 `NDEBUG`（本基线 Release）下被编译掉 ⇒ 「多一次 release」在发布构建里只表现为**不报错的提前返回**。这是 I4 的已知观测缺口，W10 请按「超时判据」而非「断言」取证（本包 L6 churn 用 owner 归还 + `route_count` 做替代判据）。

## 5. 锁顺序与所有权

### 5.1 锁清单与本包实测

| 层 | 锁/原子 | 保护对象 | 位置 |
|---|---|---|---|
| worker | `mtx`（`mutable std::mutex`） | `routes` / `deferred` / `alive` 的读与置位 | `recv_worker.cc:117-119`、`socket_recv_worker.cc` 同型 |
| worker | `join_mtx` | `std::thread` 对象的 create/join、`thread_epoch` 递增、`thread_started_once` | `recv_worker.cc:141` |
| worker | 原子 | `running`（活动期）/`stopping`/`joined`/`alive`/各项 Stats | `recv_worker.cc:122-153` |
| Entry | 原子 | `last_seq`（SHM 事实判据）/`in_flight`/`removed`/`queued`/`fruitless`(socket) | `recv_worker.cc:86-105` |
| wait-set | 内部 `mutex` | `entries`/`ready`/`stopped`/(`waiters`) | `recv_wait_set.cpp:76-91`、`socket_wait_set.cc:83-110` |
| RouteSession | `mtx_` + `cv_` | `route_`/`generation_`/`receive_inflight_`/`stopping_`/`rebuilding_` | `shm_route_session.cc:128-134` |
| 调度器 | `mtx`（tick 数据）/`stop_mtx`+`stop_cv`（join 所有权） | `entries`/`next_due`/`tick_inflight`；`stop_joining`/`stop_joined` | `shm_control_scheduler.cc:53-123` |
| 模块 | `*_state_mtx_` / `state->mtx` / `state->quiesce_mtx` / `state->pending_mtx`(SHM ser) / `state->queue_mtx`(socket ser) | 成员快照 / 模块内状态 / 静默等待 / FIFO | 见 §5.3 表 |

### 5.2 三条硬性锁序（违反即死锁，均已实测过形态）

```text
L-1  worker.mtx  →  ✗  join_mtx        （禁止在 mtx 内调 ensure_thread_alive）
L-2  join_mtx    →  ✗  等待 worker 线程退出时持锁做需要 mtx 的事
L-3  RouteSession::mtx_  →  ✗  recv 的唤醒路径（disconnect 必须在锁外）
L-4  模块成员锁  →  快照（释放）→  state 锁      （两组绝不交叉持有）
L-5  调度器 mtx  →  ✗  回调（回调在锁外执行）     （回调内不得 unregister/stop 自身）
```

**L-1 的完整三方死锁链**（`recv_worker.cc:640-660` 实现注释原文）：`add_route` 持 `mtx` 等 `join_mtx` ‖ `stop()` 持 `join_mtx` 等 worker 线程退出 ‖ worker 线程退出前取 `mtx`（`drain_deferred`）⇒ 三方交叠即死锁。因此 `ensure_thread_alive()` 一律在 `mtx` 外调用（`start()` 也走同一条路，`recv_worker.cc:520-525`）。**`add_route` 因此不是单一临界区操作**，正确性由 §4.1 的两个不变量拼出。

**L-2 的正确形态**（`RecvWorker::stop()` `:528-552`）：置 `stopping`/`running` → `wait_set.stop()` → 在 `join_mtx` 内**只做 `thread` 的移动**，`join()` 在锁外执行。

**L-3 的正确形态**（`RouteSession::begin_rebuild`/`stop_and_wake`）：`disconnect()` 一律在 `mtx_` 外（`shm_route_session.cc:57-62`、`:134-140`），避免 recv 的唤醒路径回头再要 `mtx_`。

**L-4（模块侧）**：t8 §3.2 已固化并被 W07/W08 消费：

```text
成员锁（取完快照即释放） → state 锁（state->mtx / queue_mtx / quiesce_mtx / pending_mtx）
⛔ 两组绝不交叉持有；⛔ 访问器内不得取任何 state 锁、不得 join、不得回调、不得访问 worker pool
```

访问器实现见 `socket_pub_sub_ipc.cc:1234-1245`、`socket_ser_cli_ipc.cc:461-476`（三个访问口 + 成员访问全在 `receive_state_mtx_` 临界区内），`shm_ser_cli_ipc.cc:915-942`（`state_mtx_`）。

### 5.3 所有权（谁保活谁、谁在何时释放）

| 对象 | 持有者 | 释放时机 | 禁止 |
|---|---|---|---|
| route 适配器 `RecvRouteSource` | 模块（`shared_ptr`）**与** worker 的 `Entry`（`shared_ptr` 保活） | 模块 `remove_route` 返回后才可 reset（契约 §4.4） | 注销后继续持有裸指针回调（`shm_ser`/socket 模块都用 `shared_ptr<State>`，见 §5.1 表） |
| `ipc::route` / `ipc::server` / `UDPNode` | `RouteSession::route_` 或模块 `state` | `begin_rebuild` 第 5 步 / `teardown` 第 4 步 | **在 wait-set 仍有该 token 时释放**（W04-F2） |
| `recv_wait_token` / `SocketWaitToken` | worker 的 `Entry` | `wait_set.remove` 之后 | token **不拥有**通道；`remove` 返回后宿主才能 close fd |
| `RecvWorkerPool` / `SocketRecvWorkerPool` | 进程级**故意泄漏**的指针单例 | 永不（随进程） | 模块**不得**调用池 `stop()`（实测：三模块 `grep -c "pool.stop"` = 0 ✅）；否则其它模块整体静默停收 |
| `ShmControlScheduler` | 同上（故意泄漏） | 永不 | 同上；`RegistrationToken` 持 `shared_ptr<Impl>`，令牌比调度器长寿也安全 |
| `SubState` / `SerState` / `socket_*_receive_state` | 模块 + 处理线程 + worker route 适配器（`shared_ptr`） | `remove_route` + 线程 join 之后 | 不得把 `shm_*_ipc*` 裸指针交给 worker（W05/W06 现状已满足） |

## 6. 六种运行态行为（任务书第 3 项）

| 态 | 行为（契约 → 实现） | 判据 | 守门用例 |
|---|---|---|---|
| **无数据** | `recv_once()` 返回 0 ⇒ 本轮结束；worker 走**阻塞** `wait`（`min(wait_timeout, 剩余空闲窗口)`，下界 1 ms），⛔ 不得 `try_recv`/`receive_nowait` 全量忙轮询 | `wait_timeouts` 与墙钟同量级（600 ms 内 ≤ 20 次） | `RecvWorker.ThreadStaysAliveWhileRouteRegisteredAndIdle`；socket：`SocketRecvWorkerBytes.IdleRecvOnceReturnsZeroImmediately` + `SocketReadable.IdleRecvOnceReturnsImmediatelyWithoutBlockingOnTimeout` |
| **断开** | 与「有数据」共用**同一个 seq 变化**（SHM）：断开会推进 seq ⇒ 必须被处理；socket 侧靠 `cancel_wait()` 唤醒 + `readable()` 短路为 false | `remove_route` 返回后 ≤ 1 次 `recv_once`；无悬挂调用 | `RecvWorker.RemoveRouteWaitsForInFlightRecvAndStopsCallingIt`；本包 L4（注销后 `recv_once` 计数静止） |
| **部分分片** | libipc 内部完成重组（`recv` 返回完整消息）；socket 侧 `chunk_rev_*` 一次调用可跨多片但要到**完整边界**才返回 | 预算**只在完整 `recv_once()` 返回后**检查；⛔ 不得中途切走 | `RecvWorker.BudgetYieldIsNotMessageLoss`；socket：`SocketRecvWorker.ReceivesRealChannelAndRemoveIsSynchronous` |
| **预算耗尽** | 三项预算（32 条 / 1 MiB / 200 µs）任一到限 ⇒ `more=true` ⇒ 该 route 进 **deferred FIFO 队尾**；`last_seq` **不**推进 ⇒ 下一轮 `collect_pending` 重新发现它 | `budget_yields` / `deferred_drains` 增长；消息不丢 | `RecvWorker.BudgetYieldIsNotMessageLoss`；本包 L4 的「恒真 `has_pending`」上限 4 次/轮 |
| **空闲退出** | route 表连续为空 ≥ `max(idle_keep_alive, wait_timeout)`（默认 1000 ms）⇒ 线程归还 OS；`idle_keep_alive==0` 表示下一轮检查即退出（仅测试）；`running()`（活动期）**仍为 true** | `idle_exits` / `thread_restarts` 只增；`thread_alive()` 反映真实线程 | `RecvWorker.IdleExitReturnsThreadWithinLegacyAssertionWindow`（1000 ms 窗口）+ `AddRouteRestartsIdleExitedThreadAndKeepsReceiving` |
| **重新激活** | 任何 `add_route` 命中空闲退出的 worker ⇒ 锁外 `ensure_thread_alive()` 按需拉起；**恰好一次**（`alive` 双检 + `thread_epoch` 代际检查） | `thread_restarts` 恰好 +1；重拉后**真的收包** | `RecvWorker.ConcurrentAddRouteRestartsThreadExactlyOnce`（8 线程并发）+ `RemoveRouteInterleavedWithIdleExitKeepsTableConsistent` |

**三种「空闲」必须分开记账（方案 §10.1）**：① 无注册 route（可退出）；② 已注册但无发布者/未连接（是否入等待层由模块契约决定）；③ 已连接且有效订阅但停止发布（**保留接收能力，恢复发布不依赖重新注册**）。③ 的强制用例在 W10（本包只保证机制：route 表非空期间线程不退出，见 `ThreadStaysAliveWhileRouteRegisteredAndIdle`）。

**§10.2 的扫描成本**：`collect_pending()` 是**全量**在册 route 遍历（`recv_worker.cc:166-184`），成本 `O(route)`；`consume_ready()` 不是唯一事实来源 ⇒ **没有替代正确性证明前不得删除扫描**。本包不改该设计，只在 §10 的 W10 判据里要求「每轮扫描 route 数 / 扫描耗时 / deferred 深度」可观测。

**§10.3 的预算不可抢占**（本包 L5 已把推测变成实测）：

- 构造：闸门把 worker 停在一条 route 的 `recv_once()` 内，把 `max_processing_time_per_route` 压到 **1 µs**（若预算能抢占，这个状态就不可能出现）；
- 结果：被占住期间投递邻居消息，`received_count==0`（**确定性**，非睡眠猜测）；放行后邻居在 **1 ms** 内被补服务；
- 结论：**一次耗时 `recv_once` 让同 worker 邻居确定性延迟**，且这是底层接口限制（组包/解码不可中断），不是可被「调容量/加线程」修好的性能抖动。若团队要消除它，属**另立评审**的选项（非阻塞增量重组 / 独立接收通道 / 有界慢处理池），不得在模块适配器里隐式改变缓存与顺序契约。

## 7. 容量：分片偏斜与边界（任务书第 4 项）

### 7.1 上界 ≠ 保证（构造性偏斜，实测）

| 事实 | 实测值 | 说明 |
|---|---|---|
| 每 worker route/token 上限 | **127**（Linux；`recv_wait_set.cpp:27`，`futex_waitv` 128 槽留 1 给中断）；Windows **63** | 与 `worker_count` 无关的**常数** |
| 理论上界 | `127 × 32 = 4064` ≥ 1000 | 只说明**总量口径不会先报警** |
| 顺序命名 1000 路（`topic_0..999`，domain=7，32 worker）直方图 | **min 28 / max 34**（均值 31.25，max/均值 ≈ 1.088） | 本包 L1 实测；W00 §5.2 复算给 1.18–1.28×（命名不同），两者同量级 |
| 构造性偏斜（`skew_7_*` 枚举） | **128/128 全部落 worker 0** | 固定哈希是**纯函数**，敌对命名集合可整片压到一个分片 |
| 第 126/127/128 个 route | 126 → ok；**127 → ok**；**128 → `wait_set_full`** | 本包 L2 实测；断言 128 的返回码**不是** `backend_unavailable` |

⇒ **W00 的结论被本包端到端证实**：「`127 × worker_count` 是理论上界而非千路保证；最差 worker 叠加同话题多订阅仍可能先满」。W06/W10 必须在容量表里同时报 **每 worker route 数 / token 数 / 最大偏斜**，不得只报总量。

**同话题多订阅会集中**：哈希 key 是 `route_name ‖ domain_id`，同话题多订阅若共用 key（SHM pub/sub 是多播，一个订阅者一条 route，key 必须含订阅者身份；socket 侧 `route_key = topic + "#" + domain` 是**每订阅一份 state**）⇒ 模块必须保证「同一 worker 的表内 key 唯一」，否则 `add_route` 会返回 `duplicate`。W06 落地时须在容量表里说明 key 的构成，并给「1 话题 N 订阅」与「N 独立话题」**分开**的结果（方案 §13.1）。

### 7.2 generation 切换的顺序（W04-F2，崩溃复现）

见 §4.4。**对 W05/W06 的可执行要求**：

```text
// 重建前（任何来源：控制面 tick、handshake 分支、restart）
pool.remove_route(route_adapter);        // ① 同步摘除 wait 项（这一步会唤醒 worker 并等 in-flight 归零）
route_session_.begin_rebuild(new_gen, create);   // ② 内部 release 旧 route（此刻已无 token 指着它）
pool.add_route(route_adapter);           // ③ 新 generation 重新注册（返回非 ok ⇒ 显式回退兼容线程）
```

**反例（禁止）**：任何「先 `begin_rebuild`/`release()` 再 `remove_route`」或「不摘 wait 项就直接换 route」的写法 ⇒ `recv_wait_set::wait`/`SocketWaitSet` 解引用已释放资源（SIGSEGV 或静默停收）。
**socket 侧注**：`SocketWaitSet::consume_ready()` 按「当前在册 token + 代际」过滤，已 `remove` 的 fd 残留事件不会误触发；但**这不替代**「先摘项再关 fd」的时序——`epoll_ctl(DEL)` 本身不唤醒 `epoll_wait`（本机实测）。

### 7.3 socket 侧差异（复审结论）

| 项 | SHM | socket | 影响 |
|---|---|---|---|
| 等待后端 | `ipc::recv_wait_set`（`futex_waitv`，等共享内存里的 seq 字） | `SocketWaitSet`（epoll / `WaitForMultipleObjects`） | 机制不可复用，语义对齐（契约 §3） |
| 每 worker 上限 | 127 | **Linux 4096（策略上限）/ Windows 63（硬上限）** | Linux 侧 4096 远超单进程话题数，不是瓶颈 |
| 事实判据 | 共享内存 seq（内核没点名也能靠全扫发现） | **只有「内核说可读」** ⇒ 需要假就绪兜底 | 见下方 W04-F3 |
| `recv_once` 准入 | 无（seq 判据） | **必须先 `udp_node_readable()` 再 `chunk_rev_*`** | 否则共享 worker 线程空读阻塞到 tm（50/200 ms） |
| 字节出口 | `recv()` 的 buffer 长度 | 必须走 `chunk_rev_topic/server` 的 `out_bytes`（t12 追加） | 否则「成功」被记成 1 字节，预算与统计静默变错 |
| 池线程数来源 | `hardware_concurrency()`（**无** env 覆盖） | `DZIPC_SOCKET_RECV_WORKERS`（进程内只读一次）⇒ `hardware_concurrency()` | **口径差异必须在容量表分列**（方案 §10.4 末条） |

**W04-F3（medium，实测）**：契约 §5 表格称「假就绪兜底 ⇒ 循环速率有界」。**实测不成立**：构造一个「LT 持续可读但宿主恒返回 0」的通道（pipe 读端，永不消费），worker 的 `recv_once()` 速率达 **1.30–1.34 M 次/秒**（3 轮：1 302 599 / 1 326 816 / 1 314 465），即 CPU 级忙转。原因是 `requeue_ready()` 的 `fruitless ≥ 4` 只做 `remove+add` 重挂并**清零计数**，而 fd 仍是 LT 可读 ⇒ 下一轮 `wait(0)` 立刻又报就绪，计数从头累积，**周而复始**。同 worker 的真邻居**未被饿死**（2 字节全部收到，`got=2`）⇒ 危害限于该 worker 的 CPU 占用（可观测、可归因），但这正是契约 §4.5「⛔ 不得忙轮询」要禁止的形态，且会让「空闲 CPU」门槛（W00 §6.2 第 3 行 ≤0.20 core）**假失败**。
**建议收敛**（属实现变更，须 owner + 评审）：把「本 token 本轮判为假就绪」转成**有下界的等待**（例如把该 token 从本轮 `ready` 集合移出并把 `wait` 切片抬到 ≥1 ms），或把 `fruitless` 计数与「是否真的读不到」做成**每 token 一次退避**（而非全局重置）。本包不擅自改（属共享层接口行为，需走接口变更流程），只登记并给出复现件 `build/w04/w04probe10` 与日志 `build/w04/probe10_fruitless.txt`。

## 8. 进程级共享池：首次初始化责任方与后端纪律（任务书第 5/6 项，方案 §10.4）

### 8.1 责任方（已定，可判定）

**规则**：进程级池（`RecvWorkerPool` / `SocketRecvWorkerPool`）的 **worker 数与预算由「首个成功的 `start()` 调用方」一次性决定**；此后任何 `start()` 返回 `false` 且**不得改变**已生效配置；池**不得**被任何模块的析构调用 `stop()`。

| 项 | 冻结结论 | 取证 |
|---|---|---|
| 责任方 | **首个成功 `start()` 的调用方**（当前三模块都在「池未 running」时调 `start()`，参数取默认 = 不由模块传值） | `shm_ser_cli_ipc.cc:964-969`、`socket_pub_sub_ipc.cc:1152-1157`、`socket_ser_cli_ipc.cc:1072-1077` |

| 预算来源 | `RecvBudget` 默认值（`{32, 1 MiB, 200 µs, wait_timeout=100ms, idle_keep_alive=1000ms}`）；目前**无**模块级配置入口（启动配置可由部署方通过 `start()` 传参，但三模块都传默认） | `recv_worker.h:240-251` |

### 8.4 启动配置选择与重启回滚（任务书第 6 项）

三者语义分工（读代码即可核对，`shm_pub_sub_ipc.cc` 的 `fallback_to_compat()` 的 `switch`）：
· `fallback_total` = **回退总量**，在 `kBackendUnavailable` / `kPoolStartFailed` / `kWaitSetFull` **三个原因分支里各 +1**（⇒ 3 处写入点）；
· `wait_set_full` = **容量满**这一具体类别，只在 `kWaitSetFull` 分支 +1（⇒ 1 处）；
· `wait_token_invalid` = **token 无效**，在 `kInvalidToken` 分支 +1（⇒ 1 处），该分支**不加** `fallback_total`（属「进不了等待集合」的能力缺口，不是回退）。
⇒ 同一次事件里，原因 ID **只 +1 一个**（不会两个原因同时加），因此原因计数之和 = 回退总量；而 `wait_token_invalid` 与回退族**互斥**。

### 11.4 独立评审要点（`t14`/R1 与队长）

请**非实现者**逐条反证（方案 §10.9 的四件事）：

1. **有效订阅是否真的存在**：千路运行中每 route 是否真有注册成功 + 首包确认（不是只构造对象）；本包范围内需核对 R-12/R-13 与 W06 的容量表。
