## 1. 接线点与口径（逐条对齐 W03 字段定义）

### 1.1 `collect_pending()` 是唯一的扫描点

```cpp
// src/dzIPC/threepools/recv_worker.cc（接线后）
void RecvWorker::Impl::collect_pending()
{
    std::lock_guard<std::mutex> lock(mtx);

    const std::size_t scanned  = routes.size();    // 本轮**遍历**的 route 数
    const std::size_t depth_in = deferred.size();  // 入队**前**的 deferred 深度
    dzIPC::measure::ScanRoundScope scan(scanned, depth_in);
    std::size_t queued = 0;

    for (const auto& entry : routes) { /* 既有全扫逻辑，逐字不变 */ ++queued; }   // ← 只加了 ++queued

    scan.set_ready(queued > 0);
    /* 常驻孪生（无时钟、无诊断门控）：scan_rounds / scanned_routes_total /
       scan_ready_rounds / deferred_depth_last / deferred_depth_max */
}
```

| §10.2 要求的量 | 诊断门控面（W03 `CounterId`） | 常驻面（`RecvWorkerStats`） | 取值口径 |
|---|---|---|---|
| 每轮扫描 route 数 | `scanned_routes_total` / `scan_rounds` | `scanned_routes_total` / `scan_rounds` | `routes.size()`（**含已标记 removed 项**：它们同样在循环里被读一次 seq，构成扫描成本） |
| 扫描耗时 | `scan_time_ns_total`（÷轮数 = 均值） | —（唯一需要两次 `clock_gettime` 的量，故不常驻） | `ScanRoundScope` 构造/析构各取一次单调钟 |
| 等待超时次数 | `wait_timeout_count` | `wait_timeouts` | `wait_set.wait()` **返回 false** 的次数（⛔ 不含后端不可用的 `wait_errors`、也不含有就绪的 `wait_wakeups`） |
| 有效就绪比例 | `ready_observed / scan_rounds` | `scan_ready_rounds / scan_rounds` | 本轮全扫**确实入队 ≥1 条新就绪 route** 的轮数（`collect_pending` 是事实来源，不用 wait-set 的 ready 集合） |
| deferred 深度 | `deferred_depth_last` / `deferred_depth_max` | 同名字段 | **入队前**的 `deferred.size()`（与 W03 样例 `ScanRoundScope(n, deferred.size())` 同口径） |

**其它同族接线**（与 §10.2 的"等待/让出"直接相关，同一计数点）：
`wait_timeout_count`（`wait_once` 超时出口）、`budget_yields` / `deferred_drains`（`run_budget` 让出入口）、
`idle_exits`（空闲退出）、`thread_restarts`（按需拉起，**不含首次**）、`recv_once_calls` / `recv_once_over_budget`（§10.3）。

### 1.2 常驻面 vs 诊断面为什么必须**并存**（这是设计，不是重复）

- §10.2 原文要求"**低开销常驻计数**与**详细诊断采样**分开"，且要求报告注明诊断是否开启。
- 门控面（`scan_*`）在 `diagnostics_enabled()==false` 时**一个数都不写**；而按 W03/W08 的既有纪律，正式性能窗口通常**关闭**诊断（`test_w08_dzflat_ab` 即如此）。若只留门控面，正式窗口里就**没有任何扫描量可读**，W10 只能拿"CPU 随 route 近似线性"当替代量 —— 这正是 D-23 要消除的缺口。
- 因此新增常驻面：只做 relaxed 原子加 + 一次 CAS 最大值，**不取时钟**；唯一的时钟开销留在门控的 `ScanRoundScope`。
- 两套量在**同一位置、同一取值**写入 ⇒ 诊断开启时**比值必须相等**（见 §4.2 的自洽判据）。
- 报告纪律：本文件所有读数均标注 diag 状态（表格里 `diag` 列）。

### 3.1 「线程 O(1)、扫描 O(route)」的同一份证据

| 命题 | 证据（同一次运行取） |
|---|---|
| 线程数**不随 route 数增长** | `threads_breakdown pool_workers=32 control_scheduler=1 orchestration=1 residual=0`，N=100/500/1000 **三次完全相同**（total 34）。`residual` 判据：**必须为 0**（扣除池 worker、控制面调度器与本工装自身线程后不得有剩余 ⇒ per-topic 线程 = 0，§13.2 条件 4） |
| 扫描工作量**随 route 数线性** | 同一 W 下 `scan/s ÷ 在册 route` 近似常数：W=4 → **39.92/39.83/39.71**；W=8 → **25.56/25.72/25.78**；W=16 → **17.86/18.01/18.05**；W=32 → **14.25/14.40/14.28**（N=100/500/1000） |
| 扫描**轮数**不随 route 数增长 | 同一 W 下轮数近似常数（如 W=32：2717 / 2722 / 2728）⇒ 轮数由**等待节奏**决定，每轮成本才随 route 数增长 |
| 每轮确实**全量遍历** | `mean_routes/round` 与 `route_count/W` 逐档吻合（25.00 vs 25.00；125.00 vs 125.00；31.48 vs 31.25；…） |

**读法**：扫描成本 = 轮数 × 每轮 route 数；固定线程把**轮数**压成常数（由 `wait_timeout` / 唤醒节奏决定），但**每轮要遍历的 route 数仍随规模增长** —— 这正是 §10.2 的命题，现在有计数器级证据（此前只有 W10 的 CPU 近似线性替代量）。

### 3.2 容量边界（必须显式记录，不得被"attached==n"掩盖）

`W=4` 时池容量 = `4 × 127 = 508`，故 N=1000 有 **492 条装不下**。读数：

```
route_count=508  capacity_binds=1  threads=498
threads_breakdown pool_workers=4 control_scheduler=1 orchestration=1 residual=492
                  overflow=492 compat_path=492 compat_waitsetFull=492 worker_path=508
```

⇒ 溢出 route **按设计显式回退**兼容线程（`kRecvPathCompat(kWaitSetFull)`），且 `rx == 1000`（回退线程照样收得到；静默丢包是禁止的）。
工装对"容量受限"与"不受限"**分别**给判据（不受限 ⇒ `residual == 0`；受限 ⇒ `residual == overflow` 且 seam 回退数 == overflow），避免把回退线程误报成"per-topic 线程泄漏"。

### 3.3 诊断开关的代价（常驻 vs 详细诊断）

`diag=off` 时门控计数**恒为 0**（含 `scan_time_ns_total`），常驻量照常非零。CPU 对照（同档同窗口，只差一个布尔）：

| N | W | cpu(off) | cpu(on) | 判定 |
|---|---|---|---|---|
| 100 | 32 | 0.0433 | 0.0417 | 无差异（噪声内） |
| 500 | 32 | 0.2967 | 0.3033 | 无差异 |
| 1000 | 32 | 0.5100 | 0.5417 | 无差异（±6%，落在逐次波动内：同档重跑 off 为 0.5200/0.5100/0.5200、on 为 0.5150/0.5050/0.5225） |
| 1000 | 16 | 0.5100 | 0.5167 | 无差异 |
| 1000 | 8 | 0.5417 | 0.5783 | 无差异 |

扫描耗时本身（W03 采集器口径，`observation_overhead.json`）：`scan_scope_disabled_ns` **0.46 ns/轮**、`scan_scope_enabled_ns` **37.8 ns/轮**、`diagnostics_inc_enabled_ns` 4.2 ns、`diagnostics_inc_disabled_ns` 0.47 ns。
⇒ 常驻接线在**关闭诊断**时的代价 = 每轮 3 次 relaxed 原子加 + 1 次 `store` + 1 次 CAS（**不取时钟**）；在 1000 route / 453 轮/s 的量级下（≈ 450 轮/s × 数 ns）完全落在 CPU 读数噪声内。

**建议默认值**：`diagnostics_enabled=false`（常驻面已覆盖 §10.2 五项中的四项 + 等待超时；只有"扫描耗时"需要开诊断）。
理由：① 正式性能窗口按既有纪律本就关诊断（W08 先例）；② 开诊断的 CPU 差值在噪声内，但耗时量只在需要归因"每轮扫描耗时"时才有意义，属"详细诊断采样"的定义域；
③ 常驻面使 W10 在**不开诊断**时也能给出计数器级扫描量，消除 D-23 的替代量缺口。

### 4.2 自洽判据（两套计数必须同源）

常驻量与门控量分处两个对象、快照非同取，故判据用**嵌套窗口 + 比值**而不是逐值相等：

- 读法：`r0 → k0 → 窗口 → k1 → r1`（门控窗口**嵌套**在常驻窗口内）⇒ `d_g_rounds ≤ d_rounds` 恒成立；
- 接线正确性由**比值**判定：窗口内 route 集合不变 ⇒ 两边 `scanned/rounds` 是同一个加权平均，**必须相等**（容差 0.5% + 0.01）；
- 另断言 `d_g_timeout ≤ d_timeout`、`d_g_ready ≤ d_ready`；`diag=off` 时门控五项**必须全为 0**。

24 组读数全部满足（见 `summary.md`；例如 W=32/N=1000：常驻 2721/85659、门控 2721/85659）。

## 6. 🔴 顺带发现的工程风险：按值返回的结构体追加字段 ⇒ 共享层工装必须随库重编

**现象**：`build/bin/w10_matrix`（20:24 编）对 `build/lib/libipc.so.1.3.0`（21:59 重链）运行，
功能读数全对（`W10_MATRIX_DONE verdict=PASS`），但进程**退出时** SIGSEGV：

```
Thread 1 "w10_matrix" received signal SIGSEGV, Segmentation fault.
0x00007ffff78a53be in __GI___libc_free (mem=0x1a1) at ./malloc/malloc.c:3368
#0 __GI___libc_free (mem=0x1a1) at ./malloc/malloc.c:3368
#1 0x00005555555610a3 in main ()
```

**根因**：`RecvWorkerStats` 是 `RecvWorker::stats()` / `RecvWorkerPool::stats()` 的**按值返回**类型。
t30 在其中追加 5 个 `uint64_t` 字段 ⇒ **结构体尺寸变化**；陈旧调用方按**旧尺寸**在**栈**上留空间，
新库按**新尺寸**写 ⇒ 覆写相邻栈变量（此处是 `main` 的一个指针），退出时 `free(0x1a1)` 崩。

**影响面判定**：这是**工装侧 ABI 不匹配**，不是产品缺陷 —— 生产代码走的是同一份头文件、随库一起编译，
不存在"旧调用方"。但它有真实风险：任何**不随库重编**的第三方/历史二进制（含 W10 工装、tmp 里的历史探针）
在结构体追加字段后会以"功能全对、退出即崩"的形式失败（甚至可能更早崩）。

**处置**：本 run 前把 `test/perf/w10/*.cpp` 全部 11 个工装**重编**（与 W10 相同方式），随后 100/500/1000 **rc=0 且全绿**。
**建议**（提请队长/架构负责人与共享层负责人裁决，属团队级纪律）：
- 共享层"按值返回的结构体"（`RecvWorkerStats`、`SocketRecvWorkerStats`、`ShmControlScheduler::Stats` 等）追加字段时，
  必须**同步重编所有引用方**；W00 的"防陈旧 build 假绿"纪律（§10.6 要求正式验收先重跑 CMake+编译）**天然覆盖**这一条，
  但本 run 的教训是：**工装不在 CMake 里**（`test/perf/w10/*.cpp` 由手工命令编译）⇒ 不受该纪律保护 ⇒ 需要单列一条纪律。
- 或者（更彻底、属共享层决策，⛔ 本任务不做）：把 stats 访问改成"引用出参 + 版本/尺寸字段"。

**本 run 的做法**：不掩盖 —— 把崩溃、gdb 栈、根因、重编前后的 rc 对比全部落盘（`w10_reuse.log`），
并把"重编后的二进制指纹"写进同一证据目录。

## 7. 已知限制

| # | 内容 |
|---|---|
| L1 | 本工装的负载是"每 route 3 条 + 窗口内轮转发布（20 ms 间隔）"，**不是**满速压力；§10.2 关心的是"扫描成本随规模的形状"，不是吞吐上限。满速场景归 W10/W11。 |
| L2 | `scan_time_ns_total` 只在 `diag=on` 时非零（设计，见 §1.2）。`ns/round` 因此包含**扫描本身 + 一次 `clock_gettime` 对**，不能当作纯扫描耗时（W03 口径已如此）。 |
| L3 | `deferred_depth_*` 取的是"入队前"快照，与 `ScanRoundScope` 样例同口径；它不是"整个窗口的最大深度"的连续观测（窗口内每秒 450 轮，采样足够密，但严格说仍是逐轮采样）。 |
| L4 | 池级的 `deferred_depth_last` 取各 worker 的**最大值**而不是求和（"最繁忙的 worker 有多深"才有物理意义）。逐 worker 值可由 `RecvWorker::stats()` 单独读。 |
| L5 | W=4 档的容量受限是**刻意构造**的（127×4=508 < 1000）；默认 32 worker 容量 4064，不构成实际约束。 |
| L6 | 常驻面新增了 5 个 `RecvWorkerStats` 字段 ⇒ **按值返回结构体尺寸变化** ⇒ 共享层所有引用方（含工装）必须重编（见 §6）。 |
| L7 | 本任务只接线、不改算法；"减少冗余扫描 / 延长等待"属 §10.2 的**后续**选项，必须以"消息、断开、注销均有可靠唤醒"为前提另行评审（本 run 的 `wait_timeouts` 与 `wait_wakeups` 同量级读数可作为该评审的输入，但**不构成本任务结论**）。 |
