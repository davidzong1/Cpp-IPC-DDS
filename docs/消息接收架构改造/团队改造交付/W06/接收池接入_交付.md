## 3. 🔴 我发现并修复的缺陷：W06-F1「先睡再干活」

### 3.1 现象与定位

接入后探针给出两条互相矛盾的读数：**数据确实到了**（`try_send` → `recv(0)` 可见 45–70 µs），
但从 worker 侧的**交付延迟恒为 100 ms 的整数倍**。定位手段与结论：

| 探针 | 读数 | 结论 |
|---|---|---|
| `probe/w06_probe_notify` | 在订阅端 seq 字上做**阻塞 `FUTEX_WAIT`** 3 s，`try_send` 后 `rc=0`、延迟 **300 089 µs = 恰好 300 ms**（send 前已睡 300 ms） | libipc 的 `notify` **确实打到了同一个 seq 字**；发布侧/共享段都没问题 |
| `mini3.c` / `mini4.c`（scratch） | `futex_waitv(..., timeout=3s, CLOCK_MONOTONIC)` 立刻返回 `ETIMEDOUT`（`waited_us ≈ 4`，且 `FUTEX_WAKE` 报 `woken=0`）；同场景 `FUTEX_WAIT` 正常被唤醒（`waited_us = 300 005`） | 本机（`6.8.0-138-generic`）`futex_waitv` 与 `FUTEX_WAKE` 的**配对条件**与 `FUTEX_WAIT` 不同 ⇒ `recv_wait_set::wait()` 实际上**从不被及时唤醒**，只能靠超时返回。这是共享层的既有形态，见 §7 已知限制 |
| `probe/w06_probe_stale` | worker 持有的 seq 指针与"新开一条 receiver"的 seq 指针**同值**，段文件 `dev:inode` 相同（`00:f8 26 …WAITER_STATE_`） | ⛔ **不是** token 陈旧、也不是跨进程各自映射 —— 排除目标修复方向 |
| `probe/w06_probe_rearm` | send **前**做 `remove_route + add_route` 重新 arm，延迟仍 **100.16 ms** | ⛔ **不是** arm 值陈旧 |
| `probe/w06_probe_split` | 同进程第三方 `ipc::route(sender)` 的原始 `try_send` 也会被 100 ms 地板拦住 | ⛔ **不是** dz 发布栈的问题 |

⇒ 剩下的唯一变量是 **worker 自己等待的时机**。

### 3.2 根因（一行顺序）

`Impl::loop()` 的 `else` 分支（即有就绪项时）原来是：

```
drain_deferred_detect();          // collect_pending() 已把就绪 route 排进 deferred
wait_once(budget.wait_timeout);   // ← 先阻塞一整个等待切片（且本机 waitv 从不被唤醒）
drain_deferred();                 // ← 100 ms 后才真正服务它
```

而 `run_budget()` 的收尾是 `entry->last_seq.store(entry->token.sequence()->load())` —— 读的是
**调用返回那一刻**的 seq。于是这个顺序还带来第二个后果：若真实数据恰好落在
"`recv_once()` 读到 0"与"写 `last_seq`"之间，这次 seq 变化被**吞掉**，该 route 要等到
**下一次** seq 变化才被重新选中（同进程 generation 重建只有一次变化）⇒ 表现为"偶发慢/偶发收不到"。

### 3.3 修法与反事实证明

修法（`src/dzIPC/threepools/recv_worker.cc`）：

```cpp
const std::uint64_t msgs_before = messages_received.load(std::memory_order_relaxed);
drain_deferred();
if (messages_received.load(std::memory_order_relaxed) == msgs_before)
{
    wait_once(budget.wait_timeout);   // 一条都没取到 ⇒ 阻塞让出，速率上界还给等待
}
```

⛔ 不是"改成忙轮询"：只有当 drain **一条都没取到**（队列里只剩"预算耗尽但读不到数据"的项）时
才阻塞。这条约束是实测逼出来的 —— 无条件 drain 会让宿主 `has_pending()` 恒真的病态实现每轮
自我 requeue（每轮 4 次空读）⇒ 实测 **947 次/s**，而 W04 的 `test_lifecycle_contract` L4 判据是
**≤ 200 次/s**（该用例因此在中间版本变红，加上空轮让出后回到 **36 次/s**）。

**反事实实验**（`src/w06_f1_counterfactual.sh`，同一二进制、同一域，只改这一段顺序；脚本自带
前后 sha256 断言）：

| 版本 | `case=lat` mean / max | 判定 |
|---|---|---|
| 旧顺序（先 wait 再 drain） | **90.1 ms** / **100.2 ms** | FAIL（地板 = `wait_timeout`） |
| W06-F1（先 drain，空轮才 wait） | **0.17 ms** / **0.32 ms** | PASS |

修复前 sha256 `c79758698c20af60…` / 修复后 `8031f9aced716704ed…`（脚本断言"还原后与运行前逐字一致"）。
证据：`logs/f1_counterfactual.log`、`logs/regress_lat_worker.log`。

### 3.4 这个缺陷的**影响面**（谁会被它改变）

- 千路有效收发**不受影响**（`msgs=1000/1000`）—— 它只影响**延迟**，不影响最终到达；修复前
  千路同样能通过，所以**不能**拿"千路绿"当作没有这个缺陷的证据。
- 它会把"延迟"升级成"延迟 + 丢一次发现"，因此**同进程 generation 重建**（pub 析构那一瞬）
  落在窗口里的消息会被推迟到下一次 seq 变化 —— 这正是 `test_wakeup_artifact` /
  `test_shm_sub_dtor_gate` 在 worker 臂上暴露的形态（underlying 原因见 §4）。

## 4. 既有回归在两条接收臂上的等价正对照（测试侧改动与理由）

| 用例 | 原判据 | 为什么在 worker 臂失效 | 现在的按臂判据 |

## 5. 预算、容量与回退观测（逐条证据）

### 5.1 预算（消息/字节/处理时间）

- 默认值与冻结值逐字一致（`RecvBudget{}`）：`32 msg` / `1 MiB` / `200 µs` / `wait 100 ms` / `idle 1000 ms`。
- 启动配置可改：`DZIPC_SHM_RECV_BUDGET_MSGS|BYTES|US`、`DZIPC_SHM_RECV_IDLE_MS`、`DZIPC_SHM_RECV_WORKERS`
  （进程内**只读一次**，⛔ 禁运行中换配置）。
- **回显生效值而非请求值**（§10.4）：`RecvWorkerPool::budget()` 由**首个成功 `start()` 的调用方**
  一次性决定；后到者请求值与生效值不一致时**打诊断**（`shm_pub_sub_ipc.cc:1806-1816`）。
  证据：`DZIPC_SHM_RECV_BUDGET_MSGS=7` 时探针读到 `effective_max_msgs=7`（默认 32）。
- **预算耗尽不是丢弃**（承重条）：`DZIPC_SHM_RECV_BUDGET_MSGS=1` 下发 5 条 ⇒ `sent=5 got=5/5`
  （预算轮让出 → 进 deferred FIFO → 下一轮继续收）。证据 `logs/regress_budget.log`。

### 5.2 时间预算与队头阻塞（§10.3）

- 计时边界 = **完整一次 `recv_once()`**（含宿主侧组包/分流/入队），**在返回之后**读取；
  与预算检查同一安全边界。三项统计 `recv_once_calls` / `recv_once_max_ns` / `recv_once_over_budget`
  恒开（不受 diagnostics 门控），与 `CounterId::{recv_once_calls, recv_once_over_budget}` 同口径
  （后者的写入点归 W03/W09 接线，本层不写）。
- **队头阻塞实测**：同一 worker 上（`worker_for` 碰撞对）「64 KiB 大消息热路（另一线程满速灌）+
  小消息冷路」：

  | 读数 | 值 |
  |---|---|
  | 热路 64 KiB 发布成功 | **81 386/81 386** |
  | 冷路投递延迟 | **255 µs**（有界） |
