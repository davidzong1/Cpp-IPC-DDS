## 5. 次严重发现：R1-W09-F1 —— t22 的 v2 修复引入内存别名

### 5.1 缺陷

`ipc.cpp:544` 在**释放** `handles_` 的 `lock_` **之后**才调 `reclaim_orphan_segment()`，而其内部是**三次独立加锁 + 锁外毫秒级 `/proc` 扫描** ⇒ 同进程另一线程可在窗口内 `acquire()` 借走 id#0，reclaim 随后仍判「段内无活持有者」并 `reset_free_chain()` ⇒ **同一 chunk 被两块借样同时持有**。

### 5.2 证据

| 库 | 命中率 |
|---|---|
| FIX（当时工作区） | **10/60** |
| UNDERSAME（把 reclaim 移入 `lock_`） | **0/60** ← 修法已验证 |
| ABLATE（删调用点） | 0/60 ← 缺陷由 reclaim 引入 |
| **BASELINE（`ipc.cpp.HEAD` 逐字）** | **0/60** ← **v2 新引入** |
| NORECHECK（只删重锁 memcmp） | 7/60 ← 缩小但未关死 |

命中样例（**直接的内存别名证据**）：`TWO_ROUTES_ALIAS r=0 same_id=3 same_data_ptr=3 bytes=[GBEGEBFH]` —— 两条被**分别 `memset` 成不同字节**的借样**指向同一块内存**。

**场景是受支持用法**：同进程 N 个不同话题（每话题单生产端）+ 默认空前缀 ⇒ 8 个话题共享同一档池 —— 正是 W09 §2.3/§8 描述的部署形态。

### 5.3 修复状态

t73 已完成修复（`orphan_candidate`/快照移入 `handles_` 的 `lock_` 临界区），并给出**同二进制换库对照**（`lib_fixed` `bad_rounds=0` ×3 / `lib_negative` `bad_rounds=1` ×3）；t74 **复审 = pass**（并自建三负控 + ABA 窄窗口专项攻击：FIX 0 / V2NEG 3 / NEG 6 ⇒ **该窗口本次未被打开，⛔ 不等于已封死**）。

> ✅ **本轮终态（T07，§8.4）**：**W09 = 修复已完成并通过独立验证**。
> ⚠️ 限定：该结论只针对**本缺陷**；⛔ 不等于「整体规模门槛已达标」（门槛 3 CPU 子项、门槛 6 仍按 §8.4 未达标/不作判定，G2/G4 未关闭）。

## 10. 本轮积累的合同与流程纪律（队长记账，⛔ 待并入 W00 / W12）

> 本节全部来自**实际发生的返工**，每条都附本轮真实案例。**建议在 W12 结案前正式并入 W00 §4.4 闸门纪律与 W12 交付纪律。**

### 10.1 **提交前必须逐文件 sha 对照 HEAD**（防「工作区回退被 commit」）

- **案例**：§1 的工作区回退事故 —— 4 文件被批量写回 `e800ccc` 且**已 staged**（`272 insertions / 1757 deletions`）。我此前两次提交前只核了 `tracked=0 / untracked=0`，**没核过「内容是否 == HEAD」**。
- **纪律**：提交前逐文件 `sha256(worktree) == sha256(HEAD:<file>)`；对**未修改**的已跟踪文件也应抽样核对。⛔ 「工作区干净」**不等于**「工作区正确」。
- **已发生的代价**：`ctest` 从 29/29 掉到 26/29；若不慎提交则 1757 行删除进历史。

### 10.2 **`inScope` 必须写「允许新增文件的目录」**（防「变更被平台校验拒绝」）

- **案例（第 3 次同类）**：t71（内联后删文件）、t75（已提醒）、t73（C9 用例 + W09 §7.5 **被拒落地**、还原留档）、t77（**7 项已落地但无法声明**）。
- **根因**：平台校验器**只接受 `inScope` 点名的路径** ⇒ 逐文件枚举时，任何新增/旁及文件都会被拒。
- **纪律**：`inScope` 一律按**目录白名单**给（如 `docs/…/W09/**`、`test/**`、`artifacts/perf/<本任务 run>/**`），并对**必须修改的既有文件**再逐条点名。

### 10.3 **「判据的判据」：常驻用例必须做反向验证**

- **案例（两次）**：① t73 —— 上一版常驻用例每轮 `clear_storage` ⇒ 面对全新段 ⇒ 复位函数首行 **早退** ⇒ **被测代码路径根本没跑**（`orphan segment reset` = 0），**连负控都"绿"**（假绿）；② t77 的新用例**只在默认臂有牙**，`DZIPC_SHM_CONTROL_SCHEDULER=1` 臂下**双判据变红**（t78 发现）。
- **纪律**：写完常驻用例后**必须**做反向验证 —— 把被测修改**回退**（或换回错误形态的库）⇒ 用例**必须变红**。⛔ 单看 PASS 完全无法区分「通过」与「根本没跑」。
- **推荐交付形态**（t83 已示范）：**同二进制 + 只换 `libipc.so.3`** 的 FIX/NEG 双库对照，并把两个库副本归档 ⇒ **第三方无需改源码即可离线重放**。

### 10.4 **同一判据/同一事实只允许存在一处**

- **案例**：① W10-F7（渲染表达式与 `c4` 机械断言不一致 ⇒ 同份 verdict 内 `c4=1` 而表格 ❌）；② W08（失效值在 §2.5 标失效、却在 §0/§1.2 继续使用）；③ **W05-N1**（同一 `has_peers()` 门控被**复制到两条驱动路径** ⇒ 修了一条、回退臂仍 0/400）；④ t75/t77 的归档自述件与实物不一致。

### 10.6 **裁定必须路由到承接者，不能只落盘**

- **案例**：我在 `W12/任务失败与事故报告.md:139-143`（落盘 12:11:44）裁定「R1-W05-F1 必须修，不得登记为已知代价」，而 t75 的合同是平台按 `deps=t6` 生成的，其中只有复核者的 requiredFix ③（字面允许「请裁决」）⇒ **承接者从未收到该裁定**，于是把已被否定的分支又提回"请队长裁决"，造成一整轮返工（t76 判 blocker）。
- **纪律**：任何**改变某任务方向**的裁定，必须在**同轮**以 `agent_teams_send_message` 送达该任务承接者；⛔ 只写进文档/报告**不构成送达**（承接者不读队长的报告文件）。

### 10.7 **质量任务的 `inScope` 须与 `acceptance` 自洽**

- **案例**：t60（共享层负责人）—— 其 `acceptance` 第 6 条要求「为 R-01 反例加常驻用例」，而 `inScope` **未列** `test/test_lifecycle_contract.cpp` ⇒ 承接者按最小范围改了文件并**如实上报越界**，请我裁定。

### 10.8 **`failed` 状态 ≠ 技术失败（区分基础设施失败）**

- **案例**：t69 与 t73 均因服务端 **`503 system cpu overloaded (92.3% > 90%)`** 被自动标 `failed`，而两者的产出**实际已完成**（t69 的 report 226 行已落盘；t73 五项验收全完成）。
- **纪律**：见到 `failed` 先查 `output` 是否为基础设施错误；以「**产出是否在树 + 是否可复算**」判定实质。⛔ 不得据 `failed` 字面推翻已完成的工作，⛔ 也不得据此跳过复核。
