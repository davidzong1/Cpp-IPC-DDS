# W10-R6b CPU 双工装分歧仲裁（t45）

> 任务：`t45`（门槛 3 CPU 项前置的 2.3× 分歧仲裁），attempt `03d76fa8-029f-4573-80cd-d41c4a9a121c`
> 负责人：**验证与性能负责人**｜输入：t38（R5）§8 登记 + t32（R6）离散度上报 + t31-F2 归因
> 证据目录：`artifacts/perf/20260930-r47-W10-R6b/`（新 run_id）
> 自评等级：**S3**。⛔ S4 独立验收归 `t14`/R1。

**一句话结论**：**2.3× 分歧不是"两个工装测法不同"，而是 `state2 / n=1000` 这一档本身的 tick 率是双峰的（3.4–3.5×）。**
两个工装的 CPU 口径**完全相同**（已用 `rusage` 权威核对），外部逐 TID 与进程内读数一致到 **1%**；
真正的不变量是 **`cpu ≈ tick 率 × 每 tick 成本`** —— 每项每 tick 成本稳定在 **11.9–14.3 ns**，
而 tick 率在 `state2/n=1000` 上可在 **2 699–15 905 /s** 之间跳变（5.29× 极差）。

## 2. 要求 ②：分歧根因**逐条判定**

t38 列出 4 条候选。我用**单变量配对实验**逐条判定（同一二进制、交替执行、每格 ≥3 次）：

| 候选 | 实验 | 判定 |
|---|---|---|
| **(a) 窗口前阶段不同（settle）** | 同二进制 `--settle-s 0` vs `4`，win=30 s，3 轮配对：`0.28867/0.29467/0.28200` vs `0.25967/0.29333/0.29267` | ⛔ **无可测效应**（差落在同格离散内） |
| **(b) 是否读取 `stats()`/register 探针项** | 同二进制两变体（一档在窗口前多读一次 `stats()`），3 轮：`0.28800/0.29733/0.29667` vs `0.11133/0.18133/0.13000` | ⛔ **不是"读 stats"导致**——两变体都能出现高低两态（见 §3） |
| **(c) 30 s vs 60 s 摊薄** | 同二进制 win=30 s vs 60 s 配对 3 轮：`0.25967/0.29333/0.29267` vs `0.29400/0.29333/0.29017` | ⛔ **无可测效应**（60 s 不摊薄掉高态） |
| **(d) 逐 TID vs 进程内 `/proc`、rusage vs stat** | §5 的 4 轮对照 | ⛔ **不是口径差异**（比值 0.99–1.00） |
| **真正根因** | 见 §4 | ✅ **该档 tick 率双峰**（3.4–5.3× 极差），而 CPU 与 tick 率**近线性**（per-tick 成本恒定 10–13 µs） |
| (e) 其它：CPU 亲和性 | 不 pin vs `taskset -c {0,6,12}`，各 3 轮 | ✅ **可复现杠杆**：钉核后 cpu 从 ≈0.11 降到 0.035–0.062（3/3 轮），per-tick 成本不变 ⇒ 支持"CPU = tick 率 × 常数" |

**另做了两条排除性实验**（因为"topic 名长度"曾一度看起来像根因）：

1. **前缀长度扫描**（4/5/6/7/8/9/12/16/20 字符，各 2–3 次）：出现 4–6 字符 ≈0.13、≥7 字符 ≈0.29 的**表面台阶**；
   但把顺序随机化（6 vs 9 字符各 6 次交错、逐次清 `/dev/shm`）后，台阶**在两组内部消失**
   （短前缀 0.0825–0.1808、长前缀 0.2950–0.3100 仍有交叠）⇒ **不是名字长度效应，而是同一双峰在两组间的分布不均**。
2. **SSO/堆布局假设否定**：显式构造 `name_len 8–10`（SSO 内联）与 `16–18`（堆分配）两变体，
   各 3 次：`short` 0.1250/0.1108/0.1550 vs `long` 0.1658/0.1350/0.0983 —— **两态在两变体内都出现**；
   再加 `short_pad`（预先打散堆）与 `long_nopad`（预分配长名）两变体同样**都出现两态**
   ⇒ **SSO/堆布局不是根因**（假设被证伪并如实记录）。

## 3. 要求 ③+④：冻结三元组、逐档读数与离散度

### 3.1 三元组**冻结定义**（建议 H.3 CPU 判据引用此定义）

| 维 | 冻结定义 | 理由 |
|---|---|---|
| **窗口** | `--window-s 60` + `--settle-s 4`；⛔ 外部采样器时长必须**完整落在**该窗口内（本 run 用 `WIN - SETTLE - 8`） | settle/窗口长度本身无效应，但**外部采样错位**会造出假偏差（本 run 修正过一次） |
| **项数** | **注册项数**（不是 route 数）：`state2` = n（仅订阅）；`state3` = **2n**（订阅 + 发布） | t32 已指出"CPU 与 `ticks×entries` 不是单系数线性"——按**项数**分档才能作判据 |
| **tick 口径** | `ShmControlScheduler::stats().tick_count` 的**同窗口差值 / wall**；⛔ 不用 `wakescan` 推算、不用公式 `Σ1000/heartbeat` | 与 §11.3 R-1 的"唤醒率按实测上界"一致；公式口径已证高估 13–36× |

## 4. 不可稳定测量的**机制**：CPU 是 tick 率的因变量（并找到一个可复现杠杆）

### 4.1 已证实的定量关系

对全部 52 个窗口计算 `每 tick 成本 = cpu / tick_rate`：

| 格 | 每 tick 成本（中位） | 范围 |
|---|---|---|
| state2 n=500 | **7.3 µs** | 7.2–7.4 |
| state2 n=1000（22 次） | **12.0 µs** | 11.5–12.9 |
| state3 n=1000（10 次） | **45.2 µs** | 39.9–50.2 |

⇒ **每个 tick 的"固定开销 + 每项开销"是稳定的**；`state2/n=1000` 的 CPU 3.52× 极差
**几乎全部**来自 **tick 率**（tick 率极差 5.29×，且 cpu/tick 的极差仅 1.12×）。

### 4.2 决定性杠杆：**CPU 亲和性**（可复现，⛔ 非结论性解释）

| 运行方式 | cpu | tick/s | 每 tick 成本 |
|---|---|---|---|
| 不 pin（3 轮，win=15，`affinity_lever.txt`） | 0.10067 / 0.10533 / 0.12400 | 8637 / 9826 / 10845 | 11.3–11.7 µs |
| `taskset -c 0`（3 轮） | **0.03600 / 0.03533 / 0.03467** | 3543 / 3551 / 3461 | 10.0–10.2 µs |
| `taskset -c 6`（3 轮） | 0.04400 / 0.04200 / 0.06200 | 4226 / 4058 / 5870 | 10.4–10.6 µs |
| `taskset -c 12`（3 轮） | 0.05067 / 0.05733 / 0.03667 | 5044 / 5687 / 3432 | 10.0–10.7 µs |

⇒ **钉核后极差从 1.2×（未 pin 的 3 轮内）放大到 1.7×（跨核），但绝对水平从 ≈0.11 降到 ≈0.04–0.06**
（**down 2.1–2.9×**），而**每 tick 成本保持 10–12 µs 不变** ⇒ 又一次印证"CPU = tick 率 × 恒定每 tick 成本"。

### 4.3 机制陈述（**置信度分层，⛔ 不越界**）

- ✅ **已证实**：每 tick 成本恒定（10–13 µs @state2/n=1000）；CPU 3.5× 极差 100% 来自 tick 率；
  亲和性可把 tick 率与 CPU 同时压低 ≈2.5×（3/3 轮复现）。
- ✅ **已证伪**：settle 时长、窗口长度、是否读 `stats()`、topic 名长度、SSO/堆布局、
  采样口径（逐 TID vs 进程内 / rusage vs stat）、注册时长分散 —— 七类候选**均无效应或无单一效应**（§2、`root-cause/README.md`）。
- ➖ **未闭环**：为何同一二进制、同一配置下"每 tick 选中项数"会落在 7 或 23（对应 tick 率 ≈14 kHz 与 ≈4.3 kHz）。
  它与 CPU 调度机会（亲和性/抢占窗口）相关，但**不能**用上述任一路径解释；
  **⛔ 我不声称已定位根因**，登记为开放观察项，建议归 t32/R6 与调度器作者。

> ⚠️ 对判据的直接含义：既然"每 tick 成本恒定、CPU = tick 率 × 常数"，
> 那么**用一个不稳定的 tick 率去乘**必然得到不稳定的 CPU ⇒ **CPU 绝对值不合适做该档判据**；
> 正确形态是**要么归一化到 tick 率，要么先把 tick 率钉住**（§6）。

## 5. 要求 ⑤：与**外部逐 TID**（上位口径）的关系与偏差来源

`w10_idle` / `w10_r5_matrix` 的进程内读数都是 `/proc/self/stat` 的 **token[11]+token[12]**。
**索引推导**：after-`)` 的第 0 个 token 是 field 3（state）⇒ 索引 = field 号 − 3；
`proc(5)` 的 **field 14 = utime、field 15 = stime** ⇒ 正确索引 **11 / 12**。
我用 `rusage` 做了**权威核对**（三阶段实验）：

| 阶段 | `rusage` utime/stime | stat token[11] | stat token[12] | 判定（field 14/15） |
|---|---|---|---|---|
| 纯用户态 3 s | 3.001 / 0.002 | **300** | 0 | token[11] = utime ✅ |
| 再加 1 s 系统调用 | 3.100 / 0.903 | 310 | **90** | token[12] = stime ✅ |

⇒ **两个工装取的是同一对字段，口径零差异**（`w10_idle` 用 `i==13/14` 从 2 起数 ⇒ token 11/12；
`w10_r5_matrix` 直接取 `v[11]+v[12]` —— 连索引写法都等价）。

**外部逐 TID 对照**（同一工装、同库、采样窗口完整落在工装窗口内，4 轮）：

| 轮 | 进程内 cpu | 外部逐 TID cpu | 比值 |
|---|---|---|---|
| 1 | 0.14696 | 0.14646 | **0.9966** |
| 2 | 0.17927 | 0.17792 | **0.9925** |
| 3 | 0.16161 | 0.16146 | **0.9991** |
| 4 | 0.13630 | 0.13687 | **1.0042** |

**偏差来源（逐条）**：
1. **采样窗口错位**：外部采样只能"近似对齐"进程窗口；不一致时**必出假偏差**。
   本 run 第一次尝试就踩到（外部时长 = 进程窗口 ⇒ 采到窗口之外的段，比值 0.000）；
   修正为 `WIN - SETTLE - 8` 后比值即收敛到 ±1%。
2. **TID 新生/退出**：外部按"两快照都在"的 TID 求和；`state3` 有 34–35 条 worker 线程，
   窗口内若有退出/拉起会漏计（本 run 的 4 轮 `tids_gone/tids_new` 均为 0 ⇒ 该偏差这轮未出现）。
3. **观测器自身开销**：外部只读 `/proc`，自身墙钟占比 **≤0.0036%** 窗口 ⇒ 可忽略。
4. **tick 与 ctx 不同源**（R0-B1）：`tick_count` 是调度器自述，`ctx` 来自
   `/proc/<tid>/status`；两者**不得互相换算**（本 run 只把它们并列，未做换算）。

⇒ 结论：**外部逐 TID 与进程内 `/proc/self/stat` 在本场景下等价（≤1%）**，
可互为独立复核；t31-F2 的"逐 TID + 2×2 反事实"结论**不受读数口径影响**。

## 6. 要求 ⑥：**可判定判据的形态建议**（⛔ 不直接改数值）

基于本 run 的实测，给出三条**形态**建议（数值须由架构负责人按 W00 §11.3/§11.4 流程决定）：

1. **把 CPU 判据改成"tick 率归一化"形态**：
   `cpu ≈ (每项每 tick 成本) × (注册项数) × (tick 率/秒)`，其中
   **每项每 tick 成本**按要求 ③ 的三元组固定后**是稳定的**（state2：11.9–14.8 ns；state3：45.2 ns），
   而 **tick 率**必须**同窗口实测**（⛔ 不用公式）。这样判据对"tick 率抖动"免疫。
2. **分档 + 分态给系数**：`state2` 与 `state3` 的系数**差 3.8×**（§3.3）⇒ 必须分列；
   `n < 500` 的档位含显著固定开销 ⇒ ⛔ 不作 CPU 判据（或显式加固定项）。
3. **对 `state2/n=1000` 单列"不作判据"**：该档**不可稳定测量**（22 次 3.52× 极差、双峰、机制未闭环）
   ⇒ 若必须保留，请给**双峰上界**（本 run 22 次最大 0.18829）+ 明确"以最坏值为准"，
   ⛔ **不得**用中位数或平均值；⛔ **不得**因实测值超过 0.20 就抬高阈值。
4. **`threads` 与 CPU 分列**（R-2c 已解）：状态 1 线程数 ≤8、状态 3 = 34；⛔ 本报告未做任何混谈。

### 9.1 被更正的量纲：列名「每项每 tick」≠ 实测值「每 tick 成本」

§0/§1/§3.2/§3.3/§4.1/§6 的列名写作「**每项每 tick**」（ns per item per tick），
但**实测值实为「每 tick 成本」**（µs per tick）。

**原始算式（逐行归档，⛔ 不改）**：`值 = cpu_cores ÷ tick_rate × 1e9 ÷ 分档自变量 n`。
即除数是**分档自变量 `n`（topic 数）**，而**不是**冻结三元组定义的「**注册项数**」：

- `state2` 各档：`注册项数 = n = 除数` ⇒ **除数正确** ⇒ 数值是**正确的每注册项值**（§9.3 前四行 ✅）；
- `state3`：`注册项数 = 2n = 2000`，而`除数 = n = 1000` ⇒ **除数小了一半** ⇒ 数值被放大 2×；
  又因该格除数恰为 **1000**，`× 1e9 ÷ 1000` 在数值上正好等于 `× 1e6` ⇒
  该格原值（`45.2`）**恰好等于「每 tick 成本」以 µs 计的裸数** —— 这就是「量纲看起来像 µs/tick」的由来。
  ⚠️ **两重巧合都只对 `n=1000` 成立**（若除数 ≠ 1000，原值既不是每注册项、也不等于 µs/tick 裸数）。

| 格 | 原始算式（未变） | 每 tick 成本（实测值真身） | 每注册项（另一口径） |
|---|---|---|---|
| `state2/n=1000` | `0.16705 ÷ 14092 × 1e9 ÷ 1000` | **11.85 µs/tick** | **11.85 ns/项·tick** |
| `state3/n=1000` | `0.26977 ÷ 5903 × 1e9 ÷ 1000` ⚠️ 除数应为 2000 | **45.70 µs/tick** | **22.85 ns/项·tick** |

> ℹ️ 也正因如此，本次更正**不是**「整张表的数字都错」：**出错的只有 `state3` 一格**；
> `state2` 的 `n=1 / 100 / 500 / 1000` 四格数字**本身是正确的每注册项值**（只是列名与 `state3` 格的口径声明不统一）。

### 9.2 为何 `state2` 长期掩盖了它、而 `state3` 暴露了它

**换算关系**（把「每 tick 成本」换成「每注册项」必须**再除一次注册项数**）：

```
每注册项(ns/项·tick) = 每 tick 成本(µs/tick) × 1000 ÷ 注册项数
                     ⇒ 因子 = 1000 ÷ 注册项数
```

- **`state2` 掩盖**：`state2` 的**注册项数恰为 1000** ⇒ 因子 = `1000/1000 = **1.00**`
  ⇒ **两种口径数值上碰巧相等**（`11.85 µs/tick` 与 `11.85 ns/项·tick` 写法不同、数值相同）
  ⇒ 谁也无法靠这一个格子发现口径混用。**这就是它未被发现的原因。**
- **`state3` 暴露**：`state3` 的注册项数 = **2n = 2000** ⇒ 因子 = `1000/2000 = **0.50**`
  ⇒ **45.70 µs/tick ≠ 22.85 ns/项·tick**，两者**恰好差 2 倍**，差异就此暴露。
- **同时 `n=1000` 又造出第二重巧合**：`state3` 的除数恰为 1000 ⇒ `×1e9÷1000` 数值上等于 `×1e6`
  ⇒ 该格原值（`45.2`）**恰好等于「每 tick 成本」的 µs 裸数** ⇒ 列名与数值看起来"自圆其说"。
  ⚠️ **两重巧合都只对 `n=1000` 成立**（若 `n ≠ 1000`，原值既不是每注册项、也不等于 µs/tick 裸数）。

> ℹ️ **顺带排除一个常见误读**：`windows.csv` 的 `routes` 列在 `state2` 为 **0**
> （无发布者 ⇒ 无有效 route 入池）、`state3` 为 1000 ⇒ **不能用 `routes` 当「注册项数」**。
> 冻结三元组定义的**注册项数**是 `state2 → n`、`state3 → 2n`，这也是本更正的关键前提之一。

### 9.4 量纲机械复核式（两式**恒不相等**，差一个「注册项数」因子）

```
每 tick 成本(µs/tick) = cpu_cores ÷ tick_rate × 1e6
每注册项(ns/项·tick)  = 每 tick 成本(µs/tick) × 1000 ÷ 注册项数

⇒ 每注册项 = 每 tick 成本 × 1000 ÷ 注册项数      ← 两式相差因子 (1000 ÷ 注册项数)
```

- `state2`：`11.92 × 1000 ÷ 1000 = 11.92` ⇒ **恒等**（因子 = 1，**故不可用于判别**）
- `state3`：`45.16 × 1000 ÷ 2000 = 22.58` ⇒ **≠ 45.16**（因子 = 0.5，**差 2.00×**）

**误判量级**：若照抄原值 `45.2` 当作「每项每 tick 成本」代入
`cpu ≈ 每项每 tick 成本 × 注册项数 × tick 率`：

```
45.2e-9 × 2000 × 5903 = 0.5336  core
实测                   = 0.26977 core
⇒ 高 1.98×（≈ 差一个「注册项数/1000」因子 = 2.00×）
```

⇒ **新判据一上线就会把 `state3` 的正常读数误判为「超标约 2 倍」**。该错误**在落地前被 t49 拦下**。
