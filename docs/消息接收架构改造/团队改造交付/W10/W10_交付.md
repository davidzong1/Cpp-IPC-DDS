## 1. 逐 route 收发台账（本包的核心交付，回答 W07 留下的缺口）

### 1.1 为什么必须自建

W07 的 `sent=20/received=20` **只来自 `subs[0]` 一条 route**（`test/test_socket_high_fd.cpp:330-334`）。
方案 §13.2 第 2 条要求 `valid_rx_count == expected_count` 且**每条 route 至少收到规定数量序号并完成载荷校验**。
⇒ 本工装的核心不是"总共收到多少"，而是**逐 route 的台账**。

### 1.2 台账字段（`ledger.csv`，每 route 一行）

`route, registered, planned, sent, rx, dup, out_of_order, corrupt, timeout, rx_after_silence, first_packet_ok, first_packet_us`

### 1.3 载荷校验设计（⛔ 不用固定载荷）

每条消息的载荷由 `(route_idx, seq)` **确定性生成**：前 4 B = seq、次 4 B = route_idx、次 8 B = `magic ^ (seq×2654435761)`、其余字节 = `(route_idx×31 + seq×131 + i×7) & 0xFF`。
接收端**逐字节重算**校验；不通过即计 `corrupt`。⛔ 固定载荷会把旧帧与内容损坏一起放过（§10.7）。

### 1.4 千路 SHM 结果（`shm-ind-1000/`）

```
registered_count=1000/1000 threads_after_create=34 create_ms=692.8 fds_open=5 max_fd=4
pool_routes_alive=1000 socket_pool_routes_alive=0 (registered=1000)
valid_rx_count=1000/1000 dup=0 corrupt=0 out_of_order=0
recover silence_ms=3000 rx_after_silence=5 first_packet_ok=1 lost=0
counters fallback_total=0 ... wait_set_full=0 wait_token_invalid=0 chunk_exhausted=0
worker_path_count=1000 compat_total=0 fallback_count=0 path_choice=0 reasons=
routes_before_destroy=500 routes_after_destroy=0 threads_after_destroy=4 fds_after_destroy=4
```

**逐 route 台账统计**：1000 行全部 `registered=1`、`rx == planned`、`dup=0`、`corrupt=0`、`timeout=0`、`out_of_order=0`。

### 1.5 fd 与内存对账（§13.2 条件 6）

| 项 | 实测 | 判据（W00 §6.2 第 6 行） | 判定 |
|---|---|---|---|
| SHM 千路 fd | 创建后 `fds_open=5 / max_fd=4`（SHM 不走 fd） | ≤ 3.5 fd/route | ✅ |
| socket 100 路 fd | `fds_open=468 / max_fd=467` ⇒ **4.68 fd/route** | ≤ 3.5 fd/route | ⚠️ **超判据**（socket 侧：每订阅者约 2 个数据 fd + 预占；W07 千路实测 2068 fd = 2.07/route，本工装因 ACK 通道多一组 fd） |
| 销毁后回收 | `routes 500→0`、`fds 5→4` | 回可解释基线 | ✅ |

> ⚠️ socket fd/route 高于 3.5 判据的原因已定位：本工装每条订阅同时建**数据通道 + ACK 通道**两组 socket（`socket_pub_sub_ipc.cc:1006-1013`），而 W07 的读数来自单一数据通道口径。两者的差异属**口径不同**，本报告如实分列，⛔ 不据此判「fd 超预算」。

## 3. 门槛 3（空闲 CPU / 切换）—— 千路三态实测（W00 §11.3 P-2 的收口输入）

### 3.1 三态分列（n=1000，60 s 窗口，逐 TID ctx 聚合）

| 状态 | 含义 | threads | CPU (core) | ctx (s⁻¹·进程⁻¹) | 判据（W00 §11.3 R-2） |
|---|---|---|---|---|---|
| **1** `no_registered_route` | 无注册 route | **2** | **0.00000** | **0.0** | `threads ≤ 8`、`idle_exits` 增长 ✅ |
| **2** `registered_no_publisher` | 已注册未连接 | 2 | 0.12–0.29 | 5032.6 | — |
| **3** `connected_silent` | 已连接、有效订阅、停止发布 | **34** | **0.583** | **9101.1** | `threads == 33 ± 编排`、`idle_exits==0` ✅ |

**状态 3 的 `idle_exits=0` 是本报告的关键断言**：worker **保持接收能力**，⛔ 不回落到 ≤8 线程（这正是 R-2 三态分列的由来）。

### 3.2 空闲 CPU 归因（把 0.58 core 拆开）

| 分量 | 实测 | 依据 |
|---|---|---|
| **控制面**（`ShmControlScheduler`，2000 项） | **0.069 core**（`mean_tick 15.5 µs`、`wakes 4426 /s`） | `w10_tickcost` |
| **RecvWorker 池**（32 worker × 每 100 ms 超时唤醒 × `collect_pending()` O(route) 全扫） | ≈ **0.51 core** | `w10_threadscan` |
| 与 `N_worker` 的关系 | **几乎无关**：4/8/16/32 worker 均 ≈0.51–0.52 core @1000 route | `w10_threadscan` |
| 与 route 数的关系 | **近似线性**：100 → 0.039、500 → 0.30、1000 → 0.51 core | `w10_threadscan` |

⇒ **空闲 CPU 的主成本是「route 总数 × 唤醒次数」的扫描成本**，而不是 worker 数或线程数（与 §10.2 的口径一致）。

### 3.3 回溯门槛 3 修订式 R-1 的**两项输入**（本包实测发现其中一项高估 13–36×）

R-1（架构负责人 t23/D-15 采纳）为：`⌈N_worker × 1000/wait_timeout + Σ_在册控制项 1000/heartbeat⌉ × 1.5`。

| 输入项 | 实测 | 与公式的偏离 |
|---|---|---|
| `N_worker × 1000/wait_timeout` ∈ {100 ms} | **320 /s**（`wait_timeouts = 320 / 10 s`） | ✅ 与 324.3 /s 的 ctx 自洽 |
| **`Σ_在册控制项 1000/heartbeat`** | 1000 sub + 1000 pub ⇒ 公式 **120000 /s**，实测 **1.5–4.6 k /s** | ⚠️ **公式高估 13–36×** |

**原因（`w10_wakescan` / `w10_mixwake` 标定）**：调度器把**同一批到期项合并到一次 tick** ⇒ 唤醒率由"到期分组的分散度"决定，`Σ` 只是**理论上界**：

```
entries=1    → 100.0/s（公式 100.0/s，比值 1.00）
entries=100  → 100.3/s（公式 10000/s，比值 0.01）
entries=1000 → 353.6/s（公式 100000/s，比值 0.00）
sub=1000+pub=1000 → 1539.8–4139.7/s（公式 120000/s，比值 0.013–0.034）
```

⇒ **请求架构负责人按 §11.3 追加修订 R-1 的控制面项**：`Σ` 应改为**实测唤醒率上界**（本 run 给出 `wakes ≤ ~4.6 k/s @2000 项`），否则该项会让预算被算松 1–2 个数量级。⛔ 本包**不改** W00 §6.2 任何数值，只提供依据。

### 3.4 与门槛 3 预算的对照（如实分列，不做「达成/未达成」结论）

| 版本 | 阈值 | 本 run 实测 | 判定 |
|---|---|---|---|

### 5.1 缺陷 ② 的完整取证链（本包新增，**阻塞级**）

```
现象：w10_matrix --transport socket --topology independent --n 1000  →  rc=124（timeout 420 s 后被杀）
      30 s 内 373–479 行 "Failed to connect subscriber,reconnect 1fter 1 second"
定位：topic #38 的端口 = udp_discovery_port_calculate("w10_socket_independent_3103_38", 3103) = 48650
      ss -uln 显示 0.0.0.0:48650 已被【别的进程】(未开 SO_REUSEADDR) 占用
机制：UDPNode::connect() 用 SO_REUSEADDR|SO_REUSEPORT 绑【组地址】:PORT（udp.h:172-196）
      占用者未开 SO_REUSEADDR ⇒ bind 必 EADDRINUSE ⇒ connect() 返回 false
      socket_sub_ipc::InitChannel:  while (!subscriber_->connect()) { sleep(1s); }   ← 无上界、无诊断
A/B 反事实（port-conflict/ab_counterfactual.log）：
      STEP1 占用者 bind 0.0.0.0:36162（不开 REUSEADDR）
      STEP2 占用者在位时 dzIPC 式 bind 224.0.0.87:36162 ⇒ EADDRINUSE   ← 阻断成立
      STEP3 释放占用者后 dzIPC 式 bind ⇒ ok                            ← 因果成立
碰撞面（w10_portconflict_scope）：
      ip_local_port_range = [32768, 60999] 与 dzIPC 端口窗口 [11451, 65531] 大范围重叠
      ⇒ **50.9–52.0% 的话题接收端口落在内核临时端口区间内**
      （含本工程自己的 SendOnly ACK 套接字，udp.h:169 明确"不 bind" ⇒ 用临时端口）
逐话题复算：domain=3103 的 1000 路里 **12–13 路**与"本机已占 UDP 端口"冲突
```

**归属建议**：端口公式、bind 方式、无界重试**全部在既有 `libipc`/socket 模块**，与本轮固定 worker 改造无关。
⛔ **本包结论**：按 §13.2 末句，「**1000 路 socket 有效收发**」**本轮不能声明通过**（现有 100 路通过，千路被该缺陷阻断）。
建议由 socket 模块侧修复（**至少有界重试 + 可识别诊断**，不要求改端口公式）。

### 11.1.4 更正后的正确表述

| 分量 | 更正前（§3.2 原表述） | **更正后（实测）** | 依据 |
|---|---|---|---|
| 控制面 `ShmControlScheduler` | 0.069 core | **0.29 core @1000 项 / ≈0.59 core @2000 项** | `state2_scale` + A 格逐 TID |
| `RecvWorker` 池 `collect_pending()` | **≈0.51 core（主成本）** | **≈0（池整体停用后 CPU 不降反升）** | C 格 vs A 格，3 轮复现 |
| `N_worker` 依赖 | 「几乎无关」 | 结论**保留**，但**原因不同**：池本身不是成本项 | 4/8/16/32 worker 均 ≈0.51–0.52（r25） |

⇒ **正确结论**：空闲 CPU 的**主成本是「在册控制项数 × 每项控制成本」（控制面 tick）**，
不是 `collect_pending()` 的 O(route) 全扫。池在该窗口内 `recv_once_calls=0`、
`wait_timeouts ≈ 19200/60 s`（= 32 worker × 10/s），量级仅 10³ 次 seq 读/秒，**撑不起 0.5 core**。

**原 §3.2 的 `w10_tickcost` 读数（0.069 core）为何低**：该工具用**空回调**测 tick 自身开销
（`mean_tick 15.5 µs`），而真实负载下每项都要跑 `on_sub_heartbeat()`（含控制面读写、peer 心跳）。
⇒ 两者**不可比**，原报告把「空回调 tick 成本」与「池成本（错误地估为 0.51）」相减得到 0.51，
属**双重错误**（池高估 + 控制面低估）。该算术差在 §3.2 表格里表现为「0.583 − 0.069 ≈ 0.51」，
本质是**把差额默认归给了池**，缺少反事实检验。

## 11.5 F4（medium，纪律项）—— 本 run 横跨两个工装世代，**不可原样重放**

- **现象**：`fingerprint.txt`(19:19) 记 `w10_matrix` = `c3459700…`；`gate3/harness_fingerprints.txt`(20:38)
  记 `b56e7f39…`；即 r25 内**两批产物用了不同二进制**。且工装二进制早于库（库在 21:17 被再次重建）。
- **复核者实测**：用**当时树上**的 `build/bin/w10_matrix` 复跑任意 SHM 臂 ⇒ **6/6 rc=139（SIGSEGV）**，
  栈 `__GI___libc_free ← main()`，发生在 `run()` 返回**之后**；**同源重编后 rc=0**。
- **我的复现结果（如实登记一处与复核者不同）**：
  - **"当前树上二进制会 rc=139" 我未能复现**：t36 开始时 `build/bin/w10_matrix` = `1876ad2c…`，
    直接 `--topology independent --n 10` ⇒ **rc=0**（该二进制与当时的库已经是配对状态 —— 我与
    t29/t30 的并发重编已把它更新过）。⇒ 复核者所处的**更早时间点**（工装早于库）我无法回到。
  - **我改从"构造"路径独立复现 ABI 机制**（见下条），并额外确认：**同源重编后仍 rc=0**
    （我重编全部 7 个工装，`w10_matrix` 哈希**不变** = `1876ad2c…`，说明构建确定性）。
  - ⇒ 结论与复核者**同向**（库一变、工装必须重编），但**判据来自构造复现**，不是来自复现其 rc=139。
    ⛔ 如实标注：`rc=139` 是复核者的现场读数，我**未独立复现该信号**。
- **ABI 形态（t30 同源）**：`RecvWorkerPool::stats()` **按值返回** `RecvWorkerStats`；**t30 在该结构体
  尾部追加了 5 个 `uint64`**（`scan_rounds`/`scanned_routes_total`/`scan_ready_rounds`/`deferred_depth_last`/`deferred_depth_max`）。
  C++ by-value 返回由**调用方**按**调用方看到的**大小分配返回槽 ⇒ 旧调用方（旧头）+ 新库 = **越界写**。
  **我构造了最小复现**（`artifacts/perf/20260929-r25-W10/abi_f4/`）：

  ```
  # 旧头 = 当前头截掉 t30 追加的 5 个 uint64；同一新库
  $ g++ -I <旧头> abi_old_caller.cpp -L build/lib -lipc ⇒ 可编译可链接（符号名一致，这正是危险处）
  $ ./abi_old_caller
    sizeof(RecvWorkerStats) [old header] = 136     ← 当前头为 176
    stats.route_count=0 wait_timeouts=0
    guard_clobbered=4                              ← 返回槽之后的哨兵被越界写坏
  $ ./abi_crash   （连续 64 次按值取 stats）
    *** stack smashing detected ***: terminated    3/3 rc=134（SIGABRT）
    gdb: SIGABRT ← __GI_abort ← __GI_raise ← __GI___pthread_kill
  ```

  ⇒ 崩溃点随优化与栈布局而变（复核者现场见 `rc=139 __libc_free ← main`；我构造复现见
  `rc=134 *** stack smashing detected ***`，另一变体 `guard_clobbered=4` 但 rc=0）
  ⇒ **判定依据是 ABI 形态本身**（by-value 返回 + 尾部追加字段 + 陈旧调用方），不是某个具体信号。
  两个信号（139/134）与"哨兵被写坏"三者指向同一形态，互为印证。
- **写进报告的纪律（R0/R3 输入）**：
  1. **引用 r25 证据时必须同时引用「当时的库指纹 ↔ 当时的工装二进制指纹」配对**；

     r25 的 `gate3/repro` 批（20:35–20:53）是 **`b56e7f39…`**。⛔ 两者不得混用。
  2. **库变更后必须重编全部工装**；`w10_repro.sh` 应加首步一致性检查（本 t36 未改脚本属他包射程，已登记为后续项）。
  3. ⛔ **不得声称「本 run 可原样重放」**；正确的说法是「同源重编后可复现」。
