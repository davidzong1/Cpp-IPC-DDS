## 1. 复验矩阵（方案 §6.3）

**每个配置一个独立进程**：池的 worker 数是"首个成功 `start()` 的调用方"**一次性**决定的
（契约 §8.1），同进程跑多档会串档。domain 逐 run 唯一（SHM 段名与 domain 绑定，避免残留段互见）。

| 组 | 配置 | 轮数 | 目的 |
|---|---|---|---|
| **A 主对照** | state 3 × n∈{1,100,500,1000} × diag∈{off,on} | **5 轮/格**（共 40） | 方案要求"主要对照至少 5 轮"；diag 交替采集 |
| **B 三态补齐** | state∈{1,2} × n∈{1,100,500,1000} × diag∈{on,off} | 1 轮/格（共 **16**） | 三态必录（含 diag 开/关两面） |
| **C 有效消息负载** | state 3 + 持续发布（5 ms 周期）× n∈{1,100,500,1000} × diag∈{off,on} | 2 轮/格（共 16） | "有效消息负载"对照（有真实就绪） |
| **D worker 对照** | W∈{4,8,16,32} × n=1000 × diag=on | 2 轮/格（共 8） | 单独实验；W=4 为**容量受限档** |

固定主配置：**32 worker**；空闲窗口 **60 s**（实测 `wall_s = 60.00–60.05`）。

**worker 对照的两支判据**（方案 §6.3）：

| 档 | 容量 127×W | 窗口 `routes` | 判据 | 实测 |
|---|---|---|---|---|
| 不受限 W=8/16/32 | ≥1000 | **1000** | `residual == 0` | ✅ 全部 1000 归属 worker |
| **受限 W=4** | **508** | **508** | `residual == overflow == 492` | ✅ seam 报文证实 492 条走显式回退 |

W=4 的原始证据（`D-W4-capacity-limited.md`）：
`shm recv worker unusable (wait_set_full (per-worker 127 token capacity exceeded)); receive on per-topic compat thread`，
且该 run `recover_ok_routes = 1000/1000`（回退线程接住）⇒ **规模语义未被容量边界破坏**，只是线程账不同
（`scan/round = 127.000` 正是每 worker 满载 127 条的证据，⛔ 不是"应该 250 却只有 127"）。

差异只在 CPU（0.128 vs 0.147，同批噪声范围内）与门控量是否采集。

（定版 `r40` 的 `state 2` 采用了 `settle 4 s` ⇒ 窗口内线程已归还，故线程列与 CPU 列反映**纯控制面**；
`state 2` 的 n=1/100/500 分别为 0.00167/0.00533/0.03547 core，控制项 1/100/500。
第一代 `r38` 未加 settle ⇒ 窗口内 32 条线程**全部退出**（`window_idle_exits=32`、`threads=2`、
CPU 0.16 core 含退出瞬态）—— 该差异正是本次加 `--settle-s` 的目的：**把控制面与线程退出瞬态分开**。）

> ⛔ **不得以"线程数少 / CPU 低"代替有效订阅的成绩**。状态 3 的"有效订阅"由**逐 route 确认帧**证明：
> 1000 个 route 各发一条 `CF<i>` 并**逐字节校验**收回 ⇒ `confirm confirmed=1000/1000 missing=0`，
> 且每个 route 的确认首包延迟都落盘（`confirm_first_packet_us`，数组长度 = 1000，⛔ 不缩短数组）。

**状态 3 的恢复**（方案 §10.1 强制用例，⛔ **不重新注册**）：静默 60 s（≫ keep-alive：wait 100 ms / idle 1000 ms）
后原发布者恢复发送 ⇒ 实测 `recover ok=1000/1000 lost=0`，**`recover_first_packet_us` 数组长度 = 1000**（逐 route 记录，
缺项写 -1 并在 `recover_missing_routes` 单列）。⇒ 「已连接 → 静默 → 恢复」全链路成立。

**状态 2 的一个可解释现象**：窗口内 32 条 worker 线程**全部按需退出**（`window_idle_exits=32`、`threads=2`）——
因为状态 2 的订阅者**没有发布端**，控制面无 peer ⇒ route **不进 worker 池**（`worker routes=0`）⇒
route 表为空 ⇒ 空闲线程按 `idle_keep_alive=1000 ms` 归还。这与状态 1 的区别正是**控制项 0 vs 1000**（不是线程数）。

**状态 1 的一个可解释现象**：窗口内线程退出为 0、累计 idle_exits=32 —— 因为在进入窗口**之前**
（`pubs/subs` 析构后、settle 阶段）32 条线程就已归还完毕；窗口内已无可退线程。

## 3. 五项派生值（同一窗口差值）

**主对照 A 档（定版 `r40`：state 3 静默、diag=on、**5 轮**均值 [min,max]）**：

| n | 平均每轮扫描条目 | 平均每轮扫描耗时 | 平均每条目扫描耗时 | 发现就绪的轮次占比 | 每秒等待超时 |
|---|---|---|---|---|---|
| 1 | 1.000 [1.000, 1.000] | 449.7 ns [379.7, 519.0] | 449.7 ns [379.7, 519.0] | 0.0000 | 0.0100 |
| 100 | 3.125 [3.124, 3.126] | 460.6 ns [453.9, 476.1] | 147.4 ns [145.2, 152.3] | 0.0000 | 0.3198 |
| 500 | 15.626 [15.625, 15.627] | 966.0 ns [912.1, 1024.6] | 61.8 ns [58.4, 65.6] | 0.0000 | 0.3199 |
| 1000 | 31.251 [31.250, 31.251] | 1649.2 ns [1487.3, 1762.2] | 52.8 ns [47.6, 56.4] | 0.0000 | 0.3199 |

（第一代 `r38` 的同格读数：1.000/3.125/15.624/31.250（scan/round）、370.4/475.8/1077.9/1727.0 ns（ns/round）、
544.6/152.2/69.0/55.3 ns（ns/entry）、0.0151/0.3198/0.3198/0.3198（to/s）—— **两代同格一致到 1% 以内**，
可作为复现交叉检查。）

**关键读数与读法**：

1. **`平均每轮扫描条目` ≈ n / 32**（1→0.68、100→3.125、500→15.624、1000→31.250）——
   即每个 worker 只扫**自己那一份** route（『全池平均每轮条目数**不等**全池 route 数』，方案原文的告诫得到实测支持）。
   若把全池 n 当作每轮扫描量代入，会把扫描成本**高估 ~32 倍**。
2. **`平均每条目扫描耗时` 随 n 下降**（544.6 → 55.3 ns）：n 越大，每轮扫的条目越多、`clock_gettime` 的
   固定开销被摊薄 ⇒ 该量**不是常数**，引用时必须带 n。
3. **`发现就绪的轮次占比 = 0`** 在状态 3 静默窗口下是**正确**结果（无消息 ⇒ 无新 seq ⇒ `queued==0`）。
   负载档（C）对照给出非零值：**0.2439–0.3313**（§5.2）⇒ 说明该项**不是恒 0 的坏计数器**。
4. **`每秒等待超时` = 0.3198 @n≥100** = 32 worker ÷ 100 ms × 1 s ⇒ 与冻结预算 `wait_timeout=100 ms`
   逐值吻合，且**与 n 无关**（超时是"没有事件"的轮次数，与 route 数无关）。

**diag=off 档**（⛔ 关键读法）：

| n | 平均每轮扫描条目（常驻） | 平均每轮扫描耗时 | 平均每条目扫描耗时 | 发现就绪占比 | 每秒等待超时（门控） |
|---|---|---|---|---|---|
| 1 / 100 / 500 / 1000 | 0.680 / 3.125 / 15.625 / 31.251 | **`null`** | **`null`** | 0.0000（常驻） | **`null`** |

⇒ 三门控量在诊断关闭时**标为"未采集"（`null`）并给出原因**，⛔ **不得**解释为零成本
（`null_audit.txt` 逐项列出原因：`诊断关闭 ⇒ 未采集` 与 `routes=0 ⇒ 分母为 0` 两类可区分）。

**两项常驻量在 diag=off 下仍可用**（这是本任务新增的"常驻孪生"价值）：

| n | 平均每轮扫描条目（常驻） | 每秒等待超时（常驻孪生 `wait_timeouts`，列名 `resident_wait_timeouts_per_s`） |
|---|---|---|
| 1 | 1.000 | 0.0100 |
| 100 | 3.125 | 0.3198 |
| 500 | 15.626 | 0.3199 |
| 1000 | 31.250 | 0.3199 |

⇒ 关诊断时"发现就绪占比"与"每秒超时"**仍可判**（前者用 `scan_ready_rounds`，后者用常驻孪生），
只有「扫描耗时」必须开诊断 —— 这正是 §6 结论的依据。⛔ 但引用常驻孪生时必须写明列名，
不得与门控 `wait_timeout_count` 混用（两者虽同口径，但**一个是未采集、一个恒采**）。

## 4. 运行时门禁（方案 §6.2）逐条

有 route 的有效采样窗口内（diag=on 共 **9 条**，diag=off 共 **7 条**，全部 ✅）：

| # | 门禁 | 依据 |
|---|---|---|
| 1 | `Δscan_rounds > 0` | 空转也在按轮扫描 |
| 2 | `Δscanned_routes_total > 0` | 真实遍历发生 |
| 3 | 扫描时间有效（`Δscan_time_ns_total > 0`，仅 diag=on） | 门控面确实在写 |
| 4 | `0 ≤ Δready_observed ≤ Δscan_rounds`（门控） | 分子不超过分母 |
| 5 | `0 ≤ Δscan_ready_rounds ≤ Δscan_rounds`（常驻） | 同上（常驻面） |
| 6 | deferred 深度非负 | `deferred_depth_last/max ≥ 0` |
| 7 | deferred 深度 ≤ 在册 route 数 | 深度不可能超过候选总数 |
| 8 | 常驻/门控同窗口自洽 | diag=on 时两侧**逐值相等**；diag=off 时门控恒 0 |
| 9 | 门控 `Δwait_timeout_count` 与常驻 `Δwait_timeouts` 同口径 | 同一 `wait()` 返回点 |
| **10** | **`Δscanned_routes_total ≤ Δscan_rounds × routes`**（本次新增） | 每轮至多扫 `routes` 条 ⇒ 上界可算 |
| **11** | **扫描量同向（rounds 与 scanned 同时为 0 或同时 >0）**（本次新增） | 挡住"不可能读数" |

> 门禁 10/11 是 **t38 采集后**新增的（触发原因见 §7）：原门禁只能发现"两者都为 0"，
> 无法发现"`Δscanned=660000` 而 `Δscan_rounds=0`"这种**内部不自洽**。
> ⛔ 「`rg` 找到调用点」或「schema 出现字段」**不算完成** —— 本任务全部以**运行期读数**判定。

## 5. 扫描成本 vs 控制面成本（**分开陈述**）

> ⚠️ 队长提示（必须遵守）：t31 的 F2 已推翻「扫描是空闲 CPU 主因」的旧归因（真凶是 `ShmControlScheduler`）。
> ⇒ 本节**单列**扫描成本，与控制面 CPU 分开，⛔ **不**把扫描成本当作 CPU 达标/不达标的唯一依据。

### 5.1 扫描成本（本任务的口径）

| 量 | 来源 | 值（定版，n=1000，W=32，静默 60 s 窗） |
|---|---|---|
| 每轮扫描条目 | `Δscanned/Δrounds` | **31.251**（= 1000/32） |
| 每轮扫描耗时 | `Δscan_time_ns/Δg_rounds` | **1649 ns**（5 轮 [1487, 1762]） |
| 每条目扫描耗时 | `Δscan_time_ns/Δscanned` | **52.8 ns**（5 轮 [47.6, 56.4]） |
| 扫描轮数/秒 | `Δrounds/wall` | **≈352 轮/s 全池**（21128/60） |
| 扫描总时长/秒 | 轮数/s × 每轮耗时 | ≈ **0.58 ms/s** ≈ 0.00058 core 当量（⛔ 见下方警告） |

⇒ 诊断开启的 CPU 代价落在 **0.004–0.012 core @n=1000**（≈1.5–4.7%），与 W03 采集器的
`scan_scope_disabled_ns=0.46` vs `enabled_ns=37.8`（每轮 +37 ns × 352 轮/s ≈ 0.013 ms/s）量级一致。
**结论：诊断开销小但**非零**；是否默认开启取决于"是否需要扫描耗时"这一项（见 §6）。

### 5.3 控制面 CPU（**单列**，仅供 t32/R6 取用；本任务不做门槛判定）

`state 2`（只建订阅、**无发布端** ⇒ 池内 route=0、线程 2 条、`settle 6 s` 让空闲线程先退完）
⇒ **纯控制面**读数：

| 在册控制项 | CPU（本进程 `/proc/self/stat`） | 控制面唤醒率 | 每项成本 |
|---|---|---|---|
| 1 | **0.00167 core** | 100 /s | 1667 µcore/项 |
| 100 | **0.00533 core** | 919 /s | 53.3 µcore/项 |
| 500 | **0.03547 core** | 4827 /s | 70.9 µcore/项 |
| 1000 | **0.12773 core** | 12173 /s | 127.7 µcore/项 |

（定版为 `state 2` + `settle 4 s`；早期 `settle 0/2/6/12 s` 四档实测 0.161/0.144/0.163/0.116 core，
⇒ 该读数对 settle 与窗口长度**敏感**，引用时必须带口径。**控制面成本随控制项非严格线性**
（每项 53.3 → 70.9 → 127.7 µcore/项），与 t36-F2「主成本在控制面」的结论方向一致；
⛔ 但与本任务 §8 登记的不一致仍需 t32/R6 用单一工装复核。）

### 5.4 两条归因**分开**的结论

1. **扫描成本**：n=1000 静默窗下每轮 1649 ns × 352 轮/s ≈ 0.58 ms/s；外部实测该配置**整进程** 0.276–0.283 core，
   ⇒ 扫描**不可能**是这 0.276 core 的主项（量级差约 3 个数量级）。
2. **控制面成本**：仅控制面（state 2、route=0）在 1000 项时**已 0.128 core**，且唤醒率 12173/s
   ⇒ 与 t31-F2 的结论一致（主成本在控制面 tick，不在扫描）；同窗口 state 3 的唤醒率降到 6497/s
   （有 1000 条 route 时调度器的合并批量更大），而 CPU 升到 0.241–0.251 core。
3. ⛔ 因此本报告**不**给出"扫描是否达标"的判定；只给出扫描成本的**单列读数**，
   并注明它是控制面成本的**次级项**。

## 6. 「诊断默认口径」结论（t30 建议的裁定）

**结论：同意 `diagnostics_enabled=false` 作为 W12 默认口径。** 依据：

| 判据 | 证据 |
|---|---|
| 覆盖度 | 常驻面覆盖 §10.2 五项的 **4 项 + 等待超时**（`scan_rounds`/`scanned_routes_total`/`scan_ready_rounds`/`deferred_depth_last,max`/`wait_timeouts`）；只有**「扫描耗时」**必须开诊断（它是唯一需要两次 `clock_gettime` 的量，W03 实测关 0.176 ns/轮 vs 开 29.3 ns/轮） |
| 自洽性 | `diag=on` 时常驻与门控**逐值相等**（§4 门禁 8，四档全部 ✅）⇒ 关诊断不会让常驻面"漂移" |
| 代价 | 开诊断的 CPU 代价 **+0.004~0.012 core @n=1000**（§5.2），并**不显著**；但会引入每轮两次时钟读取 |
| 正式窗口纪律 | 既有纪律（W08 先例）在正式性能窗口关诊断；若默认开，会与既有窗口口径冲突 |
| 可判定性 | §10.2 的"运行时门禁"要求 `scan_rounds>0`/`scanned_routes_total>0` —— **这两条在关诊断时仍可判**（常驻面）；只有"扫描时间有效"需要开诊断 |

**配套要求（写进 W12 口径）**：
1. 关诊断时，**任何门控量必须标 `null`（未采集）+ 原因**，⛔ 不得写 0、不得解释为零成本；
2. 需要"扫描耗时"的场景（≙ R6/G3 的详细采样）**显式**开诊断，并在 manifest 里记录 `diagnostics_enabled=true` 与判据版本；
3. 引用扫描量时必须同时给出 `diagnostics_enabled` 与该 run 的 `lib_sha256`/`tool_sha256`。

## 7. 异常轮审计（F4 / R0-A1 纪律）——1/72

### 现象
| 项 | 值 |
|---|---|
| run | `A-st3-n1000-diagoff-r3`（st=3、n=1000、W=32、diag=off、round=3） |
| 时间 | 2026-09-30 **04:48:23** |
| 读数 | `Δscan_rounds = 0` 而 `Δscanned_routes_total = 660000`、`Δwait_timeouts = 19200`、`cpu = 0.2916` |
| 判定 | **rc=1**（门禁「有 route 时 Δscan_rounds>0」未过）⇒ 工装**没有**把它放过 ✅ |

### 为什么这是**采集纪律**问题（不是"产品缺陷"）
1. **内部不自洽本身就是判据**：`scan_rounds.fetch_add(1)` 与 `scanned_routes_total.fetch_add(scanned)` 是
   `recv_worker.cc:257-258` 的**相邻两条语句**。出现 `Δscanned = 660000`（= 3300 轮 × 200 条）同时
   `Δrounds = 0`，在源码上**不可能** ⇒ 只能是"增量没被读对"。
2. **同 sweep 期间库被并发重建**（时间线，全部来自文件 mtime）：
   | 时刻 | 事件 |
   |---|---|
   | 04:24:01 | 本工装编译完成 |
   | **04:30:39** | `build/src/CMakeFiles/ipc.dir/dzIPC/shm_pub_sub_ipc.cc.o` 被重编（随之重链库） |
   | **04:48:23** | **异常轮发生**（落在两次重建之间） |
   | **04:56:10** | `recv_worker.cc.o` 再次重编并重链库 |
   ⇒ 违反 **R0-A1**（按值返回结构体 + 追加字段 ⇒ 所有引用方**必须随库重编**）。
3. **复跑不可复现**：用**重编并断言指纹**的工装对同一配置复跑 **9 轮**：
   `Δrounds = 21120 / 21120 / 21092 / 21106 / 21100 / 21116 / 21106 / 21104 / 21106`，
   `Δscanned ≈ 659114–660000`，**9/9 全绿且内部自洽**。

### 处置（本次已落地，作为 R0-A1 的工装侧闭环）
1. `w10_r5_matrix` 新增**运行时指纹自证**：
   - 开跑前从 `/proc/self/maps` 取**实际加载库**路径算 sha256；`--require-lib-sha256` 不符 ⇒ rc=1、不出结论；
   - 收尾**再算一次**，若运行期间库被替换 ⇒ 直接判失败并写入门禁失败清单；
   - `manifest.json` 落盘 `lib_sha256` / `tool_sha256`（每个 run 自证）。
2. 新增两条**内部自洽**门禁（§4 门禁 10/11），把"不可能的读数"挡在门外。
3. `w10_r5_sweep.sh` 每个子运行强制带 `--require-lib-sha256`，并记录逐 run 指纹 + 跨 run 漂移检测。
4. **原始证据保留**（⛔ 不删、不覆盖），本审计单独标注"不作数"。

> ⛔ 引用纪律（重申）：引用任何 run 读数必须同时给出**该 run 自己 manifest 里的 `lib_sha256`/`tool_sha256`**；
> ⛔ 不得跨库版本引用，⛔ 不得把本异常轮计入通过率。

## 8. 与控制面 CPU 读数的**一处不一致**（如实登记，归属 t32/R6）

同一台机器、同为 `state 2`（只建订阅、无发布端）、n=1000：

| 工装 | 库/工装 | 窗口 | 读数 | 调度器 tick 唤醒率 |
|---|---|---|---|---|
| `w10_idle --state 2 --cpu-only`（t36 期间） | 库 `e1c2a7e9…` | 60 s | **0.293 core** | 14339 /s |
| `w10_idle --state 2 --cpu-only`（**本次**） | 库 `558f47ed…` | 30 s | **0.293 core** | 14339 /s |
| `w10_r5_matrix --state 2`（第一代 r38） | 库 `558f47ed…` | 30 s，settle∈{0,2,6,12} | **0.116–0.163 core** | ctx 11005–14659 /s |
| `w10_r5_matrix --state 2`（**定版 r40**，settle=4 s） | 库 `558f47ed…` | 60 s | **0.12773 core**（n=1000） | tick 12173 /s、ctx≈14622 /s |

⇒ **两个工装对"同一形态"给出约 2 倍的差异**（`w10_idle` 0.293 vs `w10_r5_matrix` 0.128），
但**调度器唤醒率一致**（≈1.2–1.4 万/s）⇒ 差异不在"调度器干了多少轮"，而在别的路径。
两者都是进程级 `/proc/self/stat` 口径、窗口内都是 2 条线程。

**我不给出结论**（⛔ 超出本任务边界），只登记**候选原因**供 t32/R6 复核：
1. `w10_r5_matrix` 在窗口前还有 `handshake`/`confirm` 阶段（对本档虽为空操作）与一次 `settle`，
   而 `w10_idle` 的窗口前只 sleep 2 s；
2. 两者对 `ShmControlScheduler` 的**触碰方式**不同（R5 在 `state 2` 下用 `cp.open(...)` 逐 topic 轮询过控制面，
   `w10_idle` 只读一次 `peer_count()`）——开启过的控制面板可能影响调度器的 peer 扫描路径；
3. 30 s vs 60 s 窗口对"启动突发"的摊薄程度不同（t36 已记录启动期 tick_max 达 2.5–4 ms）。

⛔ 本报告**不**据此修改任何门槛，也**不**据此否定任一读数；t32/R6 需用**单一工装**在**同一库**上重采后再定论。
