## 2. 未满足条件 1（阻塞级）：socket 千路挂起

### 2.1 现象

`socket` 拓扑 1000 独立话题 **rc=124（超时挂起）**；100 路通过。

**队长核验的证据**：`artifacts/perf/20260929-r25-W10/socket-ind-1000.hang.log`（404 行）内容全部为：

```
SocketRecvWorker[3]: idle exit (no routes for >= 1000 ms)
SocketRecvWorker[2]: idle exit (no routes for >= 1000 ms)

```

⇒ **worker 空转退出，route 从未成功归属** —— 卡点在**连接建立阶段**，不是收包阶段。

### 2.2 根因（第三条为代表性证据链，A/B 反事实成立）

| # | 机制 | 位置 / 数据 |
|---|---|---|
| 1 | `InitChannel` 的等待**无上界、无诊断、不可退出** | `socket_sub_ipc::InitChannel`：`while (!subscriber_->connect()) { sleep(1s); }` |
| 2 | `bind(组地址:PORT)` 用 `SO_REUSEADDR\|SO_REUSEPORT`；占用者若**未开** `SO_REUSEADDR` ⇒ 必 `EADDRINUSE` | `UDPNode::connect()` |
| 3 | **碰撞面 50.9–52.0%**：`ip_local_port_range = [32768,60999]` 与 dzIPC 端口窗口 `[11451,65531]` 重叠；**含本工程自己的 SendOnly ACK 套接字**（`udp.h:169` 明确「不 bind」，故内核把它放进临时端口池） | `artifacts/perf/20260929-r25-W10/port-conflict/`（`ab_counterfactual.log`、`topic_port_clashes.txt`、`observed_topic38_port.log`、`topic38_48650.log`、`scope_3104.txt`、`w10_portconflict.cpp`） |

**实测碰撞**：topic #38 / 端口 48650 被别的进程占用。

### 2.3 归属与定性

- **归属**：**socket 模块侧**（`src/dzIPC/socket_pub_sub_ipc.cc` 的连接等待 + 端口选择策略）
- **非本轮改造引入**：A/B 反事实成立（本轮改造前后同现象）
- **建议修法**：**有界重试 + 可识别诊断**（⛔ 不要求改端口公式）
- **对判定的影响**：按 §13.2 末句，「1000 路 **socket** 有效收发」本轮**不可声明**。SHM 侧的千路闭环**不受此影响**。

## 4. 顺带产出的关键结论（**建议按 §11.3 追加修订**，本包未改 §6.2 任何数值）

### 4.1 门槛 3 三态实测（60 s 窗口、逐 TID 聚合）

| 状态 | threads | CPU (core) | ctx (s⁻¹) | idle_exits |
|---|---|---|---|---|
| 状态 1（无 route） | 2 | 0.00000 | 0.0 | — |
| 状态 2（已注册无发布者） | — | 0.12–0.29 | — | — |
| 状态 3（已连接、有效订阅、停止发布） | **34** | **0.583** | **9101.1** | **0** |

⇒ **支持 R-2 三态分列**（状态 3 必须常驻、`idle_exits == 0`，与方案 §10.1 一致）。

### 4.2 🔴 R-1 的控制面项 `Σ 1000/heartbeat` **高估 13–36×**

- W00 §11.3 R-1 的公式：`⌈N_worker×1000/wait_timeout + Σ_在册控制项 1000/heartbeat⌉ × 1.5`
- 1000 sub + 1000 pub 时公式给出 **120000 /s**
- **实测仅 1.5–4.6 k/s**（调度器把**同批到期项合并到一次 tick**，`Σ` 只是理论上界）
- ⇒ 若按公式冻结预算，门槛将被**算松 1–2 个数量级**
- **建议**：该项改为「**实测唤醒率上界**」形式，并在回滚/复核中注明「同批合并」语义

### 4.3 空闲 CPU 归因（**直接支撑 §10.2**）

| 来源 | 占用量 |
|---|---|
| 控制面（2000 项、mean_tick 15.5 µs） | ≈ 0.069 core |
| **`RecvWorker` 池的 `collect_pending()` O(route) 全扫 × 320 次/10 s 超时唤醒** | **≈ 0.51 core** |

⇒ 「线程 O(1) 但扫描 O(route)」得到实测支持。

### 10.1 §4.3 的归因**反转**（F2，high）

**原 §4.3 表述（保留，⛔ 不删）**：
> 控制面（2000 项、mean_tick 15.5 µs）≈ 0.069 core；
> **`RecvWorker` 池的 `collect_pending()` O(route) 全扫 × 320 次/10 s 超时唤醒 ≈ 0.51 core**
> ⇒ 「线程 O(1) 但扫描 O(route)」得到实测支持。

**更正**：该归因与反事实相反。我按 R1 的 2×2 反事实**独立复现**（外部逐 TID 读 `/proc`）：

| 格 | 调度器 | 池 | 线程数 | 逐 TID 总 CPU | 唯一非零 TID |
|---|---|---|---|---|---|
| A | ON | ON | 34 | **0.5775 / 0.5850 / 0.5925**（3 轮） | 调度器线程 |
| **C** | ON | **OFF**（`DZIPC_SHM_RECV_COMPAT=1`，`route_count=0`） | 1002 | **0.6025 / 0.6125 / 0.6150** | 调度器线程 |

⇒ 池被**整体停用**后 CPU **不降反升**（3/3 轮稳定）⇒ 「池 ≈0.51 core」**被证伪**。

**决定性标定**（`--state 2`：只建订阅不建发布端 ⇒ 池完全不参与、全进程**仅 2 条线程**）：

| 在册控制项 | CPU（进程内） | 逐 TID | 调度器 entries |
|---|---|---|---|
| 100 | 0.00286 | 0.0030 | 100 |
| 500 | 0.06500 | 0.0660 | 500 |
| 1000 | 0.29428 | 0.2930 | 1000 |

⇒ **无接收池时 1000 项已耗 0.29 core**；state3（entries=2000）实测 0.575–0.618 ≈ 0.293×2。

**更正后的正确表述**：

| 来源 | 更正前 | **更正后** |
|---|---|---|
| 控制面 `ShmControlScheduler` | 0.069 core | **≈0.29 core @1000 项 / ≈0.59 core @2000 项** |
| `RecvWorker` 池 `collect_pending()` | **≈0.51 core（主成本）** | **≈0**（池停用后 CPU 不降反升） |

⇒ 「线程 O(1) 但扫描 O(route)」**不再有实测支持**；正确的表述是
「**线程 O(1)，但空闲 CPU 的主成本在控制面 tick，随在册控制项数增长**」。

**原 §4.1（门槛 3 三态实测）不受影响**（该节只报测量值，未做归因）；但其中
「其余 ≈0.51 core 来自 RecvWorker 池」这句若被引用，**必须替换为本节结论**。

**对 §4.2（R-1 高估 13–36×）的影响**：唤醒率项的高估结论**保留**；但新增一条边界——
`w10_tickcost` 用的是**空回调**，其读数（0.069 core）**不可**用作 R-1 的 CPU 预算输入
（真实回调负载下控制面成本高一个量级）。
