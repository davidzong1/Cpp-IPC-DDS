### 1.2 冻结条款

**【R0-1】失败必须以异常到达调用方；`void InitChannel(...)` 签名不变（含虚函数签名不变）。**
- 冻结接口：`socket_pub_ipc::InitChannel` / `socket_sub_ipc::InitChannel`，失败时**抛出**异常；异常类型与消息必须携带：`topic`、`domain`、端点角色（pub / sub / ack）、端口、`connect_errno_class()` 分类、`first_errno`、`attempts`、`elapsed_ms`。
- **异常行为变化本身属本接口语义冻结范围**：本次冻结**把「内部吞错后正常返回」改为「抛出」**是一处**可观测语义变更**，须在 `接口责任表.md` §2 冻结接口清单登记（由架构负责人落地）。
- 失败路径的**清理义务**（任一异常路径都必须满足）：不注册 `info_pool` 条目、不注册接收 route、不启动兼容收包线程、不留控制面发现条目、已取得的 fd 立即 close；再次调用 `InitChannel()` 只保留**一代**有效状态。
- 例外：`running==false`（对象正在停止）**不抛异常**，按「静默取消」处理并返回（与 D-22 现状一致，`:237-242`）。此例外必须写进 R1 的测试断言。

**【R0-2】调用方义务：所有调用链必须处理失败；⛔ 禁止「吞异常后继续用一个半初始化对象」。**
- 冻结的**逐链**要求（R1 必须逐条给出证据）：

| 调用链 | 位置 | 冻结要求 |
|---|---|---|
| 工装（验收） | `test/perf/w10/*.cpp` | **必须** catch 并把该 route 记为该次运行的**显式失败**（进入 `verdict`/退出码），⛔ 不得 catch 后继续跑完全程再报 PASS。R3 落地 |
| 自动路径选择 | `src/dzIPC/auto_ser_cli_ipc.cc:241,573` | socket 腿建失败 ⇒ 必须能区分「socket 腿不可用」与「socket 腿可用但无对端」。R1 落地（归 socket与数据面负责人；`auto_ser_cli_ipc.cc` 写入权见 §6 表 → 需先提需求） |
| Builder / 直连用户 | 任何 `pub_ipc_base*`/`sub_ipc_base*` 多态调用点 | 用户侧**必须**把异常视为「本通道不可用」。R0 只冻结义务，**不改**任何示例/产品调用点 |
- **若 R1 最终改为「状态接口」而非异常**：则上表**每一个**调用方都必须检查状态，且必须在 `接口责任表.md` §3 走接口变更流程。**R0 的推荐是异常**（签名不变、失败不可忽略、与现有 `catch` 位置天然对齐），但不排除状态接口——两者**只能选一种**，选后者时本条款的全部调用方义务**照旧成立**。

## 2. R0-3 / R0-4：截止时间边界

### 2.1 冻结的计时层级（三层，互不叠加成无界等待）

| 层 | 冻结值 | 计时起止 | 与其他层的关系 |
|---|---|---|---|
| **L1 单通道建连内部期限** | **29.0 s 上界**（`attempts=30` × (1 s 间隔)；实测 `elapsed_ms=29018`），**冻结为「≤30 s」** | 从 `connect_with_bounded_retry()` 进入（`t0`）到返回 false | **硬上界**，与 `running` 取消同受约束；⛔ **不得**改成无界 |
| **L2 批注册总期限** | **90 s**（1000 route × L1 的**并发上限** + 建对象开销；见下式） | 从批注册开始到最后一个 route 得到确定结果 | **批内并发/顺序**由 R3 决定，但**总期限固定 90 s**；超时 ⇒ 该批**判失败**并保留进度 |
| **L3 外部 watchdog 宽限** | **120 s** | 从测试进程 fork/exec 起 | = L2 + 30 s 余量；⛔ **外部 `rc=124` 不得作为正常路径的结束方式**（D-22 前的失败模式正是它） |

### 2.2 与「对象构造」「握手」的边界（⛔ 不得混淆）

- **对象构造 ≠ 建连**：构造函数**不**做任何 UDP 绑定/入组（现状即如此），因此**构造不消耗 L1**。冻结：`InitChannel()` 是唯一的建连入口，L1 只在它内部计。
- **握手期限与建连期限是两个量**（W00 §6.2 第 5 行冻结）：握手 `≤ 5 s`（`Test_handshake`），**建连 L1 = 30 s**。二者**不得互相顶替**：⛔ 不能用「握手 5 s 通过」证明「建连有界」，反之亦然。R4 的报告必须**分别**给出两列。
- **⛔ 禁止用拉长外层 `timeout` 掩盖内部无界等待**：L3=120 s 是**外部兜底**，任何正常/故障运行时若观察到进程由外部 kill 结束（`rc=124` 或 `SIGKILL` 退出），该 run **直接判失败**，并在 `verdict.md` 记为「内部期限失效」。这条是 D-22 的**反例守卫**，R3 必须实现为机械判据。

### 2.3 若某项无法在 R0 内冻结

- **L2 = 90 s 是 R0 内可冻结的**（由 L1 与并发度推出），但**前提是 R3 确定批注册的并发度**。⇒ 本项的**冻结值已给**，**唯一的条件**是 R3 落地后若采用**串行**批注册，则 1000 route × 29 s 会远超 90 s ⇒ 此时 R3 **必须**采用并发/分批，或按 §9 走「未冻结」流程。**这一条件已写明，不构成沉默放行。**

> **影响的工作包**：R1（L1 实现 + 单通道上限上报）、R3（L3 watchdog 与 rc=124 判失败、L2 批期限）、R4（两列分别报告）、R7（评审项）。

### 3.2 冻结条款

**【R0-5】分母 = 端点（endpoint），冻结为「1000 对 pub/sub = 2000 端点」，含入项为三类：**
1. **pub 侧**：每 pub **恰好 2 fd**（数据 `SendOnly` + ACK `RecvOnly`；`socket_pub_sub_ipc.cc:618,621`）。
2. **sub 侧**：每 sub **恰好 2 fd**（数据 `RecvOnly` + ACK `SendOnly`；`:1193,1197`）。ACK 通道连不上会 `reset()`（pub `:641-651` → `ack_rx_.reset()` `:646`；sub `:1213-1223` → `ack_tx_.reset()` `:1222`）⇒ 该 route **少 1 fd**，属**允许的减项**，但必须在报告里显式给出「ACK 不可用 route 数」，⛔ **不得**把它当作省 fd 的默认手段。
3. **固定池开销**：**每活跃 socket worker 2 fd**（`epoll_create1` + `eventfd`；`socket_wait_set.cc:132-133`），上限 `2×32 = 64`。SHM 路径不消耗 fd（`fds_open=5`，r25 实测）。
- **⛔ 不得**用「除以 2000 端点」之外的任何分母（例如只数 sub、只数 pub）来稀释该预算；**端点 = 2 × topic 数**，是唯一合法分母。
- 报告义务：`fds_open` 的**快照时点**必须写明（建对象后 / InitChannel 后 / 存活期 / 回收后），且**四态分别给值**（W00 §6.2 第 6 行已要求「结束回到可解释基线」）。

## 7. 团队级纪律一：ABI（按值返回结构体追加字段 ⇒ 所有引用方必须随库重编）

**【R0-A1】共享层凡**按值返回**的结构体追加字段，所有引用方（含不在 CMake 内的工装）必须随库重编。**
- **根因**（T30 实测，非转述）：`RecvWorkerPool::stats()` **按值返回** `RecvWorkerStats`；追加字段后**旧工装二进制**仍按旧尺寸分配返回槽 ⇒ 栈布局不一致 ⇒ **功能读数全对但退出时 SIGSEGV**（`__libc_free(mem=0x1a1)`，`RecvWorkerStats` 按值返回 + 追加字段）。我本次亦独立复现到同类形态（t31 F4：`build/bin/w10_matrix` 早于库 ⇒ 6/6 `rc=139`）。
- **为什么现有纪律挡不住**：总方案 §10.6「正式验收先重跑 CMake + 编译」只覆盖**被 CMake 收集**的目标；`test/perf/w10/*.cpp` **不在 CMake 内**（手工 `g++`），因此**不触发**重建。
- **冻结要求**：
  1. **重编纪律（硬）**：任何对 `include/dzIPC/threepools/*.h` 的**结构体尺寸改变**（追加/删除字段、改字段类型、改对齐）⇒ 该 WP 必须在交付物中列出**全部引用方**（含 `test/perf/**` 手工编译件），并证明它们**已随新库重编**（给命令与指纹）。
  2. **登记位置**：已作为 **闸门纪律 ③d** 写入 `基线与门槛.md` §4.4（append-only），裁决登记为 **§11.4 D-29**。
  3. **根治方向（评估结论：**列为独立条目**）**：建议把 `RecvWorkerPool::stats()` 从「按值返回」改为「**引用出参**」（`void stats(RecvWorkerStats& out)`），并在结构体首部加**版本号 + `sizeof` 尺寸字段**，调用方校验不匹配即**显式失败**而非静默越界。⇒ 该改动触及**冻结接口**（`接口责任表.md` §2）与全部调用方 ⇒ **单列为 W00-R1 的独立条目**（W12 前的接口变更流程），**不在 R0 内改代码**。

## 8. 团队级纪律二：tick 次数 / 系统调用返回次数 / 线程唤醒次数 / 上下文切换次数**不是同一指标**

**【R0-B1】R6 及任何性能判定⛔ 不得在这些量之间互相替代；⛔ 尤其不得用旧报告的 `4.6 k/s` 直接替换 R-1 公式的一项就宣布通过。**
- **冻结的指标分列**（每项必须**各自**给出定义、口径、来源与判据）：

| 指标 | 冻结定义（与 W03 的 ctx 口径一致，见 §11.4 D-8） | 唯一来源（禁止换用） |
|---|---|---|
| **tick 次数** | `ShmControlScheduler` 的 `tick()` 完成次数 | `ShmControlScheduler::Stats::tick_count` |
| **系统调用返回次数** | 由 `wait`/`epoll_wait`/`futex` 等**系统调用返回**驱动的次数 | 后端各自的返回计数；⛔ **不得**用 tick 次数代替 |
| **线程唤醒次数** | 线程从阻塞态被唤醒的次数 | 后端等待原语统计；⛔ **不得**用 tick 次数代替 |
| **上下文切换次数（ctx）** | **逐 TID 聚合**或 `wait4` rusage 全生命周期（§11.4 **D-8** 已冻结口径，废止 `/proc/self/status`） | `/proc/self/task/<tid>/status` 聚合 或 rusage |
- **R-1 的控制面项**：其**唯一合法替代前身**见 `基线与门槛.md` §11.3 **R-1 / R-1b**（判定式 `Σ/B_min`，`B_min` 为冻结输入），且**落实前不得用于判定**（R-1b 无生效 `run_id`）。⛔ 「用 4.6 k/s 换掉公式一项 ⇒ 门槛 3 通过」这一路径被**明确禁止**。
- **R6 的输出要求**（方案 §7）：控制项回调执行数、调度批次数/每批到期项数、控制线程**逐 TID ctx**、CPU**分列**；SHM worker 与测量线程**单列**；同窗口跨来源核对；无法解释的合并残差**保留为问题**（⛔ 不得丢弃）。
- **CPU 与 ctx 分别判定**：门槛 3 的 CPU 项（`0.20 core`）与 ctx 项是**两个独立判据**，⛔ 不得用一个的达标掩盖另一个（W00 §11.4 **D-26** 已上报 CPU 项待另行裁决）。

> **影响的工作包**：R6（性能判定）、R5（观测开销）、R7（评审项）、W11/W12。
