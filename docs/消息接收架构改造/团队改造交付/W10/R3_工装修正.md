## 1. H1 端口预检：读错列 ⇒ 预检从未生效

### 现象（队长已独立核实，本次逐字复现）
`w10_pick_socket_topics()` 原实现：
```cpp
std::istringstream is(line);
std::string addr;
if (!(is >> addr)) continue;                    // ← 取【第一个】token
const auto colon = addr.find(':');
used.insert(strtol(addr.c_str() + colon + 1, nullptr, 16));
```
`/proc/net/udp` 的列序是 `sl  local_address  rem_address  st ...`，行首 `sl` 形如 `145:`
⇒ 冒号在索引 1 ⇒ `colon+1` 指向**串尾** ⇒ `strtol("") = 0`。

### 最小反例（可执行）
```bash
$ python3 test/perf/w10/h1_buggy_parse.py
== 修前（逐字复现）==
  行前 3 列 = ['145:', '00000000:A874', '00000000:0000']  第一个 token = '145:'  冒号后子串 = ''  → 解析值 = 0
  used 集合 = [0]    |used| = 1
== 修后（按列解析，第 2 列 local_address）==
  used 集合大小 = 161（解析失败 0 行）
判定：修前 |used|=1（[0]）⇒ **端口预检从未生效**；修后 |used|=161 ⇒ 预检生效
```
输出存证：`artifacts/perf/20260930-r28-W10-R3/counterexamples/h1_buggy_parse.txt`。

### 修法
1. **按列解析**第 2 列 `local_address`（`is >> slot >> addr`，`rfind(':')` 取端口段）；
2. **同时读 `/proc/net/udp6`**（IPv6 双栈绑定会占同一个 IPv4 端口号）；
3. **读取失败不得按"无占用"处理** —— 任一表打不开 ⇒ `picker.verdict=FAIL_PORT_TABLE_UNREADABLE`，
   调用方直接判失败（⛔ 不得静默当作"端口都空闲"）；
4. `ip_local_port_range` 读不到同样判失败（原实现用默认值兜底，会把"读不到"伪装成"有默认区间"）；
5. **保存原始表与解析结果**：落盘 `port_table.txt`（`/proc/net/udp` + `udp6` 原始行）与
   `port_parse.txt`（`parsed_ok/parsed_bad/used_set_size/used_ports/错误列表/picker 诊断`）；
6. 顺手补齐 t33 遗留的**重名/临时端口区间**约束（去重 + 排除 `ip_local_port_range` 整段）。

### 修后验证
| 判据 | 读数 |
|---|---|
| `used_set_size` | **166**（修前 1） |
| `parsed_ok / parsed_bad` | 182 / 0 |
| 是否排除"确实被占用"的端口（53） | 修前**不排除**（预检失效的直接证据）、修后**排除** ✅ |
| 落盘物 | `portev/run/port_table.txt`、`portev/run/port_parse.txt` ✅ |

## 2. H2 握手：修前"睡够就报成功"，且 1000 路要睡 400 s

### 现象与最小反例
修前 socket 分支：
```cpp
std::this_thread::sleep_for(400ms);
return true;                       // ← 不证明注册，更不证明通信
```
对拍件（`w10_r3_counterexamples` 的 H2 节）把两侧结论并列：

| 场景 | 修前 | 修后 |
|---|---|---|
| **无发布端**（无对端） | `registered=1000/1000`（**假通过**），耗时 ≈400 s | `confirmed=0/1000` ⇒ `registered=0` ⇒ **判失败** |
| 有发布端 | `registered=1000/1000`，耗时 ≈400 s | `confirmed=1000/1000`，**批量** `batch_ms≈50` |

### 修法（方案 §5.3）
- **注册状态**与**通信状态分开**：
  - 注册：该 route 在**自己那一侧接收池**真实在册（`route_count`），shm 另用控制面 `Ready + peer_count≥1` 交叉核对；
  - 通信：逐 route 发**确认帧**（`seq = kConfirmSeqBase() + i`，载荷含 run_id/route/generation/seq）并**逐字节校验**收回来。
- **批量轮询**：外层一轮遍历全部 route、每轮 `sleep 5ms`；⛔ 不对已就绪对象逐个睡眠。
  **批次总期限** = `--register-batch-deadline-ms`（默认 90000，即 R0-4 的 L2=90 s）。
- **确认帧与规模帧完全分账**：确认帧 seq 落在专用区间，只累 `confirm_rx`，⛔ 不计入 `rx/dup/ooo`；
  握手结束后 `sent/sent_ok/first_publish_us` 复位，规模阶段的记账从零起算。
- **逐 route 记失败**：未确认的 route **逐条**写入失败清单（H6：不靠日志提示代替失败状态）。

### 修后验证（真实运行）
```
# 正常（socket n=1000，域 32302）
handshake_register pool_routes=1000 control_ready=1000/1000/0 ms
handshake_confirm  confirmed=1000/1000 batch_ms=49 failed=0
registered_count=1000/1000

# 负控（--negctl-no-pub，socket n=20）—— 修前会宣称 20/20
handshake_confirm  confirmed=0/20 batch_ms=90005 failed=20
registered_count=0/20
W10_MATRIX_DONE verdict=FAIL failures=27   ← rc=1
```
⛔ 负控里 `batch_ms=90005` 是**批次总期限**（90 s）到顶，属预期；这正是"有界"的证据
（修前是 400 s 顺序睡眠且**无条件成功**）。

## 3. H3 恢复时间戳：绝对时间当延迟 ⇒ 无法作判据

### 现象
r25/r27 的 `manifest.json`：
```
r25 shm-ind-1000:  recover_first_packet_us = 95200500000.0   ← 26.44 小时（CLOCK 原点绝对时间）
r27 socket final-1: recover_first_packet_us = 118157000000.0 ← 32.82 小时
```
且恢复阶段只重置了 `first_publish_us`，**未重置首次接收状态** ⇒ 恢复首包可能被**旧帧**满足。

### 修法
- 首次接收与恢复接收使用**独立状态**（`first_packet_*` vs `recover_first_rx_us`）；
- `恢复延迟 = 恢复首个有效帧的接收时刻 − 该帧的发送时刻`，**同一单调时钟**（`steady_clock`）；
- **只接受新恢复序号**（`seq >= resume_seq_base_`，即恢复阶段新发的）；旧帧单独计 `recover_old_seq_rejected`；
- 机械校验：`延迟 ≥ 0` **且** `延迟 ≤ 恢复阶段实际耗时`，否则判失败；`phases.csv` 同时给出三个绝对时刻。

### 修后验证
```
recover silence_ms=3000 rx_after_silence=5 ok=1 delay_us=2170 send_abs_us=124710122990 recv_abs_us=124710125160 phase_us=2192 lost=0 old_frames_rejected=0
manifest: recover_first_packet_us = 2170
phases:   recover,2,"... 恢复延迟=2170us 发送绝对=... 接收绝对=... 阶段耗时=2192us lost=0 new_seq_only=1"
```
⇒ 字段语义从「绝对时刻」改为「**延迟（µs）**」，且 `2170 ≤ 2192` 满足同钟一致性。

## 4. H4 重建：原阶段**没有重建代码**

### 现象
原阶段名为 `concurrent-close-rebuild`，但体内只有 8 lane 并发 `reset()` **后半数订阅**，
**没有任何 generation 推进** ⇒ 阶段名暗示的能力无法证明。

### 修法（拆两段，各自独立判据）
- **阶段 8a `concurrent-close`**：保留原并发析构（后一半），按 R0-4 的**分层**时限判定：
  `close_ms ≤ min(批次总期限, 通道数 × 单通道上限)`；另单独打印 `per_channel_avg_ms` 供归因。
  ⛔ 修前（我的中间版本）曾把 500 条通道的**总耗时**与**单通道上限 2 s**直接比较 ⇒ 千路必然假失败，
  这正是 R0-4「不得用一个量顶替另一个量」要防的错。
- **阶段 8b `rebuild`**：走**生产路径** —— 旧发布端析构 → 新发布端重建（`generation` 递增）；
  记 `begin_rebuild` 时刻、等对端重新 attach（Ready 且 peer≥1）、发**新代首包**、
  判「是否在冻结时限（`--rebuild-deadline-ms`，默认 1000）内收到」；**旧代帧独立计数**。
  另逐子步记录时刻（`pub_back` / `peer_ready` / `first_pkt`），把"重建慢"拆开归因。
  socket 无 generation 概念 ⇒ 本段标 `n/a`，⛔ 不加假判据。

### 修后验证
```
rebuild gen 1→2 rebuild_ms=18 极限=1000ms 新代首包=1 pub_ok=1 peers_after=1
        旧代帧(重建前)=1 旧代帧(重建后)=0 pub_back=8672us peer_ready=18256us first_pkt=19324us ok=1
```
三轮重复：`rebuild_ms = 18 / 19 / 20`（远低于 1000 ms 上限）；**重建后旧代帧 = 0**（旧 generation 无投递）。

## 5. H5 批跑失败传播：最后一条 `echo` 不再决定总结果

### 现象
原 `w10_run_matrix.sh`：`run()` 不累积子失败，脚本末尾 `echo W10_MATRIX_BATCH_DONE` 决定总结果；
`write_artifacts()` 拒绝写入时仅 `return` ⇒「批次成功」可与「某运行失败」「证据缺失」并存。

### 修法
- `record_and_tally()`：**rc + verdict + 必需文件**三者共同决定该子项 `ok`；
  - `rc != 0` ⇒ 失败；`verdict != PASS` ⇒ 失败；必需文件（`ledger.csv/phases.csv/samples.jsonl/counters.json/manifest.json/verdict.md`）
    **缺失或零字节** ⇒ 失败；
  - **`rc=124`（watchdog 超时）与 `rc=139`（ABI 不匹配）显式判失败**（R0-3 / R0-A1）；
  - `--expect-fail <sub>` 把"预期故障已正确处理"与"规模运行失败"分开：预期失败**有正确诊断**才算通过，
    否则记 `UNEXPECTED_PASS` 并判失败。
- 批次退出码 = 失败子项数 > 0 ⇒ **exit 1**；⛔ 不再由最后一条 `echo` 决定。
- **参数化**：`--build`（构建路径）、`--run-id-prefix`、`--topic-manifest`、`--only`，删除 r25 硬编码。
- 每个子运行自动带 `--require-lib-sha256/--require-bin-sha256`；跑前把**成对指纹**与 mtime 配对结论写进 `fingerprint.txt`。

### 修后验证（`w10_r3_batch_acceptance.sh`，可复跑）

## 6. H6 总判定：§13.2 六条逐条机械断言

### 现象
修前记录 `dup`/`ooo` 但**总判定不据此判失败**；生命周期与资源条件也未全部机械判定 ⇒
人工台账审计与 `PASS` 可能不一致。

### 修法
- 六条各建一个**布尔断言** `c1..c6`，任一失败即 `verdict=1`；断言结果打印并写入 `verdict.md`；
- `registered_count` / `valid_rx_count` **从逐 route 台账重算**，并与计数器自述**交叉核对**
  （不一致本身即失败）；
- **#2 明确纳入** `dup` / `out_of_order` / `corrupt` / `timeout` / `rx` 五类（⛔ 直接判失败）；
- **#5 纳入**：恢复延迟非负且不超阶段耗时、并发关闭不超**分层**上限、重建通过、**重建后旧代帧 = 0**；
- **#6**：route/token（代理）/fd 已测；**queue/chunk 无公开读数 API ⇒ 标「部分测量/不可判定」**，
  ⛔ 不接受把未测项打成 ✅；
- **fd** 按 R0-5/R0-6 冻结模型：`fd = 4 + 2W + 2N_pub + 2N_sub`，分母是**端点总数**（不是话题数），
  超硬上限 4096 判失败（修前判据 `> 3.5*n` 是**陈旧分母**且只 INFO 不判失败）。

### 修后验证
| 场景 | 修前 | 修后 |
|---|---|---|
| `dup=50` | **PASS**（漏判） | **FAIL** |
| `ooo=7` | **PASS**（漏判） | **FAIL** |
| `corrupt=3` / `timeout=1` / 少收 | FAIL | FAIL |
| 真实 socket 千路 | — | `verdict_assertions c1=1 c2=1 c3=1 c4=1 c5=1 c6=部分测量`，`fds_open=4068 predicted=4068 budget_4096=OK` |

## 8. F4 工装不在 CMake ⇒ 陈旧二进制与库 ABI 不匹配

### 现象（本次独立复现）
`RecvWorkerPool::stats()` **按值返回** `RecvWorkerStats`；t30 在结构体**尾部追加了 5 个 `uint64`**。
C++ 的 by-value 返回由**调用方**按自己看到的 `sizeof` 分配返回槽 ⇒ **旧调用方 + 新库 = 越界写**。

### 最小反例（本次构造，与 t30/t31 同型）
```bash
# 旧头 = 当前头截掉 t30 追加的 5 个 uint64
$ g++ -O2 -I artifacts/perf/20260930-r28-W10-R3/f4_abi/oldinc -I include ... \
      -o w10_matrix_stale test/perf/w10/w10_matrix.cpp -L build/lib -lipc
  编译 rc=0（**能编译能链接** —— 符号名一致，这正是危险处）
$ ./w10_matrix_stale --transport shm --topology independent --n 20 --domain 5101 --msgs 2 ...
  run1 rc=124    run2 rc=139    run3 rc=139      ← 功能读数看似正常，退出时崩溃
$ gdb -batch -ex run -ex bt --args ./w10_matrix_stale ...
  Thread 1 received signal SIGSEGV, Segmentation fault.
  #0 __GI___libc_free (mem=0x3a6) at ./malloc/malloc.c:3368
  #1 (anonymous namespace)::Harness::run()
  #2 main()
```
⇒ 与 t30（`__libc_free ← main`）、t31（6/6 rc=139）**同一形态**；崩溃点取决于优化与栈布局，
判定依据是**ABI 形态本身**。

### 修法（三重）
1. **重编 + 配对检查**：`test/perf/w10/build_harnesses.sh`
   - 默认：重编全部 11 个链库工装 + 1 个无库依赖的对拍件；
   - `--check-only`：只比较「库/头文件 mtime vs 工装二进制」，落后即报 `STALE` 并 **rc=1**；
   - 重编后打印**成对指纹**（库 sha256 + 各工装 sha256），`--fingerprint-file` 可直接写进 run 目录。
2. **运行时断言**：`w10_matrix --require-lib-sha256 <hex> --require-bin-sha256 <hex>`
   - 库指纹从 `/proc/self/maps` 取**实际加载的**库路径再算 sha256（⛔ 不猜路径）；
   - 工装自身指纹用本进程 `readlink("/proc/self/exe")` 解析（⛔ 若直接 `sha256sum /proc/self/exe`，
     经 `popen` 起来的 `/bin/sh` 会解析成 **sh 自己** —— 本次踩到并已修）；
   - 不配对 ⇒ 打印 `FINGERPRINT_MISMATCH` 并 **rc=1 且不产出 verdict**。
3. **提交 CMake 登记需求给架构负责人**（`test/CMakeLists.txt` 归其写入，⛔ 本任务不自行改）：
   精确的 `add_executable` / `target_link_libraries` 块与「是否注册 `add_test`、是否 `RUN_SERIAL`」的选项，
   见 `docs/消息接收架构改造/团队改造交付/W10/R3_CMake登记需求.md`。
