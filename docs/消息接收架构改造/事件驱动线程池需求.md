# SHM 事件驱动接收线程池需求

> 状态：需求规格（实现前）。
>
> 本文与《shm_sub_thread_consolidation_plan.md》配套，规定 SHM 订阅侧从“每个 route 一组线程”演进到进程级控制面调度器和固定分片接收线程池的目标、约束、分阶段实施门槛和验收标准。

## 1. 范围、目标与非目标

### 1.1 首批范围

- 仅改造本机 SHM pub/sub 的控制面和收包数据面。
- 以进程为单位复用调度线程和接收 worker，消除按话题扩张的握手线程和收包线程。
- 在保持收包与用户取数异步的前提下，降低空闲唤醒、上下文切换和线程数量。

socket/UDP、ser/cli 不在首批实现范围内；它们继续使用现有线程模型，待 SHM 方案稳定后另行评估。

### 1.2 必须保持不变的行为

改造不得改变以下 API、队列契约和消息语义：

- `get`、`try_get`、`get_clone`、`try_get_clone` API；
- `view_queue_`、`msg_queue_` 的职责和背压/淘汰语义；
- DZFlat/TLV 分流、`msg_id`/schema 校验、`AcceptWire()`、adopt 配额、evict 回调和 chunk 生命周期；
- nodelet 快路径直接投递 `msg_queue_`；
- 同一 route 的消息顺序、多片消息重组和单消费者约束；
- 关闭、generation 重建、断线检测、死连接回收语义。

不得把 `get`、`get_clone` 或用户回调搬入收包 worker。不得因为引入处理池而让 SHM chunk 脱离现有配额控制。

## 2. 现状问题与设计边界

当前每个 `shm_sub_ipc` 至少创建 `subscribe_thread_` 和 `sub_handshake_thread_`；发布端另有 `publish_thread_`。订阅收包在 `channel_mtx_` 内执行 `subscriber_->recv(50)`，借此避免与握手线程并发 `release/reset`，但会带来线程数、空闲唤醒和重连等待线性增长。

方案必须正视以下约束：

1. `libipc::conn_info_head::recv_cache()` 使用 `thread_local` 分片缓存；同一 route 不能在 worker 间随机迁移。
2. 同一 route 必须单消费者且保持消息顺序。
3. `route` 的 `release/reset` 不能与 `recv` 并发；仅复制 `shared_ptr<ipc::route>` 不能解决内部句柄并发修改问题。
4. 当前 `rd_waiter_` 是共享内存条件变量等待器，不是 fd；发布进程不能直接写订阅进程创建的 `eventfd`。
5. 将 `recv(50)` 改成长等待后，析构必须先 wakeup/disconnect 再等待 worker，否则可能永久阻塞。

因此，普通全局任务队列、work-stealing 或“每次有事件就把 route 投递给任意线程”均不是本需求的实现方式。

## 3. 总体线程模型

```text
ShmControlScheduler（每进程 1 个）
  ├─ subscriber heartbeat（10ms）
  ├─ publisher owner heartbeat / stale 扫描（50ms）
  └─ peer 死连接判定（2s）

ReceiveWorker 0..N-1（N 默认 CPU 数或配置上限）
  ├─ 每个 route 固定归属一个 worker
  ├─ worker 自有 wait-set、ready 队列和统计信息
  └─ 事件到达后按 route 预算批量 recv 和入队

Optional ProcessingPool（可选）
  └─ 仅处理已完成接收和重组的消息
```

### 3.1 控制面调度器

新增 `ShmControlScheduler`，替代每订阅/每发布者的握手线程：

```cpp
class ShmControlScheduler {
public:
    using EntryId = uint64_t;
    EntryId register_subscriber(std::shared_ptr<SubControlState>);
    EntryId register_publisher(std::shared_ptr<PubControlState>);
    void unregister(EntryId);
};
```

注册项必须通过 RAII 生命周期令牌持有，调度器不得保存裸 `this`。注销语义为：

```text
标记 inactive → 唤醒调度器 → 等待正在执行的 tick 完成 → 返回
```

第一版时间语义保持不变：订阅 heartbeat 10ms，发布 owner heartbeat/stale 扫描 50ms，peer 死连接判定 2s。即使没有 peer，发布端仍需维持 owner heartbeat；仅可在 `peer_count() == 0` 时跳过 stale 扫描。

### 3.2 固定 route 归属

route 注册时计算并固定归属：

```text
worker_id = hash(route_name + domain_id) % worker_count
```

route 在整个生命周期内只能由该 worker 调用 `recv()`；注销并重新注册后才允许重新分配。worker 不得通过 work-stealing 抢占其他 worker 的 route。

## 4. RouteSession 生命周期协议

在移除 `channel_mtx_` 外层等待前，必须为每个订阅 route 引入生命周期封装：

```cpp
class RouteSession {
public:
    struct ReceiveLease {
        std::shared_ptr<ipc::route> route;
        uint32_t generation;
    };

    std::optional<ReceiveLease> acquire_receive();
    void begin_rebuild(uint32_t new_generation);
    void stop_and_wake();
    void wait_quiescent();
};
```

内部至少维护 `route_`、`generation_`、`receive_inflight_`、`stopping_`、`rebuilding_` 及其互斥量/条件变量。

### 4.1 收包与重建

`acquire_receive()` 成功后递增 `receive_inflight_`，取得 lease 后解锁，再执行 `route->recv()`，最后递减计数并通知条件变量。generation 重建必须严格按以下顺序执行：

```text
禁止新的 receive lease
→ 对旧 route disconnect()/wakeup
→ 等待 receive_inflight_ == 0
→ release/reset 旧 route
→ 创建新 route
→ 发布新的 generation
```

### 4.2 析构与注销

对象析构顺序必须为：

```text
1. 从 LocalPubSubRegistry 注销
2. 从收包调度器注销
3. 从控制面调度器注销
4. 标记 RouteSession stopping
5. disconnect/wakeup 当前 recv
6. 等待 worker 不再使用 route
7. release/reset route
8. 释放队列和其他资源
```

注销完成后不得再回调已析构对象，也不得向已销毁的 `msg_queue_` 投递。

## 5. 跨进程多路等待（前置能力）

只有 `libipc` 提供真正的跨进程 wait-set 后，才能启用固定分片接收池。建议增加：

```cpp
class recv_wait_token {
public:
    bool valid() const;
};

class recv_wait_set {
public:
    void add(const recv_wait_token&);
    void remove(const recv_wait_token&);
    bool wait(std::chrono::milliseconds timeout);
    std::vector<recv_wait_token> consume_ready();
};
```

Linux 优先评估基于共享内存 sequence 的 `futex_waitv` 或等价机制，并明确最低内核版本和不支持平台。不能把 `rd_waiter_` 直接拼成 `epoll/eventfd`：这既不是跨进程通知协议，也会迫使每个 route 增加代理线程，重新引入 O(话题数) 线程。

wait-set 必须保证：

- 消息到达和断开都能唤醒；
- generation 切换不丢 wakeup；
- 动态 add/remove 与 wait 无竞态；
- 返回后支持 level-triggered 重新检查；
- 能返回并定位 ready route；
- route 注销后不再产生悬挂 token 或回调。

在 wait-set 尚未具备前，兼容后端继续使用原有每 route 收包线程；不得默认用全量 `try_recv()` 扫描，也不得静默退化为高 CPU 轮询。不支持真正多路等待的平台必须显式报告不支持或回退兼容后端。

## 6. ReceiveWorker 数据面

worker 循环为：

```text
wait_set.wait()
→ 获取 ready route
→ 为每个 route 获取 ReceiveLease
→ 在预算内批量 route->recv()
→ 完成多片重组和基础 wire 判断
→ process_received_buffer()
→ 投递 view_queue_/msg_queue_
→ 预算耗尽后让出并返回 wait-set
```

每个 route 必须配置有界预算：

- `max_messages_per_route`（示例默认 32）；
- `max_bytes_per_route`；
- `max_processing_time_per_route`（建议 100~500 微秒起步）。

批处理用于减少 waiter 唤醒、锁/原子操作和上下文切换，但不得无界；预算耗尽后必须让出，使冷话题获得调度机会。worker 默认使用普通调度；绑核、`SCHED_FIFO` 或独占收包线程仅作为显式 opt-in 逃逸通道。

现有订阅 lambda 中从 `buff_t raw_data` 开始的逻辑应提取为：

```cpp
void process_received_buffer(
    const std::shared_ptr<SubState>& state,
    ipc::buff_t&& raw_data);
```

提取只改变调用者，不改变 DZFlat/TLV 分流、校验、adopt 配额、evict 回调、统计和队列行为。

## 7. 可选慢处理池

只有测量证明 DZFlat 解码、复杂反序列化或转换成为 CPU 瓶颈时，才引入 `ProcessingPool`。收包核心路径必须完成 `recv()`、多片重组、chunk 生命周期接管、基础 wire 判断和入队；慢处理池只接收完整消息。

慢处理池必须具备：

- 有界队列和明确满载策略；
- 每 route 独立 FIFO 或带 sequence 的有序提交；
- 按 route/优先级调度；
- 明确 chunk 所有权转移点、归还点和 adopt 配额约束；
- 禁止无界 MPMC 队列堆积仍持有 SHM chunk 的任务。

## 8. nodelet 快路径

`LocalPubSubRegistry` 不纳入 SHM 收包 wait-set。初始化顺序：

```text
构造队列和 RouteSession
→ 注册 LocalPubSubRegistry
→ 注册控制面调度器
→ 注册收包调度器
```

析构顺序按相反方向执行，且必须先注销 registry，再停止 RouteSession，避免发布端快路径继续向销毁中的 `msg_queue_` 投递。

## 9. 错误处理与恢复

- `wait_set.wait()` 超时属于正常事件；系统调用错误、token 失效或 wait-set 破坏必须记录 route/worker/generation，唤醒并重建受影响 wait-set，不能忙等。
- `recv()` 返回断开、旧 generation 或底层错误时，停止该 route 的新 lease，按 RouteSession 重建顺序恢复；不得跳过顺序或直接释放仍在使用的 chunk。
- wire、schema 或 decode 校验失败时丢弃当前消息并记录计数，必须执行完整 chunk 归还/adopt 配额结算，不得影响同一 route 后续顺序。
- 队列满时沿用现有 evict/backpressure 语义；adopt 超额按现有配额拒绝或驱逐，禁止无界堆积。
- worker 异常退出、处理池满载或重建失败必须上报并触发受控降级到兼容后端；不得静默创建额外 O(N) 线程或切换为全量轮询。

## 10. 分阶段实施与门槛

### 阶段 0：基线和观测

不改变行为，覆盖 1、100、1000 个订阅，1000 个空闲订阅，1 热+999 冷话题，大消息/多片消息，generation 重建、关闭、nodelet 快路径和多进程发布/订阅。记录线程数、`nvcsw`/`nivcsw`、CPU、收包 p50/p99、关闭延迟、丢失/重复/乱序、chunk/adopt 占用及归还。

### 阶段 1：控制面调度器

实现 `ShmControlScheduler` 和 RAII 注册/同步注销；先保持数据面不变。验收握手线程从 O(N) 降为 0，heartbeat、generation、stale peer 和注销回调回归通过。

### 阶段 2：RouteSession

实现 receive lease、rebuild、stop/wake/quiescent 协议。只有通过并发 `recv`/`release`、关闭唤醒和 generation 重建测试，才能移除原有外层同步。

### 阶段 3：分流逻辑提取

提取 `process_received_buffer()`，验证解码、队列、配额、chunk 和 nodelet 语义与基线一致。

### 阶段 4：libipc wait-set

实现 token/set、动态注册注销、消息/断开唤醒及跨进程竞态测试，明确 Linux 内核和平台能力矩阵。未通过前不得启用 worker pool。

### 阶段 5：固定分片接收池

启用固定 route→worker、route 级有界批处理和 ready 重检。验证热冷公平、单 route 顺序、多片完整重组及 worker 注销安全。

### 阶段 6：可选统一收包

仅在 wait-set 可用且产品明确需要时评估单线程统一 spin；若重解码造成全局队头阻塞，必须拒绝该模式或将重处理移入有界处理池。

每阶段均须可独立回滚；任何阶段不得以静默高 CPU 轮询作为降级方案。

## 11. 验收标准

1. 1000 个订阅时不再创建 1000 条握手线程；启用线程池后收包线程数为固定 N，而非 O(订阅数)。
2. 1000 个发布者/订阅者组合下，控制面线程数仍为进程级固定数量，heartbeat、owner heartbeat、stale reclaim 语义不变。
3. 关闭、断开和 generation 重建均能唤醒阻塞 worker，不永久等待、不访问已析构对象。
4. 单 route 消息无丢失、重复、乱序；多片消息完整重组；`thread_local` 缓存不跨 worker 迁移。
5. 热话题受消息数/字节数/时间预算约束，冷话题可获得调度；批处理无无界增长。
6. `get*` API、队列、DZFlat/TLV、adopt/chunk、nodelet 快路径与基线一致。
7. 不支持 wait-set 的平台显式报告或回退兼容线程模型，不出现静默全量轮询和异常 CPU 占用。
8. 相对阶段 0 基线，线程数、上下文切换和空闲 CPU 有可复现改善，且收包 p99、关闭延迟和吞吐不劣化到产品阈值之外。

## 12. 风险、未决项与开源库选型边界

### 12.1 主要风险

- `libipc` wait-set 的跨进程 ABI、内核版本和 wakeup 丢失问题；
- route 动态注销、generation 重建与 wait-set token 的竞态；
- `thread_local` 多片缓存对 route 迁移的隐性依赖；
- 热话题预算、队列背压和 chunk 配额相互作用；
- 统一收包模式中的全局队头阻塞。

### 12.2 未决项

worker 数量与哈希策略、wait-set 的具体 futex 实现、预算默认值、token 注销同步、CPU/NUMA 绑核、独占线程逃逸通道，以及慢处理池的有序提交协议，须以阶段 0/4 的测量和实现验证结果定稿。

### 12.3 开源库选型边界

可评估 `liburing`、`libevent`、`libuv`、Folly `EventBase` 等用于进程内事件循环或线程调度参考；但它们不能自动把当前基于共享内存条件变量的 `rd_waiter_` 变成跨进程 wait-set，也不能替代 `libipc` 的 route 生命周期和多片缓存协议。任何库引入都必须先证明：跨进程消息/断开唤醒、动态注册注销、generation 不丢 wakeup、ready route 定位和单 route 亲和性均可满足；否则只能作为实现参考，不能直接作为默认后端。
