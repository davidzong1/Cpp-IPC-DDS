## 3. 锁序核对（方案 §3.2）

```text
reset_message / reset_callback
  message_mtx_ / callback_mtx_（只做「写成员 + 取 receive_state_ 快照」）
    → 释放 receive_state_mtx_（退出访问口）
      → state->mtx（改模板/回调）
```

- `current_receive_state()` / `set_receive_state()` / `clear_receive_state()` 只碰 `receive_state_mtx_`，**不**取任何 state 锁、不 join、不回调、不访问 worker pool ⇒ 满足「`receive_state_mtx_` 不得与 `state->mtx` 同时持有」。
- `InitChannel` / `start_receive_path` 在**锁外**调用 worker pool（`pool.start()` / `add_route`），成立。
- 头部注释已把上述规则与锁序写在字段旁（`include/dzIPC/socket_ser_cli_ipc.h` / `socket_pub_sub_ipc.h`），供后续 Review 直接核对。

### 6.1 已落地的容量规则（§6.3 规则 1 + 规则 2 的组合）

```text
入库前判定：pending_bytes + request_bytes <= kMaxPendingBytes(8 MiB)
  · 满足        -> 入队；顺带更新 fifo_peak_requests / fifo_peak_bytes / max_request_bytes
  · 超限且队列非空 ->          不收取（backpressured=true，backpressure_hits++，请求留在通道里，零丢弃）
  · 超限且队列为空 -> 放行这一条（oversize_admissions++）
     理由：recv_once 一旦 try_recv 成功，请求已在本地 buffer，无法退回通道；
           此时拒绝＝静默丢弃，违反"背压而非丢弃"的总原则。
严格上界：内存持有 <= kMaxPendingBytes + max(单条请求实测尺寸)；条数 <= kMaxPendingRequests(64)
```

- ⛔ 不再把 8 MiB 表述为「绝对内存上界」；`SerState` 注释与方案第 6 章同口径。
- ⛔ 背压路径**零静默丢弃**：不收取时请求仍在共享内存通道里，`has_pending()` 因 `backpressured` 返回 true，共享 worker 下一轮预算重新选中本 route（方案 §6.3 末段要求）。
- 已核实「背压不会饿死其它 route」：`backpressured` 只是让本 route 保持可选中，不占用 worker 的额外轮转；同 worker 其它 route 由共享层固定 FIFO deferred 保证（`recv_worker.cc`/`socket_recv_worker.cc` 的 `deferred` 语义，未改）。

### 11.3 证伪证据：同一环境下的等价探针复现同一告警

探针（`docs/消息接收架构改造/.tsan_probe.cpp`、`.tsan_probe2.cpp`；纯 std 库，零项目代码）：

- 探针 1（单对象）：`State{mutex mtx; condition_variable cv; deque<shared_ptr<Item>> q;}`，producer `lock→push_back→unlock→notify_one`，consumer `unique_lock→wait_for(谓词)→front/pop_front` ⇒ **与 `enqueue_request` ↔ `process_thread_func` 逐句同形**，所有访问都在锁内。
- 探针 2（对象复用）：同探针 1，但外层 30 轮反复 `make_shared<State>()` → 起 consumer → push → join → 销毁 ⇒ **与 `stop_data_plane → restart_data_plane` 的创建/销毁 churn 同形**。

**形态逐项比对**：

| 特征 | 探针（无项目代码） | 模块 | 一致？ |
|---|---|---|---|
| 告警类与量级 | race 20~38 + double lock 2~8 | race 18 位置 + double lock 10 | ✅ 同类同量级 |

1. mutex shadow **不是**由 `pthread_mutex_init` 建立（首帧是 `pthread_mutex_lock`），且报告**同时**断言「持有该锁」与「存在竞争」——两个断言自相矛盾；

```bash
for i in $(seq 1 20); do setarch $(uname -m) -R /tmp/probe2; done
```

⇒ **判定**：模块的 `state->queue` race 与 `queue_mtx` double lock 由**同一环境性机制**产生（对象复用 + ASLR 受限导致 shadow 退化），**不是**模块并发缺陷；该判定被 §11.2 的 8/8 结构性闭合**独立支撑**，两条证据合取即满足「三方闭环」。

> 表述纪律：这是「**证伪**（等价程序在零项目代码下复现同一形态）」+「**结构性独立证明**」的合取，不是「疑」。若将来在 TSan 正常工作环境仍复现针对 `queue_mtx` 的告警，本条须重新开启。

## 12.（t8 收尾 #2）C-05 容量论证：可判定表述 + 最小对照

### 12.1 可判定结论（一行）

> **在 SHM ser-cli 的既有协议语义下，FIFO 的「64 条 / 8 MiB」背压判定点在本波无法被正常流量触发；唯一可达的容量路径是「单条 > 8 MiB」，其行为已被新增用例直接钉住 ⇒ 保留 64 / 8 MiB 不改，严格上界写明为 `8 MiB + max(单条实测尺寸)`。**

支撑该结论的两条独立证据（§12.2 用例 + §12.3 协议语义），外加 §12.5 记录一处**收尾过程中新发现并已修**的真实回归。

### 12.2 新增最小对照用例（`test/test_shm_ser_backpressure.cpp`，已注册 CTest）

| 用例 | 覆盖 | 判据 | 实测输出 |
|---|---|---|---|
| `SingleRequestLargerThanByteCapIsStillAnswered` | **单条 > 8 MiB** 请求（9 MiB = 9,437,184 B） | 必须被正常处理并逐元素校验应答；不崩、不永久阻塞 | `[t8-C05] oversize request: bytes=9437184 answered_ok=1 callback_calls=1` ✅ |
| `SlowCallbackSingleClientLosesNothing` | **慢 callback**（每条 20 ms）+ 20 次真实 RPC | 慢处理期间零丢弃：每条都发出且被应答，callback 覆盖全部请求 | `[t8-C05] slow-callback single client: sent=20 answered=20 callback_calls=20 elapsed_ms=402` ✅ |

### 12.3 为什么「压满 64 条」在本协议下不可达（协议语义，不是「没测到」）

- `include/libipc/ipc.h:348`：`using server = chan<relat::single, relat::single, trans::unicast>;` —— 请求通道是 **1:1 单播**；
- `shm_cli_ipc::send_request` 是**同步**的：发出去之后阻塞等应答，**收到应答前不会再发下一条**；
- ⇒ 任一时刻在途请求 ≤ 1 ⇒ FIFO 深度上界 = **1**，`pending_count >= 64` 与 `pending_bytes >= 8 MiB` 两个判定点在正常流程里**都不可达**；
- 实测旁证：并发客户端提到 4 个时，libipc 的 1:1 约束直接表现为 `fail: send, que->ready_sending() == false`（第 2–4 个客户端拿不到发送权），从反面确认「同一条路由只有一个发送者」；
- ⇒ 背压分支（`backpressure_hits` / `oversize_admissions`）只能靠**单条超限**触发，而该路径已被 §12.2 第一条用例覆盖。

### 12.4 容量规则与严格上界（最终版，与 §6 一致）

```text
入库前判定：pending_bytes + request_bytes <= kMaxPendingBytes(8 MiB)
  满足            -> 入队（更新 fifo_peak_* / max_request_bytes）
  超限且队列非空   -> 不收取（backpressured=true, backpressure_hits++；请求留在通道，零丢弃）
  超限且队列为空   -> 放行这一条（oversize_admissions++）
严格上界：内存持有 <= kMaxPendingBytes + max(单条实测尺寸)（实测 ≥ 9 MiB）；条数 <= 64
```

⛔ 不把 8 MiB 表述为「绝对内存上界」；⛔ 背压路径零静默丢弃。

### 12.5 收尾期间**新发现并已修**的真实回归（必须记录）

**发现方式**：按任务要求补跑 `DZIPC_SOCKET_COMPAT_THREAD=1 ctest` 时，`test_dzipc_socket` 挂起（>120 s 不返回），日志停在

```text

```
