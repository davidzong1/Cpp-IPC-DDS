### 2.4 裁定

**接受 t8 的「误报（已证伪）」结论。** 依据是三条**独立**证据的合取，且其中第①③条由我本次亲自复跑/扩展：

1. **零项目代码的等价程序在同一 `setarch -R` 环境下复现同形态告警**（我复跑：3/20 与 18/20，逐类逐量级一致）；
2. **要素隔离**（我新增）：去掉 condvar 后连「mutex+deque+对象复用」都 0/20 告警 ⇒ 触发要素锁定在 condvar/shadow 交互，而非项目代码结构；
3. **结构性证明**（我逐点核对）：8/8 容器访问在锁内 ⇒ 从语言语义上不存在竞争；
4. **告警零帧命中 P0 修复对象**（我 grep 计数 = 0）。

**边界（必须写明，避免过度外推）**：这是「**在这台机器的 ASLR 受限环境下、这批具体告警**」的证伪，**不是**「TSAN 对本项目无用」的结论。`/proc/sys/vm/mmap_rnd_bits` 本次仍**不可读**（`权限不够`）⇒ 无法通过调参消除环境失真，「等价探针复现 + 要素隔离」是当前可得的最强证伪证据，这一表述我认可。若将来在 TSan 正常工作的环境（可读 mmap_rnd_bits、无需 `setarch -R`）仍复现针对 `queue_mtx` 的告警，本条须**重新开启**（与 t8 §11 末尾的纪律表述一致）。

`thread leak`（2+30）：池是**故意泄漏的进程级单例**（`recv_worker.h` / `socket_recv_worker.h` 文件头已论证），日志末尾即 `SocketRecvWorker[i]: idle exit` ⇒ **设计使然，非缺陷**，我认可该归类。
