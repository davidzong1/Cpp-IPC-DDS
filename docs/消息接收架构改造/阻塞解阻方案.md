# 消息接收架构改造：Review 阻塞解阻方案

> 输入：[`交叉Review报告.md`](交叉Review报告.md)、[`维度C失败原因分析.md`](维度C失败原因分析.md)
> 适用基线：`HEAD=1d38512`（t7 review 所记录基线）。开始修复前必须重新核对当前 HEAD 和对应代码；若代码已变化，先按 finding 逐条重判，不能直接把历史结论当成现状。
> 目标：给 t8 一个范围受控、可验证的修复顺序，并为 t9 提供明确的通过判据。

## 1. 阻塞判断

t7 的 `needs_revision` 由维度 C 未闭环触发。真正阻止继续收尾的是 C-01 的 `shared_ptr` 并发读写未同步；它是 C++ 数据竞争，功能测试通过不能消除该风险。C-02 是同类问题。C-03/C-04 属于单消费者契约没有在兼容接收路径完整落地；虽然报告判断当前构造路径下双收概率低，仍须修复，避免后续路径变化时出现静默双收或静默无收。

C-05 是待量化的资源设计问题，不是已经证明的故障。C-06～C-08 是停机次序和可观测性缺口。B-01、B-02 是文档/验收口径收尾项，不应与数据竞争混成一个 blocker。

## 2. 修复原则

1. **先修指针同步，再谈压力验证。** 对象成员中的 `shared_ptr` 自身需要独立同步；`message_mtx_`、`topic_msg_mtx_` 和 `state->mtx` 保护的是不同对象，不能代替它。
2. **持锁只复制快照。** 通过短临界区取得 `receive_state_` 的局部 `shared_ptr`，释放成员锁后再访问 `state->mtx`、队列锁或执行 callback。禁止持有成员锁进入可能阻塞或调用用户代码的路径。
3. **所有接收者竞争同一个 owner 原子状态。** worker 和兼容线程必须以同一个 `state->owner` 做 CAS；不能依赖 `req_route_` 是否存在来决定是否 claim。
4. **资源上界要覆盖极端消息。** 64 条 / 8 MiB 是队列约束，需另外说明单条请求超过 8 MiB 时的处理规则和额外持有上界。
5. **证据按 finding 验收。** 静态访问点审计、并发回归和容量压力实验分别回答不同问题，不能用一次全量 CTest 绿替代。

## 3. P0：收口 `receive_state_` 并发访问（C-01、C-02）

### 3.1 修改方式

在 `socket_ser_ipc` 和 `socket_sub_ipc` 中分别为 `receive_state_` 增加 `mutable std::mutex receive_state_mtx_`，并提供统一访问口：

- `current_receive_state() const`：锁内复制并返回 `shared_ptr` 快照。
- `set_receive_state(state)`：锁内替换成员指针。
- `clear_receive_state(expected)` 或等价的生命周期操作：锁内清空；若需要防止旧代误清新代，可比较 generation/指针后再清。

逐个替换下列访问：

- socket 服务端：`reset_message()`、`reset_callback()`、`process_thread_func()`、`start_receive_path()`、`restart_data_plane()` 和 `teardown_receive_path()`。
- socket 订阅端：`reset_message()`、`InitChannel()`、`start_receive_path()`、`teardown_receive_path()`。

所有读写成员指针的地方都必须经过访问口；拿到局部快照后才锁 `state->mtx` 或队列锁。`receive_route_`、`worker_mode_` 等生命周期字段若只由串行的 Init/stop/restart 路径访问，应在代码注释和 API 约束中写明；若它们也允许并发调用，则用生命周期锁覆盖整个建/拆路径，不能只给 `receive_state_` 加锁后声称整个生命周期线程安全。

### 3.2 锁序

推荐顺序：

```text
message_mtx_ / topic_msg_mtx_（如确有需要）
  → 短暂取得 receive_state_ 快照并释放 receive_state_mtx_
  → state->mtx 或 state 队列锁
```

`receive_state_mtx_` 不得与 `state->mtx` 同时持有。避免在成员锁内 clone 大对象、等待条件变量、join 线程、调用 callback 或调用 worker pool。

### 3.3 可判定验收

- 对 `receive_state_` 的每个读、写、reset 命中逐一登记调用访问口；不得留下直接无锁成员访问。
- C++17 下不采用 `std::atomic<std::shared_ptr<T>>`。
- 增加/补齐压力用例：并发执行 socket 服务端 `reset_message/reset_callback` 与 stop/restart；并发执行订阅端 `reset_message` 与 Init/teardown churn。每轮验证无崩溃、无挂起、消息仍可收取。
- 若项目构建允许，单独构建并运行 ThreadSanitizer 版本；若不兼容或不可用，记录原因。TSAN 通过是补充证据，静态访问点闭合仍是必需项。

## 4. P1：兼容接收路径统一 owner CAS（C-03、C-04、C-08）

### 4.1 推荐设计：把 claim/release 放在 shared state

在 `SerState`/socket receive state 上提供无锁的 `try_claim_recv(owner)`、`release_recv()`、`recv_owner()`；内部直接操作现有 `std::atomic<RecvOwner> owner`。`SerRequestRoute` 及 socket route 的接口转调这些 state 方法。这样兼容路径即使没有成功注册 worker route，也能遵守同一份独占状态机。

### 4.2 线程入口及退出

- socket 服务端 `response_thread_func()`：启动循环前从安全访问口取 state，claim `compat_thread`；失败时打印 route/topic 与当前 owner 并返回。线程退出用 RAII guard 保证 release，覆盖正常停止和异常退出。
- SHM 服务端 `response_thread_func()`：不再以 `req_route_ != nullptr` 作为 claim 条件；从 `current_ser_state()` 取 state 并在任何回退模式下 claim。失败时诊断；退出时释放同一 state 的 owner。
- socket 订阅兼容线程：保留对 state 的 claim/release，但 claim 失败也打印 route key。release 建议统一用 RAII guard。
- worker 注册仍由 `add_route()` 通过同一个 owner CAS 抢占；注销由 `remove_route()` 释放。不要引入两套 owner 状态。

如果不改为 state 方法，最低限度的备选是：所有回退路径在任何可能返回前创建并保存有效 route，并保证其成员访问本身同步。但该方案扩大 `req_route_` 生命周期耦合，优先级低于 state 级 CAS。

### 4.3 验收

- 三个兼容接收入口都能看到 `compat_thread` claim/release；失败分支有显式诊断。
- 覆盖 worker 注册失败/nodelet/fork 回退时 owner 从 `none → compat_thread → none`；停止后重启能再次成功 claim。
- 验证 worker 注册和兼容线程不能同时成功 claim；重复 release 是安全的。

## 5. P1：完善注销诊断和停机顺序（C-06、C-07）

- socket subscriber teardown 一开始同时设置 `stopping=true` 和 `running=false`，随后再 `cancel_wait`、join；维持“先禁止新工作，再唤醒当前等待”的顺序。
- 三个 `wait_quiescent()` 检查 `wait_for` 返回值。超时只输出一条带 route/topic、generation、等待上限和当前 `receive_inflight` 的错误诊断，然后按既有有界注销策略继续，不改成无限等待。
- 诊断输出不要在持有 quiesce/队列/member mutex 时格式化或写日志；先保存超时和计数快照，释放锁后输出。

## 6. P1：闭合 SHM FIFO 资源预算（C-05）

### 6.1 不先拍脑袋改 8 MiB

现有 FIFO 保存 `ipc::buffer`，队列字节上限不会自动代表共享内存池的 chunk 数量上限。报告中 `large_msg_cache=32` 与当前 `include/libipc/def.h` 的 40 存在口径差异，且 C-05 报告没有实测证明 8 MiB 已造成 DZFlat 回退。因此先把容量和实际池档逐一核实，再做隔离压力对照；不能直接把结论写成“已影响 Publisher”。

### 6.2 实验矩阵

同一构建、同一固定数据集和并发度，至少跑以下两组并重复多轮：

| 组别 | 请求处理 | SHM FIFO | 观测 |
|---|---|---|---|
| 基准组 | 原兼容接收路径（或可复现的同步处理基准） | 不产生新增排队持有窗口 | 各尺寸档池可用量/借样成功率，`DzFlatFallbackCount()` 增量，吞吐、延迟 |
| 改造组 | worker + process thread | 64 条 / 8 MiB 及代表性大请求 | 同上，并记录 FIFO 峰值条数/字节、请求最大尺寸、背压次数 |

覆盖请求尺寸：常规消息、接近各 chunk 尺寸档边界、大于 8 MiB（若协议允许）、多 server 同时拥塞；分别观察慢 callback 与快 callback。每组开始前重置计数并使用干净、同等状态的共享内存池，保存命令、构建指纹、原始计数和结果。

### 6.3 容量和超大请求规则

落实以下一项并写进方案：

1. **优先：硬限制单请求最大尺寸**，保证 `pending_bytes + request_bytes <= cap`，超限走已有协议错误/拒绝路径，并验证不会静默丢失或破坏连接；或者
2. **明确单个超大请求特例**：允许队列空时放入一个超过 8 MiB 的请求，同时记录严格总上界 `8 MiB + max_request_size`，且同时限制条数；必须由协议现有限制给出 `max_request_size`；或者
3. 若没有可依赖的消息尺寸上限，则修改接收/缓冲设计，使入队前可安全判断容量，避免“先收下超大 buffer 再发现超限”。不得把 8 MiB 描述成绝对内存上界。

实验若显示 DZFlat 回退率无统计显著上升且资源峰值在明确界限内，可以保留 64 / 8 MiB，并把测量条件和上界依据写入方案；否则调小 byte cap/条数或减少持有完整 chunk 的窗口，再重跑对照。背压仍须保持零静默丢弃，并验证 `has_pending()` 的重检不会饿死其他 route。

## 7. 文档收尾（B-01、B-02）

- 更新 `shm_ser_cli线程池移植方案.md`：`recv_once()` 仅执行完整请求接收、基础 wire 判断和 FIFO 入队；用户 callback、响应序列化/发送由处理线程完成，明确对应裁决 D1。
- 修正收益口径：本波没有减少每 server 的处理/握手线程数；收益是接收等待/组包进入有界进程级 worker。线程总数相关数据按实际基线报告，不能写成“数据接收线程数受 worker 上限约束”而不加口径。
- B-02 选一种口径统一：更低风险的做法是改方案中的名字以匹配实际代码，保留已验证的 2000 ms / 128 取值；避免为命名一致而改动共享层常量。
