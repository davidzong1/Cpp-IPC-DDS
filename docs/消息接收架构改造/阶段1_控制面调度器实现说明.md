## 0. 结论摘要

1. **阶段 1 的目标是把控制面握手线程从 O(N) 降到进程级常数**：订阅 heartbeat（10ms）、发布 owner heartbeat（50ms）、stale 扫描（50ms）、peer 判死（2s）全部由 **1 条进程级调度线程**按项到期驱动，替代每实例 `std::thread`。
2. **数据面一行不动**：`subscribe_thread_`、`channel_mtx_`、`recv(50)`、队列、DZFlat/TLV 分流、adopt 配额、nodelet 快路径全部保持原样（§5）。
3. **落点两选一，CMake 代价不同**（§2.6）：
   - **推荐**：`include/dzIPC/common/shm_control_scheduler.h` + `src/dzIPC/common/shm_control_scheduler.cc` —— **零 CMake 改动**，`src/CMakeLists.txt:15` 的 `aux_source_directory(.../src/dzIPC/common SRC_FILES)` 自动收编。
   - **备选**：`include/dzIPC/threepools/` + `src/dzIPC/threepools/` —— **必须新增一行** `aux_source_directory(${LIBIPC_PROJECT_DIR}/src/dzIPC/threepools SRC_FILES)`，否则新 `.cc` **静默漏编**（不报错，只是不参与链接）。
4. **两条当前工作树的硬约束**：
   - `include/dzIPC/threepools/` 与 `src/dzIPC/threepools/` 目前是**空目录**（`ls -a` 仅 `.`/`..`；`git ls-files` 无输出）⇒ git 不跟踪空目录，他处克隆后目录不存在。
   - 项目标准是 C++17，但**无 `CMAKE_CXX_STANDARD_REQUIRED`、无 `CXX_EXTENSIONS`**，`build/**/flags.make` 里没有 `-std=`，实际靠 GCC 11.4 的默认 `gnu++17` ⇒ 新代码必须按 **C++17** 写（§6.3）。
5. **必须在阶段 1 就处理的真实回归风险**：现状 `sub_handshake()` 在 `control_plane_.open()` 失败时**在子线程里 `throw`**（`src/dzIPC/shm_pub_sub_ipc.cc:618-623`）——`std::thread` 入口未捕获即 `std::terminate()`。迁移到调度线程后，同一个失败会**杀掉整个进程并连累所有其它 topic**。协议因此强制"回调不得抛出 + 调度器兜底 catch + 坏项隔离"（§4.5）。
6. **可观测性是交付物的一部分**：需求 §10 阶段1 要求"记录扫描耗时和最大抖动"。`Stats`（§3.2）不是可选项。

### 1.1 收益口径（不要误读）

阶段 1 减少的是**空闲唤醒次数与上下文切换**，**不是** heartbeat 写入总量 —— 写入仍是 O(N)（每项每周期一次）。因此验收必须带读数：`Stats::tick_count`、`tick_overrun_count`、`tick_duration_max_ns`，以及 `/proc/self/status` 的 `Threads:`。

### 1.2 时间语义必须逐位保持

| 语义 | 值 | 现状出处 |
|---|---|---|
| 订阅 heartbeat | **10 ms** | `src/dzIPC/shm_pub_sub_ipc.cc:757`（`sleep_for(10ms)`） |
| 发布 owner heartbeat | **50 ms** | `src/dzIPC/shm_pub_sub_ipc.cc:179`（`sleep_for(50ms)`） |
| 发布 stale 扫描 | **50 ms**（与 owner heartbeat 同频） | 同上一行，同一循环体 |
| peer 判死超时 | **2 s** = 200 × 订阅 heartbeat | `src/dzIPC/shm_pub_sub_ipc.cc:158` `kPeerDeadTimeoutNs = 2'000'000'000LL` |
| 发布端无 peer 时 | **仍须 owner heartbeat**，仅跳过 stale 扫描 | `src/dzIPC/shm_pub_sub_ipc.cc:148`（`heartbeat()` 在 `collect_stale_peers` 之前，无条件） |

⚠️ **`2s` 是两份字面量**：`src/dzIPC/shm_pub_sub_ipc.cc:158` 与 `src/dzIPC/shm_ser_cli_ipc.cc:336` 各写了一份 `constexpr int64_t kPeerDeadTimeoutNs = 2'000'000'000LL;`。阶段 1 若把调度器周期做成 `ControlTiming` 结构（§3.1），应同时把这两份收敛到一处常量，否则调度器接管后会立刻出现**三份口径**。

## 3. `ShmControlScheduler` API

> 本节与 deliverable `ipc-protocol-phase1-shm-control-scheduler-design-3f30d9309170.md` §3 一致；该协议已在 `/tmp` 用 `g++ -std=c++17` 编译通过并实跑 20 条断言（附录 A 原始输出）。

### 3.1 类型与周期

```cpp
namespace dzIPC { namespace shm_control {

using ControlClock = std::chrono::steady_clock;

struct ControlTiming
{
    std::chrono::milliseconds sub_heartbeat{10};
    std::chrono::milliseconds pub_heartbeat{50};
    std::chrono::nanoseconds  peer_dead_timeout{2'000'000'000LL};
};
```

**周期按项传入、调度器不做全局假设**：将来要给实时话题单独调周期，不需要改调度器。

### 3.2 调度器

```cpp
class IPC_EXPORT ShmControlScheduler
{
public:
    using EntryId = std::uint64_t;
    static constexpr EntryId kInvalidEntry = 0;

    struct Stats
    {
        std::uint64_t tick_count{0};            // 已执行 tick 轮数
        std::uint64_t tick_overrun_count{0};    // 单轮耗时 > 最小到期周期的轮数
        std::int64_t  tick_duration_last_ns{0}; // 最近一轮耗时
        std::int64_t  tick_duration_max_ns{0};  // 最大轮耗时（扫描抖动上界）
        std::uint64_t tick_deferred_count{0};   // 因等待 in-flight tick 而延迟的注销数
        std::size_t   entry_count{0};           // 当前注册项数
    };

    static ShmControlScheduler& instance();

    EntryId register_subscriber(std::shared_ptr<SubControlState> state,
                                const ControlTiming& timing = ControlTiming{});
    EntryId register_publisher(std::shared_ptr<PubControlState> state,
                               const ControlTiming& timing = ControlTiming{});

    void unregister(EntryId id) noexcept;       // 同步注销，见 §4
    Stats stats() const;
    bool worker_active() const noexcept;
    std::size_t entry_count() const noexcept;

    ShmControlScheduler(const ShmControlScheduler&) = delete;
    ShmControlScheduler& operator=(const ShmControlScheduler&) = delete;
};
}}
```

**注册契约**：
- `state` 为空 ⇒ 返回 `kInvalidEntry`；
- `EntryId` **单调递增、永不复用**，`0` 保留为无效值（避免 ABA：迟到的 `unregister(旧 id)` 不会注销别人的项）；
- 注册**不执行任何回调**，第一次回调在下一个到期点。

### 3.3 状态抽象

```cpp
class SubControlState
{
public:
    virtual ~SubControlState() = default;
    // 每 10ms：首次 open 控制面、generation 检测与重建、detach、peer 心跳刷新
    virtual void on_sub_heartbeat(ControlClock::time_point now) = 0;
};

class PubControlState
{
public:
    virtual ~PubControlState() = default;
    // 每 50ms：owner heartbeat（无 peer 时也必须执行）+ subscribed_ 刷新 + verbose 迁移日志
    virtual void on_pub_heartbeat(ControlClock::time_point now) = 0;
    // peer_count() > 0；为 false 时调度器跳过 stale 扫描
    virtual bool has_peers() const = 0;
    // 每 50ms，仅当 has_peers() 为真：collect_stale_peers(dead_timeout) + disconnect_receivers(stale)
    virtual void on_pub_stale_scan(ControlClock::time_point now,
                                   std::chrono::nanoseconds dead_timeout) = 0;
};
```

**两条实现约束（写在头注释里，不是可选建议）**：
- ⛔ 实现**不得抛出**（§4.5）；
- ⛔ 实现**不得在回调内调用 `unregister`**（§4.4）。

### 3.4 RAII 注册令牌

```cpp
class ControlRegistration
{
public:
    ControlRegistration() noexcept = default;
    ControlRegistration(ShmControlScheduler* sched, ShmControlScheduler::EntryId id) noexcept;
    ~ControlRegistration() { reset(); }                 // 析构 = 同步注销

    ControlRegistration(ControlRegistration&&) noexcept;            // 可移动
    ControlRegistration& operator=(ControlRegistration&&) noexcept;
    ControlRegistration(const ControlRegistration&) = delete;       // 不可拷贝
    ControlRegistration& operator=(const ControlRegistration&) = delete;

    ShmControlScheduler::EntryId id() const noexcept;
    bool valid() const noexcept;                        // 未注册 ⇒ false
    void reset() noexcept;                              // 未注册时为空操作
};
```

默认构造即"未注册"⇒ **未调 `InitChannel()` 就析构的对象无需特殊处理**：`ctrl_reg_.valid()==false`，`reset()` 是无操作，与现状 `if (sub_handshake_thread_ != nullptr)` 天然跳过**行为等价**。

## 4. 注册令牌与同步注销时序

### 4.1 状态机

每项 4 态：`Active` → `Inactive` → `Erased`（`Erased` 后 id 永不复用）。

```text
register_*():   新建 Entry{Active, tick_inflight=false, next_due=now+period}
                → 插入 map（mtx 内）→ notify_all

unregister(id): [mtx]
                ① find(id)；未找到 → 直接返回（幂等）
                ② entry->inactive.store(true, release)          ← 标记 inactive
                ③ cv.notify_all()                               ← 唤醒调度器
                ④ 若 entry->tick_inflight:
                      ++tick_deferred_count
                      cv.wait(lk, [&]{ return !entry->tick_inflight; })  ← 等正在执行的 tick 完成
                ⑤ entries.erase(id)                             ← 摘除
                [mtx 释放] 返回

tick():         [mtx] 收集 { !inactive && !tick_inflight && now >= next_due } 的项
                     对每项置 tick_inflight = true
                [mtx 释放]
                对每项：Sub → on_sub_heartbeat(now)
                        Pub → on_pub_heartbeat(now); if (has_peers()) on_pub_stale_scan(now, timeout)
                [mtx] 每项：推进 next_due；tick_inflight = false；cv.notify_all()
                [mtx 释放]
```

**注销返回后的三条保证**：① 不再发起该 id 的新回调；② 在途回调已结算；③ 调度器不再持有 `state`。幂等：未知 id / `kInvalidEntry` / 重复注销均为无操作。

### 4.2 为什么 `tick_inflight` 必须在锁内标记

`tick()` 在**同一个临界区**内既检查 `inactive` 又设置 `tick_inflight`；`unregister()` 在**同一个临界区**内既设置 `inactive` 又检查 `tick_inflight`。共用 `mtx` 才使下面两条互斥：

- `tick` 先拿锁 ⇒ `tick_inflight=true` 已可见 ⇒ `unregister` 会等待，回调结算在返回之前完成；
- `unregister` 先拿锁 ⇒ `inactive=true` 已可见 ⇒ `tick` 不会选中该项，回调根本不会发起。

这是不变式 I2/I3 成立的机制。原型证据：注入 250ms 慢回调后 `unregister waited 249ms`。

### 4.3 "调度器不得保存裸 `this`"的落地

需求只禁止**调度器**保存裸 `this`，不禁止宿主内部自引用。

```cpp
// shm_sub_ipc（改动后）
class SubStateImpl final : public dzIPC::shm_control::SubControlState
{
public:
    explicit SubStateImpl(shm_sub_ipc* host) : host_(host) {}
    void on_sub_heartbeat(ControlClock::time_point) override;   // 转调 host_->...，不抛
private:
    shm_sub_ipc* host_;                                          // 宿主内部自引用
};
std::shared_ptr<SubStateImpl> ctrl_state_;
dzIPC::shm_control::ControlRegistration ctrl_reg_;               // 声明顺序在 ctrl_state_ 之后
```

**令牌的注销必须在宿主析构体内、成员销毁之前显式执行**，不依赖成员析构顺序：

```cpp
shm_sub_ipc::~shm_sub_ipc()
{
    { /* ① LocalPubSubRegistry 注销（现状 src/dzIPC/shm_pub_sub_ipc.cc:546-554 保持） */ }
    ctrl_reg_.reset();          // ② 控制面注销：返回后调度器不再持有 ctrl_state_，零回调
    running.store(false, std::memory_order_release);
    /* ③ 停 subscribe_thread_ / ④ disconnect + reset route（现状 :556-578 保持） */
}
```

理由：`ctrl_state_` 与 `ctrl_reg_` 都是成员，析构顺序由声明顺序决定；而"调度器仍持有 `ctrl_state_` 的 shared_ptr"期间若宿主已在销毁中，任何回调都会踩到半销毁的宿主。显式 `reset()` 把这件事从"顺序约定"变成"代码顺序"。

### 4.4 ⛔ 回调内不得调用 `unregister`（会自死锁）

若 `on_*_heartbeat` 内部调用 `unregister(自己)`，`unregister` 会在 ④ 步等待 `tick_inflight` 清零，而该标志正由**当前这次 tick** 持有 ⇒ 永久等待。

处置（推荐第 1 项）：
1. **协议禁止 + debug 断言**：在 `unregister` 里比较 `std::this_thread::get_id()` 与 worker 线程 id，命中则打印诊断并直接返回（不等待）。阶段 1 的真实调用点只有 `shm_sub_ipc`/`shm_pub_ipc` 的析构体，不可能从回调里注销；加断言是防将来误用。
2. 提供 `unregister_async(EntryId)`：只置 `inactive` 并唤醒，不等 tick。代价：返回时**不满足 I2**，阶段 1 用不到。
3. 回调改为锁内执行：**否决** —— 回调里注册/注销即自死锁，且会把 `disconnect_receivers`、`new ipc::route` 塞进调度器临界区，直接违反"扫描耗时必须有界"。

### 4.5 ⛔ 回调不得抛出（现状隐患的必修项）

现状 `sub_handshake()` 的 `control_plane_.open()` 失败会 `throw std::runtime_error`（`src/dzIPC/shm_pub_sub_ipc.cc:618-623`）。今天该异常发生在**该订阅自己的线程**里，未捕获 ⇒ `std::terminate()`，影响面是单个 topic 所在的**整个进程**。

迁移后同一失败发生在**调度线程**：异常逃出 `on_sub_heartbeat` → 逃出 `tick()` → 逃出 worker 线程体 ⇒ `std::terminate()`，影响面扩大到**该进程全部 topic 的控制面**。因此协议强制：

- `on_*` 实现内部 `try/catch(...)`：`open` 失败 → 记一次告警（**不受 `verbose_` 约束**，参照 `src/dzIPC/shm_pub_sub_ipc.cc:694-704` 的"静默失败不该要求开调试开关"先例）+ 该项下次到期改为 100ms 退避重试；
- 调度器在 tick 外层 `try/catch(...)` 兜底：捕获后把该项标 `inactive`、`entries.erase`、打印含 `EntryId` 的诊断。**宁可丢掉一个坏项的控制面动作，也不要让一个坏项带走整个进程的控制面。**

### 4.6 四条可判定不变式（验收直接断言这些）

| 编号 | 不变式 | 判定方法 |
|---|---|---|
| **I1** | `unregister` 返回后**不再发起**该 id 的新回调 | 注销后取基线计数，等待 ≥3 个周期，计数不变 |
| **I2** | `unregister` 返回前**在途回调已结算** | 注入 250ms 慢回调，断言 `unregister` 阻塞 ≥150ms 且返回后 `in_callback==false` |
| **I3** | `unregister` 返回后调度器**不再持有** state 对象 | `shared_ptr::use_count` 回落 + 全局存活计数回落 + 析构标志置位 |
| **I4** | 并发 register/unregister 与 tick 交错：无数据竞争、无死锁、无崩溃 | 4 线程 × 600ms churn，`late_calls == 0`；ASan 干净 |

### 4.7 调度循环的实现要点

1. **1 条线程、按项到期、睡眠合并**：维护 `Entry::next_due`，worker 计算"距最近到期项的等待时长"并 `cv.wait_for`。**不是**固定 10ms 轮询 —— 若只有发布项在册，轮询周期就是 50ms，空闲唤醒直接减半；无任何项时无限期 `cv.wait`。
2. **不追赶风暴**：`next_due` 推进用 `next = old + period`，若已落后则对齐到 `now + period`。理由：一次长 tick 之后不能让该 topic 立刻被连续补发 N 次（会把"扫描抖动"放大成"心跳风暴"）。
3. **回调在锁外执行**：锁内收集 due 列表并置 `tick_inflight=true`，**出锁**依次回调。既避免回调期间阻塞注册/注销，也避免"回调里再注册"自死锁。
4. **worker 启动**：构造期启动，`instance()` 内完成。原型实测 `instance()` 后线程数 +1，此后注册 200 项**线程数不再变化**。

### 5.1 阶段 1 与数据面唯一的交界面：`channel_mtx_`

阶段 1 不动数据面，所以 `subscriber_`（`shared_ptr<ipc::route>`）仍由 `subscribe_thread_` 在 `channel_mtx_` 内 `recv(50)`（`src/dzIPC/shm_pub_sub_ipc.cc:791-798`）。重建分支必须**继续**持有 `channel_mtx_`（现状 `:642-653`、`:657-663`、`:670-675`、`:734-741` 都是如此）。

## 7. 现有握手循环的状态拆解（迁移依据）

`SubControlState`/`PubControlState` 不是凭空设计，而是把现有两个循环体逐句拆成"每 tick 执行一次的纯动作"。

### 7.1 `shm_sub_ipc::sub_handshake()`（`src/dzIPC/shm_pub_sub_ipc.cc:616-762`）

| 现有语句 | 频次 | 迁移到 |
|---|---|---|
| `control_plane_.open(...)`（失败即 throw，`:618-623`） | 一次 | `on_sub_heartbeat` 内 `ensure_open_()`（一次性 + 退避重试，且**不得抛出**，§4.5） |
| 读 `generation()`/`state()`（`:628-629`） | 每 tick | `on_sub_heartbeat` |
| `Ready && gen!=0 && (未握手 \|\| attached!=gen)` 重建分支（`:630-747`） | 事件 | `on_sub_heartbeat` → `rebuild_attach_(gen)` |
| `remove_peer`/`release_peer_slot`/`subscriber_->release()`/`new ipc::route`/`add_peer`/`connected_id()`/`acquire_peer_slot`（`:636-707`） | 事件 | 同上（**必须持 `channel_mtx_`**，§5.1） |
| `cc_id == 0` → 不置 `handshake_completed`、退 peer、`sleep(100ms)` 重试（`:687-713`） | 事件 | `rebuild_attach_` 返回 `Retry`，由**项内**下次到期时间做 100ms 退避 |
| `state != Ready` → `handshake_completed.exchange(false)` + `disconnect` + 退 peer/slot（`:725-746`） | 事件 | `on_sub_heartbeat` 的 detach 分支 |
| `peer_heartbeat(peer_slot_)`（`:753`，slot<0 时空操作） | **每 tick** | `on_sub_heartbeat` 末尾 |
| `sleep_for(10ms)`（`:757`） | 每 tick | **删除**；由 `timing.sub_heartbeat` 到期驱动 |

**关键**：`peer_registered`/`attached_generation`/`peer_slot_` 是**每个订阅项自己的记账**，而 `TopicControlPlane::add_peer/remove_peer` 改的是**共享段里的 `peer_count`**（`src/dzIPC/common/control_plane.cc:164-185`）。因此这三个字段必须留在项内，**不能**因为"同一 topic 共用一个控制面"就把记账提到 topic 级 —— 否则同进程两个订阅项会重复 `add_peer`，`peer_count` 偏大 ⇒ 发布端 `subscribed_` 与 stale 判定全部失真（§8 R4）。

### 7.2 `shm_pub_ipc::pub_handshake()`（`src/dzIPC/shm_pub_sub_ipc.cc:140-183`）

| 现有语句 | 频次 | 迁移到 |
|---|---|---|
| `control_plane_.heartbeat()`（`:148`，owner 心跳） | **每 tick，且不得因无 peer 而停** | `on_pub_heartbeat` |
| `collect_stale_peers(2s)` + `disconnect_receivers(stale)`（`:158-169`） | 每 tick | `on_pub_stale_scan(now, dead_timeout)`，**仅当 `has_peers()` 为真** |
| `peer_count()>0` → `subscribed_.store(has_peer)`（`:170-171`） | 每 tick | `has_peers()` 读 `peer_count()>0`；`subscribed_` 写入放 `on_pub_heartbeat` 末尾 |
| `has_peer && !had_subscriber` 的 verbose 日志（`:172-178`） | 事件 | 项内 `had_subscriber_` |
| `sleep_for(50ms)`（`:179`） | 每 tick | **删除**；由 `timing.pub_heartbeat` 到期驱动 |

口径澄清：需求原文是"仅可在 `peer_count() == 0` 时跳过 stale 扫描"，计划文档 §4 阶段1 写的是"可仅在 `peer_count() > 0` 时跳过"—— 两者**语义等价**（都是"有 peer 才扫"）。本文采用需求文档（`事件驱动线程池需求.md` §3.1）的口径：`peer_count()==0` ⇒ 跳过扫描；`on_pub_heartbeat` 无条件执行。

### 8.1 回滚

阶段 1 改动集中在 2 个文件 + 2 个新文件（推荐落点）；`git revert` 单个 commit 即可。数据面一行未动，因此回滚不影响任何消息语义。

### 8.2 TSan 不构成本阶段合并门（测量伪影）

原型报告记录：`-fsanitize=thread` 在同一份"语义上不可能死锁、程序正常跑完"的最小复现（单例 `Impl{mutex,cv,map}` + worker `unique_lock`/`wait_for`/`unlock`/`tick`/`relock` + 主线程 `lock_guard` 插入）上也报 `double lock of a mutex` + `data race`。环境：glibc 2.35、g++ 11.4.0；本机 TSan 与该模式不兼容（`unexpected memory mapping`，需 `setarch -R` 绕过 ASLR 才能启动）。

⇒ 并发正确性由 §4.6 的四条不变式 + ASan + 慢回调计时断言来守；**不要**把 TSan 是否干净作为合并门。若 leader 要求 TSan 门，需换环境并先在最小复现上确认基线干净。
