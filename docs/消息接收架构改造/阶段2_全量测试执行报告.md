### 2.1 为什么必须加测试缝（而不是"随机压力碰窗口"）

- **§4.1 的窗口只有几条指令宽**：`recv()` 返回到 `release_receive()` 之间。方案原文禁止"以随机压力碰撞窗口"，要求"用条件变量或测试钩子在「recv 返回」与「分流入队」之间暂停"。不暂停就**不可能**确定性命中 —— v4 只读验收正是因此把「在收包循环加 generation 判断」这条变异判为「靠**无人写该判断**成立，不是测试守住的」。
- **§4.2 要求记录因果顺序**：v4 §3.2 已实测证否了另一条路 —— 在 `recv(50)` 下用析构**耗时**做判据不可行（基线 27/28/29 ms 与删掉 disconnect 的变异体**逐样本相同**）。析构顺序在外部不可见，只能在内部打点。

钩子的设计约束写在头文件里：默认关闭、行为逐位不变、**不持锁时调用**、`kAfterRecv` 点钩子不得阻塞（此时 `inflight == 1`）、只有 `kAfterRecvRelease` 点允许阻塞（此时 `inflight == 0`）。阶段 3 提取 `process_received_buffer` 时两个收包点必须随函数体迁移。

## 4. 三项补强守门

### 4.1 I5 确定性守门（方案 §4.1）

**用例**：`test_shm_i5_pop_buffer`（3 条）

固定事件序列（方案原文）：recv 已返回带唯一序号的非空 buffer → 在收包线程处理前推进 generation → 放行 → 断言该序号恰好入队一次。

实现方式：钩子把收包线程停在 `kAfterRecvRelease`（此刻 `inflight == 0`，重建方能推进到 §4 第 5 步 release 旧 route）；主线程用测试自己打开的 `TopicControlPlane` 调 `begin_rebuild() + set_ready()` 推进 generation，再**轮询 `peer_count()` 归零→回 1**（因果条件，不是 sleep）判定重建完成，然后放行。

| 用例 | 判据 |
|---|---|
| `PoppedTlvSurvivesGenerationRebuild` | 序号恰好入 `msg_queue_` **一次**；宽/高/载荷逐字节等于发送端构造的那条；`tlv_accepted == 1` 且 `defects() == 0` |
| `PoppedDzFlatSurvivesGenerationRebuild` | 借样段进 `view_queue_`；段头 msg_id / schema_hash 正确；**前 `total_size` 字节逐字节相同**；clone 队列不得同时冒出一条 |
| `NoRebuildControlDeliversExactlyOnce` | 阴性对照：无重建时也必须恰好一条（否则上面两条的 `got == 1` 失去参照） |

**正对照**（防"窗口没打开"的伪绿）：每条承重用例都断言钩子 `hits() > 0`、`paused_size() > 0`、且 `new_gen > old_gen`。

### 4.2 析构唤醒集成守门（方案 §4.2）

**用例**：`test_shm_sub_dtor_gate`（2 条，子进程 + 15 s 父进程硬超时）

`DtorWakesInflightRecvInOrder`（10 轮）三条**互相独立**的判据：

1. **因果序**：每轮析构的 6 个阶段点严格递增 `16(注销) → 17(stop_and_wake) → 18(join 收包) → 19(join 握手) → 20(quiescent) → 21(release)`。方案 §4.2 明确要求的「registry 注销发生在 stop 之前」即 `o[0] == 16 < o[1] == 17`。
2. **叫醒而非超时**：存在「stop_and_wake 之后」的 recv 返回，其 `connected_id() == 0` —— disconnect 已生效。删掉析构的 `stop_and_wake()` 时该事件不存在（收包线程等 50 ms 超时后 `running` 已为 false，循环直接退出）。
3. **计数面**：`WakeupArtifactCount()` 增量 ≥ 1（与 ② 互为独立证据：② 看 libipc 句柄状态，③ 看上层守门是否真被走到）。

实测：`rounds=10 woke=10 recv_after=10 artifacts=10 peers=1`（peers=1 是占位 keeper，见下）。

`DtorWakeIsNotControlPlaneDriven`（阴性对照）：publisher 全程存活、控制面**保持 Ready**（析构前显式断言 `state() == Ready`），证明叫醒不是靠"控制面离开 Ready 触发的 stop_and_wake"；顺带断言析构前的真消息被取到、析构期的那次叫醒没吞掉它。

**不断言析构耗时** —— v4 §3.2 已证该判据无判别力。

**多轮之间必须留一个存活的占位订阅者（keeper）**：`pub` 一析构，其 `pub_handshake` 收尾就会 `set_stopping()`，把**下一轮**要用的控制面置成 Stopping ⇒ 下一轮订阅者永远 attach 不上。首版实现没有 keeper，实测症状就是第 2 轮 `fail:sub_never_attached`。

### 4.3 Ready 状态转换（方案 §4.3）

**用例**：`test_shm_ready_transition`（3 条）

| 场景 | 判据 |
|---|---|
| Ready → 非 Ready（同 generation） | `peer_count()` 归零（`remove_peer` 是唯一能让它归零的路径）；generation 不变；此后发布**不投递**；wire 计数不被污染 |
| 非 Ready → 新 generation Ready | 重新 attach（`peer_count() == 1`）；新消息**恰好一条**且内容正确；无重复投递 |
| 转换全程无伪影 | 两轮 `set_stopping + begin_rebuild + set_ready`，无发送方 ⇒ 用户队列必须为空；`tlv_accepted == 0` 且 `tlv_id_skipped == 0`；**正对照**：`WakeupArtifactCount() > 0` |

第三条每轮推进前先用测试缝等"收包线程确实在 recv 循环里"（`kAfterRecvRelease` 计数前进），否则 disconnect 可能落在两次 recv 之间 ⇒ 不产生伪影 ⇒ 正对照失败。这是把"前提成立"变成**因果条件**而不是靠 sleep 猜。

**未覆盖（按方案 §4.3 原文标注为间接覆盖，不冒充集成覆盖）**：

- `add_peer` 第一次失败、第二次成功 —— `TopicControlPlane` 是具体类，无虚函数、无 friend、`shm_sub_ipc` 也不接受注入（`include/dzIPC/shm_pub_sub_ipc.h:198`）；要在 `sub_handshake` 的 `generation()` 读取（`:655`）与 `add_peer`（`:684`）之间强制失配只能靠竞态 ⇒ **做不到确定性**。该分支的**调用序列**由 RouteSession 单测 `StopThenSuccessfulRebuildReopensLeases`（`test/test_shm_route_session.cpp:465`）建模。
- `cc_id == 0`（连接位耗尽）—— 由 `test_shm_receiver_cap` 独立覆盖（33 订阅者），未重复造。

## 7. 定向变异（方案 §7）

`scripts/stage2_mutation.py`。纪律：变异只在 `/tmp` 隔离副本上进行（rsync 工作树，排除 `build/`），每次校验 marker 落上、`ldd` 复核实际加载的是变异库；跑两遍（全量记红集 + 按期望用例过滤判承重）。

| **X5** | **recv 返回后按 generation 不匹配丢弃 buffer** | **test_shm_i5_pop_buffer** | `PoppedTlvSurvivesGenerationRebuild` + `PoppedDzFlatSurvivesGenerationRebuild` | ✅ |

| X7 | 伪影门只扫尾 12 字节 | test_wakeup_artifact | `RealDzFlatOfArtifactLengthIsNotFlagged` | ✅ |

**8/8 全部被指定用例杀死**。要点：

- **X5 / X6 是本轮新增守门的直接证据**：这两条正是 v4 只读验收判为「集成层零守门 / 靠无人写该判断成立」的失效模式，现在各有专门用例把守。
- **X2 / X3 的"被杀"形态是 abort / 挂死，不是 FAILED 行**：X2 破坏 I2 后 `begin_rebuild` 的等待与 `release_receive` 互相错位，用例走到 `terminate`（rc=-6）；X3 放行新 lease 使计数不配对，`wait_quiescent` 永不返回（rc=124，120 s 超时）。判定脚本因此把「用例已开始执行 + 超时/信号」也算杀死 —— 只认 `[  FAILED  ]` 行会把这两条漏判成"不承重"。这是本轮踩到并修掉的一个判定陷阱。
- **X8 多杀一条**（`RealMessageOnMsgIdZeroTopicIsStillDelivered`）：删掉伪影门后，同长度真 TLV 的用例也会红 —— 属于同一缺陷的连带面（伪影与真消息在同一队列里），已记录为**越界红**，不是缺陷。
- **X2 的两遍判定**：全量跑时 `RebuildRejectsNewAcquire` 先 abort，把目标用例挡在后面 ⇒ 红集为空。按期望用例过滤单跑后目标用例确实红。因此脚本固定跑两遍：全量（看"还打破了什么"）+ 过滤（判承重）。
- **工作树零污染**：`git status --porcelain` 实验前后逐字一致；仓内 `grep -c MUTANT` 只在脚本自身（变异模板字符串）命中。

## 9. 对方案文本的两处订正（必须记录）

1. **`--gtest_brief=1` 在本仓不可用**。方案 §6 / §6.1 的脚本原文用了它，但本仓 gtest 是 **1.10.0**（`CMakeLists.txt:131` 的 `GOOGLETEST_VERSION`），而该旗标是 **1.11** 才加入的。实测直接 usage error + 非零退出 ⇒ **照抄会让每个目标都判失败**。三个 harness 均已去掉该旗标，改为逐目标统计 `[       OK ]` / `[  FAILED  ]` / `[   SKIPPED ]`。
2. **`--gtest_filter` 单跑是承重判定的必要条件**（§7 变异的判定）。原因见 §7 的 X2：一个变异可能让**别的**用例先 abort/挂死，把目标用例挡在后面 —— 只看全量跑的输出会把"目标用例确实被杀死"漏判成"该臂不承重"。变异脚本因此固定跑两遍。

**ThreadSanitizer**：按方案 §8 原文，TSAN 是"额外证据、非硬门槛"。本轮**未运行**（本仓无现成 sanitizer 配置，且 TSAN 与共享内存映射的已知交互会产生第三方库告警）。本报告的"无数据竞争"级结论是「计数精确归零 + 20 轮无挂死 + shuffle 稳定」，**不是 TSAN 证明**。

## 11. 已知限制与残留风险

| 项 | 说明 |
|---|---|
| `add_peer` 首次失败分支 | **间接覆盖**（RouteSession 单测建模调用序列），无集成级确定性用例。原因：`TopicControlPlane` 无注入点，强制失配只能靠竞态（§4.3） |
| `cc_id == 0` 分支 | 由 `test_shm_receiver_cap` 独立覆盖，本报告不重复计入 §4.3 的新增覆盖 |
| TSAN | 未运行（§10） |
| 复跑结论的边界 | 20 轮全绿**不等于**无竞态证明（方案 §6.1 原文） |
| 段残留 | 新增的 `test_shm_sub_dtor_gate` 在**子进程**里跑，子进程用 `::_exit()` 退出（多线程 fork 后不能走普通 exit/栈展开）⇒ 段清理必须在 `_exit` 前**显式**调用。首版只靠 RAII 析构，实测每轮残留 12 个段（`*_WAITER_*` / `QU_CONN` / `_topic_control2`）；改为 `child_exit()` 统一出口后实测 delta = 0 |
| 测试缝的迁移义务 | 阶段 3 提取 `process_received_buffer` 时，`kAfterRecv` / `kAfterRecvRelease` 两个收包点必须随函数体一并迁移，否则阶段 5 的 worker 会各自漏掉一处（与 `IsWakeupArtifact` 的迁移守则同一条理由） |
