# 阶段 2 · RouteSession 全量测试方案

> 目的：为阶段 2 主线实现提供可重复、可定位、能发现静默并发错误的测试与验收流程。
> 范围：`RouteSession` lease 协议、`shm_sub_ipc` 收包/握手/析构接入、disconnect 唤醒伪影门、已有 SHM pub/sub 与 nodelet 回归。
> 不包含：阶段 3 分流函数提取、阶段 4/5 wait-set 或线程池迁移、吞吐优化验收。
> 关联：[`阶段2_RouteSession实现说明.md`](阶段2_RouteSession实现说明.md)、[`阶段3_收包分流提取实现说明.md`](阶段3_收包分流提取实现说明.md)。

## 1. 验收原则

1. **先看因果顺序，再看最终功能。** rebuild 后又能收到消息，不能证明旧 route 是在 recv 结束后才 release，也不能证明 rebuild 窗口已弹出的 buffer 没被丢弃。
2. **并发失败必须有界。** 等待、子进程、CTest 均设置超时；超时视为失败并留下可定位的用例名，不允许测试永久挂住。
3. **区分协议层、集成层和回归层。** RouteSession 单测证明状态机；真实 route 测试证明 libipc disconnect 语义；pub/sub 测试证明握手、队列与 nodelet 接入。
4. **全绿必须对应本次构建的二进制和库。** 运行前确认没有遗留的 `LD_LIBRARY_PATH` 将 `build/lib/libipc.so` 替换成其它版本。
5. **不要把耗时当作唯一判据。** 耗时可作诊断数据；协议正确性应通过事件顺序、计数、队列内容和状态变化断言。
6. **把测试结果分为通过、失败、跳过和未覆盖。** 环境不支持的用例可以 skip，但不能把 skip 计作通过；未覆盖项必须保留在报告中。

## 2. 覆盖地图

| 层 | 目标 | 主要测试 | 验收重点 |
|---|---|---|---|
| A. RouteSession 状态机 | lease 与 route 生命周期协议 | `test_shm_route_session` | I1–I4、重建顺序、失败可重试、stop 非终态、并发 churn |
| B. 真实 route 唤醒与伪影 | 锁外 disconnect 的真实 libipc 行为 | `test_shm_route_session`、`test_wakeup_artifact` | rebuild/stop 都能叫醒 recv；伪影精确识别且真实 buffer 不误杀 |
| C. 订阅端集成 | generation 重建、数据投递、析构与 nodelet | `test_dzipc_shm`、`test_shm_nodelet`、`test_shm_receiver_cap`、`test_dzflat_rx` | 连接/重连、容量边界、消息仍可取、析构后不再投递 |
| D. wire 与队列回归 | TLV、DZFlat、adopt/view、接收计数 | `test_wire_accept`、`test_chunk_hold`、`test_lap_safety` | 计数、借样生命周期、队列内容与 chunk 归还 |

## 3. 详细测试矩阵

### 3.1 A 层：RouteSession 状态机

运行目标：`test_shm_route_session`。该套件使用真实 `ipc::route`，不能用“route 最终有效”替代并发顺序判据。

| 不变式/分支 | 现有用例 | 必须观察的结果 | 失败信号 |
|---|---|---|---|
| 空状态与首次建立 | `EmptyStateIsWellDefined`、`AcquireLeaseCarriesRouteAndGeneration` | 空 session 不发 lease；首次 rebuild 后 route/generation 正确 | 空 route 被借出或初始 generation 错误 |
| I1：lease 保活对象 | `DtorReleasesOnlyItsOwnShare` | session/lease 各自持有的 shared_ptr 生命周期符合预期 | lease 期间对象提前析构 |
| I2：release 不与 recv 并发 | `RebuildWaitsForInflightBeforeReleasingOldRoute` | inflight 未归零时旧 route 仍 valid；`release_receive` 后才 release 并进入 create | create 或旧 route invalid 早于 release_receive |
| I3：重建期拒绝新 lease | `RebuildRejectsNewAcquire` | rebuild 等待期间 `acquire_receive()` 为空 | 重建过程中仍能取得旧 route lease |
| I4：计数归零与多余 release | `WaitQuiescentBlocksWhileInflightNonZero`、`ExtraReleaseDoesNotUnderflowQuiescence` | inflight 非零时 wait 阻塞；释放后返回；多余释放不下溢 | wait 提前返回、永久挂起或计数下溢 |
| rebuild 的 disconnect | `RebuildDisconnectUnblocksBlockedRecv` | recv 真正阻塞时调用 `begin_rebuild`，disconnect 令 recv 返回，rebuild 完成 | recv 只能等满超时；rebuild 不返回 |
| generation 发布顺序 | `RebuildSwapsRouteAndPublishesNewGeneration` | 新 generation 和新 route 一起可见，旧 route 不再可 lease | generation/route 不匹配或旧 route 再被借出 |
| create 失败后可恢复 | `RebuildFailureLeavesEmptyAndRetryable` | 空 route、rebuilding 复位，后续成功 rebuild 可取得 lease | 永久停在 rebuilding 或错误发布 generation |
| stop 后恢复 | `StopThenSuccessfulRebuildReopensLeases`、`StopIsIdempotentAndNonTerminal` | stop 幂等；成功 rebuild 可重新收包；stop 后直到重建前无 lease | stop 被错误当成永久终态或自动放开 lease |
| stop 唤醒与 quiesce | `StopAndWakeUnblocksBlockedRecv`、`StopThenQuiesceReturns` | 真实阻塞 recv 被唤醒，inflight 可归零 | 只依赖 recv 超时、wait 永久阻塞 |
| 并发压力 | `ConcurrentAcquireReleaseWithRebuildIsRaceFree` | 多次并发 acquire/release/rebuild 有界完成、无非法状态 | 崩溃、死锁、generation 回退或计数不归零 |

要求：状态类测试采用同步信号/条件变量建立先后关系；短超时只用来断言“尚未发生”，不得靠固定长 sleep 制造并发窗口。对异常违约行为（如多余 `release_receive`）要遵守构建模式：Debug 断言可能终止进程，该用例应单独运行或明确跳过，不能令整批结果无法读取。

### 3.2 B 层：叫醒伪影与真实消息判别

运行目标：`test_wakeup_artifact`。

| 行为 | 现有用例 | 断言 |
|---|---|---|
| disconnect 唤醒的返回形状 | `DisconnectWokenRecvProducesDetectableArtifact` | 真实阻塞 recv 被 disconnect 后得到符合当前 libipc 版本的全零固定长度 buffer |
| msg_id=0 的历史误收 | `ArtifactWouldBeAcceptedAsRealMessageWithoutTheGate`、`NoPhantomMessageOnGenerationRebuild` | 伪影若进入 wire 接收可造成假消息；正式收包路径必须拦住，队列无伪消息 |
| 同长度真实 TLV | `RealTlvOfArtifactLengthIsNotFlagged` | 非全零的真实 TLV 不被判成伪影，消息可投递 |
| 同长度真实 DZFlat | `RealDzFlatOfArtifactLengthIsNotFlagged` | 尾部全零但整段非零的 DZFlat 不被误杀 |
| 判别边界与计数 | `NonArtifactLengthsAreNeverFlagged`、`DetectionItselfDoesNotTouchCounters` | 长度条件精确；判别纯函数不偷偷增加诊断计数 |
| 已有真实消息保留 | `RealMessageOnMsgIdZeroTopicIsStillDelivered`、`RealMessagesSurviveGenerationRebuild` | generation 切换前后真实 TLV/DZFlat 仍进入正确队列；唤醒计数与 wire 计数口径分离 |

迁移守则：阶段 3 提取收包分流时，伪影门及 `NoteWakeupArtifact()` 必须与 `raw_data.empty()` 之后的路径一起迁移；阶段 3/5 新增调用点后，应在相应测试中确认每条收包路径都通过该门。

### 3.3 C 层：集成行为

| 验收场景 | 当前回归目标 | 必查结果 | 增强项/缺口 |
|---|---|---|---|
| 发布订阅基本行为 | `test_dzipc_shm` 的 `PubSub`、`test_shm_nodelet` | 消息值、数量、topic 隔离与现有 API 行为不变 | 保留至少一条 `get/try_get` 和一条 `get_clone/try_get_clone` 路径 |
| publisher 重启引起 generation 重建 | `test_dzipc_shm` 的 `SubscriberRecoversAfterPublisherRestart`、`test_wakeup_artifact` rebuild 场景 | 重启后新消息可收；队列无伪影；旧 route 释放 | 必须同时保留 A 层的真实阻塞 recv 顺序守门，不能只凭最终收到消息验收 |
| `add_peer` 失败重试 | 当前通过 RouteSession stop/rebuild 语义间接覆盖 | 失败后 route 被清空且没有 lease；下次成功建立后恢复接收 | 若测试夹具能注入控制面失败，增加集成用例直接覆盖失败一次、下一轮成功；不为此改动生产接口或控制面协议 |
| `cc_id == 0` 连接位耗尽 | `test_shm_receiver_cap` 的 `ThirtyThirdSubscriberDoesNotSilentlyPretendToBeConnected` | 第 33 个订阅者不报告已连接/不假成功；释放 slot 后重试策略符合现有约定；上限内订阅者都能收消息 | 确认此目标进入全量手工套件；组播/系统资源受限时标记 skip 原因 |
| Ready 离开与重新 Ready | 现有 publisher restart / control-plane 回归 | 离开 Ready 后 route 停止收包；重新 Ready 后新 generation 能建立 | 当前没有精确命中“短暂非 Ready、同对象随后重新 Ready”的专用集成用例，后续可加控制面状态注入用例 |
| 析构期间阻塞 recv | RouteSession stop-wake 单测、`test_shm_nodelet` 的 `PublishAfterSubDestroyNoCrash` | stop 令阻塞 recv 返回；线程 join 后无 UAF；registry 注销后快路径不再 push 到被销毁队列 | 不用 `recv(50)` 下析构耗时作为唯一判据；若做对象级析构探针，使用可控长超时/因果计数/子进程硬超时 |
| Registry 注销顺序 | `test_shm_nodelet` 的 `PublishAfterSubDestroyNoCrash` | subscriber 析构后同进程发布不崩、不投递到失效队列 | 重复运行以覆盖发布与析构交错；确保每轮 topic/key 隔离 |

### 3.4 D 层：消息格式、队列及资源回归

执行 `test_wire_accept`、`test_dzflat_rx`、`test_chunk_hold`、`test_lap_safety`，检查：

- TLV 接收成功、msg_id 不匹配、截断/损坏 buffer 的队列结果和计数正确。
- DZFlat 正确类型可借样，msg_id/schema 不符和坏头不入队且计数正确。
- schema-less/adopt 容量与 spill 行为、消息出队或 evict 后 borrowed 计数归还。
- route rebuild 不破坏仍由 `Sample`/用户队列持有的 buffer；chunk 仅在最后一个持有者释放后归还。
- 收到与伪影同长度的真实 DZFlat/TLV 时仍能正常处理。

测试若因资源池或组播能力在特定环境 skip，报告中写明 skip 的用例、条件和目标平台；不可把这类环境 skip 用来替代基础单测。

### 3.5 E 层：生命周期及仓库回归

`test_shm_control_scheduler`、`test_shm_route_session`、`test_wakeup_artifact`、`test_dzipc_shm`、`test_shm_nodelet`、`test_shm_receiver_cap`、`test_dzflat_rx`、`test_wire_accept`、`test_shm_domain_isolation`、`test_shm_sniffer_control_name`、`test_uf003_crash_reclaim`、`test_uf004_shutdown_monitor_optout`、`test_uf009_graceful_exit`、`test_handshake_probe`。

## 4. 测试缺口与补测设计

下列项目用于判断后续是否需要增加用例，不代表当前实现已失败。

### 4.1 已弹出 buffer 不丢失（I5 / §8.4）

测试必须固定如下事件序列：

```text
旧 route 的 recv 已返回一条带唯一序号的非空 buffer
→ 在收包线程处理该 buffer 前推进 generation / 启动 rebuild
→ 允许收包线程继续处理
→ 断言该序号恰好进入 view_queue_ 或 msg_queue_
```

用条件变量或测试钩子在“recv 返回”和“分流入队”之间暂停，不以随机压力碰撞窗口。断言队列中序号恰好一次、消息内容完整，并确认没有根据 `lease.generation` 丢弃。测试钩子应限制在测试构建或内部测试夹具中，不新增公共生产 API。若现有 `RealMessagesSurviveGenerationRebuild` 未能控制上述事件顺序，则它作为端到端回归保留，但不能单独宣称确定性覆盖 I5。

### 4.2 析构唤醒集成守门

对象级测试须证明析构顺序，而不依赖普通 `recv(50)` 超时自然返回。推荐两种可审计方式：

1. 在测试夹具中使用可控阻塞点/事件探针，记录 `stop_and_wake`、recv 返回、join 完成的因果顺序；或
2. 在子进程中让收包线程进入长超时 recv，再析构 subscriber，以 pipe 报告阶段事件并给父进程设置硬超时。父进程仅在收到“recv 被 stop 唤醒且析构完成”事件后判通过。

不可只断言析构耗时小于某个毫秒值；线程调度、系统负载和共享内存实现会污染这种判据。无论选择哪种方式，都应验证 registry 注销发生在 stop 之前，并在析构后执行同进程 fast-path publish。

### 4.3 握手失败和 Ready 状态转换

若控制面测试夹具可独立控制 `add_peer` 返回值及 `TopicState`，覆盖：

- `add_peer` 第一次失败：route 停止、release；第二次成功：generation 正确、可以收消息。
- Ready → 非 Ready：握手状态撤销、route 释放、peer/slot 回收。
- 非 Ready → 新 generation Ready：新 route 建立，心跳和消息接收恢复。
- `cc_id == 0`：不置 `handshake_completed`，退回 peer 并继续重试。

不要通过公开接口添加只供测试使用的控制面注入点；优先使用现有控制面抽象、进程隔离测试或小型内部测试 seam。若无法可靠注入，报告明确标注间接覆盖，不把已有 RouteSession 单测冒充为握手集成覆盖。

## 6. 全量执行清单

先运行确定性协议和伪影用例，再运行 SHM 集成，最后跑退出/探针用例。SHM 资源型测试先串行执行，避免共享段名、topic 或控制面资源互相污染。

```bash
set -euo pipefail
unset LD_LIBRARY_PATH

focused=(
  test_shm_route_session
  test_wakeup_artifact
  test_shm_control_scheduler
)
integration=(
  test_dzipc_shm
  test_shm_nodelet
  test_shm_receiver_cap
  test_dzflat_rx
  test_wire_accept
  test_shm_domain_isolation
  test_shm_sniffer_control_name
  test_chunk_hold
  test_lap_safety
)
lifecycle=(
  test_uf003_crash_reclaim
  test_uf004_shutdown_monitor_optout
  test_uf009_graceful_exit
  test_handshake_probe
)

for t in "${focused[@]}" "${integration[@]}" "${lifecycle[@]}"; do
  echo "===== $t ====="
  timeout 120s "build/bin/$t" --gtest_brief=1
done

ctest --test-dir build -R 'test_(udp_port_boundary|shm_control_scheduler|shm_route_session|wakeup_artifact)$' \
  --output-on-failure
```

说明：

- 单个可执行文件超时、非零退出码、gtest FAILED 数非零，都判该目标失败；`GTEST_SKIP` 单独计数并说明原因。
- 若当前分支没有某个可执行文件，先核对源码是否存在、CMake 是否重新配置；不要静默跳过。
- 若特定测试依赖外部服务或平台能力，拆分为“必过核心”和“平台条件项”，保留原始输出及环境信息。
- `ctest -j` 只并行执行已登记测试；不要用它代替上面的全目标清单。确认各测试使用唯一资源后才提高并发度。

### 6.1 并发稳定性复跑

完成一次全量后，对最容易出现竞态的核心套件做至少 20 轮串行复跑；提交前或修改 RouteSession 同步逻辑后建议 50 轮：

```bash
set -euo pipefail
unset LD_LIBRARY_PATH
for i in $(seq 1 20); do
  timeout 120s build/bin/test_shm_route_session --gtest_brief=1 >/tmp/route-session-test.log 2>&1 || {
    cat /tmp/route-session-test.log
    echo "test_shm_route_session failed at iteration $i"
    exit 1
  }
  timeout 120s build/bin/test_wakeup_artifact --gtest_brief=1 >/tmp/wakeup-artifact-test.log 2>&1 || {
    cat /tmp/wakeup-artifact-test.log
    echo "test_wakeup_artifact failed at iteration $i"
    exit 1
  }
done
```

复跑的用途是暴露偶发死锁、资源污染和竞态；它不能取代确定性顺序断言，也不能把“20 次未复现”解释成无竞态证明。

## 7. 定向变异测试

变异只在独立临时 worktree/build 目录进行，不改当前工作树；每次确认目标二进制实际加载变异库。阶段 2 关键变异及预期杀死者：

| 变异 | 应失败的用例/判据 | 证明内容 |
|---|---|---|
| 删除 `begin_rebuild()` 对旧 route 的 `disconnect()` | `RebuildDisconnectUnblocksBlockedRecv`，且 rebuild 在长超时 recv 下不能等待到超时才返回 | §4 第 3 步有守门 |
| 不等 inflight 归零便 `release()` 旧 route | `RebuildWaitsForInflightBeforeReleasingOldRoute` | §4 第 4/5 步有守门 |
| rebuild 期间允许新 acquire | `RebuildRejectsNewAcquire` / 并发 churn | I3 有守门 |
| 成功 rebuild 不复位 stopping | `StopThenSuccessfulRebuildReopensLeases` | stop 非终态和失败重试路径可恢复 |
| `recv` 返回后按 generation 不匹配丢弃 buffer | §4.1 固定事件顺序的 I5 用例 | 已弹出字节不会被 generation 门丢弃 |
| 删除析构的 `stop_and_wake()` | §4.2 对象级析构唤醒用例 | 析构不依赖普通 recv 超时退出 |
| 伪影门只查长度或只查尾部 | `RealTlvOfArtifactLengthIsNotFlagged`、`RealDzFlatOfArtifactLengthIsNotFlagged` | 守门不会吞同长度真实消息 |
| 删除/放宽伪影门 | `NoPhantomMessageOnGenerationRebuild`、msg_id=0 集成判据 | disconnect 伪影不会成为用户可见假消息 |

变异测试通过条件：每个变异都被其指定用例稳定杀死；若变异后仍全绿，先判为测试缺口，不能把基线全绿当作充分验收。变异库路径与测试日志单独记录，实验后恢复干净运行环境。

## 8. Debug、Release 与并发工具

至少在项目常用的 Release 配置运行核心与集成套件；RouteSession 单测还应在 Debug 配置单独运行，以覆盖断言构建行为。Debug 下故意违约型用例可能触发 assert，应按该测试的说明单独筛选运行。

若编译器和依赖允许，再用 ThreadSanitizer 对 `test_shm_route_session` 及集成中的 rebuild/析构用例构建运行。TSAN 是额外证据，不替代确定性事件顺序；运行环境若不支持共享内存映射或出现已知第三方库告警，记录限制与完整日志。当前仓库没有现成 sanitizer 配置时，不把它列为普通提交的硬门槛。
