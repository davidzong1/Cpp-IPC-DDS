# 传输延迟、接收正确性与多话题性能改进执行方案

编制日期：2026-10-02。当前交付范围：综合已有测试和代码复核，形成后续执行方案。2026-10-02 用户已指示开始执行；运行记录见文末执行日志。

执行顺序：**先证明并修复停止推进，再闭环接收计数差异，建立正确性合格的基线，随后按 CPU 与调度证据优化，最后完整回归。** 性能数字不能替代消息完整性验收。

## 1. 依据及对已有问题的结论

依据：[总报告](results.md)、[速度分析](speed_analysis.md)、[压力分析](stress_analysis.md)、[分段计时分析](latency_breakdown.md)。旧报告和逐轮账本保留原始口径，后续新增修复版本列，不能覆盖成“修复后成绩”。

### 1.1 延迟从哪里开始，大包为什么看起来变化较小

原速度工装 [comparison.cpp](../../test/transport_comparison/comparison.cpp) 在准备本条载荷前记录时间，到接收端应用取得消息结束。**起点不是发布者写入完成，也不是 publish 返回。** RPC 则从准备请求前到取得 success 响应，属于往返延迟。

| 指标 | 原工装边界 | 应如何解读 |
|---|---|---|
| 准备耗时 | 准备开始 → 发布 API 入口 | 含载荷填充；B 还含借样，Prebuilt 还含段编码 |
| 发布耗时 | 发布 API 入口 → API 返回 | 不代表对端已经收到；不同路径将编码、填充放在不同阶段 |
| pub/sub 端到端延迟 | 准备开始 → 应用取得 | 含准备、发布过程中影响交付的工作、排队和接收；不含应用全量遍历载荷 |
| 本轮分段的投递点 | 共享描述符 que->push 调用前 | 载荷已写完，但不是精确的队列 release 指令，也不是 API 返回 |

原报告的发布均值：A 从 8 B 的 **0.69 µs** 增至 1 MiB 的 **19.50 µs**，并非基本不变。B 从 **0.46 µs** 增至 **0.92 µs**，但其准备均值从 **0.22 µs** 增至 **13.38 µs**。B 在共享借样中写数据，大块写入主要计入准备阶段；发布主要提交描述符并通知接收方。小尺寸区间固定开销占主导，也会弱化尺寸变化。

后续必须同时报告准备、发布、投递后到达和端到端指标。不得将不同样本的均值、p50 或 p99 相加；publish 返回与接收可以并发，不能把“API 返回后到达”当作天然非负的传输延迟。

### 1.2 小消息差距的已知部分与未知部分

以下是分段实验中，8 B、最多 8 条在途、各自饱和发送时，三轮完整运行的抽样均值中位数：

| 路径 | 端到端 | 投递前 → worker 开始 | worker 开始 → 取包 | 取包后 → 应用 | 其中应用队列交接 |
|---|---:|---:|---:|---:|---:|
| DzFlatA | 7.190 µs | 5.789 µs，80.2% | 0.575 µs | 0.530 µs | 0.181 µs |
| DzFlatB | 7.054 µs | 5.668 µs，80.3% | 0.589 µs | 0.525 µs | 0.189 µs |

DDS/iceoryx 同档抽样总均值为 1.672 µs，但其实际饱和发送速率与 CPP 不同。相同 **50 万条/s** 输入时，A、B、DDS 分别为 **2.478、2.505、2.107 µs**，三方均三轮完整送达；这组更适合比较相同输入负载的延迟。

据此确定以下优先级：

- 修正“先优化应用队列交接”的早期判断，首先调查 worker 处理前的驻留与调度。
- 处理前区间包含共享队列驻留、前序消息处理、通知和调度；尚未直接测量内核唤醒，不能把约 5.7 µs 全算成 futex 成本。
- 等待占比不等于 CPU 热点占比。Sample 构造虽约 0.15 µs，也可能通过降低服务能力放大排队，是否优化要结合每消息 CPU 和分配次数。
- DDS 当前路径在内部线程中取样，减少了 CPP 所用应用交付路径中的部分交接；DDS 的具体优势仍需 CPU、批次和调度证据拆分，不能仅凭低 p50 断言是某个通知机制所致。
- 不将单条在途或限速形成的低排队状态宣称为产品优化，不承诺简单修改即可达到 1 µs 或旧 DDS 的 1.27 µs p50。

### 1.3 正确性问题必须分别闭环

| 编号 | 已有事实 | 当前判断与下一步 |
|---|---|---|
| C1 | 8 B 单条在途 A/B，探针开关共 12 轮全部最后未收 1 条；分段实验共 29 个异常，其中 9 个探针关闭 | 异常中发送 > 池收 = 应用收，缺口在池取包统计之前；优先验证空读后确认序号的竞态 |
| C2 | 千话题六轮 CPP 池收包均为 1000 万，应用少收 0–6 条 | 缺口在池统计与应用交付之间；须核对分流、入队、淘汰、出队、析构和工装收尾，不能与 C1 合并定因 |
| C3 | SHM RPC 37 轮、A RPC 27 轮请求失败；B/Prebuilt 各两轮尾部未收 8 条 | 分别建立请求/响应及发布订阅事件链，检查是否共享 C1 原因，不能预先认为同一修复全部解决 |
| C4 | Socket/TLV 128 KiB–1 MiB 发布订阅 12 轮中 10 轮内容错误或未收 | 独立检查分片、组包、长度、缓冲区生命周期及收尾，作为完整回归硬项 |
| C5 | DDS/iceoryx 千话题扩容档三轮全收，其中两轮池容量告警；原安装无法创建全部端点 | 保留容量限制与告警，单独评估扩池对尾延迟的影响；不将扩容成绩冒充原安装成绩 |

分段实验共 126 个组合，97 个完整送达、29 个有未收；已关联的 1,642,088 个采样全部关联成功且无时序异常。**未收消息没有到达时间，不进入已收样本的延迟分布**，所以异常轮不能凭低 p99 通过验收。

## 3. P01：工装、计时与分层计数

### 3.1 构建及实验隔离

沿用 [transport_comparison](../../test/transport_comparison/) 与 [latency_breakdown](../../test/latency_breakdown/) 工装。现有分段入口为 `bash test/latency_breakdown/execute.sh /var/tmp/my-breakdown`，**本文编制期间不执行**。后续先扩展工装再运行新矩阵；不能假定现有脚本已经实现本文新增项目。

建立三档，使用相同产品版本及编译优化参数：

| 构建档 | 用途 | 约束 |
|---|---|---|
| U：真正无分段探针 | 正式性能基线与验收 | 产品路径无新增探针调用；保留原有产品计数与计时 |
| O：插桩但关闭记录 | 估计空调用和分支扰动 | 不能称为未插桩二进制 |
| T：开启抽样记录 | 阶段归因和事件关联 | 本地预分配记录，默认每 64 条抽样，轮次轮换相位 |

原探针对 8 B 饱和吞吐的开/关差异为 A -5.43%、B -3.45%、DDS +4.03%，含运行波动。后续 U/O/T 必须交错运行，正式收益以 U 对 U 为准；不能把 T 档时间当作无扰动成本。

构建和原始记录放在独立的 `/var/tmp/cppipc-plan-<run-id>/`，使用任务自己的 IPC、/dev/shm、/tmp 和私有 RouDi。保留宿主既有 RouDi，不停止 PID 1207，也不覆盖本级 DDS/iceoryx 安装。源码副本应包含当前必要的未跟踪测试文件，并核对指纹；仅按 Git HEAD 导出会漏掉这些工装。

### 3.2 明确计时边界

保留原端到端计时，并增加如下可关联事件：

| 事件 | 位置与用途 |
|---|---|
| t0：准备开始 | 原速度延迟起点 |
| t1：发布入口 | t1-t0 为准备成本 |
| t2：共享描述符投递前 | 载荷已写完；t应用-t2 为“投递前至应用到达”，明确近似边界 |
| tw：本次 recv_once 开始 | 定位处理前驻留；另记 worker 原始服务时长 |
| tr：recv 返回 | 取包完成，随后分别记录 lease 释放、校验/分流、Sample 构造 |
| tq：应用队列提交前 | 紧邻槽位 release；区分入队和消费者交接 |
| t应用：consume 入口 | 与原报告一致，不含全量载荷遍历 |
| tret：发布 API 返回 | 单列 tret-t1，不混入可加的跨线程阶段链 |

CPP 继续按 `max(t2, tw)` 分解重叠区间，并保留原始 tw；这只用于明确并发边界，不得用截断掩盖真正的时钟或关联错误。DDS 保留发布入口、dds_take 前后、应用到达，批次时间单列，不能将其合并区间直接当作 CPP 的单独出队成本。

增加独立的全载荷读/校验档，回答“大包被应用实际处理完成”的成本；与原“取得视图即到达”档分开。RPC 分别记录请求准备、服务收到、success 回调完成、响应提交和客户端取得，并保留 RTT。不得假定单向耗时等于 RTT/2。

### 3.3 消息计数守恒及尾部处理

诊断档按 topic、generation、sequence 关联，覆盖发端成功、原始取包、伪影/校验拒绝、成功入队、队列淘汰、应用出队、有效交付和析构清空。先核实每个旧计数的语义：当前池计数由 recv_once 返回非零累加，**不保证每条都已成功交付，可能包含后续被分流丢弃的包**。

在发送停止、接收仍存活、在途操作归零的审计边界检查：

- 成功发送 = 原始取到的唯一业务消息 + 尚未取到的消息；伪影、重复及非业务数据单列。
- 原始取包 = 成功入队 + 各类拒绝/伪影 + 尚在分流中的数量，各类原因互斥且穷尽。
- 成功入队 = 应用出队 + 队列淘汰 + 析构清空 + 仍留在队列的数量。
- 应用出队 = 有效唯一交付 + 无效/重复/过滤数量。

运行中计数跨线程、更新边界不同，瞬时不相等不能直接判丢包。最终同时报告逐层数量、每话题序号覆盖和缺失序号；不能只看最大 ack，因为出现中间空洞时最大序号仍可正确。

收尾改为双方协议：发送端公布最后成功序号及成功数量，接收端继续消费到全部覆盖或统一 5 秒排空上限，先保存审计快照再析构。5 秒仅用于区分迟到与永久未收，不计入稳态吞吐，也不能用它掩盖停顿；另列 0.5 秒、1 秒时的缺口及最终状态。不得补发测试消息唤醒尾包。小规模全序号/全字节检查与高负载预分配计数分开，避免逐条加全局锁改变被测性能。

## 4. P02–P03：先证明并修复接收停止推进

### 4.1 待验证的竞态

代码落点：

- [recv_worker.cc](../../src/dzIPC/threepools/recv_worker.cc)：collect_pending、run_budget、wait_once、loop。
- [shm_pub_sub_ipc.cc](../../src/dzIPC/shm_pub_sub_ipc.cc)：sub_recv_attempt、SubRecvRoute::has_pending。
- [recv_wait_set.cpp](../../src/libipc/recv_wait_set.cpp)：等待前后扫描及独立的 entry.last。

当前 run_budget 在空读后将 worker 的 last_seq 更新为“此刻最新 sequence”；SHM 的 has_pending 恒 false。候选交错如下：

```text
worker 确认一次 recv_once 返回空
    发布者提交一条消息，并递增 sequence
worker 将最新 sequence 写入 last_seq
    共享队列仍有消息，但 sequence == last_seq
后续没有新发布 → collect_pending 不再发现该条消息
```

这与单条在途停止推进相符，但**代码疑点尚不等于已证明根因**。P02 必须证明旧实现受该交错影响；若不能复现，转查通知发布顺序、token 生命周期、注册初始基线、断开/重建和工装 ack，保留反证，不能继续按预设原因修改。

### 4.2 确定性测试

在 [test_recv_worker.cpp](../../test/test_recv_worker.cpp) 增加受控 fake route 或仅测试构建存在的同步缝。通过栅栏控制事件次序，不依赖短 sleep 碰概率；不在现有“lease 持有期间不得阻塞”的测试缝上阻塞。

| 用例 | 受控交错 | 通过标准 |
|---|---|---|
| 空读后发布 | 空读结果已确定、尚未确认序号时发布一条 | 无第二条消息、无假唤醒，唯一消息自动交付 |
| 稳定检查后发布 | 空读后的序号检查已完成、写入确认值前发布 | 后续序号差异仍可发现 |
| 进入等待前发布 | wait-set 已观察过某序号，worker 尚未完成相应处理 | worker 不因“两层都看过通知”而睡到超时 |
| 预算边界到达 | 消息数/字节数/时间预算恰好耗尽时补一条 | 保留待续任务，尾包交付，邻路不饥饿 |
| 无数据假 pending | has_pending 恒真且 sequence 不变 | 有界空读/退避，不把同一差值反复当新事件 |
| 生命周期及序号边界 | 注销、重建、初始已有数据、uint32 序号跨最大值回零 | 无悬空访问、重复消费者、尾包丢失 |

旧版反例与修复版使用同一受控测试。关键交错至少重复 1000 次；旧实现必须出现预期失败，修复版必须全部通过。真实跨进程 A/B 补测单条在途与静默后单条，证明 fake route 的结论适用于 SHM。

### 4.3 候选最小修复算法

以下是设计约束和伪代码，实施时需结合 P02 结果及真实发布端 release/acquire 顺序确认：

```text
每次完整 recv_once 尝试：
    检查 stopping / removed；不允许启动新的接收则退出
    seq_before = acquire_load(sequence)
    outcome = 完整执行 recv_once

    如果异常 / 生命周期禁止接收：
        不确认“已经读空”；按独立原因退出或有界重试
    如果收到数据：
        累加；在完整消息边界检查预算
        耗尽则保留待续；否则继续尝试
    如果真正空读：
        seq_after = acquire_load(sequence)
        如果 seq_after != seq_before：
            不推进 last_seq
            记录本次真实新序号，有限重试或进入待续队列
        否则如果 has_pending 为 false：
            last_seq = seq_before
            标记为确认稳定空读
        否则：
            有界空读，之后按“无进展 pending”退避
```

不能在函数尾部统一把最新 sequence 当作消费完成值；预算退出、异常、停止和注销不得冒充读空。存储 seq_before 的意义是：即使检查后发生新发布，新序号仍与确认值不同。需审计底层队列可见性及 sequence 更新顺序，不能只靠增加内存屏障宣称修复。

同时修改 loop 的进展判断，区分“收到了数据、观察到真实新序号、预算待续、只有无数据 pending、错误/生命周期退出”。**不能继续仅以 messages_received 是否变化决定等待，也不能只要 deferred 非空就无限循环。**

worker 的 last_seq 表示已确认消费至读空的边界；wait-set 的 entry.last 只表示通知观察进度。它们不能互相替代。必要时单列 last_observed_seq，使持续存在的 sequence != last_seq 不被误判为每轮都有新事件。新序号触发及时复查，稳定无进展的 pending 维持有界退避，其他就绪 route 仍正常服务。

保留固定 route→worker 归属、单 route 单消费者、完整 recv_once 安全边界、remove 等待在途归零、stop 唤醒及空闲退出/重启契约。不得通过减小 wait_timeout、周期假消息、持续全扫或永久自旋隐藏问题。

## 5. P04：其他正确性问题的闭环方式

**C2：池统计后少收。** 在 process_received_buffer 的所有拒绝路径、view_queue/msg_queue 的提交、满队淘汰、消费者取得以及析构处补齐诊断原因。现有 [circularqueue.h](../../include/dzIPC/common/circularqueue.h) 已是原子 MPMC 环形队列，不能按“大锁队列”假设重写；其满队由生产方 dequeue 淘汰，尤其需要明确淘汰计数。先用修正后的收尾协议区分迟到、计数边界和实际丢弃，再对已确定原因作最小修复。

若定位为队列容量不足，先保留原配置证明现象，再单列增容或背压实验，记录内存和阻塞代价。不能仅增大队列后把“消失的症状”称作竞态修复。目标百万负载仍须零淘汰、零未收；故意超载测试则验证丢弃/背压行为及可观察性。

**C3：RPC 与 B/Prebuilt 尾包。** 复现旧异常尺寸，记录请求成功提交、服务收到、回调次数、响应成功提交、客户端完成/超时及序号。服务只响应 8 字节 success。检验超时是否发生在同一接收 worker、响应路由或独立握手/背压路径。若 P03 后消失，仍要通过受控反例或同版本补丁开关对照建立关联。成功请求延迟与失败率分列，超时样本不能删除。

**C4：socket 大包。** 用固定种子的非均匀字节模式和端到端全字节校验，避免只有首尾检查漏掉中间损坏；记录每片长度、偏移、消息序号、完成/取消和缓冲区归属。增加短读、连续大包、断开重连与预算边界用例，保留完整消息边界，不能用切断 recv_once 的方式降延迟。

**C5：DDS 限制。** 原安装容量失败保持 N/A/容量不足。扩容档统一使用同版本重建的 DDS、iceoryx、C binding、RouDi，禁止 ABI 混用；独立保留原池配置与增容池配置，记录池告警、等待和尾延迟。1 MiB 应用载荷继续使用能覆盖协议开销的 2 MiB 档。DDS 异常不能伪装修复成 CPP 收益，也不因第三方容量上限给 CPP 正确性放宽标准。

## 6. P05–P07：小消息与多话题性能优化

### 6.1 先建立可比较基线

采用同机同版本、相同 CPU 集合和负载的修复版 U 档作为优化基线；旧含停止推进的版本只保留作历史/反例。记录 P/E 核、SMT、NUMA、频率策略、系统负载和各角色 CPU 时间，不悄悄修改系统调度策略。

主对照保持相同输入速率与资源预算；另列各自饱和吞吐。每组至少五轮，预热 1 秒、测量 10 秒，后端和版本按固定随机种子交错顺序串行运行，避免多个性能任务争用 CPU。速度测试的应用交付方式保持原样；若另测回调或阻塞获取，必须作为独立 API/工装变体。

CPU 同时报接收进程、应用主线程、worker、控制线程，DDS 另列 RouDi。原千话题 CPP 的 11.24 核当量包括应用主线程主动轮询约 1 核；DDS 0.82 核是接收进程口径。不得用仅 worker 的改进值对比包含主线程的旧总值。

### 6.2 归因指标与候选优化顺序

| 顺序 | 候选与代码落点 | 实施前需要的证据 | 实施方式及边界 |
|---|---|---|---|
| O1 | 重复 route 扫描；recv_worker、recv_wait_set | 扫描次数/有效交付、扫描 CPU、就绪命中率；旧千话题约 84 次检查/消息只是线索 | 先利用 consume_ready 返回的有效 token 定位 route，消除同轮冗余扫描；预算待续留在 deferred，重建/注册要可靠入队，睡前保留必要重检 |
| O2 | waiters 构造与就绪列表分配 | 分配次数、构造时间、注册变更频率 | 复用有容量上限的缓冲；注册表变化时更新，保留并发 remove、token 保活和控制中断 |
| O3 | 每 route 批次、预算和 worker 数 | 每批消息数、每次唤醒有效消息数、空读率、饥饿和每线程 CPU | 单变量比较消息预算 1/8/32/64，其余预算先固定；再比较 worker 数，保持完整消息与公平性 |
| O4 | lease、类型锁、Sample 分配与计数原子操作 | 每消息 CPU、锁等待、分配计数；不能仅看阶段占比 | 优先评估已有对象复用、worker 本地累计及安全的只读元数据缓存；不能删除生命周期锁或必要校验 |
| O5 | 应用队列与取样方式 | O1–O4 后残余成本确实集中于此 | 单列事件驱动取样/批量取样实验；保留原 API 对照，再决定是否需要产品设计 |

以 perf stat 的 cycles/instructions、上下文切换、迁核和缺页为基础，结合短时 CPU 采样与 sched_wakeup/sched_switch 时间线，拆分“worker 在运行但忙于前序工作”和“worker 已就绪但未得到 CPU”。调度采样独立运行，核对扰动；若内核能力不可用，明确未测部分，不把合并阶段硬拆成估计值。

O1 的首个版本只削减已证明重复的扫描，不直接移除所有全扫。wait-set 的通知观察值不是消费完成值；合并通知、预算耗尽、初始已有数据、并发注销/重建必须继续保持可发现。每项通过 P02/P03 反例及公平性测试后，才进入性能对照。

worker 数优先比较 16/32/64；8 worker 仅在实际 route 哈希分布均不超过容量时追加。Linux 每 worker wait-set 最多 127 route，1000/8 的平均值为 125 不代表每桶均能容纳。容量失败必须记录，不能悄悄少注册话题。批量预算改变后同时检查冷门话题 p99、最大无进展时间及各话题送达情况。

### 6.3 后续候选，不纳入首轮默认改动

- Sample 对象池或队列内直接存值：必须证明引用/借样生命周期、跨线程销毁和内存上界，且分配成本足够显著。
- SPSC 专用队列：只有生产者、消费者和满队淘汰所有权均满足 SPSC 才可设计。当前 MPMC 与生产方淘汰行为不能直接替换。
- worker 直接执行应用回调：会改变现有 worker 仅取包及分流的边界，引入用户回调阻塞、异常和重入，需要单独 API 与生命周期设计。
- 小消息内联或专用编码：先验证元数据/分配占比，再评估 schema、容量、兼容和回退，不以新增 wire 格式作为第一步。
- 有界自旋：仅在调度证据证明值得时作独立低延迟模式，明确 CPU 预算；不作为修复丢事件的默认方案。

每个优化单独提交、单独开关对照。收益不足或尾延迟/正确性回退就撤回该项，保留已验证的正确性修复，避免多个改动互相掩盖。

## 8. 验收标准、失败分支与回滚

### 8.1 正确性硬门槛

- 支持的正常负载：发送计划达到、成功发送与最终唯一有效交付相等；零内容错误、零重复、零无解释缺口、零未报告淘汰。
- 单条在途、发布停止及长静默后单条均能完成交付，不依靠下一条业务消息或超时周期恢复。确定性测试还要确认没有带真实待处理任务进入普通空闲等待。
- 现有预算、公平性、注销、重建、停止、固定归属及容量边界测试全通过；无崩溃、死锁或孤儿测试进程。
- 千话题每轮计划与实际均达到 100 万条/s，最终每话题数量和序号完整；不能用少发或漏注册来通过接收测试。
- RPC 成功率与 RTT 同时报；正常矩阵要求零请求失败。不支持接口、DDS 原安装容量限制分别记录，不能当作通过。
- 第三方告警及超载策略单列，不把“函数返回成功”当作链路健康的充分条件。

### 8.2 性能拟定目标

以下是筛选优化的**拟定目标，不是已经取得或保证取得的结果**。比较对象为 P05 同机修复版 U 档，各后端另有相同负载对照。

| 项目 | 拟定目标 | 防止以其他退化换收益 |
|---|---|---|
| 8 B/1 KiB，50 万条/s | CPP 端到端均值下降至少 15% | p99 不劣化超过 10%，接收 CPU 不增加超过 5%，全部轮完整 |
| 8 B 饱和 w8 | 有效吞吐提高至少 15%，或在吞吐不降超过 5% 时延迟下降至少 20% | 同时报均值/p50/p99、实际在途和 CPU，不只选有利指标 |
| 千话题百万输入 | 接收进程 CPU 核当量下降至少 30% | 零未收，采样 p99 相对基线不劣化超过 10%，内存代价明确 |
| 64 KiB–1 MiB、RPC 与 socket 回归 | 无统计上明确的超过 5% 吞吐回退或超过 10% p99 回退 | 使用相同载荷处理口径、容量和测试版本 |
| 空闲 | 保持阻塞等待、已有空闲测试门槛 | 不新增常驻忙轮询来取得低延迟 |

以独立轮为比较单位，报告各轮值、中位数、范围和配对变化；不把同一轮的百万个消息当作百万次独立实验。若运行波动覆盖目标收益或跨轮 p99 差异过大，最多补到 10 轮并说明不确定性；仍不稳定则“不足以证明改善”。未达到拟定优化目标时保留正确性修复，撤回无收益优化，不通过调整指标或工作量宣称成功。

### 8.3 提交与回滚粒度

建议顺序：工装与失败用例 → C1 最小修复 → C2 收尾/交付修复 → 各 RPC/socket 独立修复 → O1、O2、O3 各独立优化 → 经证据支持的后续优化 → 报告。

每个候选记录“前置基线、改动、回归、性能、保留/撤回决定”。正确性失败立即停止该候选性能评估，撤回该候选；若修复本身未成立，则回到相应定位节点。测试改动和产品修复分开审查，禁止为通过测试删除历史失败项或放宽生命周期断言。
