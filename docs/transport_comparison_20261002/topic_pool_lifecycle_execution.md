# 话题池身份与生命周期回收：执行方案

用户已拍板：身份由完整 topic_name 调用 fnv1a64 计算；InitChannel 清残留，活跃池不删而复用；析构触发回收，借样晚释放时延后；删除 40 块共享池，所有 SHM 载荷池强制每话题每尺寸档 10 块。

把握度 8/10。主要风险是跨进程打开/删除竞态、借样比话题长寿，以及普通 send 与 DzFlat 的池布局统一。使用 VS Code 工具与补丁编辑，真实 CMake 构建、生命周期回归和千话题资源验证；无需再次审批已授权改动。

## 实现约束

- 池头写入话题身份 ID；注册信息保存完整 prefix/name 核对哈希碰撞，domain 已包含在底层通道名中，RPC 两个方向分别管理。
- Linux 用进程间租约与目录级生命周期锁协调打开、复用、最后退出及残留清理。锁只在初始化/首次映射/清理使用，不进入每消息传输路径。异常退出由内核释放租约，下次初始化清理无人使用的残留池。
- 各话题上下文独立缓存尺寸池，通道/收到的消息/未发布借样持有上下文；不再用永久强引用全局池缓存。最后本地引用释放时解除映射，最后跨进程租约退出时删除该话题池。
- InitChannel 保持按需建载荷池。已有租约时复用池，不重置空闲链或覆盖池内容。
- 删除旧 40 块容量、存储 ID 双分支及独立借样选择入口；loan/send/DzFlat 均进入同一话题池。队列与池版本升级，要求通信双方重新构建升级。
- 为保护原始 loan_t 在 route 销毁后的持样，允许新增生命周期成员；这是本次明确记录的 ABI 变更。
- 公共 clear_storage 的队列清理与池清理分开处理；活跃池禁止强删。不会清理运行中旧版本的共享段。
