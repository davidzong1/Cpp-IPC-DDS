# 延迟与指标修复阶段验收（O01～O04）

**仍未满足整体延迟门槛。** 实现冻结于`2b90e28`。修复了重复等待、首次发送前1ms等待、ACK已到达后的1ms等待及持锁notify；补有界指标、实际计数/拒绝/回收断言与分段证据。功能通过不等于延迟通过。

## 真实结果

- [最终本机54窗口](performance-final/summary.md)：每窗口2秒预热+30秒采样，100Hz，1/8/32订阅者×64B/4KiB/1MiB×三轮×两模式。同源码基准，基线f066a82，候选2b90e28，全部CPU允许集合。162000次发布均接受、2214000次接收，丢失/错误/重复0。
- **7/9组三轮中位数、14/27逐轮配对通过；13/27不满足。** 中位数失败项是8订阅者/4KiB和32订阅者/64B。相比旧T14的5/27逐轮失败，当前数据不能证明稳定性已改善。未改门槛或丢弃不利轮次。
- [同/不同shard各3×30秒](network-summary.json)：冷消息100Hz，各窗口3000条全交付。同shard可靠完成p99为4.948/5.237/4.980ms；不同shard为0.671/0.708/0.689ms。旧T14分别约5.75～5.81ms和2.57～2.73ms。热流仍按1秒校准的70%设置，本轮约74.2～79.8条/秒，旧约61.6～65.8；因此这是同工装/归一化负载比较，不是相同绝对热流速率的因果实验。
- [空闲网关10秒](idle-gateway.json)：进程CPU时间增量为0（受内核时钟计量粒度限制）；每shard仅1次poll返回，来自诊断会话边界。未把零计量值写成绝对零CPU。
- [功能与指标验证](validation/results.md)：共享CTest36/36、主要sanitizer10/10，最终等待修复再跑3/3；旧路径8/8、OFF2/2、Python2/2、安装CLI17/17、topic_cat2/2、回滚3/3。新增8条指标断言验证真正ACK、信用耗尽、拒绝与回收。

## 证据与口径

`final-frozen-manifest.json`及performance-final内的manifest/binary_manifest记录源码、二进制、CPU与编译参数，54窗口和冷热测试结束后均校验指纹未变。原始CSV.gz、每进程CPU/RSS/FD、每线程亲和性/上下文切换均保留，context-switches.json显式标记线程集合是否相同。应用及网关直方图为进程累计，含预热，分位数仅是log2桶上界；精确端到端分位数来自正式窗口原始CSV。

`performance/`保留中断矩阵的前4个已汇总窗口及第5个已结束窗口；`affinity-pilot/`保留4个8秒诊断窗口。二者不能混入最终54窗口，也不能用固定CPU诊断代替默认配置结果。旧T14全部记录仍保留。

`gateway_queue_wait`是取出并复制出站记录后到shard prepare，未测应用enqueue→网关pull；跨物理主机单程时间和时钟误差没有证据。encode_copy_bytes表示编码出口的产出字节，未穷举用户编码器内部复制/写零；remote_target_copies表示接管时冻结的逻辑远端副本数，实际发出量查tx_bytes。每类控制队列拒绝分支尚未全部独立注入，不能把未发生的0计数当作完整测试。

默认legacy及shared_v1实验性显式启用不变。T09物理跨机、T13完整指标注入、T14完整性能矩阵和I12/I18剩余项保持未通过。当前实现确实消除了固定等待，但本机端到端稳定低延迟问题仍未解决。
