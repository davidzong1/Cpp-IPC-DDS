# CRC32C优化与固定负载网络实测（O05～O06）

**同shard冷消息可靠完成p99的三轮中位数从4.988ms降至1.057ms（下降78.8%）。** 此结论来自同一可执行程序分别加载2b90e28旧库与9039231新库的固定负载对照，不由微基准外推。整体本机延迟验收仍未通过。

| 指标 | 优化前 | 优化后 |
|---|---:|---:|

| 同shard热消息p99，中位数 | 10.404ms | 3.651ms |
| 不同shard冷消息p99，中位数 | 0.773ms | 0.720ms |

| 同shard源端重传wire字节，中位数 | 1020018208B | 48676608B |

前后各同/不同shard三轮，每窗口30秒；热流固定70Hz×1MiB、冷流100Hz×64B。总计12个窗口、61200次交付，丢失/错误/重复均为0；无调用失败，收尾重组字节与目标状态归零。原始数值、三轮范围与重传见[network-summary.json](network-summary.json)。同shard冷p99三轮为4.903/4.988/5.088ms→1.162/1.057/1.031ms；不同shard第三轮后值略高于前值，未删除该轮，也不宣称每个指标每轮都改善。

[network/manifest.json](network/manifest.json)保存所有命令、前后库与可执行文件SHA256；每个结果的loaded_library为真实网关/proc映射，排除LD_LIBRARY_PATH未生效。每窗口结束均核对所有指纹未变。latency_samples_ns保留正式窗口全部调用耗时，按数值排序而非时间顺序；已逐项校验样本数与工装的floor(n×p)分位数取法。网关直方图仍是log2桶上界，包含校准阶段，不与精确调用分位数混算。

同一CRC probe、相同编译参数/缓存预热、每尺寸五次测量：144B/1184B/1048656B调用耗时中位数分别由211.740/1648.500/1481060ns降至19.366/134.540/93122.1ns，约10.9/12.3/15.9倍。前后CRC值完全相同。原始记录在micro-before.json、micro-after.json；微基准不代表业务端到端倍率。

## 实现与验证

运行时检测SSE4.2，硬件函数单独target属性，不全局要求该指令集。不支持时继续原表算法；前缀/四个零字节/后缀分段更新，保持协议校验字段语义。没有忙轮询、增设数据线程、改变重传定时器或修改线协议。

[验证记录](validation/results.md)：共享CTest36/36；Wire7/7，独立逐bit参考同时核对硬件派发和软件回退；ASan/UBSan（含泄漏）3/3；混合真实UDP故障通过；Python2/2、安装CLI17/17、回滚3/3。全部支持结论限定于本机Linux x86_64实测，软件回退正确性有测试，其他架构无实机性能证据。

## 仍未通过的边界

- [2b90e28的完整纯本机54窗口](../20261005-optimization/performance-final/summary.md)仍只有7/9中位数、14/27逐轮门槛通过，13/27不满足。9039231仅补CRC优化，本机发布/队列/读取实现未改；没有再次跑54窗口，不把旧数据标成新二进制的实测，也不宣称CRC解决了本机调度尾延迟。
- 本文是同主机独立IPC/mount命名空间的真实UDP测试，不能替代两台物理主机、真实网卡、时钟同步误差与饱和带宽验收。
- 完整enqueue→pull、全部控制队列拒绝分支、编码器内部物理复制字节和完整负载矩阵仍有缺项。用户尚未补充CPU预算偏好，继续按既有低空闲CPU约束，不擅自加入忙轮询或更改全局CPU电源/调度配置。
