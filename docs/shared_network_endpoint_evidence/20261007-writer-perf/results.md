## 4KiB 中位数的慢段得到直接证据

按端到端排序取 p45～p55 的100条消息，再对**同一组消息**计算各阶段均值；不能把这些数称为各阶段p50，也不能把独立分位数相加。所有接收样本的阶段时间戳顺序完整，逐消息分段之和等于端到端。

|1 SUB/4KiB|端到端p50|中间10%端到端均值|通知前均值|通知→等待返回均值|其中 waking→wakeup 均值|
|---|---:|---:|---:|---:|---:|
|第1轮 OFF|49.697|49.771|6.108|36.230|未开启perf|
|第1轮 ON|53.468|55.171|11.333|33.376|26.570|
|第2轮 ON|32.904|32.809|10.237|10.810|4.006|
|第2轮 OFF|18.539|18.850|7.161|5.080|未开启perf|

单位µs。OFF 两轮通知前相近，而通知到等待返回相差约31.2µs，端到端中间组相差约30.9µs；ON 两轮的差异主要落在 waking→wakeup。相比上一轮只有最慢1%的证据，本轮直接定位到了中位数附近的变化来源。仍不能据此声称旧正式窗口的根因已完全复现，或将整个区间等同于硬件空闲退出时间。

等待返回后的 recv、分流、入队、交接及 API 返回均已分段。该批中位数组交接到出队约1.3～3.2µs，单纯省去一次交接不能解释上述约31µs波动。逐窗完整分解及每秒/发布核分组见 [stage-analysis.json](paired-clean-v2/stage-analysis.json)。

## 32 SUB 广播与长尾

两轮 perf ON 的1000次广播均具备全部32个接收者的调度链。按同一消息的 sched_waking 时刻排序，不跨消息拼接：

|均值µs|第1轮首位 / 末位|第2轮首位 / 末位|
|---|---:|---:|
|notify→waking|3.646 / 34.408|4.115 / 36.227|
|端到端|25.978 / 63.550|24.919 / 67.420|

末位唤醒发起约晚31～32µs，说明广播通知存在逐接收者累积成本。与此同时，同窗最慢1%的 waking→wakeup 均值为125.851/141.749µs，明显高于可运行后等待调度的11.401/12.995µs。通知顺序与目标核激活是两个不同区间，不能只优化前者就认定长尾已解决。

两轮完整配对端到端p99为 OFF→ON：199.338→174.228µs、183.994→204.978µs；方向混合，不能套用固定perf开销修正值。完整均值和分位数见 [scheduler-summary.json](paired-clean-v2/scheduler-summary.json)。

## 内核栈确认了什么

仅 sched_waking/sched_wakeup 开启内核调用栈，CPU空闲事件不附加栈，不采用户栈。按事件类型、目标reader TID及纳秒时间戳匹配正式消息；初始化和后台线程的其他唤醒不计入结论。

66300条样本的 waking 栈全部包含：

```text
__x64_sys_futex → do_futex → futex_wake → wake_up_q → try_to_wake_up
```

65779条（99.21%）的 wakeup 栈包含：

```text
目标核 do_idle / IPI处理
  → flush_smp_call_function_queue / __flush_smp_call_function_queue
  → sched_ttwu_pending → ttwu_do_activate
```

这确认了目标核处理待激活线程的实际路径。剩余521条直接在 try_to_wake_up 路径激活，不能推断直接激活就更快：

|栈批次|全部样本：待处理 / 直接激活|最慢1%：待处理 / 直接激活|
|---|---:|---:|
|1 SUB 第1轮|1000 / 0|10 / 0|
|32 SUB 第1轮|31686 / 314|216 / 104|
|1 SUB 第2轮|970 / 30|4 / 6|
|32 SUB 第2轮|31823 / 177|316 / 4|

例如32 SUB第1轮最慢1%中的直接激活子集，wakeup→scheduled均值729.787µs；相应待处理子集为22.124µs。两组核位置和竞争状态不同，不能当作随机化的策略对照，也不能据此改内核调度策略。栈采集本身增加开销，不与无栈批次直接比较收益。

完整栈和逐消息关联见 [stack-summary.json](stacks/stack-summary.json)、各窗 `stack-links.csv.gz` 与 `stacks.txt.gz`。栈也保留本机 syscall hook 帧，但没有该hook的对照证据，不能把延迟归因于它。

## 实施判断

1. 本轮补齐了完整无已知编译干扰配对、中位数分段和内核路径证据。没有证据支持再引入已撤回的租约复用/延后通知候选，也没有证据支持将本机三项失败交给 UDP socket 拆分解决。
2. 用户态调用已直接唤醒接收线程；大部分剩余等待位于目标核激活之前，少数长尾来自激活后的调度。贸然增加中转worker会增加交接，忙轮询或改电源策略则违反原验收约束，本轮均不实施。
3. 保留标准memcpy及上一轮1MiB核型对照结论。先整合另一位Agent的最终提交并验证身份边界、接收生命周期和网络兼容，再从组合版本中选择有证据支持的候选。
4. 原三项仍以f066a82、全部CPU0～31、无诊断54窗口、原逐轮p50/p99门槛验收。本轮短窗不改写历史24/27。

原始记录和文本日志均保留；日志只做gzip无损归档，原manifest中原始字节SHA不变。解析器新增中位数秩、分段守恒、准确TID/时间关联、缺失栈和LOST守门；相关10项Python测试通过。未修改生产代码，未重复运行生产回归来替代本轮取证。
