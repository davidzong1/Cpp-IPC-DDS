## 已交付的确定修复

提交 `6f60b512` 修复 `PublisherEndpoint`：本机直达或网关离线时，原来仅分配最外层序号，返回结果中的发布者 ID/序号却为零；现在与网络路径使用同一内部身份填写函数。序号仍由各发布对象独立分配，配额、可靠确认、wire 格式及重试语义不变。

新增确定性回归覆盖同话题两个发布者、本机/离线、对象/预构造 DZFlat，以及一方关闭后另一方继续发布。修复前红、修复后绿。详见 [修复说明](validation/identity-fix.md)。它解决发布者边界问题，不能作为延迟修复证据。

## 三项失败现在知道什么

|原失败|现有证据|结论|
|---|---|---|
|1 SUB/4KiB，p50|多个无绑核诊断窗 p50 从十几到一百多 µs；两个减少交接的候选未稳定改善|不能认定为共享网关或某一次锁操作；仍开放|
|1 SUB/1MiB，p50|首轮复制墙钟均值约 143µs，CPU 均值约 144µs，实际发布在 E 核；其他窗口复制均值显著变化|大段复制包含真实执行成本；尚无受控证据区分核型、频率和缓存，保留标准 memcpy；仍开放|
|32 SUB/64B，p99|首轮同批最慢 1% 的 e2e 均值约 349µs，其中通知到等待返回约 289µs|等待/唤醒区间主导尾部；省去一次主动 worker 通知未得到稳定尾延迟收益；仍开放|

三个原失败都是单发布者、纯本机 MPMC。增加 UDP socket 或为多发布者拆写入队列不能直接解释或关闭它们。

本机 C2/C3 的公布退出延迟为 127/1048µs，且均启用；记录在 [CPU 空闲态快照](validation/cpu-idle.json)。这只是待验证线索，不是逐样本根因证明。当前 perf 权限受限，详见 [访问结果](validation/perf-access.log)。

## 后续执行顺序

1. 保持现有电源和原验收 CPU 集合，提供可读取调度事件的环境（CAP_PERFMON 或受授权的采样进程）。按同一消息关联发布通知、目标线程 runnable、实际 scheduled-in、等待返回及所在核型；先在单 SUB/4KiB 与 32 SUB/64B 各取两轮，记录 tracing 开销，采样期不并行编译或运行其他压测。
2. 对 1MiB 只作诊断的 P/P、P/E、E/P 固定 CPU 对照，每种固定总速率，改前/改后顺序预先确定。保留复制 CPU、墙钟、地址/容量、实际核型；不把诊断绑核结果用来替换原门槛。现有证据不支持重新引入预取/分块 memcpy。
3. 只有找到可重复的热点并通过生命周期守门，才接入新的延迟候选；随后运行原 54 窗口逐轮验收。当前不得将身份修复作为执行这轮性能验收的候选依据。
4. UDP socket/worker 隔离继续由另一个 Agent 负责。写入队列隔离先按执行方案做真实多发布实验；保留发布者独立身份、局部和全局配额、广播与顺序契约，不绕过可靠账本。

分支 `fix/writer-boundaries-latency` 尚未合并。整合前核对另一 Agent 的新提交，不能直接覆盖其网关、配置或工装。
