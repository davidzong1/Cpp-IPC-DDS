# B 应用级接收路径短窗诊断（app-diagnostic-001）

## 范围与限制

在 B（二进制 `94856f7b`）上使用 `shared_v1`，串行完成 worker assist=1、worker assist=0、强制 compat 三路径；每个场景为 5 秒正式窗口、100 Hz、2 秒预热。开启现有 receive/publish/publish-cpu 缝。所有窗口通过内容完整性断言，但本组是 L1 短窗定位，不是完整平衡块，也不是性能门槛验收。

`D04` 仍被 `perf_event_paranoid=4`、无非交互 sudo 和 tracefs/debugfs 权限阻塞，因此以下结果只能解释应用层时序，不能认定 OS 调度因果，也不能准入生产修复候选。未读取或干预用户声明的 JAX 任务。

## 观察与下一步

1. 九个窗口均完成 500 个正式发布，所有订阅者均收到 500 条；trace 溢出、乱序或缺失均为 0。
2. assist=1 的 worker 路径中，现有缝观测到每条接收均走调用线程协作接收；assist=0 与 compat 的样本没有该协作标记。compat 路径按独立线程收包。
3. 场景间及短窗之间存在明显波动；不能据单次 5 秒分位数断言 assist/compat 谁更快。特别是 1 MiB 的发布复制线程 CPU 与 32 SUB 首末接收跨度只作为后续平衡复测的定位量。
4. 当前 seam 未观测 `recv_local_signal::notify/wait` 的 waiter/sequence/futex wake 细节，也未观测 `recv_wait_set::wait` 的扫描、ready 数、interrupt/error 和阻塞返回原因；D04 恢复前只准备诊断缝，不修改生产策略。

原始 `pub.csv`、全部 `sub*.csv`、日志及逐窗 `result.json` 保存在本目录；本组输入哈希和环境参数见 `manifest.json`。
