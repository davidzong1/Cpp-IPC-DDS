## 旧协议兼容失败

C1 最初四项登记测试和八项功能/生命周期 CTest 通过。
新增用例重放父版本“持有共享锁检查谓词，检查后才登记 condition waiter”的顺序：
同一测试源码对未改动 B 的头和库为 5/5 通过，对 C1 为 4/5 通过。
测试 XML 在 `c1-waiter-validation/legacy-registration-parent.xml` 与 `legacy-registration.xml`。

具体交错为：旧接收者检查队列为空、尚未登记；C1 发布并看到 `waiters == 0`，提前返回；
旧接收者继续登记并进入 condition 等待，此时 futex wake 不能替代 condition 唤醒，于是超时。
段名、共享布局相同，通知方无法根据零计数区分“没有接收者”和“旧接收者尚在登记窗口”。
顺序一致握手只保护采用新登记顺序的接收者，不覆盖旧进程。

这是候选引入的兼容性缺陷，不是父版本既有缺陷。C1 已拒绝，不合入生产。
候选保留在实验分支，测试失败和原始数据均保留；修复主分支追加旧协议兼容回归门。
未执行 C1 的 L0、OFF、ASan/UBSan 或 D12，不能把未执行写成通过。

## 三项历史失败的当前解释

1. 4KiB：当前 A/B 未复现旧候选的持续退化；窗口快慢变化主要在实际接收前的调度链。
   C1 只降低一小段发布成本，没有稳定降低端到端 p50。继续 D05/D06 分解目标 CPU 激活前区间。
2. 1MiB：复制 CPU/墙钟及发布开销存在波动，但没有同核型、同缓冲条件的 D07 证据；
   不能直接把历史失败归因于当前 memcpy。保留标准 memcpy，下一步做受控复制实验。
3. 32 SUB：当前广播首末 waking 成本与 A 接近，慢尾主要与目标线程激活前长尾相关；
   C1 没有改善该段并增加 p99。不能用跳过通知、忙等或提升优先级掩盖它。
