# 接收分段诊断与剩余延迟边界（O07～O08）

**补齐了738000条接收记录的分段证据；整体本机延迟验收仍未通过。** 本节点不继续猜测CRC或MPMC原子操作是本机尾延迟的主因。

O07提交`d8bab39`：扩展默认关闭的内部测试缝，按消息序号记录recv调用起止、DZFlat入队前和get出队后；保持Sample布局、线协议和既有收发所有权不变。启用诊断时使用固定65536条原子记录，钩子不等待、不分配、不写文件；序号超界或字段缺失明确失败。采样结束后核对发布原始时间戳、消息完整性和分段和。

## 已完成的实测

冻结d8bab39库与基准程序，与f066a82直接IPC_SHM基线比较。三种场景各三轮、每模式每轮30秒，预热2秒、100Hz、全部允许CPU；共18窗口、54000次发布全部接受、738000次接收，丢失/错误/重复/打点缺失/记录溢出均为0。两版本使用同一benchmark.cc源码，基线只具备原有recv返回打点，新字段标为未采样。

## 证据支持的定位

九个shared_v1窗口各自选取端到端最慢1%消息，再累计同一批消息的分段耗时：

- 发布起点→recv返回占50.8%～61.4%，包含发布提交、共享内存等待、worker调度、lease取得与recv调用。
- 入队前→get取出后占37.0%～46.5%，包含实际入队、排队、唤醒与出队。
- 上述两段合计96.2%～98.6%。recv返回→入队前和出队后→API返回的占比较小。

这说明后续应优先检查接收等待链路。第一段仍不能进一步区分提交、调度和等待，第二段也不是精确的队列驻留；不能将其全部标为内核调度耗时，或把核迁移当作唯一原因。不同阶段独立p99不能相加。recv调用可能在发布起点之前已经开始，工装单独记录交叠，不把合法并发误判为坏记录。

若继续追求更低的同步get延迟，下一架构候选是应用线程直接等待并读取SHM，减少worker到应用的交接；实现之前需要定义并验证慢消费者保留/淘汰、并发getter、重建/析构屏障以及应用未调用get时的缓存语义。该候选尚未实现或测量，本报告不承诺其收益。当前保留既有低空闲CPU约束，不增加忙轮询或修改全局电源/调度设置。
