# O22～O24 接收lease复用与剩余延迟复测

起点：方案9122317b、生产库4fc0a5c，最近正式验收24/27。旧失败及全部原始证据保持不变。本轮仍按原54窗口及逐轮p50/p99门槛验收。

## O22 真实SHM复制实验

同一4fc0a5c库、shared_v1、1订阅者/1MiB、100Hz、预热2秒/正式10秒，固定发布CPU0或16、订阅CPU4、网关CPU2。模式0为libc，1为AVX2对齐缓存写入与有界预取，2为每16KiB调用libc；CPU0按ABBA、CPU16按BAAB，16窗串行，16000次发布与接收全部正常。实验通过LD_PRELOAD拦截大块memcpy，影响该进程的所有匹配调用，只用于筛选，不能解释为单一生产调用的严格因果效应。

| 发布CPU / 策略 | 复制均值：libc→实验 / µs | 端到端p50：libc→实验 / µs |
|---|---:|---:|
| 0 / 缓存预取 | 65.699→121.056 | 85.880→124.127 |
| 16 / 缓存预取 | 77.686→237.778 | 96.832→243.407 |
| 0 / 16KiB分块 | 55.780→68.277 | 56.601→85.515 |
| 16 / 16KiB分块 | 76.239→76.699 | 87.393→80.322 |

每项复制均值为两个等长窗口均值的平均；端到端为两个窗口p50的中位数。预取明显退化，分块在两个CPU配置间未表现出稳定收益，均不接入产品。继续使用标准memcpy，不能声称大消息复制已修复。源码、命令、指纹、原始CSV、逐窗CPU与复制汇总在[copy-experiment](copy-experiment/diagnostic/manifest.json)。实验期间未并行编译或执行其他压测。

## O23 接收实现与验证

协作getter复用当前等待作用域已取得的lease，消除同轮第二次申请/释放。非空接收在分流前真正释放计数；空读保留映射至等待结束。异常路径释放后重新取得token，不再使用可能已失效的旧映射。消费锁、取消/停止、owner检查、混合队列、后台恢复及截止时间保持原语义。worker与兼容路径继续独立申请lease。

新增实际SHM测试将getter暂停在kAfterRecvRelease，随后推进代次；断言getter尚未入队时重建完成，恢复后旧buffer仍完整可读。保留4fc0a5c库运行相同测试时，重建500ms内无法完成；修复后通过。旧库实际加载路径见validation/caller-i5-before-loader.txt。协作空读不触发允许阻塞的kAfterRecvRelease，避免持有等待lease时制造错误测试边界。

行为验证：共享网络36/36；扩展54目标51/54，失败为旧I5、旧析构及旧Ready转换。额外两项在保留4fc0a5c库复现，旧析构已有O17对照记录；不改判通过。ASan/UBSan（detect_leaks=1）7/8，唯一失败为同一旧I5，没有sanitizer报错。OFF2/2、assist=0回退4/4通过。全部日志在validation/；初次批量构建将Python测试误列为CMake目标而失败，修正目标列表后完成构建，原日志保留。

六个8秒短窗共4800次发布、16000次接收正常，候选开启发布分段诊断。下表端到端使用全部订阅样本；未绑核，基线为f066a82，两侧已用同一benchmark.cc和相同编译参数重编。短窗允许继续正式复测，不作为因果收益或关闭验收的证据。

## O24 冻结矩阵

冻结9f536dc1，执行完整54窗口：3轮×9场景×baseline/shared_v1，预热2秒、正式30秒、100Hz、全部CPU0～31、关闭所有诊断。162000次发布全部接受、2214000次接收零丢失/错误/重复。二进制指纹、同源码基准、实际加载库与所有线程CPU允许集合均核对，见[审计](performance/audit.json)及[完整汇总](performance/summary.md)。

**24/27逐轮通过，8/9三轮中位数通过，验收仍未关闭。** 相比O18，8/1MiB本批三轮通过，出现32/64B第1轮p99失败；1/4KiB的中位数也不满足。不同时间批次不能仅凭失败场景变化归因于lease改动。

| 失败场景 / 轮次 | 基线p50 / p99 µs | 候选p50 / p99 µs | 超出原允许上限 / µs |
|---|---:|---:|---:|
| 1 / 4KiB / 第1轮 | 26.862 / 193.176 | 63.986 / 173.468 | p50：32.124 |
| 1 / 1MiB / 第1轮 | 108.485 / 306.545 | 120.911 / 239.776 | p50：1.578 |
| 32 / 64B / 第1轮 | 37.371 / 195.178 | 36.258 / 222.719 | p99：8.023 |

逐条关联发布和接收序号，以min(发布调用耗时,端到端)拆分返回前后，保留同一批慢消息；独立分位数不能相加。[完整分段](performance/local-stages.json)及[超标计算](performance/residuals.json)可复核。

| 失败场景 | 发布p50：基线→候选 / µs | 返回后p50：基线→候选 / µs | 返回后p99：基线→候选 / µs |
|---|---:|---:|---:|
| 1 / 4KiB | 3.971→9.519 | 19.544→47.879 | 175.862→150.610 |
| 1 / 1MiB | 47.010→72.503 | 51.242→43.625 | 205.532→136.407 |
| 32 / 64B | 25.386→30.848 | 9.148→0.000 | 164.559→182.146 |

1/4KiB的发布与返回后p50都增长，候选三轮p50为63.986、18.608、69.951µs；重复lease不是足以解释该波动的单一原因。1/1MiB发布变慢、返回后改善，仍须处理发布执行成本；此前复制CPU证据可以指导诊断，但本批无打点不能把整段发布增长直接等同memcpy。32/64B的p50通过、p99失败，候选同批最慢1%约79.95%的端到端时间在发布返回后，重点仍是接收等待/唤醒到取样区间，不能直接指定调度器为根因。

## 空闲与唤醒

同库assist=0/1、1/8/32订阅者各10秒空闲窗，沿用get(20ms)。每订阅进程6线程、发布者4线程、网关9线程，两模式一致。全进程CPU按单核百分比统计：

| 订阅者 | 协作关闭 / % | 协作开启 / % |
|---:|---:|---:|
| 1 | 0.800 | 0.500 |
| 8 | 1.698 | 2.397 |
| 32 | 3.388 | 4.484 |

32订阅者协作增加约1.096个百分点；10秒窗口与10ms计数粒度不能证明长期上界，也不能把单订阅者的下降解释成稳定收益。原始快照见[idle/results.json](idle/results.json)。

同一个新版基准分别加载保留4fc0a5c库与9f536dc1库，strace跟踪发布者及sub0全部线程。每窗预热2秒+正式2秒、100Hz，共400次数据发布；实际SHM唤醒均为每次1/32，没有重复唤醒。sub0所有futex唤醒调用分别为1638→1660（1订阅者）、1440→1434（32订阅者），未体现稳定减少。只跟踪sub0，不能外推全体；这些带跟踪开销的延迟不用于验收。指纹和解析计数见[wake/wake-counts.json](wake/wake-counts.json)与[资源审计](resource-audit.json)。

本节点完成了lease计数/重建边界修复及原矩阵、资源证据补齐；剩余三组延迟问题仍开放。后续应先用同库对照补齐接收唤醒返回、完整recv/入队、getter退出三个区间的墙钟与线程CPU证据，再决定具体改动；大消息保留标准memcpy，继续寻找有真实SHM证据支持的发布侧优化。不能以重复相同矩阵挑选通过轮次或增加忙轮询来关闭验收。
