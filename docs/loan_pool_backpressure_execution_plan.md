# Loan 池背压与极致吞吐执行方案

## 1. 目标

解决同一话题多发布者并发时 loan 池耗尽、重复拒绝和尾延迟抖动问题，同时保持高吞吐。
方案不得通过无限扩大池容量或固定 sleep 掩盖生命周期错误，也不得牺牲已接受消息的交付正确性。

成功标准：

- 正常消费下，8 发布者的有效发布成功率显著提升，拒绝主要只在达到明确硬上限时出现。
- 单发布者吞吐和 p99 发布延迟不回退超过既定基线。
- 所有已接受消息无缺失、重复、损坏或乱序。
- 任何 loan 失败、publish 失败和接收回收后，池最终能恢复到可验证状态。
- 空闲链无环，`storage_id` 不重复占用，禁止二次归还。

## 2. 当前基线

- 每个 `(prefix, chunk_size)` 池初始容量为 `topic_msg_cache = 10`。
- 1 发布者、2000 条、约 11 KiB 负载：2000/2000 成功。
- 8 发布者、2000 条总尝试：此前仅约 28 条成功，池很快达到 10 块占用。
- 接收单次 p50 约 0.3 us，`Sample` 析构单次 p50 约 0.6 us，主要矛盾是并发 outstanding 峰值而非单次析构耗时。
- 已修复 loan 发布回调捕获栈引用和无效 storage id 进入回收路径的问题。

## 3. 总体策略

采用三层策略，顺序实施：

1. **信用额度发布限流**：限制同一尺寸档的 outstanding loan 数，不使用固定 sleep。
2. **消费路径优化**：缩短队列驻留和 `Sample` 持有时间，避免不必要的拷贝与阻塞。
3. **有硬上限的自适应扩容**：仅在确认需求是合法突发且所有权审计通过后，追加独立 chunk 段。

发布限流是控制面，消费优化是回收面，受控扩容是容量面；三者不能互相替代。

## 4. 阶段一：信用额度发布限流

### 4.1 信用模型

每个尺寸档维护共享信用：

```text
capacity       = 当前所有段的 chunk 总数
free           = 空闲链可借数量
outstanding    = capacity - free
publisher_cap  = capacity - reserve_for_consumer
```

初始 `capacity=10`。`reserve_for_consumer` 默认保留 1~2 块，防止发布线程占满池后接收端无法完成回收。

信用必须绑定 `(prefix, chunk_size, generation)`，不能只用 `storage_id` 全局计数。

### 4.2 获取与释放

- `loan()` 前先尝试获取信用；失败时进入短暂自旋/条件等待。
- 等待必须有截止时间，超时返回 `pool_exhausted`。
- 有界等待入口默认保留 1 块消费者信用（`publisher_cap = capacity - 1`）；保留原有无超时 `loan(size)` 的即时兼容语义，允许在调用方明确承担生命周期责任时借满整档。无超时入口不等待，因此不能把它当作消费者保留配额的替代品。
- `discard_loan()`、发布失败、接收端最后一个 `buff_t` 析构时归还信用。
- 归还必须与现有位图 CAS 和 `id_pool` 归还绑定，禁止独立递增计数。
- 重复归还只记录诊断，不增加信用。

### 4.3 并发调度

- 每个发布者维护本地待发队列，避免所有线程同时抢同一把池锁。
- 使用无锁或低锁的令牌计数；令牌不足时优先让出 CPU，不固定休眠。
- 可按发布者轮转或加权公平分配令牌，防止单线程长期独占。
- 不在数据路径中打印逐条日志，只维护原子计数和采样日志。

### 4.4 禁止事项

- 不把 `topic_msg_cache` 直接改大作为唯一修复。
- 不使用固定毫秒 sleep 伪装限流。
- 不在未确认 publish 是否入队前归还 chunk。
- 不用全局共享计数代替按尺寸档、按 generation 的信用。

## 5. 阶段二：消费路径优化

- 接收线程持续 drain，避免应用线程成为唯一消费者。
- 视图队列达到高水位时触发主动消费或明确淘汰策略。
- 尽量使用 `try_get` 的零拷贝路径；需要长期持有时及时 copy 后释放 `Sample`。
- 将“队列持有时间”和“应用持有时间”分别统计，不能混成接收耗时。
- 避免在接收线程执行重计算、日志输出和不必要的内存分配。
- 对慢消费者暴露高水位、淘汰数和持样时长指标。

## 6. 阶段三：受控自适应扩容

扩容只作为合法突发的补充，必须满足全部条件：

1. 空闲链连续多窗口完整，无自环或互环。
2. 位图、`outstanding`、池链三者一致。
3. 拒绝原因明确为合法 outstanding 超过容量，而非重复归还或回收滞后。
4. 当前消费端已持续运行，且队列高水位没有失控。

扩容实现：

- 不修改既有共享段布局；按尺寸档追加独立 chunk 段。
- 新段使用新的 generation 和段句柄，回收时携带段身份。
- 每话题、每尺寸档设置最大容量；同时设置进程级和全局内存预算。
- 扩容采用阶梯策略，例如 `10 -> 20 -> 40`，每次扩容记录原因和耗时。
- 达到硬上限后继续返回明确 `pool_exhausted`，由上层进行背压处理。
- 进程重启和段清理必须兼容旧段，不允许在线原地改变旧段容量。

## 7. 观测指标

每个 `(topic, chunk_size, generation)` 至少记录：

- `pool_capacity`、`pool_free`、`pool_used`；
- `loan_attempt`、`loan_success`、`loan_reject`；
- `loan_wait_ns` 的 p50/p95/p99/max；
- `publish_ns` 的 p50/p95/p99/max；
- `recv_ns`、`queue_residence_ns`、`sample_hold_ns`、`destroy_ns`；
- `duplicate_return`、`invalid_storage_id`、`pool_chain_corrupt`；
- `queue_high_watermark`、`queue_evicted`、`consumer_lag`；
- `capacity_before/after`、`resize_count`、`resize_denied`。

采样使用 `CLOCK_MONOTONIC`。池占用曲线至少每 1~5 ms 采样一次，保留原始 CSV/JSON，不能只保存平均值。

## 8. 验证矩阵

每个配置运行至少 3 个窗口，每窗固定总消息数：

| 发布者 | 订阅者 | 负载 | 模式 |
|---:|---:|---:|---|
| 1 | 1/8 | 64 B、4 KiB、11 KiB、1 MiB | 对照 |
| 4 | 1/8 | 同上 | 并发 |
| 8 | 1/8 | 同上 | 并发 |
| 32 | 1/8 | 同上 | 压力验证（补充要求） |

每窗检查：

- 发布成功/拒绝数；
- 接收数与接受数一致性；
- 缺失、重复、损坏、乱序；
- 池占用 min/p50/p95/max；
- loan 等待和发布尾延迟；
- 测试结束后池是否恢复满容量；
- 是否出现重复归还、无效 id 或空闲链环。

## 9. 实施顺序

1. 完成当前阶段测量基准，保存 1/4/8 发布者基线。
2. 添加按尺寸档的信用计数和等待/超时接口，不改变容量。
3. 增加并发 loan、publish 失败、接收析构和最终恢复回归测试。
4. 在固定总 800Hz 矩阵中验证限流是否降低拒绝并保持吞吐。
5. 优化消费线程和队列高水位处理，重新测量。
6. 只有前五步通过后，设计并实现分段自适应扩容。
7. 扩容开启前后各运行完整矩阵，比较内存、吞吐和尾延迟。

## 10. 通过与回滚条件

通过条件：

- 拒绝只在信用或硬上限明确耗尽时出现；
- 不存在空闲链损坏、重复归还和无效 id；
- 8 发布者有效吞吐不低于当前单发布者基线的目标比例；
- p99 发布延迟和内存占用均在预算内。

回滚条件：

- 已接受消息出现缺失、重复、损坏或乱序；
- `pool_used` 长期单调增长且消费停止后不能恢复；
- 扩容后出现段代次错配或跨段错误回收；
- 发布尾延迟、CPU 或内存超过预算。

回滚时关闭自适应扩容，保留诊断指标和已验证的所有权修复，恢复固定容量与明确背压。
