# 延迟与可观测性补齐执行方案

基线：d8ead7a。沿用 shared_v1 显式启用、MPMC 本机直达、K+2 网关端点、原 deadline 与最多一次提交边界。保留 T14 全部原始结果，不能用新测量覆盖旧失败轮次。

1. 补固定容量的延迟直方图、协议/目录/配额分类计数；热路径不写文本，不按外来身份无界建表。应用与网关分别计数；每话题明细绑定已登记路由生命周期，汇总保持在控制包上限内。
2. 为共享订阅接入底层队列的可取消等待，合并重复 Wake/条件变量。仅显式共享 reader 启用，取消必须唤醒在途 getter，旧 Sample 不受影响，不丢通知。
3. 网关完全空闲时阻塞等待事件；有事务/重组/回执时仍按短定时器工作。补每 shard 字节、积压、唤醒与预算耗尽计数。
4. 从公开发布调用记录 encode/local_commit/credit_wait/outbox_wait/network_first_send/remote_commit/ack_wait/api_return。不同主机单调时钟不得相减；网关本机排队使用同 locality 时钟，跨主机只比较本地阶段和源端可靠完成时间。
5. 用协议损坏、每类配额触顶、重复片/消息、真实 ACK/丢包、迟到目录和关闭测试验证计数增量与回收。未采样/无调用的阶段必须显示 count=0，不能伪造零延迟证据。
6. 完成构建、共享/生命周期/sanitizer/旧模式测试，再冻结二进制跑正式对照。仍为三轮、每窗口至少30秒、相同编码/优化/订阅者/offered load；补CPU/上下文切换/亲和性与原始阶段记录，保存失败样本及逐轮门槛。
7. 更新缺项清单及用户说明，分实现节点提交。物理跨机主机尚未提供，该项保持“未执行”，同机隔离网络数据不能替代真实网卡证据。

成功条件：新增指标有真实非零/拒绝/回收断言；可取消等待无丢失/重复/UAF；正式性能按原门槛报告，不改门槛、不删失败。若平台调度仍导致个别轮次不满足，保留原始记录及分段证据，不宣称已全部修复。

## O03：复测中发现的剩余等待

首轮矩阵前4个已汇总窗口及第5个已结束窗口保留在`performance/`；1 sub/64B配对p50为25.304→75.334µs、p99为158.218→273.463µs，未达标，主动中断继续诊断。固定CPU的4个8秒诊断窗口也存在退化，不能把问题只归因于核迁移。

## O05：CRC32C串行开销补充方案（先修订，后实施）

分段证据显示同shard冷流queue_wait p99桶上界约2.097ms；1MiB热流在prepare中串行逐字节CRC，packet_crc每字节还判断保留字段。下一节点仅优化CRC，不加入忙轮询、额外IO线程或改变默认重传时间：

1. 保持Castagnoli多项式、初值/末异或、CRC字段视为四个零字节、所有协议字节完全不变。
2. x86_64 GCC/Clang使用运行时SSE4.2检测，硬件函数独立target属性；不支持CPU/编译器继续使用原表算法，不能全局加-msse4.2。
3. 将前缀、零字段、后缀分别更新，正确处理非对齐输入、短输入和SIZE_MAX无零字段。热路径不分配。
4. 独立逐bit参考算法核对多尺寸、多对齐、跨8字节边界的零字段；既有黄金协议向量、重组、可靠/真实UDP和sanitizer必须通过。
5. 保留2b90e28旧库做同一probe的CRC对照，记录原始耗时和指纹；网络同/不同shard在相同绝对热流速率下各3×30秒复测。不能用CRC微基准替代端到端，也不能把2b90e28本机54窗口标成新CRC版本的实测。
6. 本机剩余13/27失败继续保留，硬件CRC只解决网络/控制校验开销；若需严格本机尾延迟，后续需在低空闲CPU约束下补接收路径分段再决定架构改动。

O05实现验证：运行时SSE4.2派发及原表算法回退已接入；独立逐bit算法交叉核对通过，Wire 7/7、共享CTest36/36、sanitizer3/3、Python2/2、安装CLI17/17、回滚3/3及真实混合故障通过。先保留旧库指纹，再使用同一probe作CRC对照；网络采用前后完全相同的70Hz热流/100Hz冷流，单独保存，不覆盖O04数据。

## O09～O11：修复13/27本机失败的协作接收方案

起点dfbf488。沿用原p50/p99门槛、低空闲CPU、固定worker数量、MPMC布局、Sample布局、两条物化/借样队列与取消/代次屏障。先提交本方案，再实施与正式复测，不更改O04/O08的失败记录。

### O09：设计与边界

当前shared_v1的getter只等待进程内队列，必须串行经过SHM唤醒worker和worker唤醒getter。改为**共享worker保留、应用线程可协作取包**：

1. 仅共享后端显式为内部MPMC reader启用。getter同时阻塞等待SHM通知序号与进程内通知序号；不忙轮询、不新建每话题线程。`DZIPC_SHARED_RECV_ASSIST=0`为回退开关；不支持等待后端时回到现有队列等待。
2. 每订阅增加一个内部消费锁，覆盖完整recv→分流入队。worker按原预算持续drain；getter只try_lock并至多协作一次非阻塞recv，再从原队列取消息。二者不并发消费同一订阅cursor，也不改变FIFO入队、队列容量/淘汰或TLV/DZFlat分流。无人调用get时worker仍照常接收，慢消费者语义不变。当前libipc分片缓存属于连接对象，不依赖调用线程的thread_local存储。
3. 等待使用固定两个futex_waitv槽位，无每消息动态wait-set分配。先快照序号，再检查队列/尝试消费，最后等待；生产、取消、重建就绪更新通知序号。用内核的序号比较关闭“检查后入睡”窗口。
4. getter在等待SHM序号期间持有RouteSession lease，保证映射存活；入睡前再次核验lease仍为当前可接收代次。stop/rebuild先禁lease再更新SHM序号唤醒；getter释放lease后重建才能释放旧映射。无route时只等待本地通知，新代次就绪再唤醒。消费锁不跨阻塞等待或控制面请求。
5. reset/析构仍先撤销代次、取消所有在途getter并等待关闭屏障；取消同时唤醒现有条件变量与协作等待。多个getter仍恰好一次取得队列项，不将业务回调放到worker。
6. 出现等待后端错误或接收池回退时明确停用协作路径，保留现有可取消等待；同一路由的兼容收包线程也遵守消费锁，防止切换边界与旧getter交错。

### O10：实现及行为验证

先保留dfbf488库指纹，再实现等待原语、消费仲裁及shared_v1接线。新增实际SHM测试：worker被测试缝暂停时getter可完成；并发getter不丢失/重复；无getter后台缓冲及满队淘汰；TLV/视图互不吞消息；无限等待取消、重建中的等待lease回收、借出Sample跨关闭；等待原语覆盖通知先于wait、真实阻塞唤醒和截止时间。测试缝不得在持有lease时阻塞。

执行共享全量、相关接收/生命周期、ASan/UBSan、OFF和回退检查。既有两个旧SHM失败保持独立记录，不将其重分类为通过。通过行为检查后提交实现节点。
