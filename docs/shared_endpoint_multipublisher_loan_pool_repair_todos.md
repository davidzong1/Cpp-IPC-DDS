# P1：并发发布 loan 池耗尽修复 TODO

## 目标

修复同一话题多发布者并发发布时出现的大量 `loan()` 拒绝，区分合法背压与
loan 生命周期、引用计数或所有权错误。禁止把单纯扩大 `topic_msg_cache` 作为修复证明。

## 已知基线

- 池容量为 `ipc::topic_msg_cache = 10`，按 `(prefix, chunk_size)` 共享。
- P0 已证明：已接受消息的投递无缺失；当前主要失败发生在发布前 loan 获取阶段。
- 单发布者固定总 800Hz 可通过，多发布者并发窗口出现拒绝。
- `reclaim_dead_chunks()` 只回收已发布且所有持有者确定死亡的块，不能替代正确的 loan 所有权。

## 根因判定规则

1. 第 11 个 loan 拒绝且 discard 后恢复：容量上限行为，不是泄漏。
2. publish 失败后不能恢复：发布失败所有权泄漏。
3. 接收方析构后不能恢复：接收回收或引用位图错误。
4. 不能再次借到全部不同 id：重复 release 造成空闲链退化。
5. 已接受消息缺失：另行归类为数据面交付缺陷，不与 loan 拒绝混计。

## 自适应池设计约束

自适应池可以作为后续 P2/P1.5 方案，但必须满足：

- 初始容量仍为 10，池满时只允许按尺寸档追加独立 chunk 段，不修改现有段的
  `id_pool` 容量，避免跨进程看到不一致布局。
- 追加前必须确认空闲链无环、当前 outstanding 计数与位图一致，并记录
  `capacity_before/after`、触发次数和失败原因。
- 追加设置每话题、每尺寸档硬上限和总内存预算；达到上限仍返回明确的
  `pool_exhausted`，不能无限分配。
- 订阅端和发布端必须按段代次识别 chunk，回收时携带段句柄，不能只按旧的
  `storage_id` 归还。
- 先完成本 P1 的所有权修复及并发回归，再引入扩容，以便区分“需求超过容量”
  与“错误持有导致的假性耗尽”。
