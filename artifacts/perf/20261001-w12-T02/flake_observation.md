> 背景：T02 的 §4.3.3 复跑期间，`test_w05_stale_slot_gate` 在 **L1 回退臂**上出现过 **1 次**
> `rx=99/100`（`flake/flake1/FAILED_fallback_6.log`）。本条**不隐藏、不淡化**该读数，
> 并按「干净路径 vs 门控路径」做了判别实验。⛔ 结论只用观察到的数据说话，不替任何一方下断言。

## 3. 已排除与未排除

**已排除：**

1. **不是"回收被推迟"那个已知缺陷形态** —— 失败时判据①（`:146` 陈旧槽位回收）已通过，
   失败点在判据②；而修复前形态会在判据①先变红（消融矩阵三次都是 `rc=1`）。
2. **不是消融/构建差异** —— 失败发生在**工作区未修改**的二进制上
   （`test_w05_stale_slot_gate` SHA-256 `4990720d…`，库 `813fab5b…`，`fingerprint.txt` 有记录）。
3. **不是编译选项漂移** —— 与修改点无关的目标文件在消融树与工作区逐字节相同
   （`logs/build_equivalence.txt`）。
4. **不是宿主机 CPU 饱和**（F 组：load average 28.9 时 12/12 通过）。

**未排除（如实列出，留给后续工作包）：**

1. **同刻并行运行造成的段名/资源争用**：失败发生在 20:54:25，其间本 run 在 20:54:14–20:54:55
   连续跑同名的门控用例（同一 topic 名前缀、同一控制面段名规则），
   且此刻**同工作区的其他成员任务（T05/T08）也在并发运行**（各自 mtime 21:03/20:51）。
   本 run 用"同一用例 3 并发"确实复现出全部失败（`logs/collide/`），但那是**同段名互相摧毁**，
   形态与 `99/100` 不同 ⇒ 只能说明该实验不构成解释，**不能**据此排除。
2. **L1 回退臂的时序敏感度**（2/122）高于默认臂（0/62）。本 run **未**定位到具体机制，
   ⛔ 不声称"已修复"或"仅偶发"。
3. 本 run **未**对 L1 回退臂做 x86 TSan/helgrind 类检查（超出 T02 范围与预算），
   ⛔ 因此不排除回退线程的并发时序问题。
